## 1. 总体设计

### 1.1 适配器模式

导入导出全部实现为**适配器**，通过注册表管理，内核（文档模型、布局、渲染）不感知任何第三方格式。

```ts
// 导入适配器
export interface ImportAdapter {
  id: string;                                  // 'xmind' | 'markdown' | 'opml'
  name: string;                                // 显示名
  extensions: string[];                        // ['.xmind']
  mimeTypes: string[];
  maxSizeBytes: number;
  /** 嗅探文件类型（读魔术字节或结构特征） */
  detect(buffer: ArrayBuffer, fileName: string): boolean;
  /** 解析为 .wmind 文档 */
  parse(buffer: ArrayBuffer, options: ImportOptions): Promise<ImportResult>;
}

export interface ImportResult {
  document: WmindDocument;
  stats: { sheetCount: number; nodeCount: number; maxDepth: number };
  warnings: ImportWarning[];                   // 降级 / 忽略项
  unsupported: string[];                       // 无法还原的特性名
}

// 导出适配器
export interface ExportAdapter {
  id: string;                                  // 'png' | 'jpeg' | 'svg' | 'pdf' | 'markdown' | 'opml' | 'xmind'
  name: string;
  extension: string;
  mimeType: string;
  /** 该格式支持的导出选项，用于动态渲染导出对话框 */
  optionsSchema: ExportOption[];
  render(ctx: ExportContext): Promise<Blob>;
}

export interface ExportContext {
  document: WmindDocument;
  sheetIds: string[];
  layouts: Map<string, LayoutResult>;
  options: Record<string, unknown>;
  theme: Theme;
}
```

**注册表**：

```ts
importRegistry.register(xmindImporter);
importRegistry.register(markdownImporter);
importRegistry.register(opmlImporter);

exportRegistry.register(pngExporter);
exportRegistry.register(jpegExporter);
exportRegistry.register(svgExporter);
exportRegistry.register(pdfExporter);
exportRegistry.register(markdownExporter);
exportRegistry.register(opmlExporter);
```

新增格式（如 FreeMind `.mm`、TextBundle）只需新增一个适配器文件并注册，不改任何现有代码。后端 `convert/` 包采用相同的接口设计，保证前后端行为一致。

### 1.2 为什么导入在前端、导出也以前端为主

| 决策 | 理由 |
| --- | --- |
| 导入放前端 | ① 避免上传大文件与解析过程占用服务端资源；② 解析产出的模型与渲染层共用同一套 TS 类型，无需跨语言序列化；③ 服务端仍保留同构实现，供未来的 API 导入与客户端复用 |
| 导出以前端为主 | ① 零网络往返、零服务端负载；② 导出内容就是屏幕上渲染的 SVG，所见即所得；③ 服务端导出（Headless Chrome）作为超大导图兜底 |
| 一致性保证 | 服务端导出复用前端构建的同一份 SVG 模板（导出模块编译为独立 ESM 产物，服务端页面加载它），避免两套渲染逻辑漂移 |

## 2. 导入

### 2.1 XMind 导入

#### 2.1.1 文件结构

`.xmind` 本质是一个 zip 包，两个大版本内部结构不同：

**XMind 2020+ / 2021+ / 2022+**

```
document.xmind (zip)
├── content.json          ← 主内容（sheet / topic / theme / relationships ...）
├── metadata.json         ← 文档元信息
├── manifest.json         ← 包清单
├── Thumbnails/
│   └── thumbnail.png
├── resources/            ← 内嵌图片等资源
└── ...
```

**XMind 8（经典版）**

```
document.xmind (zip)
├── content.xml           ← 主内容
├── styles.xml            ← 样式与主题定义
├── meta.xml
├── META-INF/manifest.xml
├── Thumbnails/thumbnail.png
└── resources/
```

#### 2.1.2 解析流程

```
读入 ArrayBuffer
  → 尺寸闸门（≤ 50MB）
  → fflate 解压（只按固定文件名读，不遍历目录）
  → 探测：存在 content.json ⇒ 走现代格式解析器
          存在 content.xml  ⇒ 走 XMind 8 解析器
          都不存在        ⇒ 抛 IMPORT_PARSE_FAILED
  → 解析为中间结构
  → 按 §5.2 / §5.3 映射表转换为 .wmind
  → 校验（docmodel.Validate）
  → 返回 ImportResult（含 warnings）
```

**安全防护**：

| 风险 | 防护 |
| --- | --- |
| zip 炸弹 | 解压前检查压缩包大小（≤ 50MB）；解压时逐条累计已解压字节数，超过 200MB 立即中止 |
| 路径穿越 | 只按固定文件名读取（`content.json` / `content.xml` / `styles.xml`），不遍历目录 |
| 超大 JSON | `content.json` 超过 50MB 时拒绝 |
| 节点爆炸 | 解析过程中节点数超过 20000 时中止并提示 |
| 图片爆炸 | 一次导入最多还原 100 张图片（`maxAssets`）。多出来的不登记、不留占位符，直接计入「图片未能导入」——4000 张图不会撑爆内存（字节受 200MB 预算约束），但会拖死上传队列 |
| XML 实体注入 | 自研解析器**整个跳过 `<!DOCTYPE ...>`**（含内部子集），自定义实体永远没有被定义的机会——XXE 与 billion-laughs 结构上不可能，而不是靠配置关掉 |
| XSS | 主题标题中的 HTML 经白名单清洗后才写入 `notes.html`；`title` 一律按纯文本处理并转义 |

#### 2.1.3 XMind 2020+（content.json）解析要点

- `content[]` 数组，每项是一个 sheet；无 `content` 字段时尝试 `sheets`。
- 每个 sheet 的 `rootTopic` 递归转换为 `Topic`。
- **节点 ID**：优先沿用原 `id`，但需检测文档内冲突，冲突时生成新 ID 并记录映射（供 `relationships` / `boundaries` 引用修正）。
- **主题（Theme）**：XMind 的 `theme` 对象包含 `map` / `centralTopic` / `mainTopic` / `subTopic` / `floatingTopic` / `summaryTopic` / `boundary` / `relationship` 等分组，每组下是 `properties` 键值对。按 §5.3 映射到 wmind 的 `Style`。
  - 若 `theme` 中的调色板无法对应到内置及兼容配色，则**保留能映射的显式样式，调色板回退到「缤纷-黎明」**，并在 `warnings` 中提示「配色方案已回退」。
- **图片**：`image.src` 有三种写法——`xap:resources/a.png`（包内）、`resources/a.png`（包内）、`https://…`（外链）。外链原样保留；包内的从 zip 里取字节，**先攒起来、后上传**（见下）。条目不在包里、扩展名不在 png/jpeg/gif/webp 之内、或超过 `maxAssets` 的，一律把 `image` 置空并计入 `image-skipped`——绝不留一个指向 `xap:` 的死链。
- **未识别字段**：原样存入 `extensions`，导出时可回写，减少往返损失。

#### 2.1.4 XMind 8（content.xml + styles.xml）解析要点

- `content.xml` 命名空间 `urn:xmind:xmap:xmlns:content:2.0`。
- 结构：`<xmap-content><sheet><topic>...`。
- 节点文本在 `<title>` 子元素中；子节点在 `<children><topics type="attached">` / `type="detached"`。
- 备注在 `<notes><plain>` / `<notes><html>`。
- 标记在 `<marker-refs><marker-ref marker-id="..."/>`。
- 标签在 `<labels><label>`。
- 节点可通过 `style-id` 引用 `styles.xml` 中的 `<style id="..." type="topic">`，该 style 内含 `<topic-properties>` 与 `<text-properties>`。
- sheet 通过 `theme` 属性引用主题；主题定义同样在 `styles.xml` 中。
- 转换时先解析 `styles.xml` 建立 `styleId → Style` 映射表，再解析 `content.xml` 并套用。

实现时的补充约定（`frontend/src/editor/import/xmind/legacy.ts`）：

| 事项 | 处理 |
| --- | --- |
| 元素名 | 按**本地名**匹配、大小写不敏感：`xhtml:div` 与 `div` 是同一件事，前缀只取决于导出器绑定的命名空间 |
| 属性名 | 两种拼法都认：`fill-color` / `svg:fill`、`text-color` / `fo:color`、`style-id` / `styleId`。小版本之间确实混用过，只认一种会导致「有些文件的颜色读不出来」 |
| 分支线型 | `line-class` 的类名映射到 `lineStyle`；`bight`（XMind 8 对「圆角折线」的拼写，是的，拼错了）与 `fold` 都归为 `elbow` |
| 画布名 | XMind 8 多数版本不存画布名，只认 `<sheet title>` / `<sheet><title>`，都没有则用「画布 N」 |
| 备注里的图片 | XMind 8 没有 `topic.image`，图片只能插在备注富文本里（`<xhtml:img>`）。清洗白名单会丢掉 `<img>`，所以**第一张提升为节点图片**、其余计入「图片未能导入」——不提升等于静默丢图 |
| 主题 | `styles.xml` 的 `<master-styles><style type="theme"><map-properties>` 只还原背景色，其余沿用默认主题；`theme` 引用查不到时给 `palette-fallback` |
| 样式解析失败 | 降级为「只导入内容 + 默认主题」，给 `styles-ignored`，**不阻断导入** |

> **夹具现状**：仓库内的 XMind 8 夹具是按上述规范**重建**的（`legacy.test.ts` 里的 XML 字符串），不是真实导出文件。M4.11 验收前需要用 3~5 个真实样本（含自定义主题、图片、联系、外框、概要各一）替换，并据实修正映射——真实文件的属性拼法可能比规范描述更杂。

#### 2.1.5 不支持项的降级策略

| XMind 特性 | wmind 处理 |
| --- | --- |
| 贴纸（Sticker） | 忽略，计入 `unsupported` |
| 音频 / 附件 | 忽略，在备注中追加一行「原文件包含附件：xxx」 |
| 录音 | 忽略 |
| 智能配色 / 渐变填充 | 取渐变起始色作为 `fill`，计入 `warnings` |
| 自定义标记 | 忽略，计入 `unsupported` |
| 导图密码 | 无法打开，提示「该文件已加密，请先在 XMind 中移除密码」 |
| 甘特图数据 | 忽略 |
| 画布壁纸 / 水印 | 忽略 |

导入完成后向用户展示摘要对话框：

```
导入完成
├─ 画布：1 个
├─ 主题：42 个（最大层级 4）
├─ 已还原：结构、样式、备注、标签、标记、超链接、图片
├─ 未能还原（2 项）
│  · 贴纸 × 3
│  · 自定义标记 × 1
└─ 需要注意
   · 字体「楷体」不受支持，已归一为 serif 字体族。
```

**入口**（`features/dashboard/import-dialog.tsx`）：

- 首页主按钮「导入导图」，与「新建导图」并列；
- 直接把文件拖到首页任意位置（只在拖动的是**文件**时接管事件，否则会吃掉页面内的文字拖拽）；
- 站点开关 `importEnabled = false` 时两者都不出现。

文件选择器、弹窗拖放和首页拖放均支持多个文件，保留选择顺序，逐个读取、解析并完成图片上传。批次全部处理后展示每个文件的摘要与警告，失败文件独立列出；一次确认后依次创建所有可用项，最后打开选择顺序中最后一个成功创建的导图。创建失败不阻断后续文件，部分成功时仍提示未导入的文件名；双击确认不会重复提交，显式重试跳过已有 uid 的成功项。文本 Tab 继续作为单份 Markdown 导入。

关闭、切换来源和卸载会使当前任务失效，后续文件不再读取、上传或创建，旧回调不能改写新窗口或导航。已发出的单个上传或创建无法撤回。单文件大小与解压限制保持不变，图片上传遇到 429 后整个批次停止后续上传，并在各文件中计入未还原图片。

**摘要里每一项都来自最终文档**：`summarizeImport()` 扫的是适配器产出的 `.wmind` 文档，不是适配器的自述。「已还原：备注」意味着文档里真的有备注——适配器说导入了、实际没写进去的情况太容易发生，而那样对话框就成了谎言。

**图片还原拆成两段：解析同步、上传异步**（`editor/import/finalize.ts`）：

```
解析（同步）                收尾（异步）
──────────────             ──────────────────────
读到 resources/a.png   →   ctx.asset() 攒进 assets
topic.image.src 先写       逐张 POST /api/v1/files
占位符 xap:resources/a.png  → 换成 /uploads/file_xxx.png
                          失败的那张 → image 置空 + image-skipped
```

三条必须守住的约束：

1. **文档在上传完成前不能落库**。占位符是 `xap:resources/a.png`，存进去就是一张永远加载不出来的破图，界面上没有任何报错。
2. **一张失败不能拖垮整份导入**。图片是附属信息，正文已经解析好了；丢一张图就少一张图，不要让用户重来一遍。
3. **撞上 429 立刻停手**。继续传只会继续拿 429，把对话框卡在「正在上传」上。停下来、把剩下的都记成「未能还原」是唯一诚实的处理。

上传**串行**而不是并发：限流按次数算，并发只会让一批请求同时撞上 429 然后一起失败；串行至少能把额度用满，顺带内存也更平。上传阶段有独立的进度卡片（`正在上传图片 3/12…`），放在「解析完成 → 显示摘要」之间，而不是等用户点「创建导图」——摘要要如实说明几张图传上去了，用户才能决定是否继续。

`maxAssets`（100）与后端限流（120 次/分钟/用户）是**一对**：额度必须装得下一次完整的导入，否则用户在第 121 张之后只能看着「图片未能还原」。改一个必须同时改另一个。

**解析在主线程上同步跑**，所以点击文件后先让出一帧再解析（否则「正在解析」来不及渲染）。50MB 的 zip 会卡住几百毫秒到一秒多；真正的解法是 worker，排在 M6。

**导入模块按需加载**（首页 `React.lazy`）：里面是三种格式的解析器加 fflate，比整个首页还大，而绝大多数会话不会导入。

### 2.2 Markdown 导入

**模式判定**：

```ts
function detectMarkdownMode(text: string): 'heading' | 'list' {
  const headingCount = (text.match(/^#{1,6}\s+/gm) ?? []).length;
  const listCount    = (text.match(/^(\s*)([-*+]|\d+\.)\s+/gm) ?? []).length;
  return headingCount >= 2 && headingCount >= listCount / 2 ? 'heading' : 'list';
}
```

**标题模式规则**：

| Markdown | 映射 |
| --- | --- |
| 第一个 `#` 标题 | 中心主题 |
| `##` / `###` … | 逐级子主题 |
| 标题层级跳跃（如 `#` → `###`） | 按实际深度差补中间层级？**否** —— 直接挂到最近的上级，不补空节点 |
| 代码块 | 作为该标题下第一个子主题，内容整体放入其备注 |
| 引用块 `>` | 归属于最近的上一个主题，写入 `notes.plain` |
| 列表项 | 作为最近标题的子主题，按缩进继续嵌套 |
| 图片 | 写入 `image`，同时尝试上传到服务端 |
| 链接 | 写入 `href` |
| 行内代码 | 写入 `labels` |
| 任务列表 `- [x]` / `- [ ]` | 写入 `markers`（`task-done` / `task-start`） |
| 表格 | 转为「表格标题 + 各行作为子主题」的降级形式，计入 `warnings` |
| 加粗 / 斜体 / 高亮 | 忽略 |

**列表模式规则**：以首个非列表非空行为中心主题（若文件直接以列表开头，则中心主题取文件名）；列表项缩进每 2 或 4 空格为一层，混合缩进时按「缩进量分桶」推断层级。

**两处实现细节**：

- **独占一行的图片提升为子主题**（标题取 `alt`）。Markdown 里插图最常见的形式就是「一行一个 `![](...)`」；如果按普通段落写进 `notes.plain`，备注不渲染 Markdown，图片就彻底消失了，连警告都不会有。行内夹着图片的句子（`架构 ![图](a) 如下`）仍按段落处理，不拆节点。
- **相对路径图片暂记为 `image-skipped`**。`image` 字段存的是 URL，相对路径必须先上传拿到服务端地址；后端的通用文件上传接口（`POST /api/v1/files`）尚未提供，此时写进文档只会是一张破图，所以如实计入「未能还原」，而不是留一个坏引用。

### 2.3 OPML 导入

```ts
const root = parseXml(xmlText);                // 自研 XML 解析器（见下）
const body = childNamed(root, 'body');         // 名字忽略大小写
const outlines = childrenNamed(body, 'outline'); // 归一成数组
```

- `<outline>` 的 `text` → `title`；缺失时回退 `title` 属性，再缺失用 `(未命名)`。
- 递归 `outline.outline` 作为 `children.attached`。
- 属性映射见 [03-数据模型与文件格式](./03-数据模型与文件格式.md) §5.4。
- 根 `<outline>` 多于 1 个时：第一个作为中心主题，其余作为 `floatingTopics`。
- 「没有内容」（不是 `opml` 根 / 没有 `body` / 没有 `outline`）返回**空 sheets**，由导入框架统一判 `EMPTY_DOCUMENT`；XML 结构错误抛 `PARSE_FAILED`。「空」和「坏」是两种失败，判断只在一处做。

**为什么不用 `fast-xml-parser`**：`v5.11.2` 带 6 个传递依赖（`@nodable/entities` / `fast-xml-builder` / `is-unsafe` / `path-expression-matcher` / `strnum` / `xml-naming`），`v4.5.3` 只有 `strnum`。为一个只用来读**不可信输入**的解析器引入这些不划算。

自研解析器（`frontend/src/editor/import/xml.ts`，约 300 行）只做本项目需要的子集，并且**整个跳过 `<!DOCTYPE ...>`（含 `[...]` 内部子集）**——既然自定义实体永远不会被定义，XXE 与 billion-laughs 就是**结构上不可能**，而不是靠配置关掉的。另有 `maxDepth` / `maxNodes` 两道闸门。

## 3. 导出

### 3.1 导出上下文准备（所有格式共用）

```
1. 取 sheet 列表（按「内容」选项：当前画布 / 全部画布）
2. 对每个 sheet 重新执行布局（纯函数，不受当前视口缩放平移影响）
3. 计算内容包围盒 bounds（只算盒子与连线端点，不含布局自带的内边距）
4. 应用导出选项：
   ├─ padding（默认 40px，加在内容包围盒之外）
   ├─ 透明背景（不画背景 rect）/ 边框（1px 中性灰外框）
   ├─ 品牌标识（右下角，文字取自站点设置 `site.brand`，导出时可临时改）
   └─ 当前日期（左下角 YYYY-MM-DD，用本地时区）
5. 图片地址换成 data: URL（见 3.2）
6. 生成独立 SVG（见 3.2）
7. 交给具体格式适配器
```

三条容易踩的细节：

- **不复用画布视口**。用户导出时可能正缩到 40% 看全局，也可能平移到某个角落。把那个状态带进导出，图片就跟着歪。所以每个画布**重新跑一遍布局**，尺寸完全由内容决定。
- **包围盒不含布局内边距**。布局自己有 80px 内边距，导出留白是另一个独立参数。两者叠加的话，用户把留白调成 0 之后仍然会看到 80px 空边，只会以为选项没生效。
- **多画布纵向排列**：间距 48px，各自水平居中（左对齐会让窄画布贴边，看起来像被裁掉一块）。有日期或品牌标识时底部预留 28px。

### 3.2 独立 SVG 构建

导出的 SVG 与画布渲染共用同一套元素生成函数，但**排除**编辑器专属节点（选区框、折叠徽标、编辑中的输入框）。

```ts
function buildExportSvg(ctx: ExportContext): string   // 返回带 XML 声明的完整文档
```

要点：

| 项 | 处理 |
| --- | --- |
| 序列化 | `react-dom/server` 的 `renderToStaticMarkup`，不是手写字符串拼接 |
| 命名空间 | `xmlns="http://www.w3.org/2000/svg"`，`xmlns:xlink` |
| 尺寸 | `width` / `height` = 内容尺寸 × scale；同时写 `viewBox` 保持矢量可缩放 |
| 样式 | 全部内联（`fill` / `stroke` / `font-family` / `font-size`），不依赖外部 CSS |
| 字体 | 见 §4 |
| 图片 | 内嵌为 `data:` base64，见下 |
| 背景 | `transparent: true` 时不绘制背景 rect |
| 转义 | 文本内容由 React 转义（`& < > " '`），不手写替换 |

**为什么用 `renderToStaticMarkup` 而不是 `XMLSerializer`**：验收要求「导出的 PNG 与画布所见像素级一致」，那就必须两边由**同一套组件**产出。手写一份字符串渲染器意味着两套样式逻辑，像素级一致无从谈起；先渲染成 DOM 再 `XMLSerializer` 则需要一个真实的 `<svg>` 挂进文档（导出对话框里那个只是预览图）。`renderToStaticMarkup` 在 node 环境下就能跑，因此「导出的 SVG 里有什么」可以纯函数断言。

代价是 `react-dom/server` 会进包（压缩后约 200KB / gzip 约 65KB）。它**必须待在导出那个懒加载 chunk 里**：`vite.config.ts` 的 `manualChunks` 专门把它从 react chunk 摘出来，否则首屏会白白多下载六十多 KB 的序列化器，而绝大多数访客根本不会点「导出」。

**图片内嵌**分三步，因为抓字节是异步的、构建 SVG 是同步的：

| 步骤 | 函数 | 说明 |
| --- | --- | --- |
| 1 | `collectImageSources(ctx)` | 纯函数。列出所有需要内嵌的地址，跳过 `data:` 与空串，按 `src` 去重（XMind 里复制粘贴的节点共用同一个资源条目） |
| 2 | `loadImageSources(sources)` | 异步。`fetch` → `blob` → `FileReader.readAsDataURL`，**并发**且每张 8 秒超时；成功结果按 `src` 缓存在模块级 |
| 3 | `applyImageSources(ctx, map)` | 纯函数。换掉 `sizes[i].image.src`，不动尺寸与盒子 |

拆成三步而不是一个 `await inlineAll(ctx)`：对话框每次改选项都要重算 SVG，绑在一起的话勾一下「边框」就会重新下载所有图片。

失败（跨域被拒、外链失效、超时）的地址**保留原样**并计入「N 张图片未能内嵌」提示。不删掉那个 `<image>`：删了只会在节点里留一块空白，还看不出为什么；留着至少地址是可见的线索。

### 3.3 SVG 导出

`buildExportSvg(ctx)` 的结果就是文件内容，直接 `Blob` → `<a download>` 下载。

- 文件名：`{导图标题}.svg`，去掉 `\ / : * ? " < > |` 与多余空白，超长截到 80 字，空标题兜底「未命名导图」。
- 附带 `<?xml version="1.0" encoding="UTF-8"?>` 声明（少了它某些桌面图片查看器会当成 HTML）。
- 下载走 `URL.createObjectURL` + 临时 `<a>`，不用 `data:` 直接当 `href`（Chrome 对超长 `data:` 导航有限制，大导图会表现为「点了没反应」），并在 1 秒后 `revokeObjectURL`。

### 3.4 PNG / JPEG 导出

路线是「SVG 字符串 → `Blob` → `objectURL` → `<img>` → canvas」，不是
`canvas.drawImage(svgElement)`：后者在部分浏览器上会得到空白画布，因为 `drawImage`
不接受一个没被渲染过的 SVG DOM。

```ts
async function rasterizeSvg(
  markup: string,
  target: { width: number; height: number; format: 'png' | 'jpeg'; background: string | null },
): Promise<Blob>
```

| 项 | 处理 |
| --- | --- |
| 画布尺寸 | 直接取 `target`（= 逻辑尺寸 × 倍率），不用 `<img>` 的自然尺寸——超大 SVG 可能被浏览器降采样 |
| 底色 | 先铺底色再 `drawImage`。PNG 透明时不铺（保留 alpha）；JPEG **一定**铺白 |
| 质量 | JPEG 0.92；PNG 忽略该参数 |
| 释放 | `finally` 里 `revokeObjectURL`，失败路径也不漏 |

**JPEG 的透明要在上下文阶段就处理掉**：`ExportOptions.format` 参与背景计算，
`jpeg + transparent` 直接产出白色背景，而不是等到编码时才补白。这样预览里看到的
白底就是拿到手的白底——预览与成品不一致是导出功能最伤人的失败方式。勾着「透明
背景」导 JPEG 时，对话框会补一句「JPEG 没有透明通道，将填充白色」。

**容量保护**：Canvas 单边上限（Chrome / Firefox 16384px，Safari 尤其 iOS 实际可用
上限低得多且超限不报错）与总像素上限各不相同。导出前计算目标像素尺寸：

| 情况 | 处理 |
| --- | --- |
| 单边 ≤ 8192 且总像素 ≤ 268M | 前端直接栅格化 |
| 单边 8192 ~ 16384，总像素 ≤ 268M | 提示「较大，生成可能较慢」，允许继续 |
| 单边 > 16384 或总像素 > 268M | 禁用下载按钮，提示降低倍率或改用 SVG |

268M 像素 = 16384²，按 4 字节/像素算正好 1GB 内存。**SVG 不受此限制**——它是矢量
的，再大也只是字符串长一点，所以「太大」时给的出路是「改用 SVG」，而不是只有
「降低倍率」。

### 3.4.1 字体内嵌

SVG 通过 `<img>` 载入时**拿不到父页面的 `@font-face`**，栅格化会用系统字体
（macOS 上是 PingFang SC）而不是应用分发的思源。实测差距不小：同一个节点标题在
画布上宽 134.2，独立打开的导出 SVG 只有 113.0（-16%）——节点框是按思源量的，
换成更窄的系统字体后文字在框里显得空，换成更宽的字体会**溢出节点框**。

所以导出前把用到的字体分片读成 base64，以 `@font-face` 写进 SVG 的
`<defs><style>`。`<img>` 里的 SVG 不许引用**外部**资源，但 `data:` 是文档自身的
一部分，不受限（实现见 `frontend/src/editor/export/font-embed.ts`）。

| 项 | 处理 |
| --- | --- |
| 嵌哪些族 | 扫 `layout.styles` 里每个节点的 `fontFamily` 与主题角色；`system` 族没有 face，跳过 |
| 嵌哪些字重 | 只嵌文档里真正用到的（正文 400 + 中心主题 800 是常态）。思源黑体 5 个字重，筛掉用不到的就省 60% |
| 嵌哪些分片 | 只保留 `unicode-range` 与实际文字相交的片。`U+4E??` 这类通配写法必须展开——漏解析的症状是「嵌了字体却还是回退」 |
| 写回 `unicode-range` | **原样保留**，不重新格式化。重排一遍会把 `U+4E??` 展开成 256 个单码位，CSS 撑大几十倍 |
| 体积 | 11 节点的中文图 **418 KB**（6 条规则）；200 节点的中文图约 340 KB（5 片）。超过 512 KB 时对话框报一句「内嵌字体 N KB（M 个分片）」 |
| 抓不到分片 | 降级为「不嵌这一片」，导出继续——宁可拿到一张字不对的图，也不让导出整个失败 |

> **不是子集化**：理想做法是按用到的字形做子集，体积能小一个数量级。但那要解析并
> 重写 woff2（Brotli 解压 + `glyf`/`loca` 重排 + 重新压缩），是一个独立工程，且需要
> 新依赖。当前是「整片内嵌」，按分片筛选已经把体积压到可接受范围；等依赖能进
> `package.json` 时再换成子集化。
>
> 缺字提示（§4.2）与内嵌是两件事：内嵌的是分片，分片里本来就没有的字形（emoji、
> 扩展区汉字）照样回退，所以 SVG / PNG 下那句提示仍然显示，只有 Markdown / OPML
> 才收起。

### 3.5 PDF 导出

**实际实现是「单页图片 PDF」**：复用 3.4 的栅格化结果（JPEG），再用
`editor/export/pdf.ts` 手写一个 6 个对象的 PDF 容器把它包进去。

```
SVG 字符串 ──rasterizeSvg(jpeg)──▶ JPEG 字节 ──buildImagePdf──▶ .pdf
```

| 项 | 处理 |
| --- | --- |
| 页面尺寸 | 按导图**逻辑尺寸**换算：CSS px × 0.75 = pt（1/96 英寸 → 1/72 英寸）。页脚同时报毫米，用户按纸看的是这个数 |
| 图像尺寸 | 从 JPEG 字节里读（`jpegSize`），**不信调用方传的值**。浏览器降采样后声明错的 `/Width` 会让阅读器拉伸或裁切，而且完全不报错 |
| 压缩 | JPEG 原样嵌入，`/DCTDecode` 交给阅读器解码——不解码、不重编码，也没有 alpha 通道要处理 |
| 文字 | **位图，不可选中、不可搜索**。导出对话框的说明里写明了这一点，并指向 SVG |
| 中文 | 随像素一起走，任何设备都正常显示（不依赖阅读器里装没装思源黑体） |
| 文件结构 | Catalog / Pages / Page / Contents / Image XObject / Info，20 字节一行的 xref 表，`startxref` 指回 xref |
| 文本字符串 | ASCII 走 `(…)` 并转义 `\` `(` `)`；其余走 UTF-16BE 十六进制带 BOM。**PDFDocEncoding 不是 UTF-8**，直接塞 UTF-8 字节会让中文标题变乱码 |
| 拆分导出 | 每个分支各自一份 PDF，页面尺寸与标题用该分支自己的——否则 zip 里会出现 N 个同名同尺寸的文件 |

> **为什么不是矢量 PDF。** 矢量需要把字体程序嵌进 PDF（`Type0` + `CIDFontType2`
> + `CIDToGIDMap` + `W` + `ToUnicode`），而仓库里只有 WOFF2 分片，PDF 不接受
> WOFF2——得先做一个 WOFF2→TTF 的子集化工具。那是独立项目，不是一次导出的
> 附带功能。栅格化把渲染留在浏览器里，代价只是文字不可选中，这一点在界面上
> 明说了，用户要可编辑文字可以导 SVG。
>
> **为什么不用 jsPDF。** 同一份产出，jsPDF 压缩后约 150 KB，而这里只有 6 个
> 固定对象的容器；更关键的是 `buildImagePdf` 是纯函数，可以逐字节断言（单测
> 25 条），jsPDF 只能断言「文件不是空的」。
>
> **备选方案（未采用）**：`jsPDF` + `svg2pdf.js` + 文字转路径（需要
> `opentype.js` 与 TTF 字体）；或服务端 `chromedp` → `Page.printToPDF`（保真度
> 最高，但容器要多装一个 Chromium，镜像 +400MB）。前者卡在依赖与字体格式，
> 后者留给「服务端导出」（IE-30）。

### 3.6 文本与结构格式导出（Markdown / OPML / XMind）

这三种都**从文档模型直接序列化**，不依赖布局与渲染。区别在于承载能力：Markdown 与
OPML 是纯文本（丢样式、丢注释），XMind 是结构包（保留样式、图片、注释）。

**Markdown**（规则见 [03-数据模型与文件格式](./03-数据模型与文件格式.md) §5.6）：

```markdown
# 产品规划

> 2026 年度产品路线

## 一期

- 账号体系
- 导图编辑器 `核心`

## 二期

- 客户端 App
```

**OPML**（规则见 [03-数据模型与文件格式](./03-数据模型与文件格式.md) §5.4）：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<opml version="2.0">
  <head><title>产品规划</title></head>
  <body>
    <outline text="产品规划" _note="2026 年度产品路线">
      <outline text="一期">
        <outline text="账号体系"/>
      </outline>
    </outline>
  </body>
</opml>
```

**导出前必须提示**：Markdown 与 OPML **不承载样式信息**，导出后重新导入会丢失配色、形状、线条。导出对话框在这两个格式下显示醒目的提示条，并把倍率、留白、透明背景、边框、日期、品牌这些只对图形有意义的控件整体收起——禁用一屏控件不如直接不显示。

**实现要点**（`frontend/src/editor/export/text.ts`）：

| 决定 | 原因 |
| --- | --- |
| 根用 `#`、一级分支用 `##`、第 2 层往下用列表 | 纯列表会让导入器的模式判定（`headingCount >= 2`）判成 list 模式，根主题退化成文件名；纯标题受 Markdown 6 级标题上限约束。两级标题 + 无限层列表正好避开两者 |
| 标题里的 `\n` 压成空格 | XMind 富文本标题可能带换行，不压平会在文件里拆成两行，读回来多一个节点 |
| 行首 `#` `-` `*` `+` `>` 加反斜杠转义 | 行首这几个字符会被当成语法。导入器（`import/markdown.ts`）按 CommonMark 还原行首转义，所以「导出 → 导入」标题文字不变 |
| 备注写成 `>` 引用块，缩进跟随层级 | 引用块是导入器唯一会挂回当前节点的块级元素；表格、代码块会被降级成子主题 |
| 链接写 `[标题](href)`、标签用反引号 | 标题不能因为「有链接」而消失；反引号是导入器识别标签的唯一形式 |
| 游离主题放末尾 `## 游离主题` 下 | 它们本来就不在树上，塞进根主题下面等于凭空改结构 |
| OPML 用 `_note` / `_labels` / `_collapse` | OPML 没有标准字段，下划线前缀是业界惯例，不认识它的工具会忽略；导入器读同一套扩展，所以这三个字段往返不丢 |
| 行首转义由导入器还原 | `\#` 读成 `#` 本来就是 CommonMark 的行为，导出加转义、导入还原，两边对称 |
| 一次只导一张画布 | 两个序列化器都是单画布语义。多画布拼进一个文件会让根主题变成两个，读回来结构就变了；对话框在有多张画布时明说「只导出当前画布」 |

两个格式的验收标准是 **IE-16 / IE-17：导出后能被本项目自己的导入器读回来，层级与文字不变**，`text.test.ts` 里过半用例是往返比对而不是字符串快照。

### 3.6.1 XMind 导出

写的是**现代格式**（XMind 2020+）：一个 zip，`content.json` 装全部画布，
`metadata.json` 装工作簿信息，`manifest.json` 列条目，图片进 `resources/`。
不写 XMind 8 的 `content.xml`——那是另一套 schema（XML + `styles.xml` 引用）。

```
产品规划.xmind
├─ content.json      [{ id, class: 'sheet', title, rootTopic, relationships, theme }]
├─ metadata.json     { creator: { name: 'wmind', version } }
├─ manifest.json     { file-entries: { 'content.json': {}, … } }
└─ resources/        image-1.png …
```

**实现要点**（`frontend/src/editor/export/xmind.ts`）：

| 决定 | 原因 |
| --- | --- |
| 样式写解析后的值，不写「继承」 | XMind 主题体系与本项目不同。留着 `null` 让 XMind 套它自己的主题，导出的图会从彩色变灰白。代价是导出后在 XMind 里换主题不生效 |
| 不写 `fo:font-family` | 本项目存的是族标识符（`sans` / `serif` / `mono`），不是字体名；硬猜一个字体名在对方机器上未必存在，导入侧的 `normalizeFontFamily` 还会降级报警告 |
| 概要挂父主题、外框挂共同父主题、联系挂画布 | 这是 XMind 自己的位置。写在别处本项目读得回来，XMind 未必认得 |
| 外框归属在整棵树走完之后算 | `parentOf` 在遍历中填充，走完才知道一组节点是否同属一个父主题（`groupBoundaries` + `attachBoundaries`） |
| 图片必须内嵌进 `resources/` | `src` 可能是 `/uploads/…` 或外链，只在站内有效。换不回来的图**不写**，由对话框如实计数 |
| 多画布写多个 `sheet` 条目 | `.xmind` 本来就支持多画布，所以对话框对 XMind **保留**「内容范围」选择器，与 Markdown / OPML 不同 |

验收标准是 **IE-32：导出后能被本项目自己的 `importXmind` 读回来，标题、层级、样式、
概要、外框、联系、图片全部存活**，`xmind.test.ts` 是往返比对而不是字符串快照。

### 3.7 导出对话框

对应截图 6、7、8。**已实现**的选项：

| 分组 | 选项 | 取值 | 说明 |
| --- | --- | --- | --- |
| 格式 | `format` | SVG / PNG / JPEG / PDF / Markdown / OPML / XMind | 矢量在前：它是唯一无损的；Markdown / OPML 垫底，因为它们丢样式；XMind 是唯一能「再编辑」的 |
| 内容 | `scope` | 当前画布 / 全部画布 | 只有一张画布时「全部」禁用；Markdown / OPML 下整组隐藏（只导当前画布），XMind 保留（一个 `.xmind` 能装多张画布） |
| 缩放 | `scale` | 1× / 2× / 3× / 4× / 自定义（0.5–8，一位小数） | 只影响 PNG / JPEG 的像素数；SVG 只改 `width` / `height` |
| 留白 | `padding` | 无 / 24 / 40 / 80 | 加在内容包围盒之外，与布局内边距无关 |
| 长宽比 | `aspect` | 跟随内容 / 16:9 / 4:3 / 1:1 / 9:16 | **只加边、不裁切**，内容居中 |
| 外观 | `border` | 无 / 细描边 / 红 / 橙 / 绿底 / 蓝底 | 见下方「边框预设」 |
| 外观 | `transparent` | 开关，默认关 | JPEG 下强制白底；带底色的预设下禁用 |
| 内容 | `date` | 开关，默认关 | 左下角 `YYYY-MM-DD`（本地时区） |
| 内容 | `brand` | 开关，默认**开** | 右下角印品牌文字 |
| 内容 | `brandText` | 文本框，最多 64 字 | 打开时预填站点设置 `site.brand`（留空则回退站点名）；用户改过就以改过的为准，关掉对话框后复位 |
| 内容 | 按主分支拆分 | 开关，默认关 | 每个主分支一张图，打成 zip；仅图形格式且分支 ≥ 2 时出现 |

**边框预设**：`none` / `thin` / `red` / `orange` 只换描边色与粗细（1px 或 2px）；
`green` / `blue` 是**带底色的板**（浅绿 `#F1FAF4` / 浅蓝 `#EFF5FF`），选中时自动
关掉并禁用「透明背景」——否则会出现「勾着透明却是绿底」这种自相矛盾的状态。
底色在上下文里就写进 `background`，预览与成品因此一致。

> 六个预设的**色值是暂定值**，还没有按设计截图采样校准（docs/06 §3.7 原记的待办）。
> 校准只需要改 `BORDER_PRESETS` 这张表，`border` 的传递链路不用动。

**自定义倍率**是界面状态与数值分开记的：只用「当前倍率是不是预设值」来判断要不要
显示输入框，选「自定义」时倍率仍是 2，判断结果还是「预设」，下拉会立刻弹回 2×、
输入框永远不出现。所以对话框单独记一个 `customScale` 布尔值。

**长宽比只加边、不裁切**：目标比例比内容「宽」就加宽、比内容「高」就加高，内容
永远完整。裁切是另一种产品（「裁剪导出」），两者混在一个选项里会让人分不清自己
拿到的是哪一种。多出来的空间**取整后对称分配**（`width + extra * 2`），而不是两侧
各得小数半格——半像素偏移在栅格化时会变成一条模糊的边，左右不对称本身就是肉眼
可见的缺陷。代价是最终比例与目标可能差 1 个逻辑像素（乘倍率后 1–4 像素）。

居中的是**内容盒**（内容 + 留白 + 页脚），品牌标识与日期贴画布底边——它们是水印，
不是内容的一部分。

**按主分支拆分**：每个主分支出一张图，打成 zip，文件名取分支标题。
每张图都**带中心主题**（只画分支会丢掉「这是哪张导图的哪一支」，而中心主题往往
就是上下文本身）。关系线、边界、汇总只保留两端都还在的，游离主题不进分支图。
重名分支加 `-2` / `-3` 后缀——zip 里同名条目在多数解压工具里会静默丢掉一个。
出图串行而不是并发：每张都要过一次 `canvas.toBlob`，并发十张会让峰值内存翻十倍。
拆分时底部的尺寸换成文件数——逐张尺寸不同，报一个数只会误导。

> zip 里的中文文件名带 UTF-8 标志位（`flag_bits` 的 `0x0800`），Finder、Windows
> 资源管理器、Python `zipfile` 都正确还原。**macOS 自带的命令行 `unzip` 不认这个
> 标志**，`unzip -l` 会显示乱码——那是它的老毛病，不是文件有问题。

**预览就是成品**：左侧 `<img>` 的 `src` 与「下载」写出的字节来自同一次
`buildExportSvg` 调用，不是另画一个近似预览。透明背景时预览底板换成棋盘格，
好让用户直接看出哪里是空的。选 Markdown / OPML 时预览换成等宽文本——这两种
格式没有「画出来」的样子，给它画一张图反而是骗人；而且文本是同步序列化的，
对话框连 SVG 都不构建（一张巨型导图每次改选项都重算一遍序列化 + base64 编码
要几百毫秒）。选 XMind 时预览换成**节点大纲**（节点数 + 缩进树）：画成图会让人
以为导出的是一张图，画成 Markdown 又会让人以为导出的是 Markdown。

**底部一行同时回答五个问题**：导出尺寸（`1232 × 484 px`，文本格式换成字符数，
XMind 换成节点数）、是否超出栅格化上限、有没有图片没能内嵌、有没有字符要退回系统
字体（见 §4.2）、内嵌字体占了多少体积（超过 512 KB 才报，见 §3.4.1）。五个都是
「不写出来用户就会误解」的信息。

**尚未实现**（路线图里的后续项，不假装已有）：

| 选项 | 状态 |
| --- | --- |
| 边框预设色值 | 6 个预设已可用，但色值是暂定值，需按截图采样校准（改 `BORDER_PRESETS` 一张表） |
| PDF | 见 §3.5，**阻塞**：`jspdf` / `svg2pdf.js` / `opentype.js` 装不进依赖 |

### 3.8 分享页的导出控制

分享页（`/s/:token`）复用同一套导出能力，但入口与权限受三重控制：

| 控制点 | 来源 | 行为 |
| --- | --- | --- |
| 站点级 | `feature.export_enabled` | 关闭时所有位置（含编辑器）都不允许导出 |
| 分享级 | `share.allow_download` | 关闭时分享页**隐藏导出按钮**，且服务端拒绝该 token 的导出请求 |
| 页面级 | — | 分享页的导出对话框**不提供** Markdown / OPML 选项（这两种格式导出的是内容而非渲染结果，与「只读展示」的定位不符），仅提供 PNG / JPEG / SVG / PDF |

**服务端导出接口的鉴权**：`POST /export` 接受可选的 `shareToken` + `X-Share-Access`。当以分享身份调用时：

```
1. 解析 shareToken，按分享失效规则校验（撤销/过期/导图删除 → 404）
2. 校验 share.allow_download，为 false 时返回 403 EXPORT_DISABLED
3. 校验请求的 mapUid 必须等于 share.map_id（防止借分享身份导出其他导图）
4. 服务端渲染时同样应用 show_notes 剥离规则
```

> **能力边界重申**：分享页必须把文档结构下发给浏览器才能支持折叠、缩放等交互，因此 `allow_download = false` **无法**阻止有技术能力的访问者通过开发者工具获取数据。它降低的是门槛，不是访问控制。真正的访问控制应使用访问密码。

## 4. 字体处理

字体是导出保真度的最大风险点，尤其 PDF 与中文。**默认字体为思源黑体（Noto Sans SC，SIL OFL 1.1）**，完整决策见 [09-技术决策记录](./09-技术决策记录.md) ADR-016。

| 格式 | 策略 |
| --- | --- |
| SVG | 在 `<defs><style>` 中写入 `@font-face`，字体以 base64 WOFF2 内嵌。**只内嵌该导图实际用到的分片**（按 `unicode-range` 挑），而非全量字体；提供「文字转路径」选项进一步规避体积与字体缺失问题 |
| PNG / JPEG | 由浏览器栅格化，字体已加载即可正常渲染。导出前必须 `await document.fonts.ready`，否则会用回退字体栅格化 |
| PDF | 默认「文字转路径」（`opentype.js`）；关闭该选项时用 `jsPDF.addFileToVFS` 内嵌 TTF 子集。选 TTF 静态实例而非 OTF/可变字体，正是因为这条链路对前者的支持最稳 |
| Markdown / OPML | 不涉及字体 |
| XMind | 不涉及字体（写的是字体族标识符 `sans` / `serif` / `mono`，由 XMind 侧决定实际字体，见 §3.6.1） |

### 4.1 分发的字体

随应用分发 **Noto Sans SC 的 TTF 静态实例，4 个字重**（300 / 400 / 700 / 800），按 `unicode-range` 切片后由本站源提供，**不依赖外部 CDN**：

| 字体 | 用途 | 字重 | 许可 |
| --- | --- | --- | --- |
| Noto Sans SC（思源黑体） | **默认**，中文无衬线 | 300 / 400 / 700 / 800 | SIL OFL 1.1 |
| Noto Serif SC（思源宋体） | 中文衬线（`serif`，P1） | 400 / 700 | SIL OFL 1.1 |
| JetBrains Mono | 等宽（`mono`，P1） | 400 / 700 | SIL OFL 1.1 |
| 系统字体栈 | `system` 选项，零字节 | — | — |

> **已解决**：`NeverMind` 为 XMind 自有字体、不可分发，已由 ADR-016 决定改用思源黑体。文档里 `fontFamily` 存**标识符**（`sans` / `serif` / `mono` / `system`），导入时按 [03](./03-数据模型与文件格式.md) §5.3.1 的映射表把 XMind 的字体名归一——**不再需要「同名替换」这一层**。
>
> **不做硬子集截断**：不采用「只打包 GB2312 一级字库 3755 字」的做法。导图内容任意，截断会让常用但不在该表内的汉字显示为方框；改为全量 CJK 覆盖 + 分片按需加载。

### 4.2 字体缺失与回退的可见性

导出时必须能回答「这次导出有没有用到回退字体」：

- 导出前遍历文档全部**会被画出来**的文本，确认覆盖情况。
- 命中回退字体时，在导出结果里给出提示（「有 N 个字符使用了系统字体渲染，在其他设备上可能显示不同」），而不是静默出图。用户看到差异却不知道为什么，是比差异本身更糟的体验。
- 服务端兜底导出（chromedp）的容器必须预装同一套字体到 `/usr/share/fonts`，否则服务端渲染结果与浏览器不一致——**同一个导图在不同路径导出得到不同结果，是最难排查的一类 bug**。

**实现**（`editor/theme/coverage.ts` + `editor/export/fonts.ts`）：

| 决定 | 原因 |
| --- | --- |
| 覆盖率来自分片清单派生的码位表，**不用 `document.fonts.check()`** | `check()` 只回答「字体加载了没」，对没有字形的码位照样返回 true。拿它判覆盖率永远得出「全都覆盖」，而这正是要发现的问题 |
| 码位表由 `scripts/gen-font-coverage.mjs` 从 `manifest.json` 派生，36 KB 并进导出对话框的懒加载分块 | 直接读 manifest 是 841 KB；压成「合并后的码位区间」后只剩 36 KB，且思源黑体/宋体共用同一套 Google CJK 切分，按内容去重后只存一份 |
| `check-fonts.mjs` 第 7 项校验码位表与 manifest 一致 | 表过期不会报错，只会让提示说谎（说没缺字而实际缺）。用生成它的**同一个函数**比对，不存在两套实现跑偏 |
| 只扫「会被画出来」的文字：主题标题（取折行后的实际行）、边界标题、关系线标题 | 备注不画在画布上，为它报缺字是误报。**标签目前也不画**（`viewer/` 里没有地方读 `topic.labels`），等标签上画布要同步加进来 |
| 节点用 `system` 族时跳过 | 那本来就是系统字体，报「回退到系统字体」是自相矛盾 |
| 按码位去重、按字符遍历（`for...of`） | 用户关心「哪些字」，同一个字出现十次报 10 个没有意义；按 UTF-16 单元遍历会把一个 emoji 拆成两个代理码位各报一次 |
| 空白与控制字符不算缺字 | 它们不画字形，报出来只是噪音 |

提示文案会带上前 5 个字符作样本：只说个数，用户没法判断要不要处理。不画字的格式（Markdown / OPML / XMind）不显示这条提示。

## 5. 主题系统（配色与形状还原）

### 5.1 主题构成

一套主题（Theme）= **配色方案（Palette）** + **角色样式（Role Styles）** + **全局设置（Global）** + **布局开关（Layout）**。结构定义见 [03-数据模型与文件格式](./03-数据模型与文件格式.md) §2.5。

### 5.2 还原清单

对标截图 4 的「画布」面板，逐项列出实现要求：

| UI 项 | 数据字段 | 说明 |
| --- | --- | --- |
| 配色方案（缤纷 10 套 / 经典 9 套） | `theme.palette` | 每套含 `colors`（分支填充）、`lineColors`（线条）、`backgroundColor` |

### 5.3 配色方案数据

19 套可见内置配色方案的主色序列见 [03-数据模型与文件格式](./03-数据模型与文件格式.md) §6.2。

**每套配色还需定义**：

```ts
interface Palette {
  id: string;
  name: string;
  nameEn: string;         // 英文界面的显示名
  category: 'vivid' | 'classic';
  legacy?: boolean;      // 隐藏兼容项，不在新面板里显示
  colors: string[];        // 分支填充色，按 branchIndex 循环
  lineColors: string[];    // 分支线条色，通常与 colors 一致
  backgroundColor: string;
  centralTopic: Partial<Style>;   // 中心主题的填充/文字色
  mainTopic: Partial<Style>;
  subTopic: Partial<Style>;
}
```

> **对比度约束**：每种填充色上的文字色必须满足 WCAG AA（4.5:1）。深色填充配白字，浅色填充配深字。
>
> **不存 `textColors` 表**：字色在渲染时按填充色的相对亮度，在 `#1F1F1F` / `#FFFFFF` 中取对比度更高的一个（`theme/resolve.ts` 的 `readableTextColor`）。存表只能覆盖调色板里的固定几十种颜色，用户手动填的任意色仍然需要一个可读字色；而「选高者」永远不劣于任何手写映射表。
>
> **校验**：`npm run check:palette`（CI 已接入）读取 `palettes.json` 逐色核算，低于 4.5:1 直接失败；`palettes.test.ts` 用真实的 `computeStyle` 再跑一遍，防止脚本与运行时逻辑漂移。

默认「缤纷 · 黎明」使用参考图中的珊瑚红、杏橙、薄荷绿、青绿、浅蓝和紫色，中心主题白底深色字，当前色值见 03 文档 §6.2。接近白色的分支填充配更清楚的同色相连线。新值仅用于新建导图或主动选择色板，已保存的完整主题和节点颜色保持原样。

### 5.4 色值校准方法

当前 19 套色板根据用户提供的截图整理并通过文字对比度校验，属于**截图近似值**。取得 XMind 原始 SVG 后可按以下流程进一步精确校准：

1. **采样**：在 XMind 中依次应用 19 套配色方案，导出 SVG（XMind 的 SVG 导出会写出真实色值），从 SVG 中提取 `fill` / `stroke` 属性。
2. **补全**：截图中的色带缩略图只有 6 段，实际主题可能有更多色。以 SVG 中实际出现的颜色序列为准。
3. **对比度校验**：跑校验脚本，不达标时在保持色相的前提下取最小明度微调（保持视觉一致性）。
4. **落库**：把校准结果写入 `frontend/src/editor/theme/palettes.json`（前端内嵌资源），并同步更新 03 文档的表格。
5. **回归**：用同一份导图在 XMind 与 wmind 中分别导出 SVG，做像素级对比（容差 2%），作为主题还原的验收手段。

**XMind 形状（shape-class）还原**：XMind 的形状体系包含约 20 种（矩形、圆角矩形、胶囊、椭圆、圆形、菱形、六边形、平行四边形、梯形、星形、云形、下划线、无边框、双向箭头等）。一期实现 §2.4.1 表中列出的 10 种，其余在导入时降级为最接近的形状并计入 `warnings`，二期补齐。

### 5.5 主题与模板的关系

| 概念 | 作用范围 | 关系 |
| --- | --- | --- |
| **主题（Theme）** | 一份导图的整体视觉 | 可随时切换，不改变内容 |
| **模板（Template）** | 新建导图时的初始状态 | 一个模板**包含**一份默认主题 + 结构 + 示例内容 |

创建导图时，模板的 `document.theme` 被复制到新导图中，此后两者解耦：改模板不影响已创建的导图，改导图主题不影响模板。

| IE-22 | 分享页 `allow_download = false` | 导出按钮不可见；直接调 `POST /export` 带该 token 返回 403 |
| IE-23 | 分享页借用 token 导出其他导图 | 返回 404（`mapUid` 与 `share.map_id` 不匹配） |
| IE-24 | 分享页 `show_notes = false` 时导出 | 导出结果中不含备注内容 |
| IE-25 | 导入分别使用 `NeverMind` / `微软雅黑` / `楷体` / `Arial` / `Consolas` 的 XMind 文件 | `fontFamily` 分别归一为 `sans` / `sans` / `serif`（计入降级 warning）/ `sans` / `mono`，**不写入任何原始字体名** |
| IE-26 | 导入含 GB2312 表外汉字（如「龘」「㸚」）与 emoji 的导图 | 汉字正常显示（全量覆盖，无硬子集截断）；emoji 走回退栈，导出时给出「N 个字符使用了系统字体」提示 |
| IE-27 | 首次打开一个 200 节点导图（冷缓存，字体未加载） | 骨架屏 → 字体就绪 → 首次布局，**全程无可见跳动**（节点尺寸不因字体替换而改变） |
| IE-28 | 编辑器中把主题字体从 `sans` 切到 `serif` | 全量重排；节点宽度与新字体实测一致（证明测量缓存已随字体标识符失效） |
| IE-29 | 在 `serif` 字体族下导出 SVG / PDF | 内嵌或转路径的是思源宋体，视觉与画布一致；不出现默认字体的字形 |
| IE-30 | 同一导图分别用浏览器导出与服务端兜底导出 | 像素级一致（容器已预装同一套字体）；若有差异则判为缺陷而非「可接受差异」 |
| IE-31 | 人为删除一个字体分片后构建 | CI 的分片完整性校验失败（**不得**让缺失分片静默上线，症状是方框且不报错） |
| IE-32 | 导出 XMind 后重新导入 | 标题、层级、样式、概要、外框、联系一致；图片落在 `resources/` 且能显示 |

- **IE-27 的「无跳动」要量布局宽度**（节点自己的 `rect[width]`），不能量
  `getBoundingClientRect`——后者乘过缩放，打开时 100%、随后「缩放到适应」变成 78%，
  看起来像跳了 22%，实际什么都没变。

  长宽比 2.413 对 2.414，直接逐像素比有 2.21% 均值差（全是 1px 边缘），取 3×3 邻域
  最小值后降到 0.2%。
