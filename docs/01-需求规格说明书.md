## 1. 项目背景与目标

### 1.1 背景

思维导图是需求梳理、方案设计、知识整理的常用工具，XMind 是该领域体验最成熟的商业产品。但在自建与团队内网场景下，直接使用 XMind 存在几个绕不开的问题：

- **数据在第三方**：导图文件散落在个人电脑或商业云盘，团队资产无法沉淀，也无法纳入自有的备份与审计体系。
- **无法私有化部署**：内网、涉密环境无法使用在线服务，桌面版又缺少统一的服务端存储。
- **不可定制**：模板、主题、导出样式无法按组织规范固化；无法与内部系统（需求平台、知识库）打通。
- **订阅成本与账号管理**：团队成员账号由厂商控制，组织层面缺少统一的开通/停用能力。

### 1.2 项目目标

构建 **wmind**——一套可私有化部署、数据自主可控、体验对标 XMind 的 Web 思维导图系统。

一期目标（可验证）：

1. 用户能完成「注册 → 登录 → 从模板新建 → 编辑导图 → 导入/导出」的完整闭环，编辑体验与 XMind 桌面版的核心操作习惯一致。
2. 管理员能在一套后台中完成用户全生命周期管理与站点开关配置，无需改配置文件。
3. 通过 `docker compose up -d` 一条命令完成部署，无外部强依赖。**同时提供 PostgreSQL 版本 compose，供规模更大或需要多副本的组织选用。**
4. 数据格式自有、可扩展，为后续客户端 App 与协作能力预留接口。

### 1.3 产品定位

- **Self-hosted first**：默认部署形态是「一个实例服务一个组织」，不是多租户 SaaS。
- **Web 优先**：一期只做 Web，桌面级体验靠浏览器内的高性能渲染达成；原生客户端为二期。
- **格式开放**：数据不锁死，支持 XMind / Markdown / OPML 进出。

## 3. 用户角色与权限

| 角色 | 标识 | 说明 | 权限范围 |
| --- | --- | --- | --- |
| 游客 | `anonymous` | 未登录访问者 | 访问登录页、注册页（受站点开关控制）、读取公开站点配置 |
| 注册用户 | `user` | 普通使用者 | 对自己名下的导图 / 模板 / 主题拥有全部增删改查权限；不可访问他人资源与管理接口 |
| 管理员 | `admin` | 系统运营者 | 拥有 `user` 全部权限，外加：用户管理、站点设置、全局统计、审计日志 |

> **权限模型说明**：一期采用「资源属主 + 全局角色」两层模型，不做导图级别的共享授权。导图接口一律以 `owner_id` 做数据隔离，管理员默认**不**能直接读写他人导图内容（仅能管理账号与执行删除），以降低越权风险。若后期引入团队空间，再扩展为 RBAC。

## 4. 功能需求

需求优先级：**P0** = 一期必须交付；**P1** = 一期尽量交付，可延后；**P2** = 远期预留。

### 4.1 账号与认证（FR-AUTH）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-AUTH-01 | 邮箱 + 用户名 + 密码注册。注册开关由站点设置控制，关闭时接口返回 403 且前端隐藏入口 | P0 |
| FR-AUTH-02 | 支持「邮箱或用户名 + 密码」登录 | P0 |
| FR-AUTH-03 | 登出，令牌失效 | P0 |
| FR-AUTH-04 | 访问令牌过期后自动静默续期（refresh token），用户无感知 | P0 |
| FR-AUTH-05 | 修改密码（需校验原密码），修改后使其他设备的会话失效 | P0 |
| FR-AUTH-06 | 个人资料：昵称、头像（上传或使用默认首字母头像） | P1 |
| FR-AUTH-07 | 忘记密码 / 邮件重置。**二期实现**，依赖 SMTP 配置。一期由管理员通过后台「重置密码」为用户找回账号 | P2 |
| FR-AUTH-08 | 注册邮箱验证。**二期实现**，依赖 SMTP | P2 |
| FR-AUTH-09 | 账号被管理员禁用后，已登录会话在下次请求时被拒绝 | P0 |
| FR-AUTH-10 | 管理员可重置指定用户的密码（生成或指定新密码，一次性展示），并撤销该用户全部会话 | P0 |
| FR-AUTH-11 | 用户资料中的邮箱变更需校验唯一性，且不要求邮件确认（一期） | P0 |

> **一期账号找回策略**：由于不接入 SMTP，用户忘记密码时需联系管理员。管理员在后台「用户管理」中执行「重置密码」，将新密码线下告知用户。该流程需在登录页给出明确引导文案（「忘记密码请联系管理员」），避免用户找不到入口。
>
> 二期接入 SMTP 后，上述两项能力按已归档的设计实现（见 [09-技术决策记录](./09-技术决策记录.md) ADR-012）。

> **FR-SYS-07 的验收要点**（完整条件见 §7）：同一份代码、同一个镜像，改 `WMIND_DB_DRIVER` 就能在两种数据库上跑；两套迁移集的版本号序列必须一致；发布前必须在 PostgreSQL 上跑一遍完整回归——**不允许「开发用 SQLite、上线用 PostgreSQL」而从不验证后者**。
>
> **为什么默认 SQLite**：一期部署形态是「一个实例服务一个组织」，这个量级下 SQLite 的性能与 PostgreSQL 没有可感知差异，却省掉一个容器、一份数据库密码和一套独立的备份流程。对私有化交付（尤其是内网隔离环境）而言，「解压即用」的价值高于理论上的扩展上限。
>
> **SQLite 的硬边界**（写进需求是为了避免后期误用）：单实例部署，不支持 `api` 多副本；数据文件必须落在本地块设备，不支持 NFS/SMB/云盘；标题模糊搜索退化为全表 `LIKE`。超出这些边界时改用 PostgreSQL。

## 5. 非功能需求

### 5.1 性能

| 指标 | 目标 |
| --- | --- |
| 导图列表页 LCP | < 2s（本地/局域网） |
| 编辑器打开 1000 节点导图 | < 1.5s |
| 拖拽 / 选中 / 输入等交互 | 稳定 60fps（单帧 < 16ms） |
| 自动保存接口 P95 | < 300ms |
| 单导图节点数上限 | ≥ 5000 节点仍可编辑（> 2000 节点时允许降级为简化渲染） |
| 列表页接口 P95 | < 200ms（1000 张导图规模） |

### 5.2 兼容性

- 浏览器：Chrome / Edge 最近两个大版本、Safari 16+、Firefox 最近版本。
- 最小分辨率：1280 × 720；建议 1440 × 900 以上。
- 移动端：一期仅保证导图**只读浏览**可用，不保证完整编辑体验。

### 5.3 安全

| 项 | 要求 |
| --- | --- |
| 密码存储 | bcrypt（cost ≥ 12）或 argon2id，加盐 |
| 会话 | JWT 双令牌：access token 短时效（15 min）+ refresh token 长时效（7 天，可撤销） |
| 传输 | 生产环境强制 HTTPS，容器内 HTTP |
| 限流 | 登录/注册/导出/导入接口独立限流；登录失败次数过多临时锁定 |
| 越权 | 所有导图相关接口必须校验 `owner_id`；管理接口校验 `role = admin` |
| XSS | 主题标题、备注等富文本在渲染前清洗；导出 SVG 时转义文本 |
| 上传 | 校验 MIME 与扩展名白名单；限制单文件与解压后总大小，防 zip 炸弹 |
| CSRF | 若使用 Cookie 承载令牌，需 `SameSite=Lax` + CSRF Token；推荐 Bearer 头方案 |
| 分享令牌 | 长度 ≥ 22 字符（≥ 128 bit 熵），不可枚举；撤销/过期/密码错误返回不泄露存在性的错误 |
| 分享页 | 默认 `noindex, nofollow`；不返回导图源码，只返回渲染所需数据 |
| 审计 | 管理员敏感操作留痕；分享链接的创建与撤销也记入审计 |
| 管理员改密 | 管理员重置他人密码属高敏操作：需二次确认、一次性展示新密码、留审计记录，且不可重置自己（改自己密码走常规流程） |

### 5.4 可用性

- 自动保存 + 本地草稿双保险，异常关闭不丢内容。
- 网络异常时给出明确提示，恢复后自动重试保存。
- 所有破坏性操作（删除导图、删除用户、清空回收站）二次确认。
- 全局错误边界，单模块崩溃不白屏。

### 5.5 可维护性与可扩展性

- 后端严格分层（handler / service / repository），核心格式转换逻辑可单测。
- 前端编辑器内核与 UI 面板解耦，新增面板不改内核。
- API 版本化（`/api/v1`），OpenAPI 文档随代码维护。
- 存储层抽象接口，本地磁盘 → S3/MinIO 可切换。
- 导入导出采用**适配器模式**，新增格式不改内核。
- **数据库层双方言**：业务代码只依赖 repository 接口，不感知具体数据库；SQL 收敛在两种方言都支持的公共子集内，差异点集中在 7 处白名单分支；两套迁移集由 CI 强制版本号一致。因此从 SQLite 换到 PostgreSQL 是**改配置**而不是改代码。

### 5.6 部署环境要求

| 项 | SQLite 形态（默认） | PostgreSQL 形态 |
| --- | --- | --- |
| 前置依赖 | Docker + Docker Compose | 同左 |
| 容器数 | 2（`web` + `api`） | 3（`web` + `api` + `db`） |
| 数据库服务 | 无 | `postgres:16-alpine`（随 compose 提供） |
| 出站网络 | **不需要**（可完全离线运行） | **不需要** |
| 磁盘 | 本地块设备，用于 `data` 卷 | 任意（`pgdata` 卷） |
| 水平扩展 | 不支持多副本 | 支持 |
| 数据落盘位置 | 单文件 `wmind.db` + 上传目录，同卷 | `pgdata` + 上传目录，分卷 |

两种形态都不依赖任何外部服务，可部署在完全隔离的内网环境中。

### 6.3 为客户端 App 预留的扩展点（本期只需设计，不实现）

1. **认证**：全部使用 Bearer Token，不依赖 Cookie，便于移动端复用。
2. **API 版本**：`/api/v1` 前缀，破坏性变更走 `/api/v2`。
3. **同步接口**：导图列表接口支持 `updated_since` 参数与 `deleted` 标记，客户端可做增量拉取。
4. **设备表**：`user_devices` 表结构本期建好（可空表），记录设备标识、平台、推送 token。
5. **文档模型可序列化**：`.wmind` JSON 格式与语言无关，客户端可直接复用同一套解析/渲染逻辑（未来用 Kotlin/Swift 重写渲染层）。
6. **离线优先**：文档变更以「操作（operation）」形式也可表达，为将来 OT/CRDT 留口子（一期不做，但模型不阻碍）。
7. **公开只读接口**：分享页的数据接口是纯 token 鉴权的只读接口，客户端可直接复用同一接口实现「查看他人分享的导图」。
8. **认证状态机留口**：用户表保留 `status` 字段与状态枚举的扩展位，二期引入邮箱验证时可直接启用 `pending` 状态，不需要迁移既有数据结构。

## 7. 验收标准（摘要）

| 场景 | 验收条件 |
| --- | --- |
| 全新部署 | 在干净机器上执行 `docker compose up -d` 后，浏览器可访问并完成首次管理员初始化 |
| 注册开关 | 后台关闭注册后，注册页不可达、直接调注册接口返回 403 |
| 用户隔离 | 用户 A 通过构造请求访问用户 B 的导图 ID，返回 404 而非 403（不泄露存在性） |
| 编辑体验 | 用纯键盘完成：新建根节点下 3 个子节点 → 改名 → 加粗变色 → 折叠 → 撤销全部 → 重做全部 |
| 模板 | 8 个内置模板均可创建出符合其结构定义的导图 |
| 主题 | 10 套配色方案切换后，分支颜色与线条颜色随之改变，内容不丢失 |
| 导入 | XMind 2020+ 文件、XMind 8 文件、Markdown 大纲、OPML 各导入一次，节点数与层级正确 |
| 导出 | 同一导图导出 PNG/JPEG/SVG/PDF/Markdown/OPML 六种格式，均可正常打开且内容一致 |
| 自动保存 | 编辑后刷新页面，内容完整；断网编辑后恢复网络，内容自动补存 |
| 权限 | 普通用户访问 `/admin/*` 返回 403；管理员不能删除自己（最后一个管理员） |
| **分享链接** | 生成链接 → 用无痕窗口打开可见只读导图 → 撤销后再打开返回 404；设密码的链接未输密码不可见内容 |
| **分享边界** | 关闭站点分享开关后，所有历史分享链接立即失效；删除导图后其分享链接失效 |
| **账号找回** | 用户忘记密码联系管理员，管理员后台重置后一次性获得新密码，用新密码可登录，且该用户在其他设备的会话全部失效 |
| **暗色模式** | 切换浅色/深色/跟随系统三档，刷新后保持；跟随系统时改变系统外观界面实时响应；导出图片的背景色不受界面暗色影响 |
| **双数据库（默认 SQLite）** | 干净机器执行 `docker compose up -d` 后系统可用；`data` 卷内生成 `wmind.db`；`docker compose restart` 后数据完整保留；**全程无需任何数据库服务** |
| **双数据库（可选 PostgreSQL）** | 执行 `docker compose -f docker-compose.postgres.yml up -d` 后系统可用；功能与 SQLite 形态完全一致，无「仅在某方言下可用」的功能 |
| **方言一致性** | 同一份导图在两种数据库上创建、编辑、导出，结果一致；两套迁移集版本号序列一致（CI 的 `verify-migration-parity` 通过）；业务层代码中不存在数据库方言分支 |
| **SQLite 单实例约束** | 部署文档明确标注不支持 `api` 多副本与网络文件系统；就绪探针在 SQLite 下能识别「可读但不可写」的状态并返回 503 |
| **字体与导出保真** | 默认字体为思源黑体；导出的 SVG/PDF 在**未安装该字体的设备**上打开，中文仍正常显示（已内嵌或转路径）；含 GB2312 表外汉字（如「龘」）的导图不出现方框 |
| **字体族归一** | 导入分别使用 `NeverMind`、微软雅黑、楷体、Consolas 的 XMind 文件后，字体族被正确归一为 `sans` / `sans` / `serif` / `mono`，文档中不残留原始字体名 |
| **字体切换无跳动** | 首次打开导图时先显示骨架屏、字体就绪后才首次布局，全程节点尺寸不变；切换字体族后全量重排，节点宽度与新字体实测一致 |

## 9. 已确认的关键决策

2026-10-16 需求方答复全部开放问题，结果如下；同日需求方对第 3 项（SMTP）作了二次修订，**回归原推荐**，并新增第 11 项（双数据库）要求。详细理由与被否方案见 [09-技术决策记录.md](./09-技术决策记录.md)。

| # | 问题 | 结论 | 与原推荐是否一致 |
| --- | --- | --- | --- |
| 1 | 分享链接与公开预览 | **一期实现**（公开只读链接，支持密码与有效期） | ✗ 变更（原推荐不做） |
| 2 | 删除用户时其导图 | 默认一并删除，确认框提供「保留（转为无主）」选项 | ✓ |
| 3 | 邮件服务（SMTP） | **一期不接入**；忘记密码由管理员后台重置；二期按 ADR-012 归档设计实现 | ✓（二次修订回归原推荐） |
| 4 | S3 / MinIO 对象存储 | 一期只用本地磁盘，接口已抽象 | ✓ |
| 5 | 默认语言 | 界面默认简体中文，i18next 框架，内置中英文语言包 | ✓ |
| 6 | 配额 | 单用户导图不限，单文件上传 10MB，均可在后台改 | ✓ |
| 7 | 「一键生成」「图库」入口 | **不展示**（不做占位入口） | ✗ 变更（原推荐保留占位） |
| 8 | 暗色模式 | 一期支持浅色 / 深色 / 跟随系统 | ✓ |
| 9 | 技术栈细节 | pnpm · slog · Viper · React Router v7 · GitHub Actions | ✓ |
| 10 | SSR | 纯 SPA，不做服务端渲染 | ✓ |
| 11 | 数据库 | **SQLite + PostgreSQL 双方言**；本地开发用 SQLite；线上提供两套 compose（默认 SQLite） | — 新增需求（需求方提出） |

> **第 11 项说明**：需求方要求同时支持 SQLite 与 PostgreSQL，本地开发用 SQLite，线上提供两套 compose。这不是「一期只做 SQLite、以后补 PostgreSQL」，而是两条并行的交付路径——两套迁移集、双 sqlc 目标、双方言契约测试都在一期完成。代价是增加约 4 人日工作量（详见 [08-开发路线图](./08-开发路线图.md)）与一套 CI 校验（迁移集版本号一致性）。选 SQLite 作默认形态的收益是：**本地开发与集成测试彻底摆脱 Docker 依赖**，私有化交付的最低门槛降到「两个容器 + 一个卷」。技术细节见 [09-技术决策记录](./09-技术决策记录.md) ADR-015。

> **第 3 项修订说明**：需求方最初选择「一期接入 SMTP」，随后改回原推荐方案（一期不接）。修订理由：一期引入 SMTP 会带来外部依赖与运维负担（发信域信誉、端口封禁、退信处理），而「忘记密码」这一核心诉求可用成本极低的「管理员重置」闭环覆盖。归档设计保留在 ADR-012，二期需要时直接落地，不产生返工。
>
> **第 1 项的连带影响**：原截图中「与我分享」入口也一并调整——本期的分享是公开只读链接而非指定用户共享，不存在「别人分享给我的导图」，该入口改为**「我的分享」**，用于管理自己创建的分享链接。

**仍有待验证的技术前提**（非需求问题，属实现前置条件）：

1. XMind 的 `structureClass` 字符串与 `styles.xml` 结构未经真实样本验证——实现前需准备 5+ 真实 `.xmind` 文件。
2. 10 套配色方案的精确色值未经采样——实现 M3 前需从 XMind 导出 SVG 校准。
3. 导出 PDF 走前端 jsPDF 还是服务端 Headless Chrome——若中文质量不达标，M6 切换。
4. **SQLite 与 PostgreSQL 的 SQL 公共子集边界需在 M0 用真实查询验证**——重点是时间处理（禁止 DB 侧计算时间）、并发写入语义（`BEGIN IMMEDIATE` 替代 `SELECT ... FOR UPDATE`）、以及 JSON 字段的读写差异。ADR-015 列出的 7 处方言分支需逐一有对应测试。
5. Noto Sans SC 分片后的实际产物体积与单页传输量需在 M2 实测——预估产物 20~30 MB、单页 100~400 KB，若偏差过大会影响首屏体验，届时应评估减少字重或改用按需子集。
