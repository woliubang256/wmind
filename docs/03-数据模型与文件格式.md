## 1. 存储格式决策

### 1.1 候选方案

| 方案 | 说明 | 优势 | 劣势 |
| --- | --- | --- | --- |
| A. 直接以 **XMind 格式**（`.xmind` zip + `content.json`）为内部存储 | 原样保存用户的 XMind 文件 | 与 XMind 100% 互通，导入导出零转换 | ① 格式由厂商私有演进，随时可能变；② 无法表达 wmind 自己的扩展（权限、版本、协作元数据）；③ XMind 的样式属性体系庞大且未公开文档化，跟随成本极高；④ 数据库里存 zip 二进制，无法做 JSONB 查询与局部更新 |
| B. 以 **OPML** 为内部存储 | XML 大纲 | 格式极简、通用性好 | 只表达「层级 + 文本」，**无法表达样式、主题、形状、联系、外框、概要、标记**——而本项目一半的价值在样式 |
| C. 以 **Markdown** 为内部存储 | 标题/列表大纲 | 人类可读、Git 友好 | 同 B，且更弱（连节点 ID 都没有，无法稳定标识节点） |
| D. **自有 JSON 格式（`.wmind`）**，结构对齐 XMind `content.json`，第三方格式只作进出口适配器 ✅ | 自有 schema + 适配层 | ① 完全掌控演进；② 可扩展；③ JSONB 可查询、可局部更新；④ 字段命名与结构尽量贴近 XMind，使导入导出转换成本最低；⑤ 语言无关，客户端 App 可直接复用 | 需要自己维护一份 schema 与转换器 |

### 1.2 结论

**采用方案 D。** 具体约定：

1. 内部唯一真相源是 `.wmind` JSON 文档，存入 `maps.document`（PostgreSQL 用 `JSONB`，SQLite 用 `TEXT` + `json_valid()` 约束；Go 侧统一收发 `[]byte`）。
2. `.xmind` / `.opml` / `.md` 只在**导入**时解析为 `.wmind`，在**导出**时从 `.wmind` 生成，内核不感知第三方格式。
3. `.wmind` 的结构（`sheets[].rootTopic.children.attached`、`notes`、`labels`、`markers`、`relationships`、`boundaries`、`summaries`、`extensions`）刻意与 XMind `content.json` 对齐；样式键名与 XMind 的 SVG 风格属性名做一对一映射表，使转换是「改名」而非「翻译」。
4. 预留 `extensions` 数组与 `formatVersion`，用于承载未来能力而不破坏旧文件解析。

## 2. `.wmind` 文档格式规范

### 2.1 顶层结构

```jsonc
{
  "format": "wmind",              // 固定值，用于文件识别
  "formatVersion": "1.0",         // 语义化版本，破坏性变更时升 major
  "id": "01JFA8Z3K5N7Q2R9T4V6W8X0Y1",
  "title": "未命名导图",
  "theme": { /* Theme，见 2.5 */ },
  "sheets": [ /* Sheet[]，至少 1 个 */ ],
  "meta": {
    "createdAt": "2026-10-16T02:00:00Z",
    "updatedAt": "2026-10-16T02:30:00Z",
    "app": "wmind/1.0.0"
  },
  "extensions": []                // 保留扩展位
}
```

### 2.2 Sheet（画布）

```jsonc
{
  "id": "sh-01",
  "title": "Map 1",
  "structure": "mindmap",         // 默认结构，Topic 可覆盖
  "rootTopic": { /* Topic */ },
  "floatingTopics": [ /* Topic[]，自由主题 */ ],
  "relationships": [ /* Relationship[] */ ],
  "boundaries": [ /* Boundary[] */ ],
  "summaries": [ /* Summary[] */ ],
  "themeOverride": null,          // 该画布独立主题，null 表示继承文档级 theme
  "extensions": []
}
```

### 2.3 Topic（主题 / 节点）

```jsonc
{
  "id": "tp-01",                  // 文档内唯一，导入时生成，导出 XMind 时原样写出
  "title": "中心主题",
  "titleFormat": "plain",         // plain | rich（rich 时 title 为受限 HTML）
  "structure": null,              // 该节点子树使用的结构，null 表示继承
  "style": { /* Style，见 2.4 */ },
  "collapsed": false,
  "href": "",                     // 超链接
  "notes": {
    "plain": "",
    "html": ""
  },
  "labels": ["标签 A", "标签 B"],
  "markers": [
    { "groupId": "priority", "markerId": "priority-1" },
    { "groupId": "task", "markerId": "task-done" }
  ],
  "image": null,                  // { "src": "/api/v1/files/xxx", "width": 120, "height": 80 }
  "children": {
    "attached": [ /* Topic[]，挂在树上的子主题 */ ],
    "detached": [ /* Topic[]，该节点的浮动子主题 */ ]
  },
  "summaries": [ /* Summary[]，作用于此节点子集 */ ],
  "boundaries": [ /* Boundary[]，作用于此节点子集 */ ],
  "extensions": []
}
```

**约束**：

- `id` 在单文档内必须唯一；导入外部文件时若原 ID 冲突则重新生成。
- 树深度不设硬上限，但 UI 在深度 > 30 时给出性能提示。
- `children.attached` 的顺序即渲染顺序，是文档的一部分（排序变更需进撤销栈）。
- 叶子节点 `children.attached` 为空数组，而非省略字段——保持结构同构，简化遍历代码。

#### Topic 可选附加内容（Insert）

`content` 为可选对象，缺省无附加内容。`todo?: boolean` 表示待办完成状态；`task?: { progress, priority, assignee, start, due }` 分别表示 0–100 进度、0–5 优先级、负责人和 ISO 日期。`sticker`、`illustration` 存内置素材 id；`equation` 存 `{ latex, src, width, height }`，src 为自包含 SVG data URL。

`localLink` 与 `attachments[]` 使用 `{ id, name, kind: 'file'|'folder', bytes, data }`，data 为原字节 base64；folder 数据为保留目录结构的 ZIP。单批 2 MiB、100 个文件，文档上限 8 MiB。网页与主题链接复用 href，主题链接为 `xmind:#<topicId>`；新建链接会移除原本另一种链接。原生文件直接保留 content，XMind 自有往返通过 `wmindContent` 扩展保留。概要可作为联系端点，end1Id/end2Id 可以引用 Summary.id。

### 2.4 Style（样式）

样式采用**扁平键值对**，键名与 XMind 的 SVG 风格属性一一对应（映射表见 §5.3）。`null` 或缺失表示「继承主题」。

```jsonc
{
  "shape": "rounded-rect",        // 见 2.4.1
  "fill": "#FFFFFF",              // 填充色，null 表示无填充
  "fillPattern": "solid",         // solid | none | gradient
  "borderColor": "#000000",
  "borderWidth": 2,
  "borderStyle": "solid",         // solid | dash | dot | none
  "fontFamily": "sans",           // 字体族标识符，见 2.4.2（null 表示继承主题）
  "fontSize": 30,
  "fontWeight": 700,              // 100..900
  "fontStyle": "normal",          // normal | italic
  "textDecoration": "none",       // none | underline | line-through
  "textColor": "#000000",
  "textAlign": "center",          // left | center | right
  "width": 178,                   // 固定宽度，px
  "autoWidth": true,              // true 时忽略 width，按内容自适应
  "lineStyle": "curve",           // 分支线：straight | curve | elbow | none
  "lineEnd": "none",              // 端点：none | arrow | dot
  "lineStart": "none",            // 可选，联系起点：none | arrow | dot；缺省继承主题
  "lineWidth": 2,
  "lineColor": "#000000",
  "rainbowBranch": false,         // 该分支启用彩虹色
  "backgroundColor": null
}
```

#### 2.4.1 形状枚举

| 值 | 对应 XMind shape-class | 说明 |
| --- | --- | --- |
| `rect` | `org.xmind.ui.rect` | 矩形 |
| `rounded-rect` | `org.xmind.ui.roundedRect` | 圆角矩形（默认） |
| `capsule` | `org.xmind.ui.capsule` | 胶囊形 |
| `ellipse` | `org.xmind.ui.ellipse` | 椭圆 |
| `circle` | `org.xmind.ui.circle` | 圆形 |
| `diamond` | `org.xmind.ui.diamond` | 菱形 |
| `hexagon` | `org.xmind.ui.hexagon` | 六边形 |
| `parallelogram` | `org.xmind.ui.parallelogram` | 平行四边形 |
| `underline` | `org.xmind.ui.underline` | 仅下划线 |
| `none` | `org.xmind.ui.none` | 无形状 |

#### 2.4.2 字体族枚举

`fontFamily` **存标识符而非字体名**——标识符是封闭集合，可直接当白名单校验；字体名是任意字符串，会被拼进 CSS/SVG，构成注入面，且会把文档与具体字体绑定（将来换字体就要迁移存量文档）。用户真实意图是「黑体 / 宋体」这类**样式类别**，标识符建模更准。理由与被否方案见 [09-技术决策记录](./09-技术决策记录.md) ADR-016。

| 标识符 | 显示名 | 实际字体 | 许可 | 优先级 |
| --- | --- | --- | --- | --- |
| `sans` | 思源黑体（**默认**） | Noto Sans SC | SIL OFL 1.1 | P0 |
| `system` | 跟随系统 | 系统字体栈（零字节） | — | P0 |
| `serif` | 思源宋体 | Noto Serif SC | SIL OFL 1.1 | P1 |
| `mono` | 等宽 | JetBrains Mono + 系统等宽 | SIL OFL 1.1 | P1 |

- `null` 表示**继承主题**（与其他样式字段一致）。
- 未知取值视为非法：解析时回退到 `sans` 并记入校验 warnings，**不抛错**（保持向前兼容，便于将来新增字体族）。
- 前端把标识符映射到实际 CSS 字体栈，映射表集中在字体注册表里（见 [05-前端设计](./05-前端设计.md) §5.3）。**任何地方都不得把标识符直接当作 CSS `font-family` 使用。**
- 实际字重由 `fontWeight` 决定（100..900）；P0 只随应用分发 300 / 400 / 700 / 800 四个静态实例，其余字重由浏览器就近匹配。

### 2.5 Theme（主题 / 配色方案）

```jsonc
{
  "id": "classic-rainbow",
  "name": "彩虹",
  "category": "classic",          // vivid（缤纷） | classic（经典） | custom
  "palette": {
    "colors": ["#E32925", "#FB8C00", "#FDD835", "#43A047", "#1878CD", "#8E24AA"],
    "lineColors": ["#E32925", "#FB8C00", "#FDD835", "#43A047", "#1878CD", "#8E24AA"],
    "backgroundColor": "#FFFFFF"
  },
  "global": {
    "fontFamily": "sans",         // 标识符，见 2.4.2
    "fontSize": 14,
    "lineWidth": 2,
    "backgroundColor": "#FFFFFF"
  },
  "centralTopic": { /* Style 覆盖，仅含差异字段 */ },
  "mainTopic": { /* Style 覆盖 */ },
  "subTopic": { /* Style 覆盖 */ },
  "floatingTopic": { /* Style 覆盖 */ },
  "summaryTopic": { /* Style 覆盖 */ },
  "boundary": { "borderColor": "#999999", "borderStyle": "dashed", "fill": "#F5F5F5" },
  "relationship": { "lineColor": "#999999", "lineWidth": 1, "lineEnd": "arrow" },
  "rainbowBranch": true,
  "rainbowColors": ["#E32925", "#FB8C00", "#FDD835", "#43A047", "#1878CD", "#8E24AA"],
  "layout": {
    "autoBalance": true,
    "compact": false,
    "alignSiblings": false,
    "freeBranch": false,
    "flexibleFloating": false,
    "topicOverlap": false
  }
}
```

**样式解析顺序**（后写覆盖前写）：

```
内置默认样式
  → 文档级 theme.global
  → 文档级 theme.{centralTopic|mainTopic|subTopic}
  → 画布级 sheet.themeOverride（若存在，整链替换）
  → 节点级 topic.style（显式非 null 字段）
  → 调色板分配（同级分支按 index 取 palette.colors[i % n]）
```

> **关键规则**：调色板颜色**不写入** `topic.style`。只有当用户手动指定颜色时，才把颜色固化到节点样式里。这样切换配色方案才能整体生效——这是「一份导图随时换主题不丢内容」的实现基础。

> **`rainbowBranch` 的语义**：开 = 各一级分支按 `branchIndex` 在 `rainbowColors` 里循环取色（每条分支不同色）；关 = 所有分支统一取 `palette.colors[0]`。两者不能是同一个结果，否则面板上这个开关点下去毫无反馈，而 `palette.colors` 也会被 `rainbowColors` 架空。

### 2.6 附属结构

```jsonc
// Relationship：两个主题间的自由连线
{
  "id": "rel-01",
  "end1Id": "tp-03",
  "end2Id": "tp-07",
  "title": "依赖",
  "routing": { "start": { "x": 100, "y": -80 }, "end": { "x": -100, "y": 60 } }, // 可选：相对各自端点主题中心的控制柄偏移，缺省自动走向
  "style": { "lineColor": "#999999", "lineStart": "none", "lineEnd": "arrow", "lineStyle": "curve", "borderStyle": "dash" }
}

// Boundary：圈住一组主题
{
  "id": "bnd-01",
  "title": "第一阶段",
  "range": ["tp-03", "tp-04"],       // 目标主题 ID 列表
  "style": { "borderColor": "#8E24AA", "borderStyle": "dashed", "fill": "#F3E5F5" }
}

// Summary：对一组同级主题的汇总
{
  "id": "sum-01",
  "topicId": "tp-03",                // 汇总节点挂载的父主题
  "range": ["tp-04", "tp-05"],       // 被汇总的兄弟主题
  "title": "小结",
  "style": { /* Style 覆盖 */ }
}
```

## 3. 数据库设计

数据库支持**两种方言**，由环境变量 `WMIND_DB_DRIVER` 选择：

| 驱动 | 值 | 典型用途 | 迁移集 |
| --- | --- | --- | --- |
| SQLite | `sqlite` | 本地开发（默认）；10~100 人规模的轻量生产 | `backend/db/migrations/sqlite/` |
| PostgreSQL | `postgres` | 需要水平扩展、大团队、或需要 `pg_trgm` 检索的生产环境 | `backend/db/migrations/postgres/` |

两套迁移集**逻辑模型完全一致**，只有类型与少量语法不同。**表结构以 PostgreSQL DDL 为规范**（见 §3.3），SQLite DDL 按 §3.2 的映射规则派生。

### 3.1 ER 概览

```
users ──┬── maps ──┬── map_revisions
        │          ├── share_links
        │          └── files (缩略图)
        ├── templates

        ├── user_tokens       （二期预留：密码重置 / 邮箱验证，本期建表不启用）

        └── audit_logs
settings （全局键值）
```

### 3.2 双方言策略（类型映射与差异）

#### 3.2.1 类型映射表

写 SQLite DDL 时按此表逐列替换，不允许自由发挥：

| 逻辑类型 | PostgreSQL | SQLite | 备注 |
| --- | --- | --- | --- |
| 自增主键 | `BIGSERIAL PRIMARY KEY` | `INTEGER PRIMARY KEY AUTOINCREMENT` | SQLite 的 `INTEGER PRIMARY KEY` 即 rowid 别名 |
| 外键列 | `BIGINT` | `INTEGER` | 类型不参与 SQLite 的强制校验，但保持一致便于 introspect 比对 |
| 字符串 | `TEXT` | `TEXT` | 一致 |
| 整数 | `INTEGER` / `BIGINT` | `INTEGER` | SQLite 整数最大 8 字节，`BIGINT` 语义无损 |
| 布尔 | `BOOLEAN` | `INTEGER`（`CHECK (x IN (0,1))`） | 驱动层负责 `bool ↔ 0/1` 转换 |
| 时间 | `TIMESTAMPTZ` | `TEXT`（ISO-8601 UTC，`YYYY-MM-DDTHH:MM:SS.SSSZ`） | **必须带 `Z` 后缀**，否则跨时区比较会错 |
| JSON 文档 | `JSONB` | `TEXT` + `CHECK (json_valid(col))` | Go 侧统一 `[]byte`；`json_valid` 需要 SQLite 3.9+ 的 JSON1（默认编译进 `modernc.org/sqlite`） |
| IP 地址 | `INET` | `TEXT` | SQLite 无 `INET`，存标准文本形式 |
| 默认当前时间 | `DEFAULT now()` | `DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))` | 两边都保留默认值作为兜底，但**业务写入一律由 Go 传参**（见 3.2.3） |

#### 3.2.2 方言差异与处理落点

| 差异点 | PostgreSQL | SQLite | 处理方式 |
| --- | --- | --- | --- |
| 模糊搜索 | `ILIKE` + `pg_trgm` GIN 索引 | `LIKE`（ASCII 不区分大小写；中文为精确匹配） | 查询拆方言目录；中文标题搜索两者行为一致 |
| 行锁 | `SELECT ... FOR UPDATE` | **不支持** | SQLite 侧依赖 `BEGIN IMMEDIATE` + 单写连接；`version` 乐观锁双方言都保留 |
| 时间区间运算 | `now() - interval '30 minutes'` | `datetime('now','-30 minutes')` | **禁用**，改为 Go 计算后传参 |
| 按日聚合 | `date_trunc('day', created_at)` | `strftime('%Y-%m-%d', created_at)` | 数据概览的按日趋势查询拆方言目录 |
| JSON 路径查询 | `document #>> '{a,b}'`、GIN 索引 | `json_extract(document, '$.a.b')`，无索引 | 一期不做服务端内容检索，仅按 `title` 搜索，规避该差异 |
| Upsert | `ON CONFLICT ... DO UPDATE` | 同（SQLite 3.24+） | **可共享** |
| `RETURNING` | 支持 | 支持（SQLite 3.35+） | **可共享** |
| 部分索引 | `CREATE INDEX ... WHERE ...` | 支持 | **可共享** |
| 表达式索引 | `lower(email)` | `lower(email)` | **可共享** |
| `DESC` 索引 | 支持 | 支持（3.3+） | **可共享** |

#### 3.2.3 三条硬纪律

为了把「双方言维护成本」压到最低，写 SQL 时遵守：

1. **时间不由数据库计算**。禁止 `now()`、`interval`、`date_trunc` 出现在业务查询里（DDL 的 `DEFAULT` 除外）。所有时间值由 Go 的 `time.Now()` 计算后作为参数传入。这样既消除了方言差异，也让查询可测试（可注入固定时钟）。
2. **SQL 必须在「共享子集」内写**。能用双方言通用语法表达的查询一律放 `db/queries/shared/`，只有真正无法通用的（`ILIKE`、`FOR UPDATE`、`date_trunc`）才放 `db/queries/{postgres,sqlite}/`。目标是共享目录占绝大多数。
3. **迁移集成对修改**。任何 schema 变更必须同时改 `migrations/postgres/` 与 `migrations/sqlite/`，并跑 `verify-migration-parity`（比对两个真实数据库 introspect 出的表/列/索引集合，不一致即失败）。

#### 3.2.4 目录布局

```
backend/db/
├── migrations/
│   ├── postgres/          0001_init.up.sql / 0001_init.down.sql / ...
│   └── sqlite/            0001_init.up.sql / 0001_init.down.sql / ...   ← 与 PG 一一对应
├── queries/
│   ├── shared/            users.sql  maps.sql  shares.sql ...            ← 双方言共用
```

#### user_tokens（二期预留：密码重置 / 邮箱验证令牌）

> **本期状态**：一期不接入 SMTP，`user_tokens` 表**建好但没有任何写入路径**（同 `user_devices` 的处理方式）。建表目的是让二期的邮件能力落地时不需要改表结构，也便于提前固化语义。表名与 `purpose` 取值一经确定即视为契约，二期不得改名。

```sql
CREATE TABLE user_tokens (
  id         BIGSERIAL PRIMARY KEY,
  user_id    BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  purpose    TEXT        NOT NULL,                    -- password_reset | email_verify
  token_hash TEXT        NOT NULL UNIQUE,             -- SHA-256，不存明文
  expires_at TIMESTAMPTZ NOT NULL,
  used_at    TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_user_tokens_user ON user_tokens (user_id, purpose) WHERE used_at IS NULL;
```

**一次性语义**（二期实现）：令牌使用后立即写入 `used_at`；签发新令牌时，在 service 层先执行

```sql
UPDATE user_tokens SET used_at = now()
WHERE user_id = $1 AND purpose = $2 AND used_at IS NULL;
```

把该用户同用途的旧令牌全部作废，保证同一时刻只有一个有效令牌。

**有效期**（二期实现）：`password_reset` 30 分钟，`email_verify` 24 小时。

> **与 `refresh_tokens` 的区别**：`refresh_tokens` 是长期会话凭证（7 天，可多设备并存，用于换取 Access Token），一期即启用；`user_tokens` 是一次性动作令牌（短时效，同一时刻只允许一个有效），二期随邮件能力启用。两者生命周期与语义完全不同，不合并。
>
> **一期的账号找回为什么不需要这张表**：管理员重置密码是「管理员主动 + 已认证」的操作，直接写 `users.password_hash` 并撤销该用户会话即可，不需要向用户发放任何令牌，因此一期该表保持空表。

### 3.4 SQLite 运行时配置与约束

SQLite 的正确性依赖一组**连接级 PRAGMA**与**连接池策略**，缺一不可。这些在 `internal/repository/sqlite` 的连接初始化里统一设置，不允许调用方覆盖。

#### 3.4.1 必须设置的 PRAGMA

| PRAGMA | 值 | 为什么 |
| --- | --- | --- |
| `journal_mode` | `WAL` | 允许「单写多读」并发；默认的 `delete` 模式下读会被写阻塞 |
| `busy_timeout` | `5000` | 遇到锁时等待 5 秒而不是立刻报 `SQLITE_BUSY` |
| `foreign_keys` | `ON` | **SQLite 默认关闭外键约束**，不显式打开则所有 `REFERENCES` 形同虚设 |
| `synchronous` | `NORMAL` | WAL 下 `NORMAL` 已能保证崩溃一致性，`FULL` 会显著拖慢写入 |
| `temp_store` | `MEMORY` | 排序/临时表走内存 |

#### 3.4.2 连接池

**`SetMaxOpenConns(1)`**。SQLite 同一时刻只允许一个写者，单连接池从根本上消除 `SQLITE_BUSY` 与「database is locked」。

- 代价：读也串行化。在 10~100 人、单实例的规模下不可感知。
- 升级路径（二期可选）：**双池**——一个 `MaxOpenConns(1)` 的写连接池 + 一个 `MaxOpenConns(N)` 的只读连接池，读写分离。需要多一套连接管理与「哪些查询走只读池」的判定，本期不做。

#### 3.4.3 不可协商的运行时约束

- **SQLite 模式只能单实例运行**：`api` 不能 `--scale api=3`。需要多副本必须换 PostgreSQL。
- **数据库文件必须放在本地块设备卷上**：NFS / SMB / 网络卷的文件锁语义不可靠，会导致数据损坏。
- **不能用「复制文件」的方式备份**：WAL 模式下直接拷贝可能拿到不一致快照。必须用 `VACUUM INTO '/backup/wmind-<date>.db'`（在线、一致、可并发），详见 [07-部署与运维](./07-部署与运维.md) §7。
- **迁移不能用 `ALTER COLUMN`**：SQLite 不支持修改列类型/约束。改列需走「建新表 → `INSERT INTO ... SELECT` → `DROP` 旧表 → `RENAME`」的表重建流程。一期是全新安装，只影响二期演进；迁移文件里需附注释说明。
- **`ALTER TABLE ADD COLUMN` 有限制**：新列不能是 `PRIMARY KEY`/`UNIQUE`，若声明 `NOT NULL` 必须带非空默认值。
- **时间列必须存带 `Z` 的 ISO-8601**：`strftime('%Y-%m-%dT%H:%M:%fZ','now')` 生成的是 UTC 且带 `Z`，字符串比较即等价于时间比较。若省略 `Z` 或存本地时间，跨时区比较会静默出错。
- **`LIKE` 对非 ASCII 不区分大小写不成立**：SQLite 的内建 `LIKE` 只对 ASCII 做大小写折叠。中文标题搜索不受影响（本来就是精确匹配），但英文标题搜索是大小写敏感的——这是一期接受的差异，已在 [09](./09-技术决策记录.md) ADR-015 记录。

#### 3.4.4 集成测试的收益

因为 SQLite 是纯 Go 驱动 + 单文件，集成测试可以直接用 `t.TempDir()` 建临时库、跑真实迁移、测完删除，**不需要 Docker**。这使本地 `go test ./...` 无需任何前置条件。`testcontainers-go` 只在 CI 的 PostgreSQL 专项测试中使用。

### 3.5 设计说明

- **为什么用 `uid` 而非自增 ID 对外**：自增 ID 会暴露系统规模与创建顺序，且不利于将来分库。对外接口一律使用 `uid`。
- **为什么 `document` 整存 JSON 而不拆表**：导图是一棵整体树，拆成 `topics` 表会导致「打开导图 = 一次递归查询」和「保存 = 全量 diff 写回」，复杂度与性能都更差。PostgreSQL 侧用 `JSONB`，SQLite 侧用 `TEXT` + `json_valid()` 校验，Go 侧统一收发 `[]byte`，**领域层感知不到差异**。
- **为什么列表页需要 `node_count` / `size_bytes` 冗余**：列表与统计页需要展示节点数，实时从 JSON 统计代价高（SQLite 上尤其），保存时顺带写入。
- **软删除**：`maps.deleted_at` 非空即视为回收站内容；所有查询默认带 `deleted_at IS NULL`。
- **为什么双方言不牺牲逻辑模型**：两套迁移集的表名、列名、约束、索引名**完全一致**（见 §3.2.3 第 3 条），差异只在类型与极少数语法。这样 `verify-migration-parity` 才能用 introspect 结果做机械比对，而不是靠人眼 review。

### 4.3 敏感配置的加密存储（二期启用，方案先行归档）

一期没有任何需要加密落库的配置项（分享访问密码走 bcrypt，不是可逆加密），因此**不引入加密密钥环境变量**。二期接入 SMTP 后，`mail.password` 属基础设施凭据，不能明文落库，届时按下述方案实现：

```
存储值格式：  enc:v1:<base64(nonce)>:<base64(ciphertext)>
算法：        AES-256-GCM
密钥来源：    环境变量 WMIND_ENCRYPTION_KEY（32 字节，base64 编码）
```

- 应用启动时若 `WMIND_ENCRYPTION_KEY` 缺失：允许启动，但**禁止**写入任何加密字段，后台保存 SMTP 密码时返回 `SETTINGS_INVALID` 并提示「未配置加密密钥」。
- 密钥变更后旧密文无法解密：解密失败时把该字段视为空并记录 `ERROR` 日志，后台显示「SMTP 密码已失效，请重新填写」，不阻断其他功能。
- 未以 `enc:v1:` 开头的值一律视为非法并拒绝加载，避免历史明文残留被静默接受。
- **密钥必须纳入备份**：丢失 `WMIND_ENCRYPTION_KEY` 等同于丢失所有加密配置（详见 [07-部署与运维](./07-部署与运维.md) 备份章节）。

### 4.4 读取策略与缓存

- 设置项在后端内存中持有**不可变快照**（`atomic.Value`），读操作无锁。
- `PUT /admin/settings` 成功后整体重载快照；多实例部署时靠 TTL 60 秒兜底（二期可加 Redis Pub/Sub 做主动失效）。

**读取策略**：公开配置（`site.*`、`auth.registration_enabled`、`feature.*`）通过 `/api/v1/site/config` 暴露给未登录用户；敏感配置（`auth.login_max_attempts`、`limit.*`）仅管理员可读。

**缓存**：设置项在后端内存缓存，`settings` 表更新时失效，TTL 60s 兜底。

#### 5.3.1 字体名归一映射

导入时把 XMind 的 `fo:font-family` 归一为 2.4.2 的标识符。**做映射而不是直传**的理由：XMind 文件里的字体名是「源机器上装了什么」，在服务端和别人的浏览器上大概率不存在；直传等于把一份必然失效的引用写进文档。

匹配规则：先精确匹配，再按下方关键字做**不区分大小写**的子串匹配，最后回退。

| 匹配（精确或子串） | 归一为 | 说明 |
| --- | --- | --- |
| `NeverMind` | `sans` | XMind 默认字体，映射到本项目的默认无衬线 |
| `Source Han Sans` / `Noto Sans` / `思源黑体` | `sans` | 与本项目默认字体同源，零损失 |
| `PingFang` / `苹方` / `Hiragino` / `Microsoft YaHei` / `微软雅黑` / `DengXian` / `等线` / `SimHei` / `黑体` / `Helvetica` / `Arial` / `Roboto` / `Segoe UI` / `system-ui` | `sans` | 无衬线类，观感接近 |
| `Source Han Serif` / `Noto Serif` / `思源宋体` / `SimSun` / `宋体` / `Songti` / `Times New Roman` / `Georgia` / `serif` | `serif` | 衬线类 |
| `KaiTi` / `楷体` / `STKaiti` / `LXGW` / `霞鹜文楷` | `serif` | **本期降级为宋体**并计入 warnings（二期新增 `kai` 标识符后改映射到 `kai`） |
| `Consolas` / `Courier` / `Monaco` / `Menlo` / `JetBrains Mono` / `monospace` | `mono` | 等宽类 |
| 其他任意值 | `sans` | 回退默认，并把原字体名写入导入摘要的 warnings |

> **不做「保留原字体名 + 渲染时回退」**：那样文档里会残留一个永远无法满足的引用，同一份文档在不同机器上渲染结果不同，还会让「主题可移植」失效。归一为标识符后，导入结果在任何机器上都一致。

| --- | --- |
| `text` | `title`（缺失时回退 `title` 属性，再缺失用 `(未命名)`） |

### 5.6 Markdown 映射

**导入**（两种识别模式，自动判定）：

1. **标题模式**：`#` 为第 1 层，`##` 为第 2 层，依此类推。第一个 `#` 之前的正文作为中心主题的备注。
2. **列表模式**：以无序列表缩进（2 或 4 空格为一档）推断层级；文档中第一个非列表行作为中心主题，**文件直接以列表开头时中心主题取文件名**。

| Markdown 元素 | wmind 映射 |
| --- | --- |
| 标题 / 列表项 | `title` |
| 行内代码 `` `标签` `` | `labels` |
| 引用块 `> ...` | `notes.plain` |
| 链接 `[文本](url)` | `title` + `href`（一个主题只有一个 `href`，取第一个链接） |
| 图片 `![alt](url)` | `image`；独占一行时提升为子主题（标题取 `alt`），行内出现时按普通段落处理，相对路径无法还原时计入 `image-skipped` |
| 代码块 | 该标题下的子主题，正文整体放入 `notes.plain` |
| 表格 | 降级为「表格标题 + 各行作为子主题」，计入 `table-degraded` |
| 任务列表 `- [x]` | `markers`：`task-done` / `task-start` |
| 加粗 / 斜体 | 忽略（不进入样式，避免过度映射） |

> **层级跳跃不补空节点**：`#` 后面直接跟 `###` 时，新节点挂到最近的上级（`#`）。补一个空白的 `##` 会让人以为文档缺内容。

> **`_` 不当强调标记**：`foo_bar_baz` 变成 `foobarbaz` 比「保留了下划线」糟糕得多，所以只处理 `*` 与 `~~`。

**导出**：

```markdown
# 中心主题

> 中心主题的备注（若有）

## 分支主题 1

- 子主题 A
- 子主题 B `标签`

## 分支主题 2
```

- 中心主题 → `#`，一级分支 → `##`，二级 → `###`……超过 6 层时统一用 `######` 并加缩进列表。
- 备注 → 引用块。
- 标签 → 行内代码。
- 超链接 → `[标题](url)`。

## 7. 版本演进约定

| 变更类型 | 处理方式 |
| --- | --- |
| 新增可选字段 | `formatVersion` minor +1，旧文件可读，新文件旧版忽略未知字段 |
| 字段语义变更 / 删除字段 | `formatVersion` major +1，提供迁移函数 `migrate(v1 → v2)` |
| 未知字段 | 解析器**必须保留**未知字段并在回写时原样输出（`extensions` 机制），避免第三方格式往返丢数据 |

解析器实现要求：读取到 `formatVersion` major 大于当前支持版本时，拒绝打开并提示「该文件由更新版本创建，请升级」；major 相同、minor 更大时正常打开。
