## 1. 设计原则

| 原则 | 落地方式 |
| --- | --- |
| **单体优先，模块内聚** | 采用模块化单体（Modular Monolith），不做微服务。团队规模与业务复杂度不支持分布式带来的运维成本 |
| **格式自持** | 文档格式自有（`.wmind` JSON），第三方格式只作为进出口的适配器，避免被任何厂商格式绑架 |
| **内核与外壳解耦** | 前端编辑器内核（文档模型 / 布局 / 渲染 / 命令）不依赖任何 UI 组件库；后端格式转换不依赖 HTTP 层 |
| **可替换的边界** | 存储、数据库方言、限流、导出渲染器都通过接口隔离。数据库已实际用上这层：PostgreSQL 与 SQLite 两套实现共存，单实例 → 多实例时只换实现 |
| **无状态服务** | 后端不保存会话状态（JWT），任意实例可处理任意请求，为水平扩展留路 |
| **默认可私有化** | **零必需外部依赖**：默认 SQLite 形态连数据库服务都不需要，只有 `web` + `api` 两个容器。一期完全不出站（不接入 SMTP、不依赖对象存储、不调用任何第三方服务；邮件为二期可选依赖） |

## 2. 技术选型

### 2.1 后端 Web 框架

| 候选 | 优势 | 劣势 |
| --- | --- | --- |
| **Gin** ✅ | 生态与中间件最全、中文资料最多、性能优秀、团队上手快 | 依赖 `gin.Context`，错误处理需自行统一 |
| Echo | API 设计更统一，内置绑定/校验/静态文件 | 生态规模小于 Gin |
| Chi | 100% 兼容 `net/http`，最 idiomatic，无框架侵入 | 日志、校验、绑定都要自己拼装 |
| Fiber | 基于 fasthttp，吞吐最高 | 不兼容 `net/http` 生态，部分中间件需重写，与 `httptest` 等标准测试工具有摩擦 |

**结论：Gin**。当前版本 v1.12.0，Go 基线 1.26.10（原始选型见 [M0 工具链基线](../.agents/notes/implemented/process/2026-10-16-wmind-m0-toolchain-baseline.md)，安全更新约束见[安全工具链基线](../.agents/notes/implemented/process/2026-10-26-wmind-security-toolchain-baseline.md)）。理由是需求是「主流优秀」——Gin 在生态成熟度、问题可检索性、团队熟悉度上综合最优；其「不够 idiomatic」的缺点通过统一响应封装与错误码层弥补。

### 2.2 数据库与数据访问

**一期同时支持两种数据库方言**，由 `WMIND_DB_DRIVER` 选择。这不是「先做一个、以后再补」，而是两条并行的交付路径（见 [09](./09-技术决策记录.md) ADR-015）。

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 方言 A：**SQLite 3.45+（默认）** | `WMIND_DB_DRIVER` 缺省值；本地开发 + 默认部署形态 | 单文件零运维，`go run` 即可开发；生产形态下没有 `db` 容器、没有数据库密码、备份就是一个文件 |
| 方言 B：**PostgreSQL 16（可选）** | 大团队 / 需水平扩展 / 已有 PG 运维体系时选用 | JSONB 天然适配导图文档存储；`pg_trgm` 支持标题模糊搜索；MVCC 支持多副本写入；容器化成熟 |
| SQLite 驱动 | **`modernc.org/sqlite`** | 纯 Go 无 CGO，保住现有 `CGO_ENABLED=0` 的多阶段 alpine 构建；性能损失在本项目量级下不可感知 |
| PostgreSQL 驱动 | **pgx v5** | 原生协议、性能好、与 sqlc 集成成熟 |
| 数据访问 | **sqlc（双 target）** | 同一份 SQL 源生成两套类型安全代码；SQL 显式可控、无运行时反射、避免 ORM 隐式 N+1 |
| 事务抽象 | **`TxManager.WithTx` + ctx 传递** | 让 service 层的事务代码在两种方言下逐字相同，是双方言方案的关键抽象（见 [04](./04-后端设计与API规范.md) §7.9.2） |
| 迁移 | **golang-migrate（两套迁移集）** | 纯 SQL 迁移文件，两套集逻辑模型一致，用 `verify-migration-parity` 门禁防漂移 |
| 备选 | GORM / Ent / 查询构造器 | ORM 与构造器的方言适配是「最低公共分母」，复杂查询仍要落回方言特有写法，且会丢掉 sqlc 的类型安全。本项目 schema 简单、查询可控，sqlc 收益更高 |

**双方言的代价与边界**（必须让读者一眼看到）：

- 代价是**两套迁移集 + 少量方言查询**，以及一条硬纪律：SQL 必须在共享子集内写（时间不由数据库计算）。
- 边界是**方言不泄漏**：`internal/service` 与 `internal/handler` 禁止 import 任何方言仓储包，全局只有一个 `switch` 感知驱动。
- 已知不可逾越的差异：**SQLite 模式不能多副本**、`LIKE` 对非 ASCII 大小写敏感、无 `pg_trgm` 索引。三者都已在文档中显式记录。

### 2.5 编辑器实现路线（关键决策）

| 方案 | 优势 | 劣势 |
| --- | --- | --- |
| A. 直接用开源导图库（MindElixir / jsMind / KityMinder） | 起步最快，几天可出可用版本 | 主题/形状/布局深度受限，**无法达到「和 XMind 一样的主题、颜色、形状」**；文档模型与需求不符，导入导出需二次映射；KityMinder 已停止维护；后期定制会与库对抗 |
| B. 基于通用图库（React Flow / @xyflow/react） | 缩放、拖拽、连线等交互成熟 | 其模型是「有向图」而非「树」，布局需完全自研；主题/形状定制仍要自研；包体积大；多出的一层抽象反而拖慢 |
| C. **自研 SVG 渲染 + 自研布局引擎** ✅ | 完全掌控主题、形状、线条、布局，可精确复刻 XMind；SVG 导出 = DOM 序列化，零成本；DOM 文本编辑与字体渲染天然支持；无第三方升级风险 | 工作量大（约占一期前端 60% 精力）；需自行处理性能与命中测试 |

**结论：方案 C**。需求中「xmind 一样的编辑体验」「要和 xmind 一样的主题、颜色、形状」是硬约束，方案 A/B 都会在这条约束上反复妥协。自研的代价用**分阶段交付**控制：先做「思维导图 + 逻辑图 + 组织结构图」三种结构 + 一套主题，把内核跑通，再横向扩展结构与配色。

**渲染载体选择 SVG 而非 Canvas**：SVG 可直接序列化为导出文件、DOM 文本可编辑可选中、字体渲染由浏览器负责、便于无障碍与调试；代价是超大规模节点性能弱于 Canvas，通过「> 2000 节点时关闭阴影/渐变并简化线条」降级处理。

### 3.1 为什么是模块化单体

- 业务边界（用户、导图、模板、主题、设置）共享同一数据库事务，拆分会引入分布式事务。
- 单实例部署是本项目的核心卖点，微服务会直接破坏「一条命令部署」的体验。
- 模块间通过 Go 接口通信，未来若某模块（如导出渲染）成为瓶颈，可独立抽出为服务而不改调用方。

## 4. 后端模块划分

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| `config` | 加载配置、校验必填项、提供默认值 | — |
| `httpapi` | 路由注册、中间件链、统一响应与错误码、请求追踪 | `handler` |
| `handler` | 解析请求、调用 service、组装响应；**不含业务规则** | `service`, `dto` |
| `service` | 业务规则、事务边界、权限校验、跨仓储编排 | `repository`, `convert`, `storage` |
| `repository` | SQL 执行与领域对象映射；**不含业务判断**；**两套方言实现** | pgx / `database/sql`, `domain` |
| `repository/postgres` | PostgreSQL 方言实现（pgx v5 + sqlc `pgdb`） | pgx, `domain` |
| `repository/sqlite` | SQLite 方言实现（modernc + sqlc `sqlitedb`） | `database/sql`, `domain` |
| `domain` | 领域模型与仓储接口定义 | — |
| `docmodel` | `.wmind` 文档结构定义、校验、遍历工具 | — |
| `convert` | 导入导出适配器：`xmind` / `opml` / `markdown` / `image` | `docmodel` |
| `auth` | 密码哈希、JWT 签发与校验、令牌撤销 | `repository` |
| `share` | 分享令牌签发与校验、访问计数、只读视图构造 | `repository`, `docmodel` |
| `storage` | 对象存储抽象（本地磁盘 / S3 兼容） | — |

> **二期待建模块**：`mail`（邮件模板渲染、异步发送队列、SMTP 配置测试，依赖 `secret`）与 `secret`（敏感配置的 AES-GCM 加解密）。一期不创建这两个目录，避免出现空壳包。`auth` 模块一期即包含「管理员重置密码」所需的逻辑（生成强密码、撤销全会话）。

**依赖方向**：`httpapi → handler → service → repository/convert/storage`，`domain` 与 `docmodel` 被所有层依赖但不依赖任何层。禁止反向依赖，禁止 handler 直接调用 repository。

**方言依赖约束**：`service` 与 `handler` **只能**依赖 `domain` 中的仓储接口，**禁止** import `repository/postgres` 或 `repository/sqlite`。这条约束有静态检查兜底（见 [04](./04-后端设计与API规范.md) §9 用例 19），是「双方言不泄漏」的机械保障。

## 6. 部署拓扑

**两套 compose，对应两种数据库方言**。同一个 `api` 镜像，差异只在环境变量与是否包含 `db` 服务。

### 6.1 默认：SQLite（`docker-compose.yml`）

```
┌──────────────────── docker compose 网络 ────────────────────┐
│                                                             │
│  ┌──────────────┐    ┌──────────────┐                       │
│  │  web (nginx) │───▶│  api (go)    │                       │
│  │  :80 / :443  │    │  :8080       │                       │
│  │  静态资源 +   │    │  无状态       │                       │
│  │  反向代理     │    │              │                       │
│  └──────────────┘    └──────┬───────┘                       │
│                             │                                │
│                      ┌──────▼───────┐                        │
│                      │ data volume  │  含 wmind.db (SQLite)   │
│                      │ + uploads    │  与上传文件              │
│                      └──────────────┘                        │
└─────────┼───────────────────────────────────────────────────┘
          │
      宿主机端口映射 80/443      出站（一期：无）
```

**两个容器**，没有数据库服务。适合个人、小团队、内网隔离环境。

### 6.2 可选：PostgreSQL（`docker-compose.postgres.yml`）

```
┌──────────────────── docker compose 网络 ────────────────────┐
│                                                             │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐   │
│  │  web (nginx) │───▶│  api (go)    │───▶│  db (pgsql)  │   │
│  │  :80 / :443  │    │  :8080       │    │  :5432       │   │
│  └──────────────┘    └──────┬───────┘    └──────────────┘   │
│                             │                                │
│                      ┌──────▼───────┐                        │
│                      │ uploads      │  volume 持久化          │
│                      └──────────────┘                        │
└─────────┼───────────────────────────────────────────────────┘
          │
      宿主机端口映射 80/443      出站（一期：无）
```

**三个容器**，`db` 不映射宿主机端口。

### 6.3 选型对照

| 维度 | SQLite | PostgreSQL |
| --- | --- | --- |
| 容器数 | 2（web + api） | 3（web + api + db） |
| 备份 | 单文件，`VACUUM INTO` | `pg_dump` |
| 水平扩展 | ❌ 只能单实例 | ✅ `--scale api=3` |
| 标题模糊搜索 | `LIKE` 全表扫描（< 5000 张导图无感） | `pg_trgm` GIN 索引 |
| 建议规模 | < 100 用户 | 100+ 用户 / 多副本 / 大团队 |
| 磁盘要求 | 本地块设备（不支持网络卷） | 任意 |

- `web` 容器同时承担静态资源服务与 `/api` 反向代理，避免额外的 CORS 配置。
- 数据库与上传目录使用具名 volume，升级容器不丢数据。
- **一期零出站**：两套拓扑都不连接任何外部服务，部署在内网、无外网的环境同样完整可用。二期接入 SMTP 后会新增一条可选出站依赖（不配置时相关功能自动关闭，不影响其他能力）。
- **选定驱动后不建议切换**：两套迁移集之间没有数据搬迁工具（见 [09](./09-技术决策记录.md) Q-11）。若必须切换，用逐图导出 `.wmind` 的方式手工迁移。

详见 [07-部署与运维](./07-部署与运维.md)。

## 7. 关键流程

### 7.1 登录与会话续期

```
用户 → Web: 提交账号密码
Web  → API : POST /api/v1/auth/login
API  → DB  : 查询用户、校验状态
API  → API : bcrypt 校验密码
API  → DB  : 记录最后登录时间，写入 refresh token 记录
API  → Web : { accessToken(15m), refreshToken(7d), user }
Web  → Web : accessToken 存内存，refreshToken 存 httpOnly Cookie
   ⋮
Web  → API : 业务请求携带 Authorization: Bearer <accessToken>
API  → Web : 401 token_expired
Web  → API : POST /api/v1/auth/refresh（Cookie 自动携带）
API  → Web : 新 accessToken（并发请求需合并，避免刷新风暴）
```

> 一期使用「Cookie 存 refresh token + 内存存 access token」的组合：refresh token 走 httpOnly Cookie 天然防 XSS 窃取，access token 不入 Cookie 从而规避 CSRF。未来客户端 App 改用请求体传递 refresh token。

### 7.2 编辑与自动保存

```
用户编辑 → 命令派发 → store 更新 → 标记 dirty
                                     │
                    防抖 800ms（最长 5s 强制）
                                     ▼
                        PUT /api/v1/maps/{id}
                        body: { version, document }
                                     │
        ┌────────────────────────────┴────────────────────────────┐
        │ version 匹配 → 落库，version+1，返回新 version             │
        │ version 落后 → 409 conflict，前端提示「该导图已在别处修改」 │
        └─────────────────────────────────────────────────────────┘
```

**乐观锁**：`maps.version` 整型字段，每次保存 `WHERE id = ? AND version = ?`。避免两个标签页互相覆盖。

### 7.3 导入 XMind

```
Web  → 用户选择 .xmind
Web  → Web : fflate 解压 → 读取 content.json（2020+）或 content.xml（XMind 8）
Web  → Web : 适配器解析为 .wmind 文档模型
Web  → Web : 显示解析摘要（节点数 / 画布数 / 忽略项）
用户确认
Web  → API : POST /api/v1/maps  body: { title, document }
API  → Web : 新导图
```

导入在**前端**完成：避免上传大文件、避免服务端解压风险，且解析逻辑与渲染共用同一套模型。服务端也实现同构解析器（`convert/xmind`），用于将来的 API 导入与客户端 App 复用。

### 7.4 导出 PNG / SVG / PDF

```
导出 → 等字体就绪（await document.fonts.ready，否则会用回退字体栅格化）
     → 取当前画布几何（layout 纯函数重算，不受视口变换影响）
     → 计算内容包围盒 + 内边距（+ 边框样式 / 日期 / 品牌标识）
     → 逐码点检查字体覆盖，命中回退字体则记录并在结果中提示
     → 构造独立 SVG（内联样式与字体，不含编辑器 UI 节点）
     ├─ SVG 导出：内嵌所用分片或转路径后直接序列化下载
     ├─ PNG/JPEG：SVG → Image → Canvas → toBlob（scale 参数控制倍率）
     └─ PDF：SVG → jsPDF + svg2pdf → 单页/多页（默认文字转路径，可切子集内嵌）
```

超大导图（> 5000 节点或导出倍率导致画布超过浏览器上限）时降级调用服务端导出接口——**服务端容器必须预装同一套字体**，否则两条路径的渲染结果不一致。

### 7.5 访问分享链接

```
访客 → Web: 打开 /s/{token}
Web  → API : GET /api/v1/public/shares/{token}   （无需登录）
              ├─ X-Share-Access 头（若有）
API  → API : 校验 token 存在 / 未撤销 / 未过期 / 导图未删除
             ├─ 站点 share.public_link_enabled = false  ⇒ 403 SHARE_DISABLED
             └─ 任一不通过                              ⇒ 404 SHARE_NOT_FOUND
API  → API : 有密码且 X-Share-Access 无效 ⇒ 401 SHARE_PASSWORD_REQUIRED
API  → API : show_notes=false ⇒ 递归剥离文档中的 notes 字段
API  → Web : { title, document, allowDownload, showNotes, siteName, ... }
Web  → Web : 复用只读查看器渲染（布局 + 主题 + SVG，无编辑交互）
```

密码分支：

```
Web → API : POST /api/v1/public/shares/{token}/verify { password }
API → Web : { accessToken(30min, typ=share, sub=share.uid) }
Web → Web : 存 sessionStorage，后续请求带 X-Share-Access 头
```

**四个「失效」场景统一返回 404**，不区分原因：令牌不存在、已撤销、已过期、导图已删除。这是刻意的——区分原因会让攻击者能判断某个 token 是否曾经存在。

### 7.6 账号找回（一期：管理员重置）

一期不接入 SMTP，因此没有「用户自助重置密码」的流程，取而代之的是成本极低的管理员闭环：

```
用户 → 线下/IM: 联系管理员，说明忘记密码
管理员 → Web: 打开「用户管理」→ 目标用户 → 重置密码
Web → API: POST /api/v1/admin/users/{uid}/reset-password
API → DB : 生成强随机密码 → 写 users.password_hash
           → 撤销该用户全部 refresh token（含在线设备）→ 失效状态缓存
API → Web: 200 { password: "Xk7#mQ2pLw9z", generated: true }   ← 仅此一次
管理员 → 用户: 线下告知新密码
用户 → Web: 用新密码登录
```

**为什么这样设计**：这套流程不需要任何外部依赖、不需要新表、不需要用户等待邮件，对「一个实例服务一个组织」的自托管场景（管理员与用户通常在同一组织内）完全够用。代价是用户必须能联系到管理员——因此在登录页给出「忘记密码请联系管理员」的引导文案，避免用户找不到入口。

**安全约束**：新密码仅在响应中出现一次、不落日志；重置后强制该用户所有设备重新登录；管理员不能重置自己（`ADMIN_CANNOT_RESET_SELF`，避免误操作锁死自身，改自己密码走常规流程）；操作写入审计日志。

**二期改为自助流程**（归档设计，见 [09-技术决策记录](./09-技术决策记录.md) ADR-012）：`POST /auth/forgot-password` → 邮件携带 `{site.base_url}/reset-password?token=xxx` → `POST /auth/reset-password`。邮件异步发送，接口响应不等 SMTP 往返（SMTP 在弱网下可能耗时数秒）；发送失败不影响接口成功状态，只记日志与指标。二期接入后，管理员重置与邮件重置是**并存**的两条路径，不互相替换。

## 8. 横切关注点

### 8.1 统一响应与错误码

```json
// 成功
{ "data": { ... }, "requestId": "01J..." }

// 失败
{
  "error": {
    "code": "MAP_NOT_FOUND",
    "message": "导图不存在",
    "details": {}
  },
  "requestId": "01J..."
}
```

错误码为大写下划线常量，前端据此做文案映射（而非依赖中文 message）。完整清单见 [04-后端设计与API规范](./04-后端设计与API规范.md) 第 6 节。

### 8.2 日志与追踪

- 每个请求生成 `requestId`（ULID），写入响应头 `X-Request-Id` 与所有日志。
- 访问日志：方法、路径、状态码、耗时、用户 ID、requestId。
- 错误日志：错误码、堆栈（5xx）、请求上下文摘要。
- 敏感字段（密码、令牌）在日志层做脱敏。

### 8.3 配置

优先级：环境变量 > 配置文件 > 内置默认值。

**不可变配置**（需重启）：数据库驱动与连接、监听端口、JWT 密钥、存储后端。（二期增加「敏感字段加密密钥」。）
**可变配置**（存数据库、后台可改）：站点名称、注册开关、上传限制、分享策略等，见 [03-数据模型与文件格式](./03-数据模型与文件格式.md) 第 4 节。

**数据库配置的条件必填**：

| 变量 | 何时必填 | 说明 |
| --- | --- | --- |
| `WMIND_DB_DRIVER` | 总是（有默认值 `sqlite`） | `sqlite` \| `postgres` |
| `WMIND_SQLITE_PATH` | `driver = sqlite` | 默认 `/data/wmind.db`；首次启动自动创建 |
| `WMIND_DATABASE_URL` | `driver = postgres` | 缺失时拒绝启动并给出明确错误 |

**两类配置的边界**：凡是「运行期需要动态调整且不涉及进程启动」的配置都进数据库；凡是「改动后需要重建连接池 / 影响进程启动」的配置走环境变量。数据库驱动选择属于后者——它决定了连接池类型、迁移集与仓储实现，运行期切换没有意义。AI Provider 配置属于前者，但含密钥，整份加密落库；根密钥使用有效 `WMIND_2FA_ENCRYPTION_KEY`（未配置则使用 JWT 密钥），形成「可变的配置 + 不可变的根密钥」结构。AI 配置每次读库，不进入通用 settings 快照或公开响应。二期 SMTP 的独立变量仍是归档设计，不是当前部署要求。

### 8.4 数据隔离

所有导图相关 SQL 必须带 `owner_id = $currentUser` 条件；仓储层提供 `FindByIDAndOwner` 而非 `FindByID`，从类型层面强制隔离。越权访问统一返回 **404**（而非 403），不泄露资源存在性。

**唯一的例外是公开分享接口**：它按 `token` 查询而非按 `owner_id`，且只能读取**渲染所需的字段**，不能读取导图的元信息（属主、创建时间以外的内部字段、回收站状态）。该例外被收敛在 `share` 模块内，其他模块不得绕过属主校验。

## 9. 演进路径

| 阶段 | 变化 | 架构上需要做的准备 |
| --- | --- | --- |
| 单实例部署（一期） | 全部容器在一台机器；SQLite 或 PostgreSQL 均可 | 已完成 |
| 从 SQLite 迁到 PostgreSQL | 规模超过单实例上限 | 双方言仓储层已就位，代码零改动（改 `WMIND_DB_DRIVER` + 迁移集）；**缺的是数据搬迁工具**，一期用逐图导出 `.wmind` 手工迁移，二期补 `wmind db migrate`（见 [09](./09-技术决策记录.md) Q-11） |
| 水平扩展 | api 多副本（**必须 PostgreSQL**） | 限流换 Redis；分享访问计数去重换 Redis；导出临时文件换对象存储；会话已无状态无需改（二期接入邮件后，发送队列也换 Redis） |
| SQLite 读并发优化 | 单实例但读压力大 | 单连接池换成「双池」（1 写 + N 读），仅动 `repository/sqlite` 的连接初始化 |
| 引入客户端 App | 移动端 / 桌面端 | API 已版本化、认证已无状态；公开分享接口已可复用；需补设备表、增量同步接口 |
| 实时协作 | 多人同编辑 | 文档模型可序列化 + 命令可表达为操作，可迁移到 Yjs/Automerge；需引入 WebSocket 网关与 Redis Pub/Sub |
| 团队与权限 | 空间、角色矩阵 | 资源表已带 `owner_id`，扩展为 `workspace_id + acl` |
| 指定用户共享 | 导图级 ACL | `share_links` 已存在，可扩展 `map_acl` 表；权限判断已收敛在 service 层单点 |
