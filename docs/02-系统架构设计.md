## 1. 设计原则

| 原则 | 落地方式 |
| --- | --- |
| **单体优先，模块内聚** | 采用模块化单体（Modular Monolith），不做微服务。团队规模与业务复杂度不支持分布式带来的运维成本 |
| **格式自持** | 文档格式自有（`.wmind` JSON），第三方格式只作为进出口的适配器，避免被任何厂商格式绑架 |
| **内核与外壳解耦** | 前端编辑器内核（文档模型 / 布局 / 渲染 / 命令）不依赖任何 UI 组件库；后端格式转换不依赖 HTTP 层 |
| **可替换的边界** | 存储、数据库、限流、导出渲染器都通过接口隔离，单实例 → 多实例时只换实现 |
| **无状态服务** | 后端不保存会话状态（JWT），任意实例可处理任意请求，为水平扩展留路 |
| **默认可私有化** | 除 PostgreSQL 外无外部强依赖；邮件、对象存储均为可选 |

## 2. 技术选型

### 2.1 后端 Web 框架

| 候选 | 优势 | 劣势 |
| --- | --- | --- |
| **Gin** ✅ | 生态与中间件最全、中文资料最多、性能优秀、团队上手快 | 依赖 `gin.Context`，错误处理需自行统一 |
| Echo | API 设计更统一，内置绑定/校验/静态文件 | 生态规模小于 Gin |
| Chi | 100% 兼容 `net/http`，最 idiomatic，无框架侵入 | 日志、校验、绑定都要自己拼装 |
| Fiber | 基于 fasthttp，吞吐最高 | 不兼容 `net/http` 生态，部分中间件需重写，与 `httptest` 等标准测试工具有摩擦 |

**结论：Gin v1.10**。理由是需求是「主流优秀」——Gin 在生态成熟度、问题可检索性、团队熟悉度上综合最优；其「不够 idiomatic」的缺点通过统一响应封装与错误码层弥补。

### 2.2 数据库与数据访问

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 数据库 | **PostgreSQL 16** | JSONB 天然适配导图文档存储；`pg_trgm` 支持标题模糊搜索；稳定、容器化成熟 |
| 备选数据库 | SQLite（预留） | 单文件零运维，适合个人部署；但并发写弱、JSON 查询能力弱。通过 repository 接口隔离，二期可加 |
| 数据访问 | **pgx v5 + sqlc** | SQL 显式可控、编译期类型安全、无运行时反射开销、避免 ORM 隐式 N+1 |
| 备选 | GORM / Ent | GORM 开发更快但 SQL 不透明、复杂查询难调优；Ent 学习曲线陡。本项目 schema 简单、查询可控，sqlc 收益更高 |
| 迁移 | **golang-migrate** | 纯 SQL 迁移文件，可版本化、可回滚，与 sqlc 配合自然 |

| 用途 | 选型 | 说明 |

### 2.5 编辑器实现路线（关键决策）

| 方案 | 优势 | 劣势 |
| --- | --- | --- |
| A. 直接用开源导图库（MindElixir / jsMind / KityMinder） | 起步最快，几天可出可用版本 | 主题/形状/布局深度受限，**无法达到「和 XMind 一样的主题、颜色、形状」**；文档模型与需求不符，导入导出需二次映射；KityMinder 已停止维护；后期定制会与库对抗 |
| B. 基于通用图库（React Flow / @xyflow/react） | 缩放、拖拽、连线等交互成熟 | 其模型是「有向图」而非「树」，布局需完全自研；主题/形状定制仍要自研；包体积大；多出的一层抽象反而拖慢 |
| C. **自研 SVG 渲染 + 自研布局引擎** ✅ | 完全掌控主题、形状、线条、布局，可精确复刻 XMind；SVG 导出 = DOM 序列化，零成本；DOM 文本编辑与字体渲染天然支持；无第三方升级风险 | 工作量大（约占一期前端 60% 精力）；需自行处理性能与命中测试 |

**结论：方案 C**。需求中「xmind 一样的编辑体验」「要和 xmind 一样的主题、颜色、形状」是硬约束，方案 A/B 都会在这条约束上反复妥协。自研的代价用**分阶段交付**控制：先做「思维导图 + 逻辑图 + 组织结构图」三种结构 + 一套主题，把内核跑通，再横向扩展结构与配色。

**渲染载体选择 SVG 而非 Canvas**：SVG 可直接序列化为导出文件、DOM 文本可编辑可选中、字体渲染由浏览器负责、便于无障碍与调试；代价是超大规模节点性能弱于 Canvas，通过「> 2000 节点时关闭阴影/渐变并简化线条」降级处理。

### 3.1 为什么是模块化单体

- 业务边界（用户、导图、模板、主题、设置）共享同一数据库事务，拆分会引入分布式事务。
- 单实例部署是本项目的核心卖点，微服务会直接破坏「一条命令部署」的体验。
- 模块间通过 Go 接口通信，未来若某模块（如导出渲染）成为瓶颈，可独立抽出为服务而不改调用方。

## 4. 后端模块划分

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| `config` | 加载配置、校验必填项、提供默认值 | — |
| `httpapi` | 路由注册、中间件链、统一响应与错误码、请求追踪 | `handler` |
| `handler` | 解析请求、调用 service、组装响应；**不含业务规则** | `service`, `dto` |
| `service` | 业务规则、事务边界、权限校验、跨仓储编排 | `repository`, `convert`, `storage` |
| `repository` | SQL 执行与领域对象映射；**不含业务判断** | pgx, `domain` |
| `domain` | 领域模型与仓储接口定义 | — |
| `docmodel` | `.wmind` 文档结构定义、校验、遍历工具 | — |
| `convert` | 导入导出适配器：`xmind` / `opml` / `markdown` / `image` | `docmodel` |
| `auth` | 密码哈希、JWT 签发与校验、令牌撤销 | `repository` |
| `storage` | 对象存储抽象（本地磁盘 / S3 兼容） | — |

**依赖方向**：`httpapi → handler → service → repository/convert/storage`，`domain` 与 `docmodel` 被所有层依赖但不依赖任何层。禁止反向依赖，禁止 handler 直接调用 repository。

### 5.3 状态管理边界

| 状态 | 归属 | 理由 |
| --- | --- | --- |
| 导图文档（树、样式、主题配置） | Zustand + immer | 需要频繁局部更新、需要撤销栈 |
| 选区、视图变换、面板开合 | Zustand | 编辑器内部 UI 状态，不入历史栈 |
| 服务端数据（列表、用户、设置） | TanStack Query | 缓存、失效、重试 |
| 表单状态 | react-hook-form | 局部，不污染全局 |
| 主题（明暗）与语言 | Context + localStorage | 全局低频变更 |

## 7. 关键流程

### 7.1 登录与会话续期

```
用户 → Web: 提交账号密码
Web  → API : POST /api/v1/auth/login
API  → DB  : 查询用户、校验状态
API  → API : bcrypt 校验密码
API  → DB  : 记录最后登录时间，写入 refresh token 记录
API  → Web : { accessToken(15m), refreshToken(7d), user }
Web  → Web : accessToken 存内存，refreshToken 存 httpOnly Cookie
   ⋮
Web  → API : 业务请求携带 Authorization: Bearer <accessToken>
API  → Web : 401 token_expired
Web  → API : POST /api/v1/auth/refresh（Cookie 自动携带）
API  → Web : 新 accessToken（并发请求需合并，避免刷新风暴）
```

> 一期使用「Cookie 存 refresh token + 内存存 access token」的组合：refresh token 走 httpOnly Cookie 天然防 XSS 窃取，access token 不入 Cookie 从而规避 CSRF。未来客户端 App 改用请求体传递 refresh token。

### 7.2 编辑与自动保存

```
用户编辑 → 命令派发 → store 更新 → 标记 dirty
                                     │
                    防抖 800ms（最长 5s 强制）
                                     ▼
                        PUT /api/v1/maps/{id}
                        body: { version, document }
                                     │
        ┌────────────────────────────┴────────────────────────────┐
        │ version 匹配 → 落库，version+1，返回新 version             │
        │ version 落后 → 409 conflict，前端提示「该导图已在别处修改」 │
        └─────────────────────────────────────────────────────────┘
```

**乐观锁**：`maps.version` 整型字段，每次保存 `WHERE id = ? AND version = ?`。避免两个标签页互相覆盖。

### 7.3 导入 XMind

```
Web  → 用户选择 .xmind
Web  → Web : JSZip 解压 → 读取 content.json（2020+）或 content.xml（XMind 8）
Web  → Web : 适配器解析为 .wmind 文档模型
Web  → Web : 显示解析摘要（节点数 / 画布数 / 忽略项）
用户确认
Web  → API : POST /api/v1/maps  body: { title, document }
API  → Web : 新导图
```

导入在**前端**完成：避免上传大文件、避免服务端解压风险，且解析逻辑与渲染共用同一套模型。服务端也实现同构解析器（`convert/xmind`），用于将来的 API 导入与客户端 App 复用。

### 7.4 导出 PNG / SVG / PDF

```
导出 → 取当前画布几何（layout 纯函数重算，不受视口变换影响）
     → 计算内容包围盒 + 内边距（+ 边框样式 / 日期 / 品牌标识）
     → 构造独立 SVG（内联样式与字体，不含编辑器 UI 节点）
     ├─ SVG 导出：直接序列化下载
     ├─ PNG/JPEG：SVG → Image → Canvas → toBlob（scale 参数控制倍率）
     └─ PDF：SVG → jsPDF + svg2pdf → 单页/多页
```

超大导图（> 5000 节点或导出倍率导致画布超过浏览器上限）时降级调用服务端导出接口。

## 8. 横切关注点

### 8.1 统一响应与错误码

```json
// 成功
{ "data": { ... }, "requestId": "01J..." }

// 失败
{
  "error": {
    "code": "MAP_NOT_FOUND",
    "message": "导图不存在",
    "details": {}
  },
  "requestId": "01J..."
}
```

错误码为大写下划线常量，前端据此做文案映射（而非依赖中文 message）。完整清单见 [04-后端设计与API规范](./04-后端设计与API规范.md) 第 6 节。

### 8.2 日志与追踪

- 每个请求生成 `requestId`（ULID），写入响应头 `X-Request-Id` 与所有日志。
- 访问日志：方法、路径、状态码、耗时、用户 ID、requestId。
- 错误日志：错误码、堆栈（5xx）、请求上下文摘要。
- 敏感字段（密码、令牌）在日志层做脱敏。

### 8.3 配置

优先级：环境变量 > 配置文件 > 内置默认值。

**不可变配置**（需重启）：数据库连接、监听端口、JWT 密钥、存储后端。
**可变配置**（存数据库、后台可改）：站点名称、注册开关、上传限制等，见 [03-数据模型与文件格式](./03-数据模型与文件格式.md) 第 4 节。

### 8.4 数据隔离

所有导图相关 SQL 必须带 `owner_id = $currentUser` 条件；仓储层提供 `FindByIDAndOwner` 而非 `FindByID`，从类型层面强制隔离。越权访问统一返回 **404**（而非 403），不泄露资源存在性。
