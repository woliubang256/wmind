## 2. M0 · 工程脚手架与基础设施

**目标**：任何人在 5 分钟内能把项目跑起来。

### 交付物

| 项 | 内容 |
| --- | --- |
| 仓库结构 | `backend/` `frontend/` `deploy/` `docs/` 四目录；根 `README.md` 写清启动步骤 |
| 后端骨架 | Go module、Gin 路由、配置加载、slog 日志、统一响应与错误码、健康检查、优雅退出 |
| **数据库（双方言）** | **两套迁移集**（`db/migrations/postgres`、`db/migrations/sqlite`，覆盖初始 schema 全部表）；**sqlc 双 target** 配置与首次生成（产出 `pgdb` / `sqlitedb` 两个包）；`TxManager.WithTx` 事务抽象（ctx 传递事务句柄）；按 `WMIND_DB_DRIVER` 装配连接池（pgx v5 / `modernc.org/sqlite`） |
| **方言一致性闸门** | `verify-migration-parity` 脚本：校验两套迁移集版本号序列一致；接入 CI 作为必过检查。另加静态检查：`service` / `handler` 层不得出现方言分支 |
| 前端骨架 | Vite + React + TS + Tailwind v4 + shadcn 初始化、路由骨架、API 客户端（含错误码映射）、TanStack Query Provider |
| 代码规范 | ESLint + Prettier + `go vet` + `gofmt`；Git hooks（pre-commit 格式化、commit-msg 校验 Conventional Commits） |
| 部署 | **两套 compose**（`deploy/docker-compose.yml` 默认 SQLite 两容器、`deploy/docker-compose.postgres.yml` 三容器）+ 两个 Dockerfile + nginx.conf + `.env.example`；`docker compose up -d` 可启动空壳系统 |
| 测试基建 | 后端 `testify`；**SQLite 集成测试用 `t.TempDir()` 下的临时文件 + 真实迁移，不起容器**；PostgreSQL 集成测试用 `testcontainers-go`；**仓储契约测试用同一组用例分别跑 `pgdb` 与 `sqlitedb`**；前端 Vitest 跑通一个示例单测 |
| 笔记机制 | 建立 `.agents/notes/` 目录结构，配置 `npm run verify-notes` 等脚本（当前仓库尚无 `package.json`，需补齐） |

### 验收标准

1. `docker compose up -d`（SQLite 默认形态）后访问 `http://localhost` 看到前端页面，`/api/v1/health/ready` 返回 200；容器内生成 `wmind.db`。
2. `docker compose -f docker-compose.postgres.yml up -d` 同样可访问，功能无差异。
3. **同一份二进制**分别以 `WMIND_DB_DRIVER=sqlite` / `postgres` 启动，都能跑通一次示例 CRUD（建用户 → 建导图 → 查列表）。
4. 前端 `pnpm dev` + 后端本地启动（不启任何容器、不启数据库服务），也能正常联调（CORS 已配）。
5. 提交一次代码，pre-commit 自动格式化，commit-msg 校验生效。
6. CI（GitHub Actions）跑通：lint + 单元测试 + 双 target sqlc 生成一致性 + 构建镜像。
7. **`verify-migration-parity` 能拦住错误**：故意只在 `migrations/postgres` 加一个版本、不改 SQLite 侧，CI 必须失败。
8. **静态检查生效**：在 `service` 层故意写一个 `if driver == "sqlite"` 分支，CI 的方言泄漏检查必须失败。

### 依赖与风险

- 无前置依赖。
- **风险 1：`.agents/notes/` 的 `verify-notes` 脚本依赖 `package.json`**，而当前仓库没有 Node 工程在根目录。需决定把 npm script 放在根目录（新增根 `package.json`）还是 `frontend/`。建议根目录新增极简 `package.json` 只承载工具链脚本。
- **风险 2：M0 的最大不确定性是「双方言基建能不能在写业务代码之前定型」**。`TxManager.WithTx` 的事务传递方式、sqlc 双 target 的目录划分、以及 SQL 公共子集的边界，一旦定错，后面每个仓储方法都要返工。对策：**在 M0 就用真实的 `maps` + `users` 两张表跑通全链路**（迁移 → sqlc 生成 → 仓储 → service → HTTP），而不是只搭空壳。这一步多花半天，能省掉后面几天。
- **风险 3：时间处理的方言差异最隐蔽**。SQLite 与 PostgreSQL 对 `now()`、时区、微秒精度的处理不同。对策：**硬性规定时间一律由 Go 计算后作为参数传入，禁止在 SQL 中调用时间函数**；M0 就要把这条写进代码规范，并用一个测试断言两种方言写出的时间字符串格式一致。

## 3. M1 · 账号体系与管理后台

**目标**：管理员能管用户，用户能注册登录、改密，忘记密码时有明确的人工找回路径，界面支持暗色模式。

> **本期不包含邮件服务**。M1 的认证闭环以「注册即生效 + 管理员重置密码」实现，不引入任何外部依赖。这样 M1 可以在完全离线的环境里独立验收，也不占用发信域配置、退信处理等运维时间。

### 交付物

**后端**

| 模块 | 内容 |
| --- | --- |
| 认证 | 注册 / 登录 / 刷新 / 登出 / 改密 / 头像上传；bcrypt；JWT 双令牌；refresh token 持久化与撤销 |
| **管理员重置密码** | `POST /admin/users/{uid}/reset-password`：生成强随机密码或接受指定密码；一次性返回；撤销该用户全部 refresh token；禁止重置自己（`ADMIN_CANNOT_RESET_SELF`）；写审计日志 |
| 中间件 | Recover / RequestID / Logger / CORS / RateLimit / RequireAuth / RequireRole |
| 用户 | `GET /auth/me`、`PATCH /users/me`、`POST /users/me/password`、`POST /users/me/avatar` |
| 站点配置 | `GET /site/config`（公开）、`GET/PUT /admin/settings`、设置内存快照与失效 |
| 管理 | 用户列表（搜索 / 筛选 / 分页）、创建、编辑、禁用、重置密码、删除（含导图策略）、统计概览 |
| 审计 | 敏感操作写 `audit_logs`（含管理员重置密码，不记密码明文） |
| **双方言仓储实现** | 本里程碑涉及的 `users` / `refresh_tokens` / `site_settings` / `audit_logs` 四个表的仓储方法在 `pgdb` 与 `sqlitedb` 两侧都落地；契约测试双跑；并发控制用 `BEGIN IMMEDIATE` 替代 PostgreSQL 的 `SELECT ... FOR UPDATE`（见 [04-后端设计与API规范](./04-后端设计与API规范.md) §7.9） |

> **二期补入 M1 的模块**：`mail` 模块（`wneessen/go-mail`、异步发送队列 2 worker + 256 缓冲、3 个 HTML 模板、`POST /admin/mail/test` 分阶段错误定位）、`user_tokens` 表启用（忘记密码 30 分钟 / 邮箱验证 24 小时）、`secret` 模块（AES-256-GCM）与 `WMIND_ENCRYPTION_KEY`。这些设计已在 [04-后端设计与API规范](./04-后端设计与API规范.md) §7.6 与 [09-技术决策记录](./09-技术决策记录.md) ADR-012 中归档，二期可直接实施。

**前端**

| 页面 | 内容 |
| --- | --- |
| 登录 / 注册 | 表单校验（实现为手写，见 [05](./05-前端设计.md) §3.8）、错误码映射文案、注册开关联动 |
| **找回引导** | 登录页密码框下方的静态文案「忘记密码请联系站点管理员为你重置」；**不建** `/forgot-password` 等路由 |
| **重置密码对话框** | 用户管理页行操作；「随机生成 / 手动指定」两种方式；成功后用只读不可关闭对话框一次性展示新密码 + 复制按钮；对自己禁用 |
| 应用外壳 | 侧边导航（最近 / 我的导图 / 我的分享 / 回收站 / 首选项） |
| **暗色模式** | 语义化 CSS 变量层；`light` / `dark` / `system` 三档；`index.html` 内联首帧防闪烁脚本；画布区域与界面明暗解耦 |
| 个人设置 | 资料、改密、头像、外观偏好 |
| 管理后台 | 用户列表表格、用户编辑抽屉、站点设置分组表单（站点信息 / 注册与登录 / 分享 / 资源限制 / 功能开关）、概览卡片 |
| 基础设施 | API 客户端含 401 自动刷新 + 并发刷新合并；路由守卫（登录态、管理员态）；i18n 框架接入 |

### 验收标准

1. 关闭注册后，注册页不可达，直接调接口返回 403 `REGISTRATION_CLOSED`。
2. 用户 A 构造请求访问用户 B 的导图 → 404。
3. 禁用用户后，其已签发 Access Token 立即失效（下一次请求返回 403）。
4. 管理员不能删除自己，也不能降级/删除最后一个管理员。
5. Access Token 过期后，前端静默刷新，用户无感知；多个并发请求只触发一次刷新。
6. 连续 5 次密码错误后账号锁定 15 分钟。
7. **管理员重置密码全流程**：管理员在后台重置 → 一次性拿到新密码 → 用户用新密码登录成功、旧密码失效 → 该用户其他设备会话全部失效 → 关闭对话框后无法再次查看密码。
8. **管理员不能重置自己**：对自己执行重置返回 409 `ADMIN_CANNOT_RESET_SELF`，界面按钮禁用。
9. **注册即生效**：注册成功后立即可登录，响应中不含 `requiresEmailVerification` 字段；断言不存在任何 `mail.*` 设置键。
10. **暗色模式**：三档切换刷新后保持；`system` 档跟随系统实时变化；首帧无白闪。
11. **方言对等（本里程碑范围）**：注册 / 登录 / 刷新 / 重置密码 / 改站点设置这套流程在 SQLite 与 PostgreSQL 上各跑一遍，行为与错误码完全一致。

> **M1 状态：已完成。** 11 条验收标准的逐条结果（含不适用项的说明）见 [2026-10-17-wmind-acceptance-m1.md](../.agents/notes/implemented/process/2026-10-17-wmind-acceptance-m1.md)。
>
> **补记（2026-10-21）：标准 1 当时只验了「调用一次返回 403」。** 复核时发现闸门
> 挂在限流器**后面**：关站期间每次探测都消耗 3 次/小时的注册配额，第 4 次起返回
> 的是 429 `RATE_LIMITED`——用户点几下就把自己的 IP 锁一小时，而且报错看起来跟
> 「关站」毫无关系。现在 `middleware.RequireRegistrationOpen` 排在限流器之前，
> 关站期间的探测不消耗配额；`TestRegisterClosedOverHTTP` 连打 5 次断言全是 403，
> 并验「重开站后第一次注册就能成」。前端侧 `e2e/register.mjs` 11 条同时覆盖入口
> 消失与接口报错。

### 风险

- **刷新令牌并发**：多个请求同时 401 会触发刷新风暴，必须在前端做单例 Promise 合并。这是常见坑，需专门写测试。
- **账号找回依赖人工**：一期没有自助找回，用户必须能联系到管理员。对策：登录页引导文案必须在 M1 就落地（不能留到 M6），并在部署检查清单里增加「向用户公布管理员联系方式」一项。
- **管理员重置的误操作风险**：重置会踢掉目标用户全部会话。对策：对话框需二次确认并明确提示影响范围；对自己禁用；审计留痕。
- **SQLite 的并发行为与 PostgreSQL 不同**：PostgreSQL 下多个并发登录/刷新请求由 MVCC 自然处理，SQLite 下会串行排队。对策：M1 就加一个 SQLite 并发测试（并发刷新、并发改设置），确认不会出现 `SQLITE_BUSY` 未重试导致的 500。

## 4. M2 · 编辑器内核（关键里程碑）

**目标**：能新建一张导图，用键盘和鼠标完成结构化编辑，并可靠保存。

### 4.1 交付物拆分

| 子阶段 | 内容 | 工作量 |
| --- | --- | --- |
| M2.1 文档模型与状态 | TS 类型、遍历工具、校验、Zustand store、命令接口与撤销栈 | 3 人日 |
| M2.2 文本测量与布局（mindmap） | Canvas 测量 + 缓存（**缓存键含字体标识符**）；`mindmap` 结构布局（左右平衡）；几何输出 | 4 人日 |
| M2.3 SVG 渲染 | 分层渲染、`TopicNode`、连线、选区、编辑态输入框 | 4 人日 |
| M2.4 交互 | 命中测试、平移缩放、键盘映射、双击编辑、折叠展开 | 5 人日 |
| M2.5 拖拽与多选 | 拖拽改父级/排序、自由主题、框选、批量操作 | 4 人日 |
| M2.6 持久化 | 自动保存状态机、乐观锁冲突处理、本地草稿、离开保护 | 3 人日 |
| M2.7 其余结构布局 | `logic-right` `org-chart` `tree-right` | 2 人日 |
| M2.8 只读查看器抽象 | 抽出 `MindMapViewer`，交互能力由「插件集合」注入；编辑器与分享页共用 | 2 人日 |

> **M2.8 必须与 M2.3 同批做**，不能留到最后。若先按「只有编辑器」的思路写死 `MindMapCanvas`，再回头抽只读模式，会把渲染层拆一遍——这正是 M2 最不该付出的返工成本。抽象方式是：`MindMapViewer` 只负责「几何 + 样式 → SVG」，交互（平移缩放 / 折叠 / 编辑 / 拖拽）作为插件传入，编辑器传全套，分享页只传前两个。

### 4.2 验收标准

1. **纯键盘完成**：新建根节点下 3 个子节点 → 改名 → 加粗变色 → 折叠 → 撤销全部 → 重做全部，全程不碰鼠标。
2. 撤销/重做 100 步后文档与初始状态完全一致（快照比对）。
3. 1000 节点导图打开 < 1.5s；拖拽保持 60fps。
4. 编辑后刷新页面内容完整；断网编辑 30 秒后恢复网络，内容自动补存。
5. 两个标签页同时编辑同一导图，后保存者收到 409 冲突提示，三个处理选项行为正确。
6. 折叠节点显示被隐藏的后代数量。
7. 拖拽时非法落点（拖到自己的后代）被拒绝且有视觉反馈。
8. **只读查看器**：以只读配置挂载 `MindMapViewer` 后，页面上不存在可编辑元素，按 Tab/Enter 不产生新节点，样式面板未挂载；缩放与折叠正常可用。

> **M2 状态：已完成。** 8 条验收标准的逐条证据（单测 / 浏览器脚本 / 实测数字）见 [2026-10-19-wmind-acceptance-m2.md](../.agents/notes/implemented/process/2026-10-19-wmind-acceptance-m2.md)。

### 4.3 实现差异（M2 完成后回填）

| 计划 | 实际 | 原因 |
| --- | --- | --- |
| 布局用 d3-hierarchy | 手写带式布局，五种结构共用一套 | 只需要「有序树 + 固定间距」，d3 的 `tree` 节点尺寸模型与「带式」排版（同级间距与子树间距不同）对不上，包一层适配比自己写更绕 |
| `mindmap` 左右两侧按高度贪心平衡 | 按一级分支的**下标奇偶**分左右 | 贪心平衡会在编辑时不断把分支从一侧甩到另一侧，用户正在看的节点突然跳到对面 |
| 文本测量交给浏览器 / 第三方 | Canvas `measureText` + 手写换行 + 缓存（键含字体标识符） | 依赖极少，且能保证「测量用的字体栈」与「渲染用的字体栈」是同一串（ADR-016） |
| `Ctrl/Cmd + F` 查找主题 | **未接线** | 找到第 N 个结果之后没有可键盘操作的落点，等 M3 的样式/查找面板一起做 |
| 保存指示器在标题栏 | 在页脚状态栏 | 页头已有标题输入框与工具栏，再加状态会把标题挤窄 |
| `Topic.structure` 逐节点结构 | 只有画布级 `sheet.structure` | 逐节点结构（局部换布局）在 M2 没有交互入口，先不做字段 |
| 九种结构全实现 | 九种（`mindmap` / `logic-right` / `logic-left` / `tree-right` / `org-chart` / `brace` / `timeline` / `fishbone` / `tree-table`） | M3.4 补齐了后四种 |
| 剪贴板走系统剪贴板 | 应用内剪贴板（模块级变量） | 系统剪贴板要处理权限与异步 API，而跨应用粘贴 XMind 内容属于 M4 的导入导出 |
| 标题只改 `doc.title` | `changeTitleCommand` 同时写 `doc.title` 与当前画布 `rootTopic.title` | 两者对用户是同一件事，只改一个会出现「页头写着 A、中心主题写着 B」 |

### 4.4 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 「像不像 XMind」难以量化 | 反复返工 | 建立**对照清单**：把截图 3 的每一项交互列成 checklist，逐项打勾；每 2~3 天演示一次 |
| SVG 在 2000+ 节点时卡顿 | 大导图不可用 | 提前做性能基线测试（M2.3 结束时用 2000 节点压测），不达标就上视口裁剪 |
| 文本测量精度导致布局错位 | 视觉瑕疵 | 测量结果做四舍五入到 0.5px；布局常量集中管理便于统一微调 |
| **字体加载晚于首次布局** | 整张导图跳一下 | 严格「字体就绪 → 测量 → 布局」：首屏用 `document.fonts.load()` 阻塞等待所需分片，等待期显示骨架屏；**不用 `font-display: swap`**。见 [ADR-016](./09-技术决策记录.md) |
| **测量缓存命中过期结果** | 切换字体后节点宽度与实际渲染不符 | 缓存键必须包含**字体标识符**，不能只按文本缓存 |
| 撤销栈内存膨胀 | 长时间编辑后 OOM | 依赖 immer 结构共享；栈深上限 200；定期在 1000 节点场景下测内存 |
| Safari 的 `foreignObject` 兼容问题 | 编辑器在 Safari 不可用 | 编辑态直接用绝对定位 `div` 叠加，不用 `foreignObject` |

### 实现差异（M3 完成后回填）

| 计划 | 实际 | 原因 |
| --- | --- | --- |
| 字体分片用 TTF 静态实例、4 字重 | Google Fonts 的可变字体分片、5 字重（含 600） | 分片文件跨字重共享：三族 9 个字重面 10.10 MB，自切静态实例要到 30 MB 量级。600 是样式面板里已有的档位，可变字体能真实实例化（见 ADR-018） |
| 单份 `fonts.css` 随 `index.html` 加载 | 每族一份 CSS，由 `ensureFonts()` 按需注入 | sans 的 CSS 就有 514 KB，阻塞渲染会让骨架屏画不出来 |
| 「无连线穿越节点」按字面验 | 验「不可见穿越」：连线图层在节点之下 + 无节点重叠 | 时间轴/鱼骨的语义就是「骨/轨道」：连线拉到子节点中心、节点盖在线上（`makeBone` 的设计），绕开兄弟节点会把连续主干拆断 |
| 结构数「8 种」 | 8 类、9 个可选项（`logic-right` / `logic-left` 是镜像） | 选择器按方向拆成两项，验收按 9 项逐个跑，比按 8 类更严 |
| 第 6 条与 XMind 视觉对比 ≤ 2% | **推迟到 M4** | 依赖 SVG 导出；导出链路与字体策略互相牵制，草率实现会锁死 M4 的设计 |

### 风险

- **色值校准**是本阶段最大不确定性。必须在阶段开始时先完成采样与校准（见 [06-导入导出与主题系统](./06-导入导出与主题系统.md) §5.4），否则后续返工面很大。
- **字体许可已解决**（原风险项）：默认字体定为**思源黑体（Noto Sans SC，SIL OFL 1.1）**，随应用分发并做 `unicode-range` 分片；导入时按映射表把 XMind 字体名归一为标识符。见 [ADR-016](./09-技术决策记录.md)。**遗留风险转为体积与加载顺序**：实测三族产物 10.10 MB、单页传输约 315 KB 分片（外加一族 CSS 514 KB / gzip 156 KB），加载必须先于首次布局。分片来源与注入方式见 [ADR-018](./09-技术决策记录.md)。
- **分片完整性是最易漏的构建风险**：缺一个分片不会报错，只会静默显示方框。CI 已落地校验（`npm run check:fonts`，六项：文件与字节数、CSS 与 manifest 逐段一致、覆盖率下限、重叠报告、`font-display: block`、前端注册表一致）。

**验收暴露并修掉的两个真问题**：缺 `theme` 的文档打开时整页白屏（加载路径没走
归一化闸门）；导出的 SVG / PNG 用系统字体（字宽差 16%，文字会溢出节点框）。

**IE-15 的最终结论**：走**栅格 PDF**，不是矢量 PDF。矢量要把字体程序嵌进 PDF
（`Type0` + `CIDFontType2` + `CIDToGIDMap` + `W` + `ToUnicode`），而仓库里只有
WOFF2 分片，PDF 不接受 WOFF2——得先做 WOFF2→TTF 子集化工具，那是独立项目。
栅格化把渲染留在浏览器里，`buildImagePdf` 只负责包一层容器，25 条单测逐字节
可验。代价是文字不可选中，导出对话框的说明里写明了这一点并指向 SVG。
详见 [06](./06-导入导出与主题系统.md) §3.5。

> **这是一次改判，要记清楚。** 上一版这里明确否掉了「整张位图塞进 PDF」，理由
> 是它与「矢量 / 转路径」的方向相反。改判的原因不是难度，而是**矢量路线的前提
> 在本项目里不成立**：转路径需要 TTF，而仓库里只有 WOFF2 分片；补一个
> WOFF2→TTF 子集化工具是独立项目，不该挂在「导出 PDF」下面。位图方案至少
> 如实说明了代价（不可选中），而不是给一个「看着像矢量」的半成品。

### 风险

- **分享页的职责边界容易被扩大**：一旦分享页支持了折叠、大纲、配色切换，很容易被要求「再加个编辑入口」或「再加个评论」。需在 M5 开始时明确「只读」是硬边界，任何编辑类需求走二期。
- **访问计数的去重实现**：单实例内存实现简单，但多实例部署会重复计数。已抽象为接口，但需在文档中标注该限制，避免部署方误判数据准确性。

| 两个脚本 `bash -n` | ✅ |
| 脚本 8 个校验分支（未知参数、驱动名写错、缺 docker、备份文件不存在、tar 不存在 × 两个脚本） | ✅ 退出码与文案均符合预期 |
| 恢复片段（`mv`/`rm -wal`/`cp`/`chown`）在临时目录原样执行 | ✅ 旧库保留、WAL/SHM 清除、新库就位 |
| 上传文件片段不误删数据库 | ✅ `rm -rf /data/uploads/*` 只动子目录 |
| **完整 docker 编排路径（真实备份→恢复）** | ⬜ 开发机没有 Docker，留待 CI 或真实主机 |

两点如实记下来：

- **脚本里最危险的不是数据库那步，是上传文件那步**。SQLite 部署里数据库和上传
  文件共用 `data` 卷，如果沿用 PostgreSQL 的「对卷根 `rm -rf`」写法，会把刚恢
  复好的数据库一起删掉。所以特意单独验证了这一条。
- **`$var` 紧跟全角标点会炸**。`echo "未知参数：$arg（可用：--with-env）"` 在
  bash 5.3 + `set -u` 下报 `arg�: unbound variable`——多字节字符的首字节被当成
  变量名的一部分。三处全改成 `${arg}` 之类才通过。这类问题只有真跑一次才会
  发现，`bash -n` 语法检查是过的。

#### 无障碍验收（2026-10-21，`frontend/e2e/a11y.mjs`，23/23 通过）

数据准备走 REST（根 + 分支 A + A1 + 分支 B 的四节点文档），断言全部读 DOM 属性。

| 组 | 覆盖 |
| --- | --- |
| 容器 | `role=tree`、`aria-label` 含标题与主题数、`aria-multiselectable` |
| 结构 | 4 个 treeitem、层级 1/2/3/2、有子节点才有 `aria-expanded`、id 前缀稳定 |
| 活动项 | `aria-selected` 唯一、`aria-activedescendant` 指向真实存在的 id、方向键换人、播报跟着更新 |
| 折叠 | 折叠后 `aria-expanded=false` 且后代不再出现在 treeitem 列表；展开后回来 |
| 键位说明 | `aria-describedby` 指向的文案非空，且 `1×1` 视觉不可见 |
| 焦点 | 键盘聚焦画布时 `box-shadow` 里有 `inset` 焦点环 |
| 只读 | 预览态 `svg[role=img]`、`aria-label` 是标题、treeitem 与 tree 均为 0 |
| 大纲回归 | `role=tree`、4 行、`aria-level` 为 1/2/3/2 |
| **键盘陷阱** | 大纲里 `Tab` 能离开且不新建节点；画布里 `Shift+Tab` 能离开且不偷偷加节点 |

三条如实记下来：

- **两个真缺陷都是脚本抓的，不是想出来的**。画布的 `Shift+Tab` 被当成「新建子
  主题」、大纲的裸 `Tab` 被全局快捷键吃掉——都是标准键盘陷阱（WCAG 2.1.2）。
  `tsc`、单测、`bash -n` 一律不报。
- **`focus-visible` 不能用脚本 `focus()` 验**。它只在「经由键盘到达」时命中，
  所以脚本先点标题输入框、再一路 `Tab` 走过去；第一版直接 `locator.focus()`
  然后断言，拿到的是假失败。
- **`aria-level` 和 `data-outline-row` 不在同一层**。大纲的 `aria-level` 在
  `role=treeitem` 的 `<li>` 上，`data-outline-row` 在内层按钮上，直接查
  `[data-outline-row]` 会得到一串 `null`。

#### 性能验收（2026-10-21，`frontend/e2e/culling.mjs` 6 条；计时探针未入库）

压测文档 2001 节点（`/maps/stress`）。数字全部取自**生产构建**——dev 构建是
双渲染 + 未压缩，同一操作会慢 1.5~2 倍，拿它做判断会优化错地方。

| 指标 | 关闭裁剪（对照） | 开启裁剪 | 说明 |
| --- | --- | --- | --- |
| 渲染的节点元素 | 2001 | 137 | 视口 + 余量内的 |
| 按方向键（中位 / p90） | 22.6ms / 26.1ms | **16.5ms / 19.2ms** | 16.6ms 就是一帧，即额外开销归零 |
| 首屏到画布出图 | 1702ms | 1542ms | 少 160ms（≈9%），主要是少建 1800 多个 DOM |
| 滚轮缩放（中位 / p90） | 16.8ms / 18.0ms | 16.7ms / 17.7ms | 缩放只改一个 `transform`，本来就满帧 |

裁剪正确性 6/6（`j-culling.mjs`）：默认视口只渲染部分、渲染范围不超出画布周边
一屏、放大后是原来的子集、缩回来一个不少、选中的节点即使离开视口也仍然渲染、
全程无页面错误。

**首屏体积**（验收标准 5 的前半句）：生产构建下 `index.html` 直接引用的六个文件
gzip 合计 **235.5 KB**——`index` 74.5、`react` 101.1、`vendor` 24.8、`i18n` 16.1、
`data` 15.6、CSS 8.8（单位 KB）。上限是 350 KB，余量主要留给后面可能加的编辑器
依赖。`svg`（65.6 KB gzip）不在首屏里，是编辑器路由的懒加载 chunk。

三条如实记下来：

- **面板才是剩余开销的大头**。收起右侧面板后按键从 25ms 回到单帧 16.9ms——那
  些时间全花在「把几十个控件重画一遍」上。所以面板的**显示**用
  `useDeferredValue` 降了一档优先级；动作仍走即时选区，避免「选中 A 后立刻点
  色块却作用到 B」。
- **「缩放到适应」在 2000 节点上根本适应不进去**。包围盒远大于 `MIN_ZOOM=0.2`
  能塞进一屏的范围，fit 会把 zoom 钳在下限，所以「适应后应该渲染全部」这个
  预期是错的。第一版判据就是这么写的，拿到假失败。
- **布局不是瓶颈**：2000 节点的 `layoutMindmap` 实测 27–30ms，而 `LayoutResult`
  是四张 Map，来回结构化克隆的成本与它同量级。所以 Web Worker 布局刻意没做，
  理由与数据写进 docs/05 §8。

#### OpenAPI 契约（2026-10-21，`docs/openapi.yaml` + `openapi_test.go`）

`docs/openapi.yaml`（OpenAPI 3.1，34 条路径 / 49 个操作）写完了，并配了两条
Go 测试：`TestOpenAPIMatchesRouter` 拿 `engine.Routes()` 与 yaml 逐条比对，
`TestOpenAPIReferencesResolve` 走一遍 YAML 树解析每个 `$ref`。这份文档最容易坏
的方式是**悄悄过期**——加接口忘了写、删接口忘了删，两种都不报错，只会在某天
有人照着它写客户端时才发现。

三处踩到的地方：

- **`description: **不含**属主的 uid 与邮箱。` 让整个文件解析失败**（`did not find
  expected alphabetic or numeric character`）。YAML 里裸标量的第一个字符若是 `*`，
  会被当成别名节点（alias），后面跟的 `*不含**` 自然不是合法锚点名。改成「刻意
  不含」——加粗在这里本来也不重要。
- **gin 的 `:uid` 与 OpenAPI 的 `{uid}` 不是一套语法**。直接比对时每条带参数的
  接口都会同时报「缺一条、多一条」，21 条噪声把真正的差异全淹了。加一个
  `ginPathToOpenAPI` 把 `:param` / `*param` 转成 `{param}` 之后，差异归零。
- **「50 个接口」这个数字一直是错的**。docs/04 §5.10 早就写明合计 49，并解释了
  50 是把只有设计、没有路由的 `POST /export` 也算进去的结果；但 docs/README 的
  索引行还写着 50。这次一并对齐成 49，并把「机器可读版本」指向 `openapi.yaml`。

用 `@apidevtools/swagger-parser` 单独跑过一次全量校验（`VALID 3.1.0 34 paths`）——
这是本地一次性检查，没有进仓库依赖，CI 里真正兜底的还是那两条 Go 测试。

#### 用户使用手册（2026-10-21，`docs/10-用户使用手册.md`）

写给使用者，不写给开发者：登录、列表、模板、编辑器、样式与配色、多画布/大纲/ZEN、
导入、导出、分享、回收站、个人设置、管理后台，加一张快捷键速查表，最后一节是
**「一期做不到的事」**——把实时协作、指定用户共享、插入图片、备注编辑、标记/标签/
关系线/概要/边界、演说模式、服务端导出、版本历史逐条列出来，避免用户花时间找入口。

写法上只认一条：**每一句都要能在源码里指出来**。所以这一版纠正了两处凭印象写下的
内容——导出的「留白」不是无/小/中/大，是 0 / 24 / 40 / 80 px；审计日志没有独立
页面也不支持筛选，只在概览页露最近 8 条。这两处如果照印象写下去，用户会照着找一个
不存在的下拉框。

顺带记下几个容易被写成「应该如此」的实际行为：

- **缩略图不是实时的**：同一会话内最多每 3 分钟生成一次，所以刚改完回列表可能还是
  旧样子。没有这条限频，一次编辑会往磁盘里灌几十张几乎一样的 PNG。
- **回收站期间分享链接失效**，恢复后重新可用——`shares.sql` 把 `m.deleted_at`
  折进「找不到」的分支里，所以看起来和「链接被撤销」一模一样。
- **改密码会踢掉其它设备**：服务端从 Cookie 取当前 refresh token 并保留，其余全撤。
- **「显示备注」开关是真的在服务端剥字段**，不是前端隐藏；但备注本来也不画在画布上，
  只有导入时带进来、导出 Markdown/OPML 时带出去。

## 9. 关键路径与依赖

```
M0 ─▶ M1 ─▶ M2 ─┬─▶ M3 ─┐
                │       ├─▶ M6
                └─▶ M4 ─┤
                        │
                   M5 ──┘
```

| 依赖关系 | 说明 |
| --- | --- |
| M2 是硬关键路径 | M3（样式）与 M4（导出）都依赖 M2 的文档模型与渲染层。M2 延期会整体延期 |
| M3 的色值校准可提前 | 校准工作不依赖代码，可在 M1 期间并行开展 |
| M4 的导入解析可提前 | XMind 样本收集与格式逆向可在 M2 期间并行开展 |
| M5 依赖 M2 + M3 | 模板需要结构与主题；缩略图需要渲染层；**分享页直接复用 M2.8 抽出的只读查看器** |
| M5 的分享依赖 M1 的认证 | 分享令牌本身独立于用户体系，但「我的分享」列表需要登录态与用户上下文 |
| **双方言基建是 M0 的硬交付** | `TxManager`、sqlc 双 target、两套迁移集必须在 M0 定型——它是 M1 之后每个仓储方法的前置。若 M0 只交付单方言骨架，后面每个模块都要补一套，返工面随模块数线性增长 |
| **方言差异只能靠主动验证发现** | 本地默认跑 SQLite，PostgreSQL 的问题不会自发暴露。M6 的 PostgreSQL 完整回归 + 发布检查清单里的对应项是唯一防线，不能省 |
| 服务端导出可延后 | 属于 M6 的可选优化项，不阻塞交付 |

## 10. 并行建议

若有 2 人：

- **A（前端内核）**：M2 全程 → M3 → M4 导出 → M5 分享页前端
- **B（后端 + 产品外壳）**：M0（**含双方言基建与两套 compose**）→ M1（含暗色模式）→ M5 后端与页面 → M4 导入 → M6 部署与 PostgreSQL 回归

若有 3 人，可再拆出：

- **C（运维与质量）**：M0 部署骨架与 `verify-migration-parity` → 暗色模式 → 测试基建（SQLite 临时文件 / testcontainers / Playwright）→ M6 两套 compose 部署与 PostgreSQL 回归

若只有 1 人：严格按 M0 → M1 → M2 → M3 → M4 → M5 → M6 顺序，**不要**在中途插入样式微调或功能扩展。**尤其不要**因为「先跑起来要紧」而把 M0 的双方言基建砍掉一半——那是本项目最容易埋下返工的地方。
