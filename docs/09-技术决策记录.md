## 2. 决策详情

### ADR-001 · 内部存储采用自有 `.wmind` JSON 格式

**背景**：需求要求支持 XMind / Markdown / OPML 导入导出，且「数据存储看看是使用 xmind 还是 opml 或者其他更好的可以支持扩展」。

**决策**：内部唯一真相源是自有的 `.wmind` JSON 文档，结构刻意对齐 XMind 的 `content.json`（字段名如 `sheets[].rootTopic.children.attached`、`notes`、`labels`、`markers`、`relationships`、`boundaries`、`summaries`），存 PostgreSQL `JSONB`。第三方格式仅在进出口通过适配器转换。

**理由**：

1. XMind 格式是厂商私有且持续演进，跟随有长期风险；且无法承载 wmind 自己的扩展（版本、协作、权限元数据）。
2. OPML / Markdown 只能表达层级与文本，**无法表达样式、主题、形状、联系、外框、概要**——而本项目一半的产品价值在样式。
3. 自有格式可以同时满足「可扩展」（`extensions` + `formatVersion`）与「可迁移」（对齐 XMind 结构使转换成本最低）。
4. JSONB 支持局部路径更新与 GIN 索引，未来可做服务端检索。

**备选方案**：

- **直接用 `.xmind` zip 存二进制**：与 XMind 100% 互通，但无法扩展、无法查询、样式体系庞大且未文档化，跟随成本高。**否决**。
- **用 OPML 作为内部格式**：格式极简通用，但表达能力不足以支撑样式系统。**否决**。
- **用 Markdown 作为内部格式**：人类可读、Git 友好，但连稳定的节点 ID 都没有，无法支撑撤销、联系、外框等能力。**否决**。

**影响**：需要自行维护一份 schema 文档（见 [03](./03-数据模型与文件格式.md)）与前后端各一套转换器；换来的是完全的技术自主。

### ADR-002 · 后端 Web 框架选 Gin

**背景**：需求要求「选用主流优秀的 web 框架」。

**决策**：Gin。M0 落地版本 **v1.12.0**（Go 下限随之抬到 1.25，原因见 [M0 工具链基线](../.agents/notes/implemented/process/2026-10-16-wmind-m0-toolchain-baseline.md)）。

**理由**：在生态成熟度、中间件完备度、问题可检索性、团队上手速度上综合最优。其「不够 idiomatic」的缺点（依赖 `gin.Context`）通过统一响应封装与错误码层弥补。

**备选方案**：

- **Echo**：API 设计更统一，内置绑定/校验/静态文件更完整。**未选**：生态规模与中文资料量明显少于 Gin，对「主流」这一要求匹配度略低。
- **Chi**：100% 兼容 `net/http`，最 idiomatic，无框架侵入，长期维护性最好。**未选**：日志、校验、参数绑定、响应封装都要自行拼装，前期成本高；对追求交付速度的项目不是最优解。
- **Fiber**：基于 fasthttp，吞吐最高。**未选**：不兼容 `net/http` 生态，部分中间件需重写，与 `httptest`、`testcontainers` 等标准测试工具存在摩擦，长期风险大于收益。
- **标准库 `net/http` + Go 1.22 ServeMux**：零依赖。**未选**：路由能力（分组、中间件链）需自行实现，收益不明显。

**影响**：业务代码需通过 service 层与 `gin.Context` 解耦（已写入 [04](./04-后端设计与API规范.md) 的分层约束），保证可测试性。

### ADR-003 · 数据库选 PostgreSQL，数据访问用 pgx + sqlc

> **⚠️ 本决策的「数据库」部分已被 [ADR-015](#adr-015--同时支持-postgresql-与-sqlite-两种数据库双方言仓储层--两套-compose) 修订**（2026-10-16）：从「仅 PostgreSQL」改为「PostgreSQL + SQLite 双方言，SQLite 用于本地开发与轻量生产」。**数据访问方式（sqlc + 手写 SQL）与迁移工具（golang-migrate）不变**，pgx 仍是 PostgreSQL 的驱动。以下「备选方案」中关于 SQLite 的段落已过时，保留以记录当时的权衡过程。

**决策**：PostgreSQL 16 + pgx v5 + sqlc，迁移用 golang-migrate。

**理由**：

1. JSONB 天然适配导图文档存储，且支持路径查询与索引。
2. `pg_trgm` 扩展直接满足标题模糊搜索，无需引入全文检索引擎。
3. sqlc 编译期类型安全、SQL 显式可控、无运行时反射开销，避免 ORM 隐式 N+1。
4. 本项目 schema 简单（约 10 张表），手写 SQL 的成本可控。

**备选方案**：

- **SQLite**：单文件、零运维，个人部署体验更好。**未选为主库**：并发写弱、JSON 查询能力弱于 PG、无 `pg_trgm` 等价能力。**但保留**：repository 层通过接口隔离，二期可加 SQLite 驱动支持单机极简部署。
- **GORM**：开发速度快、自动迁移、生态好。**未选**：SQL 不透明、复杂查询难调优、隐式行为多（软删除、钩子）易埋坑。
- **Ent**：图式 schema、类型安全、代码生成能力强。**未选**：学习曲线陡，对 10 张表的项目属于过度设计。
- **MySQL / MariaDB**：更普及。**未选**：JSON 能力弱于 PG（无 JSONB、无 GIN 索引），模糊搜索需额外方案。

**影响**：需要维护 `.sql` 查询文件并执行 `sqlc generate`；schema 变更需同时改迁移文件与查询文件。

### ADR-004 · 编辑器自研 SVG 渲染 + 自研布局引擎

**背景**：需求要求「xmind 一样的编辑体验」「要和 xmind 一样的主题 颜色 形状那些」。

**决策**：不依赖任何现成导图库或通用图库，自研 SVG 渲染层与布局引擎。内核（model / layout / theme）为纯 TS，无 React、无 DOM 依赖。

**理由**：

1. 「和 XMind 一样的主题、颜色、形状」是硬约束。开源导图库的主题系统深度不足，会在这条约束上反复妥协。
2. 现成库的文档模型与我们的 `.wmind` 格式不一致，导入导出需二次映射，且会形成两套真相源。
3. SVG 可以直接序列化为导出文件，导出零成本；DOM 文本编辑与字体渲染由浏览器负责。
4. 无第三方升级风险，无包体积膨胀。

**备选方案**：

- **MindElixir**：MIT 开源、轻量、有主题与导入导出。**未选**：主题与形状定制深度不足；文档模型固定，与 `.wmind` 冲突。
- **jsMind**：老牌、简单。**未选**：样式能力弱，布局类型少，社区活跃度下降。
- **KityMinder（百度）**：功能完整、曾广泛使用。**未选**：已停止维护，代码年代久远，定制成本高于自研。
- **React Flow / @xyflow/react**：交互（缩放、拖拽、连线）成熟。**未选**：其模型是「有向图」而非「树」，布局仍需完全自研；主题/形状定制同样要自研；多一层抽象反而拖慢。
- **Canvas 而非 SVG**：性能更好。**未选为主渲染载体**：导出需重新绘制、文本编辑与测量复杂、无 DOM 可访问性。**折中**：SVG 为主，节点数 > 2000 时做视口裁剪与降级渲染。

**影响**：M2 占一期约 30% 工作量，是关键路径。需配套的布局算法单测与性能基线测试。

### ADR-005 · 采用模块化单体，不做微服务

**决策**：单个 Go 二进制承载全部业务模块，模块间通过 Go 接口通信。

**理由**：

1. 「一条命令部署」是核心产品卖点，微服务会直接破坏它。
2. 用户 / 导图 / 模板 / 主题 / 设置共享同一数据库事务，拆分引入分布式事务复杂度。
3. 当前业务规模与团队规模不支持微服务的运维成本。

**备选方案**：

- **微服务**：独立部署、独立扩缩容。**未选**：运维成本与部署复杂度远超收益。
- **前后端分离 + BFF**：多一层聚合。**未选**：本项目只有一种前端，无聚合需求。

**影响**：未来若某模块（如导出渲染）成为瓶颈，可独立抽出为服务而不改调用方——因为模块边界已由接口定义。

### ADR-006 · JWT 双令牌认证

**决策**：Access Token（HS256，15 分钟）+ Refresh Token（不透明随机串，7 天，服务端存哈希可撤销）。Web 端 Access Token 存内存、Refresh Token 存 httpOnly Cookie；客户端 App 用请求体传 Refresh Token。

**理由**：

1. 无状态，任意实例可处理任意请求，为水平扩展铺路。
2. 双令牌兼顾安全（Access 短时效）与体验（Refresh 长期免登录）。
3. 服务端持有 Refresh Token 哈希，支持「按设备撤销」与「改密后踢下线」。
4. 不依赖 Cookie 作为唯一载体，客户端 App 可直接复用。

**备选方案**：

- **纯 Session + Cookie**：实现简单、天然可撤销。**未选**：需要共享会话存储（Redis）才能水平扩展，且客户端 App 使用不便。
- **单一长期 JWT**：最简单。**未选**：无法撤销，泄露后风险不可控。
- **RS256 非对称签名**：多服务可只持有公钥验签。**未选**：单实例场景下 HS256 已足够，密钥管理更简单；若未来拆分服务可平滑切换。

**影响**：前端必须实现「并发 401 合并刷新」逻辑（见 [05](./05-前端设计.md) §7），否则会触发刷新风暴。

### ADR-007 · 导图保存用 `version` 字段做乐观锁

**决策**：`maps.version` 整型，保存时校验 `WHERE id = ? AND version = ?`，不匹配返回 409 `MAP_VERSION_CONFLICT`。

**理由**：自动保存是高频写操作，用悲观锁会长时间占用连接；乐观锁在无冲突时零开销，冲突时给出明确提示。

**备选方案**：

- **悲观锁（`SELECT FOR UPDATE` 独占整个编辑会话）**：无冲突丢失。**未选为主机制**：长时间持锁不可接受。**但保留**：保存事务内部仍用 `FOR UPDATE` 防同事务竞态，两者叠加。
- **Last-Write-Wins（直接覆盖）**：实现最简单。**未选**：多标签页场景会静默丢数据。
- **基于 `updated_at` 时间戳比较**：字段更少。**未选**：时间精度与时钟漂移可能造成误判，整型版本号更可靠。

**影响**：前端需要实现冲突对话框与三种处理策略（覆盖 / 放弃 / 另存副本）。

### ADR-008 · 导入在前端完成，导出以前端为主

**决策**：XMind / Markdown / OPML 的解析在前端（浏览器）完成；导出以前端渲染为主，服务端 Headless Chrome 作为超大导图的兜底。

**理由**：

1. 解析产出的模型与渲染层共用同一套 TS 类型，无需跨语言序列化。
2. 避免上传大文件与在服务端处理不可信 zip / XML，降低攻击面与资源消耗。
3. 导出内容就是屏幕上的 SVG，所见即所得，零网络往返。
4. 服务端仍保留同构解析器（`convert/` 包），供未来 API 导入与客户端复用。

**备选方案**：

- **全部在服务端处理**：前端更薄，多端一致。**未选**：需要上传大文件、服务端处理不可信输入风险高、导出需重新实现一套渲染。
- **全部在前端处理**：零服务端负载。**未选**：超大导图会撑爆浏览器 Canvas 内存，必须保留服务端兜底。

**影响**：前端包体积增加（JSZip、fast-xml-parser 等），需通过动态导入做代码分割。

### ADR-009 · 一期不做实时协作，但模型预留

**决策**：一期不实现多人同时编辑。但文档模型可完整序列化、命令可表达为操作、保存接口带版本号。

**理由**：实时协作需要 CRDT/OT、WebSocket 网关、状态合并策略，改动面覆盖前后端内核，会显著推迟一期交付。

**备选方案**：

- **一期就上 Yjs**：一步到位。**未选**：会迫使文档模型迁就 CRDT 的内部表示，且大幅增加 M2 的复杂度与风险。
- **做「锁定编辑」防冲突**：简单。**未选**：体验差，且已有乐观锁 + 冲突对话框覆盖了主要风险。

**影响**：未来迁移到 CRDT 时，需把 `.wmind` 模型映射为 CRDT 文档；`commands/` 层的操作定义可复用作 CRDT 的 op 定义。**要求**：`commands/` 中的操作必须是幂等且可序列化的（已写入 [05](./05-前端设计.md) §4.7 约定）。

### ADR-010 · 权限模型为「资源属主 + 全局角色」

**决策**：`users.role ∈ {user, admin}`，导图通过 `owner_id` 隔离。管理员只能管理账号与设置，**不能**直接读写他人导图内容。越权访问统一返回 404。

**理由**：

1. 一期无团队/空间概念，属主模型足够。
2. 管理员能读所有导图内容会带来隐私与合规风险，且需要额外的审计。
3. 返回 404 而非 403 不泄露资源存在性，避免被枚举探测。

**备选方案**：

- **完整 RBAC**：角色、权限、资源三层。**未选**：一期无此需求，属于过度设计。
- **导图级 ACL**：支持共享给指定用户。**未选**：一期需要的是「公开只读链接」而非「指定用户共享」（见 [ADR-011](#adr-011--分享链接独立建表支持密码与有效期不引入导图级-acl)），两者是不同的问题；`owner_id` 字段已存在，二期可平滑扩展为 ACL 表。
- **越权返回 403**：语义更准确。**未选**：会暴露「该 ID 存在但你没权限」，便于攻击者枚举有效 ID。

**影响**：若二期需要「管理员协助用户找回导图」，需新增显式的、带审计的越权操作入口，而不是放宽默认权限。

### ADR-011 · 分享链接独立建表，支持密码与有效期，不引入导图级 ACL

**背景**：需求方确认一期实现「分享链接与公开预览」（2026-10-16）。截图中有「分享」入口，但需求正文未展开。

**决策**：新增 `share_links` 表，一张导图可有多条分享链接。每条链接支持：访问密码（可选）、有效期（永久 / N 天）、是否允许访问者导出、是否允许查看备注。公开访问走独立接口 `GET /public/shares/{token}`，无需登录。

**理由**：

1. **公开只读链接 ≠ 指定用户共享**。前者是「有链接即可看」，后者是「授权给具体用户」。一期的需求是前者，用一张带令牌的表就能完整表达，不需要引入 ACL 模型与权限矩阵。
2. **独立成表而非在 `maps` 上加字段**，是为了支持一图多链接——同一张导图可以给不同场景（对外演示 / 内部评审）发不同权限的链接，也能分别追踪访问量。
3. **令牌存明文**（而非哈希）：创建者需要随时复制回完整链接，哈希会导致链接只能显示一次。权衡依据是分享令牌是**只读访问凭证**而非用户凭据，泄露后果可控且可撤销。
4. **失效四态统一返回 404**：令牌不存在、已撤销、已过期、导图已删除，对外不可区分。区分原因会让攻击者能判断某个 token 是否曾经存在。

**备选方案**：

- **复用 `maps` 表加 `share_token` 字段**：实现最简单，一个 `UPDATE` 就能开启/关闭分享。**未选**：无法支持一图多链接与差异化权限，也无法保留已撤销链接的访问统计。
- **令牌哈希存储**：安全性更好。**未选**：会导致「我的分享」页无法复制回链接，与核心使用场景冲突。改为用「可设密码 + 可设有效期 + 可随时撤销 + 默认 noindex」四道约束降低风险。
- **一期直接上导图级 ACL**：一次到位，支持指定用户共享。**未选**：需求方要的是公开链接；ACL 需要引入用户选择器、权限矩阵、邀请通知，成本是分享链接的数倍，且与「一期不做团队空间」的边界冲突。
- **失效原因分开返回**（404 不存在 / 410 已撤销 / 403 已过期）：语义更清晰。**未选**：泄露 token 存在性，便于枚举探测。
- **`allow_download = false` 时只下发预渲染 SVG**：能真正阻止数据获取。**未选**：会失去折叠、缩放等交互，分享页体验大幅退化。接受「该开关是降低门槛而非访问控制」这一局限，并在文档中明确标注。

**影响**：

- 公开接口是「按 token 查询而非按 `owner_id` 查询」的**唯一例外**，被收敛在 `share` 模块内，其他模块不得绕过属主校验。
- 分享页需要复用渲染层但关闭编辑交互 → 促成 M2.8「只读查看器抽象」，这是本期新增的架构约束（见 [08](./08-开发路线图.md) M2.8）。
- 访问计数去重当前用单实例内存实现，多实例部署需换 Redis，已在文档中标注该限制。

### ADR-012 · SMTP 走后台配置，凭据用 AES-256-GCM 加密存储

> **⚠️ 本决策的一期适用范围已被 [ADR-014](#adr-014--一期不接入邮件服务smtp账号找回由管理员重置承担) 取代**（2026-10-16 二次修订）：一期不接入 SMTP。本条目**不再作为一期的实施依据**，但作为**二期接入邮件服务时的完整设计**原样保留，ADR-014 直接引用它。以下内容不变。

**背景**：需求方确认一期接入 SMTP（2026-10-16），支持忘记密码与邮箱验证。

**决策**：SMTP 连接参数（主机、端口、加密方式、账号、密码、发件人）全部存 `settings` 表，由管理员在后台配置，支持「仅测试」不保存即验证。密码字段用 AES-256-GCM 加密后存储，密钥来自环境变量 `WMIND_ENCRYPTION_KEY`。

**理由**：

1. **自托管场景下，改 SMTP 就要改环境变量并重启容器，是不可接受的运维摩擦**。管理员应能在界面上配好、测通、立刻生效。
2. **凭据不能明文落库**。数据库备份、只读账号、误导出等场景都可能泄露，加密后即使拿到库也无法直接使用。
3. **密钥走环境变量而非数据库**，形成「可变的配置 + 不可变的根密钥」结构——这是加密存储的基本要求，否则密钥与密文同库等于没加密。
4. **允许「仅测试」传未保存的配置**，避免「必须先保存一份错误配置才能测试」的窘境，这是配置类界面的关键体验细节。

**备选方案**：

- **SMTP 全部走环境变量**：与数据库解耦，密钥管理简单。**未选**：改配置需重启容器，且非技术背景的部署者难以上手；与「后台可管站点」的产品定位不一致。
- **明文存数据库**：实现最简单。**未选**：SMTP 密码往往是企业邮箱主账号或带发信权限的凭据，泄露后果严重。
- **加密密钥也存数据库**：省一个环境变量。**未选**：密钥与密文同库，加密形同虚设。
- **引入 KMS / Vault**：企业级密钥管理。**未选**：为单实例自托管产品引入外部依赖，与「一条命令部署」冲突。二期若有需求可替换 `secret` 模块实现。
- **不提供「仅测试」**：少一个接口。**未选**：配置 SMTP 的失败率很高（端口封禁、认证方式、发件人限制），没有即时验证会显著拉高部署成本。

**影响**：

- 新增 `WMIND_ENCRYPTION_KEY` 必填环境变量，并在部署文档中强调「丢失后已加密配置不可恢复，需与备份分开保管」。
- 邮件发送必须**异步**（带缓冲 channel + worker），否则 SMTP 慢响应会把注册/找回密码接口拖到数秒。
- 邮件发送失败**不回滚主流程**（用户已创建），只在响应中标记 `emailSent: false`。

### ADR-013 · 前端采用纯 SPA，不做服务端渲染

**背景**：需求方确认「纯 SPA」（2026-10-16）。

**决策**：前端为纯客户端渲染的单页应用，Vite 构建为静态资源，由 Nginx 托管。不做 SSR / SSG。

**理由**：

1. **本产品的核心界面全部在登录后**（导图列表、编辑器、管理后台），这些页面无法也不应被搜索引擎索引，SSR 的核心价值（SEO）在此不成立。
2. **编辑器重度依赖 DOM 与 Canvas 测量**，在服务端渲染没有意义——首屏 HTML 里放一个空的画布容器，对用户毫无帮助。
3. **架构与部署显著更简单**：无需 Node 运行时容器，静态资源可直接上 CDN；后端只需提供 API，职责边界清晰。
4. **首屏性能可用别的方式解决**：路由级代码分割 + 字体按 `unicode-range` 分片按需加载 + 关键 CSS 内联，已能满足「首屏 JS ≤ 350KB、可交互 ≤ 1.5s」的预算（字体分片策略见 [ADR-016](#adr-016--默认字体改用思源黑体noto-sans-sc字体族以标识符存储)）。

**备选方案**：

- **Next.js SSR / SSG**：能做落地页 SEO、首屏更快。**未选**：为「营销落地页」这一个页面引入整套 SSR 运行时与 Node 容器，成本收益严重失衡。若将来确需落地页 SEO，用一个独立的静态页或 SSG 子站解决即可。
- **Next.js 仅静态导出（`output: 'export'`）**：享受 Next 的开发体验但不跑服务端。**未选**：既然不跑服务端，Next 的多数能力（Server Actions、Route Handlers、ISR）都用不上，反而多一层框架抽象与构建复杂度。
- **同构渲染（自建 SSR）**：完全掌控。**未选**：需要维护服务端与客户端的渲染一致性，对以编辑器为核心的交互型应用收益极低。
- **MPA（多页面应用）**：每页独立 HTML。**未选**：编辑器与应用外壳之间需要保持状态（如未保存草稿、主题偏好），MPA 的页面跳转会反复丢失上下文。


**影响**：

- 站点需要 SEO 的页面（登录页、注册页）通过 `<title>` / `<meta>` 在 `index.html` 中设置基础值，不做动态注入。
- 分享页 `/s/:token` 的社交预览需要 `og:title` / `og:description`，纯 SPA 下这些标签由前端 JS 注入，**部分社交平台的爬虫不执行 JS 会拿不到**。这是一期接受的局限；若二期需要分享页有良好社交预览，可单独为 `/s/*` 做服务端渲染或预渲染。
- 部署产物是纯静态文件，Nginx 只需配置 SPA 路由回退（`try_files ... /index.html`）。

### ADR-014 · 一期不接入邮件服务（SMTP），账号找回由管理员重置承担

**背景**：需求方最初选择「一期接入 SMTP」（见 [ADR-012](#adr-012--smtp-走后台配置凭据用-aes-256-gcm-加密存储)），随后于同日二次修订，**改回原推荐方案**——一期不接入邮件服务。因此需要一条新决策来界定一期与二期的边界，并明确「不接 SMTP 之后，忘记密码怎么办」。

**决策**：一期**不引入任何邮件能力**：不引入 `mail` 模块、不注册邮件相关路由、不读取 `mail.*` 设置、不引入 `WMIND_ENCRYPTION_KEY`。账号找回改由**管理员后台重置密码**承担：`POST /admin/users/{uid}/reset-password` 生成或指定新密码，一次性返回，撤销该用户全部会话，并写审计日志。`user_tokens` 表建好但保持空表，作为二期启用点。

**理由**：

1. **自托管场景下，SMTP 的真实成本不在代码而在运维**：发信域信誉（新 IP 常被判垃圾）、云厂商默认封禁出站 25 端口、退信与投诉处理、发件人地址与认证账号的约束。这些都不会因为「代码写完了」而消失，而是持续消耗部署者精力。
2. **「忘记密码」这个核心诉求有成本极低的替代解**：本产品定位是「一个实例服务一个组织」，管理员与用户通常在同一组织内，一条 IM 消息即可完成找回。管理员重置不需要新表、不需要外部依赖、不需要用户等待，闭环更短。
3. **一期零出站依赖是可交付性的硬收益**：不接 SMTP 意味着系统可以在完全隔离的内网部署，`docker compose up -d` 之后没有任何「先去申请一个邮箱」的前置步骤。这直接强化了「一条命令部署」这一核心卖点。
4. **延期不是删除，不产生返工**：ADR-012 的完整设计（后台配置、AES-GCM 加密、异步队列、仅测试）原样归档，表结构（`user_tokens`）与接口命名（`forgot-password` 等）已预留，二期接入时按图施工即可，预计约 3 人日。

**备选方案**：

- **一期接入 SMTP（即 ADR-012 的原始结论）**：能力更完整，用户可自助找回。**未选**：被需求方二次修订否决。核心问题是收益（省去用户联系管理员的一步）与成本（部署门槛 + 持续运维）不匹配，尤其对目标场景（内网自托管）而言成本被显著放大。
- **一期接入 SMTP 但只做忘记密码、不做邮箱验证**：折中，减一半工作量。**未选**：仍然保留了全部运维成本（发信域、端口、退信），只省下一点代码量，没有解决根本矛盾。
- **一期用「安全问题」自助找回**：不依赖邮件。**未选**：安全问题答案普遍弱且易被社工，安全性显著低于「管理员人工核验」，还要新增问题配置与答案哈希存储，成本不比管理员重置低。
- **一期用「一次性恢复码」**：注册时下发恢复码，用户自行保管。**未选**：把责任转移给用户，绝大多数用户会丢失恢复码，最终仍然要联系管理员——等于多写一套代码却解决不了问题。
- **完全不做账号找回**：成本最低。**未选**：对用户过于粗暴，且管理员重置的实现成本本来就极低（一个接口 + 一个对话框），没有理由不做。

**影响**：

- **登录页必须提供引导文案**「忘记密码请联系站点管理员为你重置」，这是本期账号找回的唯一用户可见入口，**M1 就要落地**，不能留到 M6 打磨阶段。
- **部署检查清单新增一项**：向用户公布管理员联系方式，并确认登录页引导文案与组织实际流程一致（见 [07-部署与运维](./07-部署与运维.md) §10）。
- **`.env` 不再需要 `WMIND_ENCRYPTION_KEY`**，备份章节也相应简化（一期无凭据落库，分享访问密码走 bcrypt 不可逆）。
- **一期接口总数为 50**（相比含邮件的 55 减少 5 个）；错误码 `AUTH_ACCOUNT_PENDING` / `MAIL_SEND_FAILED` / `MAIL_NOT_CONFIGURED` / `ENCRYPTION_KEY_MISSING` 编码已预留但不返回，避免二期重编号。
- **M1 工作量由 13 人日回退到 10 人日**，一期总计 92 人日（见 [08-开发路线图](./08-开发路线图.md)）。<br>⚠️ **该数字随后被 [ADR-015](#adr-015--同时支持-postgresql-与-sqlite-两种数据库双方言仓储层--两套-compose) 更新**：双数据库支持使 M1 回到 11 人日、总计 96 人日。此处保留当时的数字以便对照，实际以 ADR-015 与 08 文档为准。
- **ADR-012 的加密方案一期不实施**，但作为二期归档设计保留；`user_tokens` 表一期建好不写入，避免二期改表结构。

### ADR-015 · 同时支持 PostgreSQL 与 SQLite 两种数据库，双方言仓储层 + 两套 compose

**背景**：需求方追加要求（2026-10-16）——**同时支持 SQLite 与 PostgreSQL**：本地开发用 SQLite，线上部署提供两套 compose。这修订了 [ADR-003](#adr-003--数据库选-postgresql数据访问用-pgx--sqlc) 的「仅 PostgreSQL」结论。

**决策**：

1. **双方言并存，由环境变量选择**：`WMIND_DB_DRIVER = sqlite | postgres`。SQLite 用 `WMIND_SQLITE_PATH`，PostgreSQL 用 `WMIND_DATABASE_URL`。启动时按驱动加载对应的迁移集与 sqlc 生成包。
2. **SQLite 驱动用 `modernc.org/sqlite`**（纯 Go，无 CGO），PostgreSQL 仍用 `pgx/v5`。
3. **仓储层双实现，SQL 尽量共享**：`sqlc.yaml` 配两个 target（`engine: postgresql` / `engine: sqlite`），生成 `internal/repository/postgres` 与 `internal/repository/sqlite` 两个包，各自实现 `domain` 中同一组仓储接口。查询按「通用 / 方言特有」拆目录，通用 SQL 双方言共用同一份 `.sql`。
4. **服务层对事务的写法完全一致**：定义方言无关的 `TxManager.WithTx(ctx, fn)`，事务句柄经 `ctx` 传递，仓储内部从 `ctx` 取（sqlc 为两种引擎都生成 `DBTX` 接口）。
5. **两套 compose**：`docker-compose.yml`（SQLite，默认，单容器组、零外部依赖）与 `docker-compose.postgres.yml`（含 `db` 服务）。两套都走同一个 `api` 镜像，差异只在环境变量与是否包含 `db`。
6. **迁移集必须成对维护**：`db/migrations/postgres/` 与 `db/migrations/sqlite/`，配套一个 `verify-migration-parity` 脚本，用两个数据库的真实 introspect 结果比对表/列/索引集合，防止方言漂移。

**理由**：

1. **本地开发用 SQLite 直接消除了开发环境的最大摩擦**：不需要跑数据库容器、不需要等 healthcheck、不需要维护种子数据脚本；`go run` 起来就是一个可用的库，删文件即重置。开发迭代速度的提升是每天都能感受到的。
2. **SQLite 也是合理的轻量生产选择**：本产品定位「一个实例服务一个组织」，多数部署在 10~100 人量级。这个量级下 SQLite（WAL 模式 + 单写连接）的性能与可靠性完全够用，而且把「一条命令部署」做到了极致——没有 `db` 容器、没有数据库密码、没有 `pgdata` 卷、备份就是一个文件。
3. **两套 compose 的成本远低于两套代码**：因为仓储层已经是接口隔离的（ADR-003 时期就写下了这个约束），差异被收敛在 `internal/repository/{postgres,sqlite}` 与 `db/migrations/{postgres,sqlite}` 两处，其余代码零改动。
4. **「SQL 尽量共享」是控制维护成本的关键**：如果把所有查询写两遍，方言支持就会变成永久的双倍维护负担。因此确立一条纪律——**能由 Go 算出来的时间、区间、排序键一律不在 SQL 里算**（传参而不是 `now()` / `interval '30 minutes'` / `date_trunc`），把方言特有语法压缩到少数几个查询。
5. **`modernc.org/sqlite` 保证镜像构建不引入 CGO**：`mattn/go-sqlite3` 需要 gcc 与 CGO_ENABLED=1，会破坏现有的多阶段 alpine 构建（镜像变大、交叉编译变复杂）。纯 Go 驱动让 `CGO_ENABLED=0` 的静态二进制继续成立。

**双方言差异清单**（需要在 SQL 或 Go 侧处理的全部差异）：

| 差异点 | PostgreSQL | SQLite | 处理方式 |
| --- | --- | --- | --- |
| 自增主键 | `BIGSERIAL` | `INTEGER PRIMARY KEY AUTOINCREMENT` | 各写各的 DDL |
| 时间类型 | `TIMESTAMPTZ` | `TEXT`（ISO-8601 UTC，`YYYY-MM-DDTHH:MM:SS.SSSZ`） | 各写各的 DDL；Go 侧统一用 `time.Time`，SQLite 驱动做字符串转换 |
| 当前时间 | `now()` | `datetime('now')` | **禁用 DB 侧取时间**，一律由 Go 传参 |
| JSON 列 | `JSONB` | `TEXT` + `CHECK (json_valid(document))` | 各写各的 DDL；Go 侧收发都是 `[]byte` |
| 占位符 | `$1, $2` | `?` | sqlc 按 engine 自动生成，手写 SQL 时用各自语法 |
| 模糊搜索 | `ILIKE` + `pg_trgm` GIN | `LIKE`（ASCII 不区分大小写；中文为精确匹配） | 查询拆方言目录；中文场景两者等价 |
| 行锁 | `SELECT ... FOR UPDATE` | **不支持** | SQLite 侧改用 `BEGIN IMMEDIATE` + 单写连接；乐观锁版本校验双方言都保留 |
| 时间区间运算 | `now() - interval '30 minutes'` | `datetime('now','-30 minutes')` | **禁用**，改为 Go 计算后传参 |
| 统计聚合 | `date_trunc('day', created_at)` | `strftime('%Y-%m-%d', created_at)` | 数据概览的按日聚合拆方言目录 |
| Upsert | `ON CONFLICT ... DO UPDATE` | 同（3.24+） | 可共享 |
| `RETURNING` | 支持 | 支持（3.35+） | 可共享 |
| 部分索引 | 支持 | 支持 | 可共享 |
| 表达式唯一索引 | `lower(email)` | `lower(email)` | 可共享 |
| 并发写 | MVCC 多写者 | 单写者（WAL 下单写多读） | 运行时约束，见下 |

**SQLite 运行时约束**（不可协商，写入部署文档）：

- `PRAGMA journal_mode=WAL`、`busy_timeout=5000`、`foreign_keys=ON`、`synchronous=NORMAL`。
- **连接池 `SetMaxOpenConns(1)`**：SQLite 同一时刻只允许一个写者，单连接池彻底消除 `SQLITE_BUSY` 与「database is locked」。代价是读也串行化——在 10~100 人量级可接受。升级路径是「双池」（一个写连接 + N 个读连接），本期不做。
- **SQLite 模式不支持水平扩展**：`api` 只能单实例，不能 `--scale api=3`。文件锁不支持 NFS / SMB / 网络卷。
- **备份用 `VACUUM INTO`** 而不是复制文件（WAL 模式下直接拷文件可能拿到不一致快照）。
- **迁移注意**：SQLite 不支持 `ALTER COLUMN`，改列类型/约束需走「建新表 → 拷数据 → 换名」的表重建流程。一期是全新安装，只影响二期演进。

**备选方案**：

- **只支持 SQLite，放弃 PostgreSQL**：部署最简单，代码最少。**未选**：SQLite 无法水平扩展，且多实例、大团队、需要 `pg_trgm` 全文检索与 JSONB 路径查询的场景没有出路；放弃 PG 等于把产品的上限锁死。
- **只支持 PostgreSQL（即 ADR-003 的原结论）**：维护成本最低，能力上限最高。**未选**：被需求方明确否决；本地开发必须跑数据库容器这件事对开发体验的损耗是每天发生的，而 SQLite 恰好能消除它。
- **ORM 抽象双方言（GORM / Ent）**：由 ORM 处理方言差异，无需两套 SQL。**未选**：ORM 的方言适配是「最低公共分母」，复杂查询仍要落回方言特有写法，反而多一层不透明；且 ADR-003 已因透明性与可控性否掉 ORM，此处的理由不变。
- **运行时用查询构造器生成 SQL（如 squirrel）**：单份代码生成两种方言的 SQL。**未选**：会丢掉 sqlc 的编译期类型安全（ADR-003 选 sqlc 的核心理由），且查询构造器的方言适配同样是「最低公共分母」。
- **开发用 SQLite、生产强制 PostgreSQL**：开发体验好，生产不引入方言维护。**未选**：需求方要求线上也提供 SQLite 的 compose；而且「开发用 A、生产用 B」本身就是一类经典事故来源（只在生产暴露的方言差异）。
- **SQLite 用 `mattn/go-sqlite3`（CGO）**：更成熟、性能更好。**未选**：需要 gcc 与 `CGO_ENABLED=1`，破坏现有 `CGO_ENABLED=0` 的多阶段 alpine 构建；纯 Go 驱动的性能损失在本项目量级下不可感知。
- **SQLite 用双连接池（1 写 + N 读）**：读并发不受限。**未选（本期）**：多一套连接管理与会话级 PRAGMA 配置，复杂度换来的吞吐在本项目量级下用不到。作为升级路径记录。

**影响**：

- **新增环境变量** `WMIND_DB_DRIVER`（默认 `sqlite`）、`WMIND_SQLITE_PATH`（默认 `/data/wmind.db`）；`WMIND_DATABASE_URL` 改为「当 driver = postgres 时必填」。
- **`WMIND_AUTO_MIGRATE` 对双方言都生效**，但迁移集不同；SQLite 首次启动会自动创建数据库文件。
- **目录结构新增**：`db/migrations/{postgres,sqlite}/`、`db/queries/{shared,postgres,sqlite}/`、`internal/repository/{postgres,sqlite}/`。
- **`testcontainers-go` 仍用于 PostgreSQL 集成测试**；SQLite 侧用临时文件 + 真实迁移，不起容器，因此本地跑集成测试不需要 Docker。这是开发体验的第二个收益。
- **两套 compose 的差异被压到最小**：同一个 `api` 镜像，只有环境变量与是否存在 `db` 服务不同；`docker-compose.yml` 为默认（SQLite），`docker-compose.postgres.yml` 为可选。
- **工作量 +4 人日**（M0 双迁移集与 sqlc 双 target +2、仓储双实现 +1、两套 compose 与备份脚本 +1），一期总计 **96 人日**。
- **新增待处理项**：跨方言数据迁移（把已有 SQLite 实例的数据搬到 PostgreSQL）本期**不做**，见 §3 Q-11。

### ADR-016 · 默认字体改用思源黑体（Noto Sans SC），字体族以标识符存储

**背景**：XMind 的默认字体 `NeverMind` 是 XMind 自有字体，**不可再分发**。而 wmind 有两条硬性需求都要求能合法分发字体：（1）私有化部署必须离线可用，不能依赖 Google Fonts 之类的 CDN；（2）导出 SVG/PDF 时要内联或内嵌字体，否则「导出结果可预期」无法保证。因此必须选定一套可自由分发的字体，并把字体名从文档格式里解耦。该问题此前一直挂在待确认项 Q-03。

**决策**：

1. **默认字体 = 思源黑体**（Source Han Sans SC / Noto Sans SC，同一字形的两个发行名），许可 **SIL OFL 1.1**。
2. **随应用分发 Noto Sans SC 的 TTF 静态实例**，取 4 个字重：300 / 400 / 700 / 800（对应 Light / Regular / Bold / ExtraBold，覆盖 FR-EDIT-26 的全部字重要求）。不采用 Adobe 的 Source Han Sans OTF 发行版——导出链路（jsPDF 子集化、opentype.js 转路径）对 TTF 的支持更稳。
3. **按 `unicode-range` 分片按需加载，不做硬子集截断**。放弃原设想的「只打包 GB2312 一级字库 3755 字」。
4. **`fontFamily` 存标识符而非字体名**，取值为封闭集合。前端把标识符映射到实际 CSS 字体栈。
5. **字体族清单（分阶段交付）**：

| 标识符 | 显示名 | 实际字体 | 许可 | 优先级 |
| --- | --- | --- | --- | --- |
| `sans` | 思源黑体（默认） | Noto Sans SC | SIL OFL 1.1 | P0 |
| `system` | 跟随系统 | 系统字体栈（零字节） | — | P0 |
| `serif` | 思源宋体 | Noto Serif SC | SIL OFL 1.1 | P1 |
| `mono` | 等宽 | JetBrains Mono + 系统等宽 | SIL OFL 1.1 | P1 |

6. **加载与布局的顺序不可颠倒**：字体就绪 → 文本测量 → 布局。布局引擎用 Canvas 测量文本，若先用回退字体测量、webfont 到达后再重排，整张导图的节点尺寸都会变、画面会跳一下。因此首屏**阻塞等待所需分片加载完成**（`document.fonts.load()`），不使用 `font-display: swap` 的可见回退；等待期间显示骨架屏。
7. **导出**：SVG 内嵌 WOFF2 分片，或按需转路径；PDF 默认转路径（`opentype.js`），关闭该选项时用 jsPDF 子集内嵌 TTF；服务端兜底（chromedp）的容器需把字体预装到 `/usr/share/fonts`。
8. **导入归一**：XMind 的 `fo:font-family` 按映射表归一为标识符（见 [03](./03-数据模型与文件格式.md) §5.3），未知字体归入 `sans` 并计入导入 warnings。

**备选方案**：

- **继续使用 `NeverMind`**：与 XMind 视觉最一致。**未选**：XMind 自有字体，随应用打包是侵权，直接违反可分发前提。
- **HarmonyOS Sans SC / MiSans / 阿里巴巴普惠体**：观感更现代、更接近 XMind 的圆润风格，厂商也都声明「免费商用」。**未选**：许可为厂商自定义 EULA 而非标准开源许可，条款可随版本变更，且对**修改与子集化**的限制表述不清——而 WOFF2 分片与 PDF 子集内嵌在技术上都属于「修改」。对要长期自托管部署的产品，字体许可的确定性比观感更值钱。
- **思源宋体作默认**：衬线体更适合长文阅读。**未选**：思维导图是短标签，无衬线在小字号下的辨识度更好，且 XMind 默认也是无衬线。
- **霞鹜文楷（LXGW WenKai）**：楷体观感在中文导图里很讨喜，且是 OFL。**未选为默认**：楷体笔画粗细对比大，小字号可读性不如黑体，体积也更大。保留为二期的第 5 个字体族 `kai`。
- **不随应用分发字体，只用系统字体栈**：零体积、零许可风险、无加载延迟。**未选**：跨平台观感不一致（macOS 苹方 / Windows 雅黑 / Linux 各家不同），导致导出的 SVG/PDF 在不同机器上结果不同——而「导出背景与结果可预期」是本项目的明确要求（见 [01](./01-需求规格说明书.md) §4.11 FR-UI-03）。系统字体栈降级为 `system` 选项保留。
- **`fontFamily` 存字体名（如 `"Noto Sans SC"`）**：与 XMind 的 `fo:font-family` 语义一致，实现最直接。**未选**：字体名把文档与具体字体绑定——将来因许可、体积或观感任一原因换字体，就要迁移全部存量文档；存标识符只需改一处映射。另外字体名是任意字符串，会被拼进 CSS/SVG，构成注入面；标识符是封闭枚举，可直接当白名单校验。更本质的是，用户真实意图是「我要黑体 / 宋体」这类**样式类别**，标识符建模更准确。
- **可变字体（Variable Font）单文件覆盖全部字重**：只分发一个文件，理论体积更小。**未选**：导出链路对可变字体支持不稳——jsPDF 子集化与 opentype.js 转路径都需要「先实例化到具体字重」，工具链尚不成熟。改用 4 个静态实例。
- **只打包 GB2312 一级字库（3755 字）以控制体积**：单字体可压到 1.5 MB 以内。**未选**：导图内容完全任意（人名、术语、生僻字），截断会让常用但不在该表内的汉字显示为方框。这是用户直接可见的质量缺陷，比多传输几百 KB 严重得多。改为全量覆盖 + 分片按需加载。

**影响**：

- **数据格式**：`Style.fontFamily` 与 `Theme.global.fontFamily` 的取值从「字体名」改为封闭标识符，默认 `sans`（见 [03](./03-数据模型与文件格式.md) §2.4.2）。代码尚未开始，无存量数据需要迁移。
- **前端**：新增字体注册表（标识符 → CSS 栈 + 加载器）；`ComputedStyle.fontFamily` 的类型由 `string` 收紧为 `FontFamily` 联合类型（见 [05](./05-前端设计.md) §5.2）。
- **导入**：新增字体名归一映射表（[03](./03-数据模型与文件格式.md) §5.3），未知字体计入 warnings。
- **导出**：SVG/PDF 的字体内嵌方案就此确定；服务端兜底容器需预装字体（见 [07](./07-部署与运维.md) §3.1）。
- **构建**：前端产物新增约 20~30 MB 字体分片（4 字重 × 全量 CJK 分片），单页实际传输约 100~400 KB。CI 需校验分片产物完整——**缺分片会静默显示方框**，不会报错。
- **布局约束**：确立「字体就绪 → 测量 → 布局」的顺序要求，M2.2 文本测量与 M2.6 首屏加载都必须遵守（见 [08](./08-开发路线图.md) M2）。
- **关闭 Q-03**：不再有「待确认的默认字体」。
- 无工作量变化（原已按「随应用分发字体」估算，本决策只改变了分发方式与存储语义）。

### ADR-017 · 内置配色随前端分发，`themes` 表只存用户自定义主题

**背景**：M3 交付「自定义主题」时，[04](./04-后端设计与API规范.md) §5.5 原定 `GET /api/v1/themes` 返回「全部内置主题 + 当前用户自定义主题」，即 10 套内置配色也要进 `themes` 表（`owner_id IS NULL` + `is_builtin = true`）。落地时发现这条路会把样式体系的事实来源劈成两半。

**决策**：

1. **内置的 10 套配色只存在于前端包内**（`frontend/src/editor/theme/palettes.json`），作为静态资源随构建产物分发。
2. **`themes` 表只存用户自定义主题**：`owner_id` 恒非空、`is_builtin` 恒为 false。两个字段与 `THEME_BUILTIN_READONLY` 错误码保留，作为二期「管理员维护内置主题」的口子。
3. `GET /api/v1/themes` 只返回当前用户的自定义主题，不分页（上限 50 条）。前端把服务端结果与包内 `BUILTIN_PALETTES` 合并渲染。
4. 服务端对 `config` 做**规范化**（`id` → 主题 uid、`name` → 主题名、`category` → `custom`）与**体检**（非空 `palette.colors`、颜色为 `#RRGGBB`、`global.fontFamily` 非空、`fontSize > 0`），但**不解析**样式体系的其余字段，未知字段原样保留。

**备选方案**：

- **按原设计把内置配色种进 `themes` 表**：接口语义最统一，未来做「管理员换内置配色」无需改结构。**未选**：编辑器首帧就要用 `resolveStyle` 给每个节点算填充与字色，等一个请求回来意味着打开导图先白一帧再上色，离线打开则完全不可用；而且服务端那份 `config` 得用 Go 重写一遍 `themeFromPalette` 的装配逻辑——那是把前端样式体系抄进后端，此后每加一个样式字段都要两边同步。两份数据还必然需要一道一致性闸门（像迁移集的 `verifyparity` 那样），成本全落在「保持两份一样」这件事上，没有任何产出。
- **内置配色进表，前端仍用包内那份，表只作镜像**：接口语义满足原文档，前端不受影响。**未选**：镜像表永远没人读，却要维护播种迁移与一致性校验——纯粹的装饰性数据。
- **主题存 `Palette`（6 色）而不是整份 `Theme`**：表结构更小，与内置配色的数据结构一致。**未选**：用户点「保存为我的主题」时的意图是「记住现在这个样子」，只存 6 个颜色会丢掉全局字体字号、背景色、彩虹开关与三个布局开关——保存出来的主题和应用出来的效果差一截，比不能保存更让人困惑。

**影响**：

- **接口**：`GET /themes` 的语义收窄（[04](./04-后端设计与API规范.md) §5.5 已同步），新增 `THEME_LIMIT_REACHED`（403）。总数不变，仍为 4 个主题接口。
- **前端**：新增 `lib/api/themes.ts`、`editor/theme/custom.ts`（读路径兜底）、`panel/use-custom-themes.ts`；画布面板新增「我的主题」分区。演示与压测文档（`/maps/demo`、`/maps/stress`）不连后端，那里不发任何 `/themes` 请求——否则 401 会触发静默刷新、刷新失败会跳登录页。
- **数据格式**：不变。自定义主题是**主题的容器**，导图文档里仍然只存 `theme` 本身，不引用 `themeUid`——引用会让「删掉主题」把存量导图的颜色一起带走。
- **无迁移**：`themes` 表结构在 0001 初始化迁移里已经存在，本次没有新增迁移。

## 5. 决策变更流程

1. 决策被推翻时**不改写**原条目，新增 `ADR-0XX` 并在两条之间加相对链接说明取代关系。
2. 若新决策彻底取代旧决策，旧条目保留原内容并标注「已被 ADR-0XX 取代」。ADR-012 → ADR-014 是首次实践：ADR-012 的正文原样保留（作为二期设计），仅在标题下方加了取代声明。
3. **部分取代同样走新条目**：若新决策只修订旧决策的一部分（如 ADR-015 只改 ADR-003 的「数据库」部分，保留「sqlc + 手写 SQL」与「golang-migrate」），旧条目加「已被 ADR-0XX 修订（某部分）」的声明，并在该声明里**显式列出哪些结论仍有效**，避免读者误以为整条作废。
4. 所有决策同步到 `.agents/notes/implemented/architecture/`（见项目 `AGENTS.md` 的笔记要求），代码与笔记同批提交。
5. 提交前执行 `npm run verify-notes`。
6. **ADR 与 Agent Note 的双轨关系**：ADR 是「给需求方与团队看的决策结论」（含被否方案与影响面），Agent Note 是「给后续 AI 会话看的设计上下文」。两者内容可以重叠但**不合并**——ADR 会随决策演进被取代/归档，Agent Note 则按生命周期目录（proposed / implemented / rejected）管理。当一条 ADR 被取代时，对应的 Agent Note 需同步迁移目录（如从 `proposed/` 移到 `rejected/`）或补写新的 Note。
