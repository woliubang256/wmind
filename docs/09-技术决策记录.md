## 2. 决策详情

### ADR-001 · 内部存储采用自有 `.wmind` JSON 格式

**背景**：需求要求支持 XMind / Markdown / OPML 导入导出，且「数据存储看看是使用 xmind 还是 opml 或者其他更好的可以支持扩展」。

**决策**：内部唯一真相源是自有的 `.wmind` JSON 文档，结构刻意对齐 XMind 的 `content.json`（字段名如 `sheets[].rootTopic.children.attached`、`notes`、`labels`、`markers`、`relationships`、`boundaries`、`summaries`），存 PostgreSQL `JSONB`。第三方格式仅在进出口通过适配器转换。

**理由**：

1. XMind 格式是厂商私有且持续演进，跟随有长期风险；且无法承载 wmind 自己的扩展（版本、协作、权限元数据）。
2. OPML / Markdown 只能表达层级与文本，**无法表达样式、主题、形状、联系、外框、概要**——而本项目一半的产品价值在样式。
3. 自有格式可以同时满足「可扩展」（`extensions` + `formatVersion`）与「可迁移」（对齐 XMind 结构使转换成本最低）。
4. JSONB 支持局部路径更新与 GIN 索引，未来可做服务端检索。

**备选方案**：

- **直接用 `.xmind` zip 存二进制**：与 XMind 100% 互通，但无法扩展、无法查询、样式体系庞大且未文档化，跟随成本高。**否决**。
- **用 OPML 作为内部格式**：格式极简通用，但表达能力不足以支撑样式系统。**否决**。
- **用 Markdown 作为内部格式**：人类可读、Git 友好，但连稳定的节点 ID 都没有，无法支撑撤销、联系、外框等能力。**否决**。

**影响**：需要自行维护一份 schema 文档（见 [03](./03-数据模型与文件格式.md)）与前后端各一套转换器；换来的是完全的技术自主。

### ADR-002 · 后端 Web 框架选 Gin

**背景**：需求要求「选用主流优秀的 web 框架」。

**决策**：Gin v1.10。

**理由**：在生态成熟度、中间件完备度、问题可检索性、团队上手速度上综合最优。其「不够 idiomatic」的缺点（依赖 `gin.Context`）通过统一响应封装与错误码层弥补。

**备选方案**：

- **Echo**：API 设计更统一，内置绑定/校验/静态文件更完整。**未选**：生态规模与中文资料量明显少于 Gin，对「主流」这一要求匹配度略低。
- **Chi**：100% 兼容 `net/http`，最 idiomatic，无框架侵入，长期维护性最好。**未选**：日志、校验、参数绑定、响应封装都要自行拼装，前期成本高；对追求交付速度的项目不是最优解。
- **Fiber**：基于 fasthttp，吞吐最高。**未选**：不兼容 `net/http` 生态，部分中间件需重写，与 `httptest`、`testcontainers` 等标准测试工具存在摩擦，长期风险大于收益。
- **标准库 `net/http` + Go 1.22 ServeMux**：零依赖。**未选**：路由能力（分组、中间件链）需自行实现，收益不明显。

**影响**：业务代码需通过 service 层与 `gin.Context` 解耦（已写入 [04](./04-后端设计与API规范.md) 的分层约束），保证可测试性。

### ADR-003 · 数据库选 PostgreSQL，数据访问用 pgx + sqlc

**决策**：PostgreSQL 16 + pgx v5 + sqlc，迁移用 golang-migrate。

**理由**：

1. JSONB 天然适配导图文档存储，且支持路径查询与索引。
2. `pg_trgm` 扩展直接满足标题模糊搜索，无需引入全文检索引擎。
3. sqlc 编译期类型安全、SQL 显式可控、无运行时反射开销，避免 ORM 隐式 N+1。
4. 本项目 schema 简单（约 10 张表），手写 SQL 的成本可控。

**备选方案**：

- **SQLite**：单文件、零运维，个人部署体验更好。**未选为主库**：并发写弱、JSON 查询能力弱于 PG、无 `pg_trgm` 等价能力。**但保留**：repository 层通过接口隔离，二期可加 SQLite 驱动支持单机极简部署。
- **GORM**：开发速度快、自动迁移、生态好。**未选**：SQL 不透明、复杂查询难调优、隐式行为多（软删除、钩子）易埋坑。
- **Ent**：图式 schema、类型安全、代码生成能力强。**未选**：学习曲线陡，对 10 张表的项目属于过度设计。
- **MySQL / MariaDB**：更普及。**未选**：JSON 能力弱于 PG（无 JSONB、无 GIN 索引），模糊搜索需额外方案。

**影响**：需要维护 `.sql` 查询文件并执行 `sqlc generate`；schema 变更需同时改迁移文件与查询文件。

### ADR-004 · 编辑器自研 SVG 渲染 + 自研布局引擎

**背景**：需求要求「xmind 一样的编辑体验」「要和 xmind 一样的主题 颜色 形状那些」。

**决策**：不依赖任何现成导图库或通用图库，自研 SVG 渲染层与布局引擎。内核（model / layout / theme）为纯 TS，无 React、无 DOM 依赖。

**理由**：

1. 「和 XMind 一样的主题、颜色、形状」是硬约束。开源导图库的主题系统深度不足，会在这条约束上反复妥协。
2. 现成库的文档模型与我们的 `.wmind` 格式不一致，导入导出需二次映射，且会形成两套真相源。
3. SVG 可以直接序列化为导出文件，导出零成本；DOM 文本编辑与字体渲染由浏览器负责。
4. 无第三方升级风险，无包体积膨胀。

**备选方案**：

- **MindElixir**：MIT 开源、轻量、有主题与导入导出。**未选**：主题与形状定制深度不足；文档模型固定，与 `.wmind` 冲突。
- **jsMind**：老牌、简单。**未选**：样式能力弱，布局类型少，社区活跃度下降。
- **KityMinder（百度）**：功能完整、曾广泛使用。**未选**：已停止维护，代码年代久远，定制成本高于自研。
- **React Flow / @xyflow/react**：交互（缩放、拖拽、连线）成熟。**未选**：其模型是「有向图」而非「树」，布局仍需完全自研；主题/形状定制同样要自研；多一层抽象反而拖慢。
- **Canvas 而非 SVG**：性能更好。**未选为主渲染载体**：导出需重新绘制、文本编辑与测量复杂、无 DOM 可访问性。**折中**：SVG 为主，节点数 > 2000 时做视口裁剪与降级渲染。

**影响**：M2 占一期约 30% 工作量，是关键路径。需配套的布局算法单测与性能基线测试。

### ADR-005 · 采用模块化单体，不做微服务

**决策**：单个 Go 二进制承载全部业务模块，模块间通过 Go 接口通信。

**理由**：

1. 「一条命令部署」是核心产品卖点，微服务会直接破坏它。
2. 用户 / 导图 / 模板 / 主题 / 设置共享同一数据库事务，拆分引入分布式事务复杂度。
3. 当前业务规模与团队规模不支持微服务的运维成本。

**备选方案**：

- **微服务**：独立部署、独立扩缩容。**未选**：运维成本与部署复杂度远超收益。
- **前后端分离 + BFF**：多一层聚合。**未选**：本项目只有一种前端，无聚合需求。

**影响**：未来若某模块（如导出渲染）成为瓶颈，可独立抽出为服务而不改调用方——因为模块边界已由接口定义。

### ADR-006 · JWT 双令牌认证

**决策**：Access Token（HS256，15 分钟）+ Refresh Token（不透明随机串，7 天，服务端存哈希可撤销）。Web 端 Access Token 存内存、Refresh Token 存 httpOnly Cookie；客户端 App 用请求体传 Refresh Token。

**理由**：

1. 无状态，任意实例可处理任意请求，为水平扩展铺路。
2. 双令牌兼顾安全（Access 短时效）与体验（Refresh 长期免登录）。
3. 服务端持有 Refresh Token 哈希，支持「按设备撤销」与「改密后踢下线」。
4. 不依赖 Cookie 作为唯一载体，客户端 App 可直接复用。

**备选方案**：

- **纯 Session + Cookie**：实现简单、天然可撤销。**未选**：需要共享会话存储（Redis）才能水平扩展，且客户端 App 使用不便。
- **单一长期 JWT**：最简单。**未选**：无法撤销，泄露后风险不可控。
- **RS256 非对称签名**：多服务可只持有公钥验签。**未选**：单实例场景下 HS256 已足够，密钥管理更简单；若未来拆分服务可平滑切换。

**影响**：前端必须实现「并发 401 合并刷新」逻辑（见 [05](./05-前端设计.md) §7），否则会触发刷新风暴。

### ADR-007 · 导图保存用 `version` 字段做乐观锁

**决策**：`maps.version` 整型，保存时校验 `WHERE id = ? AND version = ?`，不匹配返回 409 `MAP_VERSION_CONFLICT`。

**理由**：自动保存是高频写操作，用悲观锁会长时间占用连接；乐观锁在无冲突时零开销，冲突时给出明确提示。

**备选方案**：

- **悲观锁（`SELECT FOR UPDATE` 独占整个编辑会话）**：无冲突丢失。**未选为主机制**：长时间持锁不可接受。**但保留**：保存事务内部仍用 `FOR UPDATE` 防同事务竞态，两者叠加。
- **Last-Write-Wins（直接覆盖）**：实现最简单。**未选**：多标签页场景会静默丢数据。
- **基于 `updated_at` 时间戳比较**：字段更少。**未选**：时间精度与时钟漂移可能造成误判，整型版本号更可靠。

**影响**：前端需要实现冲突对话框与三种处理策略（覆盖 / 放弃 / 另存副本）。

### ADR-008 · 导入在前端完成，导出以前端为主

**决策**：XMind / Markdown / OPML 的解析在前端（浏览器）完成；导出以前端渲染为主，服务端 Headless Chrome 作为超大导图的兜底。

**理由**：

1. 解析产出的模型与渲染层共用同一套 TS 类型，无需跨语言序列化。
2. 避免上传大文件与在服务端处理不可信 zip / XML，降低攻击面与资源消耗。
3. 导出内容就是屏幕上的 SVG，所见即所得，零网络往返。
4. 服务端仍保留同构解析器（`convert/` 包），供未来 API 导入与客户端复用。

**备选方案**：

- **全部在服务端处理**：前端更薄，多端一致。**未选**：需要上传大文件、服务端处理不可信输入风险高、导出需重新实现一套渲染。
- **全部在前端处理**：零服务端负载。**未选**：超大导图会撑爆浏览器 Canvas 内存，必须保留服务端兜底。

**影响**：前端包体积增加（JSZip、fast-xml-parser 等），需通过动态导入做代码分割。

### ADR-009 · 一期不做实时协作，但模型预留

**决策**：一期不实现多人同时编辑。但文档模型可完整序列化、命令可表达为操作、保存接口带版本号。

**理由**：实时协作需要 CRDT/OT、WebSocket 网关、状态合并策略，改动面覆盖前后端内核，会显著推迟一期交付。

**备选方案**：

- **一期就上 Yjs**：一步到位。**未选**：会迫使文档模型迁就 CRDT 的内部表示，且大幅增加 M2 的复杂度与风险。
- **做「锁定编辑」防冲突**：简单。**未选**：体验差，且已有乐观锁 + 冲突对话框覆盖了主要风险。

**影响**：未来迁移到 CRDT 时，需把 `.wmind` 模型映射为 CRDT 文档；`commands/` 层的操作定义可复用作 CRDT 的 op 定义。**要求**：`commands/` 中的操作必须是幂等且可序列化的（已写入 [05](./05-前端设计.md) §4.7 约定）。

### ADR-010 · 权限模型为「资源属主 + 全局角色」

**决策**：`users.role ∈ {user, admin}`，导图通过 `owner_id` 隔离。管理员只能管理账号与设置，**不能**直接读写他人导图内容。越权访问统一返回 404。

**理由**：

1. 一期无团队/空间概念，属主模型足够。
2. 管理员能读所有导图内容会带来隐私与合规风险，且需要额外的审计。
3. 返回 404 而非 403 不泄露资源存在性，避免被枚举探测。

**备选方案**：

- **完整 RBAC**：角色、权限、资源三层。**未选**：一期无此需求，属于过度设计。
- **导图级 ACL**：支持共享给指定用户。**未选**：需求未要求分享；`owner_id` 字段已存在，二期可平滑扩展为 ACL 表。
- **越权返回 403**：语义更准确。**未选**：会暴露「该 ID 存在但你没权限」，便于攻击者枚举有效 ID。

**影响**：若二期需要「管理员协助用户找回导图」，需新增显式的、带审计的越权操作入口，而不是放宽默认权限。

## 4. 待确认问题（需需求方拍板）

> 以下每一项都给出**推荐答案**。请按编号批量确认或修改，例如「1 同意，2 选 B，5 不需要」。

### 1. 分享链接与公开预览是否属于一期范围？

截图中有「分享」入口，但需求正文未提。

- **A（推荐）**：一期不做，工具栏「分享」按钮显示「即将推出」。理由：实现成本虽低，但涉及公开访问的权限与安全设计，会分散 M2/M3 的精力。
- **B**：一期做只读分享链接（生成随机 token，任何人可查看，不可编辑）。
- **C**：一期做完整分享（可设密码、有效期、是否允许导出）。

➡️ **推荐 A**

---

### 2. 删除用户时其导图的默认处理策略？

- **A（推荐）**：默认「一并删除」，但在删除确认框中提供「保留导图（转为无主）」选项。理由：符合「删账号即删数据」的直觉，同时给管理员留后路。
- **B**：默认「保留导图」，需管理员显式勾选才一并删除。
- **C**：只允许一并删除，不提供保留选项（实现最简单）。

➡️ **推荐 A**

---

### 3. 是否需要邮件服务（SMTP）？

影响「忘记密码」与「注册邮箱验证」两项功能。

- **A（推荐）**：一期不接入 SMTP，两项功能都关闭且入口隐藏。管理员通过后台「重置密码」为用户找回账号。
- **B**：一期接入 SMTP，支持忘记密码 + 邮箱验证注册。
- **C**：一期接入 SMTP 但只启用忘记密码。

➡️ **推荐 A**（自托管场景下 SMTP 配置是部署门槛，且管理员重置密码已能覆盖主要诉求）

---

### 4. 一期是否需要支持 S3 / MinIO 对象存储？

- **A（推荐）**：一期只用本地磁盘 volume，但接口已抽象，二期可切。理由：减少部署依赖，符合「一条命令部署」目标。
- **B**：一期就支持 S3 / MinIO 可选配置。

➡️ **推荐 A**

---

### 5. 站点名称与默认语言？

- **A（推荐）**：站点名默认 `wmind`，界面默认简体中文，内置中英文语言包，可在个人设置中切换。
- **B**：只做简体中文，不做 i18n 框架（实现更简单，后续补 i18n 成本高）。

➡️ **推荐 A**（i18n 框架后补代价大，建议一开始就用 i18next）

### 6. 单用户导图数量与上传大小上限的默认值？

- **A（推荐）**：单用户导图不限（`0`），单文件上传 10MB，均在后台可改。
- **B**：单用户 100 张，单文件 5MB。
- **C**：单用户 500 张，单文件 20MB。

➡️ **推荐 A**（自托管场景下磁盘由部署者掌控，默认不设限更符合预期）

### 8. 编辑器是否需要「暗色模式」？
