## 1. 部署形态

### 1.1 目标

在任意装有 Docker 的机器上，**一条命令**完成部署，**零必需外部依赖**。

提供**两套 compose**，对应两种数据库方言。**默认是 SQLite**（最简形态）：

```bash
# 形态 A（默认）：SQLite —— 2 个容器，无数据库服务
cp deploy/.env.example deploy/.env          # 按需修改
cd deploy && docker compose up -d

# 形态 B：PostgreSQL —— 3 个容器
cp deploy/.env.example deploy/.env          # 需补 POSTGRES_PASSWORD 与 WMIND_DB_DRIVER
cd deploy && docker compose -f docker-compose.postgres.yml up -d
```

两者用**同一个 `api` 镜像**，差异只在环境变量与是否包含 `db` 服务。

### 1.2 容器拓扑

**形态 A：SQLite（`docker-compose.yml`，默认）**

| 服务 | 镜像 | 端口 | 数据持久化 |
| --- | --- | --- | --- |
| `web` | nginx:1.27-alpine + 前端静态产物 | 宿主机 80（可配） | 无 |
| `api` | 自建（golang 多阶段构建，`CGO_ENABLED=0`） | 内部 8080 | `data` volume（含 `wmind.db` + 上传文件） |

两个服务位于同一 bridge 网络 `wmind`，`api` **不映射宿主机端口**，只暴露 `web`。

**形态 B：PostgreSQL（`docker-compose.postgres.yml`）**

| 服务 | 镜像 | 端口 | 数据持久化 |
| --- | --- | --- | --- |
| `web` | nginx:1.27-alpine + 前端静态产物 | 宿主机 80（可配） | 无 |
| `api` | 自建（同上） | 内部 8080 | `uploads` volume |
| `db` | postgres:16-alpine | 内部 5432 | `pgdata` volume |

三个服务位于同一 bridge 网络 `wmind`，`db` 与 `api` **不映射宿主机端口**，只暴露 `web`。

**两套拓扑都没有任何外部依赖**：容器不需要出站网络，部署在完全隔离的内网环境同样可用。二期接入 SMTP 后，`api` 容器会新增一条可选出站依赖（外部邮件服务，不放进 compose 编排）；不配置时系统完全可用。

### 1.3 两种形态的选择

| 维度 | SQLite | PostgreSQL |
| --- | --- | --- |
| 容器数 | 2 | 3 |
| 首次部署步骤 | `cp .env.example .env` → `up -d` | 同上 + 填数据库密码 |
| 备份 | 拷一个文件（用 `VACUUM INTO`） | `pg_dump` |
| `api` 多副本 | ❌ 不支持 | ✅ 支持 |
| 标题模糊搜索 | `LIKE` 全表扫描 | `pg_trgm` 索引 |
| 建议规模 | < 100 用户 | 100+ 用户 / 需要多副本 |
| 磁盘要求 | **必须本地块设备**（不支持 NFS/SMB/网络卷） | 任意 |

**选型建议**：

- **个人、小团队、内网隔离环境 → SQLite**。少一个容器、少一份密码、备份简单、资源占用更低。这个量级下两者性能差异不可感知。
- **100 人以上、需要多副本、或数据量预期很大 → PostgreSQL**。SQLite 无法水平扩展，且没有 `pg_trgm` 索引。
- **选定后不建议切换**：两套迁移集之间没有数据搬迁工具（见 [09-技术决策记录](./09-技术决策记录.md) Q-11）。若确需切换，用「逐图导出 `.wmind` + 重建用户」的方式手工迁移。

### 登录安全与升级

生产访问须使用 HTTPS。登录页通过浏览器 Web Crypto 将密码加密为 RSA-OAEP-256 信封，先获取 120 秒有效的一次性挑战；普通 HTTP 内网页面无法使用该登录方式，本机 localhost 开发例外。应用层加密与 HTTPS 同时使用。

升级此协议须同步更新 API 和 Web，默认自动迁移会应用 `0005_login_challenges`；旧前端直接提交 `password` 会被拒绝。现有 bcrypt 账号无需修改密码，不增加 PEM 文件或新的环境变量。多实例必须连接同一数据库并使用相同的有效 `WMIND_2FA_ENCRYPTION_KEY`（未配置时使用 `WMIND_JWT_SECRET`），才能跨实例消费挑战。应用 ZIP 备份不保存临时挑战，恢复成功后清除现存挑战。

### 1.4 资源建议

| 规模 | 形态 | CPU | 内存 | 磁盘 |
| --- | --- | --- | --- | --- |
| 个人 / 试用（< 10 用户） | SQLite | 1 核 | 512 MB | 10 GB |
| 小团队（10 ~ 100 用户） | SQLite 或 PostgreSQL | 2 核 | 1 ~ 2 GB | 50 GB |
| 组织（100 ~ 1000 用户） | PostgreSQL | 4 核 | 4 GB | 200 GB |

SQLite 形态比 PostgreSQL 形态少一个 `db` 容器（约 150 MB 内存、1 GB 磁盘起步），因此下限更低。

```
wmind/
├── backend/
│   ├── Dockerfile
│   ├── .dockerignore
│   └── ...
├── frontend/
│   ├── Dockerfile
│   ├── .dockerignore
│   └── ...
├── deploy/
│   ├── docker-compose.yml              # 形态 A（默认）：SQLite，web + api
│   ├── docker-compose.postgres.yml     # 形态 B：PostgreSQL，web + api + db
│   ├── docker-compose.dev.yml          # 开发用：暴露端口、api 热重载（可选）
│   ├── nginx.conf
│   ├── nginx.https.conf.example        # HTTPS 配置样例
│   ├── .env.example                    # 两种形态共用，DB 相关项按需填
│   └── scripts/
│       ├── backup.sh                   # 按 WMIND_DB_DRIVER 自动分叉
│       └── restore.sh
└── docs/
```

**开发环境不需要 compose 里的数据库**：`backend` 直接 `go run ./cmd/server` 用 SQLite（默认 `WMIND_DB_DRIVER=sqlite`），`frontend` 用 `pnpm dev`。集成测试也用临时 SQLite 文件，因此**本地开发不需要 Docker**。只有需要验证 PostgreSQL 行为时才用 `docker-compose.postgres.yml` 或 `testcontainers`。

## 3. 构建产物

### 3.1 后端 Dockerfile

```dockerfile
# ---- 构建阶段 ----
FROM golang:1.25-alpine AS builder
WORKDIR /src

RUN apk add --no-cache git ca-certificates
COPY go.mod go.sum ./
RUN go mod download

COPY . .
ARG VERSION=dev
RUN CGO_ENABLED=0 GOOS=linux go build \
      -trimpath \
      -ldflags="-s -w -X main.version=${VERSION}" \
      -o /out/wmind ./cmd/server

# ---- 运行阶段 ----
FROM alpine:3.20
RUN apk add --no-cache ca-certificates tzdata && \
    addgroup -g 10001 -S wmind && \
    adduser  -u 10001 -S wmind -G wmind

WORKDIR /app
COPY --from=builder /out/wmind /app/wmind

# 迁移文件通过 go:embed 编入二进制，无需额外拷贝
ENV WMIND_MIGRATIONS_EMBEDDED=true

USER 10001
EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
  CMD wget -qO- http://127.0.0.1:8080/api/v1/health/live || exit 1

ENTRYPOINT ["/app/wmind"]
```

**要点**：

- `CGO_ENABLED=0` 产出静态二进制，运行阶段用 alpine 而非 scratch（保留 `wget` 供健康检查、`tzdata` 供时区）。
- **SQLite 驱动选 `modernc.org/sqlite`（纯 Go 实现）而非 `mattn/go-sqlite3`（需 CGO）**，因此 `CGO_ENABLED=0` 依然成立，交叉编译与静态二进制不受影响。这是 ADR-015 里明确排除 `mattn` 的直接原因。
- 迁移文件用 `go:embed` 编入二进制，避免容器内路径依赖，也简化 `docker cp` 场景。**两套迁移集（`migrations/postgres`、`migrations/sqlite`）都编入同一个二进制**，启动时按 `WMIND_DB_DRIVER` 选择执行哪一套——同一个镜像因此既能跑 SQLite 也能跑 PostgreSQL。
- 非 root 用户运行（UID 10001）。
- 多阶段构建，最终镜像约 25 MB。

> **SQLite 的写权限**：`api` 进程要对 `/data` 有写权限（`wmind.db`、`-wal`、`-shm` 三个文件都要能创建）。镜像内以 UID 10001 运行，因此 compose 里的 `data` volume 首次挂载后需要归属正确；Docker 命名卷会自动继承容器内目录的属主，**绑定挂载（bind mount）到宿主机目录时需手动 `chown 10001`**，否则启动即报 `attempt to write a readonly database`。

**关于服务端导出（可选，二期/M6）**：上面的镜像是**默认形态**，不含 Chromium（约 25 MB）。服务端兜底导出需要 Headless Chrome，会额外增加约 400 MB，因此**不放进默认镜像**——需要时用构建参数开启一个变体：

```dockerfile
ARG WITH_CHROME=false
RUN if [ "$WITH_CHROME" = "true" ]; then \
      apk add --no-cache chromium fontconfig ttf-dejavu && \
      cp -r /src/deploy/fonts/* /usr/share/fonts/ && \
      fc-cache -f; \
    fi
```

> **关键点**：这个变体必须**预装与前端完全相同的字体**（把前端构建产出的 Noto Sans SC 分片或完整 TTF 拷进 `/usr/share/fonts`），否则同一次导出走浏览器与走服务端会得到不同字形——同一个导图导出两次结果不一样，是最难排查的一类 bug。已作为硬验收项（见 [08-开发路线图](./08-开发路线图.md) M4 的 IE-30）。
>
> 若最终决定一期不做服务端导出（Q-07 的倾向），此变体可整体跳过，默认镜像不受影响。

### 3.2 前端 Dockerfile

```dockerfile
# ---- 构建阶段 ----
FROM node:22-alpine AS builder
WORKDIR /app

RUN corepack enable
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile

COPY . .
RUN pnpm build

# ---- 运行阶段 ----
FROM nginx:1.27-alpine
RUN rm -f /etc/nginx/conf.d/default.conf
COPY --from=builder /app/dist /usr/share/nginx/html
COPY deploy/nginx.conf /etc/nginx/conf.d/wmind.conf

EXPOSE 80
```

> 前端构建上下文是 `frontend/`，但需要读取 `deploy/nginx.conf`。做法：`docker compose` 中把 build context 设为仓库根目录，`dockerfile: frontend/Dockerfile`，并在 Dockerfile 中用 `COPY frontend/package.json` 等路径。或把 `nginx.conf` 复制一份到 `frontend/`。**采用后者**（保持构建上下文最小，避免把整个仓库传给 docker daemon）。

### 3.3 nginx.conf

```nginx
server {
    listen 80;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    client_max_body_size 32m;

    # 压缩
    gzip on;
    gzip_vary on;
    gzip_min_length 1024;
    gzip_types
        text/plain text/css text/xml
        application/javascript application/json application/xml
        image/svg+xml;

    # 安全响应头
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;

    # 带 hash 的静态资源，长期缓存
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    # 字体
    location ~* \.(woff2?|ttf|otf)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    # 接口反向代理
    location /api/ {
        proxy_pass         http://api:8080;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_connect_timeout 10s;
        proxy_read_timeout    120s;   # 服务端导出可能较慢
        proxy_send_timeout    120s;
    }

    # SPA 路由回退
    location / {
        try_files $uri $uri/ /index.html;
        add_header Cache-Control "no-cache";
    }
}
```

> **注意**：`add_header` 在 `location` 块中会覆盖 `server` 块的设置。若在 `location /` 中加了 `Cache-Control`，则该 location 下的安全头会丢失。生产配置应使用 `include` 抽取公共头，或用 `nginx` 1.27 的 `add_header_inherit` 指令。**实现时需实测响应头**。

### 3.4 docker-compose.yml（默认：SQLite）

两个服务，**没有 `db`**。数据库文件与上传文件同处一个 `data` 卷。

```yaml
name: wmind

services:
  api:
    build:
      context: ../backend
    image: wmind/api:${WMIND_VERSION:-latest}
    restart: unless-stopped
    environment:
      WMIND_ENV: production
      WMIND_ADDR: ":8080"
      WMIND_DB_DRIVER: sqlite
      WMIND_SQLITE_PATH: /data/wmind.db
      WMIND_JWT_SECRET: ${WMIND_JWT_SECRET:?WMIND_JWT_SECRET is required}
      WMIND_STORAGE_DRIVER: local
      WMIND_STORAGE_DIR: /data/uploads
      WMIND_AUTO_MIGRATE: "true"
      WMIND_LOG_LEVEL: ${WMIND_LOG_LEVEL:-info}
      WMIND_ADMIN_EMAIL: ${WMIND_ADMIN_EMAIL:-}
      WMIND_ADMIN_PASSWORD: ${WMIND_ADMIN_PASSWORD:-}
      TZ: ${TZ:-Asia/Shanghai}
    volumes:
      - data:/data
    networks: [wmind]
    stop_grace_period: 20s

  web:
    build:
      context: ../frontend
    image: wmind/web:${WMIND_VERSION:-latest}
    restart: unless-stopped
    depends_on: [api]
    ports:
      - "${HTTP_PORT:-80}:80"
    networks: [wmind]

volumes:
  data:          # 内含 wmind.db / wmind.db-wal / wmind.db-shm 与 uploads/

networks:
  wmind:
    driver: bridge
```

**这个文件的三条硬约束**（违反任一条都会导致数据损坏或性能塌方）：

| 约束 | 原因 |
| --- | --- |
| `data` 卷必须是**本地磁盘**，不能是 NFS / CIFS / 云盘挂载 | SQLite 的 WAL 与文件锁依赖 `fcntl` 语义，网络文件系统上不可靠，会出现「database is locked」或静默损坏 |
| **只能有一个 `api` 实例** | SQLite 是单写者模型。横向扩容到 2 个副本会让写入互相阻塞甚至写坏。需要多副本时换 PostgreSQL |
| 备份必须用 `VACUUM INTO`（见 §7.1），**不能直接 `cp wmind.db`** | 运行中直接拷贝会拿到撕裂的快照；WAL 文件未合并时拷贝结果也不完整 |

> `WMIND_DB_MAX_CONNS` 在 SQLite 下被忽略——连接池被强制为 1（见 [03-数据模型与文件格式](./03-数据模型与文件格式.md) §3.4）。这是设计使然，不是配置遗漏。

### 3.5 docker-compose.postgres.yml（可选：PostgreSQL）

三个服务，多了 `db`。用法是显式指定文件：

```bash
docker compose -f docker-compose.postgres.yml up -d
```

```yaml
name: wmind

services:
  db:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-wmind}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?POSTGRES_PASSWORD is required}
      POSTGRES_DB: ${POSTGRES_DB:-wmind}
      POSTGRES_INITDB_ARGS: "--encoding=UTF8 --locale=C"
      TZ: ${TZ:-Asia/Shanghai}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-wmind} -d ${POSTGRES_DB:-wmind}"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 30s
    networks: [wmind]

  api:
    build:
      context: ../backend
    image: wmind/api:${WMIND_VERSION:-latest}
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    environment:
      WMIND_ENV: production
      WMIND_ADDR: ":8080"
      WMIND_DB_DRIVER: postgres
      WMIND_DATABASE_URL: >-
        postgres://${POSTGRES_USER:-wmind}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB:-wmind}?sslmode=disable
      WMIND_DB_MAX_CONNS: ${WMIND_DB_MAX_CONNS:-20}
      WMIND_JWT_SECRET: ${WMIND_JWT_SECRET:?WMIND_JWT_SECRET is required}
      WMIND_STORAGE_DRIVER: local
      WMIND_STORAGE_DIR: /data/uploads
      WMIND_AUTO_MIGRATE: "true"
      WMIND_LOG_LEVEL: ${WMIND_LOG_LEVEL:-info}
      WMIND_ADMIN_EMAIL: ${WMIND_ADMIN_EMAIL:-}
      WMIND_ADMIN_PASSWORD: ${WMIND_ADMIN_PASSWORD:-}
      TZ: ${TZ:-Asia/Shanghai}
    volumes:
      - uploads:/data/uploads
    networks: [wmind]
    stop_grace_period: 20s

  web:
    build:
      context: ../frontend
    image: wmind/web:${WMIND_VERSION:-latest}
    restart: unless-stopped
    depends_on: [api]
    ports:
      - "${HTTP_PORT:-80}:80"
    networks: [wmind]

volumes:
  pgdata:
  uploads:

networks:
  wmind:
    driver: bridge
```

**两套 compose 的关系**：

| 问题 | 答案 |
| --- | --- |
| 能同时用吗 | 不能，也没必要。`api` 只连一个数据库；同时起两套会争抢 `${HTTP_PORT}` |
| 卷名会冲突吗 | 不会。SQLite 用 `data`，PostgreSQL 用 `pgdata` + `uploads`，互不覆盖 |
| 能互相切换吗 | 代码层零改动（改 `WMIND_DB_DRIVER` 即可），但**数据不会自动过去**。一期没有跨方言搬迁工具，需要逐图导出 `.wmind` 再导入（见 [09](./09-技术决策记录.md) Q-11） |
| 该选哪个 | 见 §1.3 选型对照。内部使用 / 单机 / 小团队 → SQLite；多副本、外部系统要直连库、已有 PostgreSQL 运维体系 → PostgreSQL |

### 3.6 .env.example

```dotenv
# ── 必填 ──────────────────────────────────────────────
# JWT 签名密钥（必须 ≥ 32 字节；生成：openssl rand -base64 48）
WMIND_JWT_SECRET=change-me-please-at-least-32-bytes-long

# ── 数据库 ────────────────────────────────────────────
# sqlite（默认，无需额外配置） | postgres
WMIND_DB_DRIVER=sqlite

# 仅 driver=postgres 时需要：数据库密码（建议 24 位以上随机串）
# POSTGRES_PASSWORD=change-me-please

# ── 首次启动时创建的管理员（仅 users 表为空时生效）────────
WMIND_ADMIN_EMAIL=admin@example.com
WMIND_ADMIN_PASSWORD=change-me-please

# ── 可选 ──────────────────────────────────────────────
# POSTGRES_USER=wmind
# POSTGRES_DB=wmind
# WMIND_DB_MAX_CONNS=20            # 仅 PostgreSQL 生效
# WMIND_SQLITE_PATH=/data/wmind.db # 仅 SQLite 生效，通常无需修改
HTTP_PORT=80
TZ=Asia/Shanghai
WMIND_LOG_LEVEL=info
WMIND_VERSION=latest
```

> **用 PostgreSQL 部署时**，把 `WMIND_DB_DRIVER` 改成 `postgres` 并**取消 `POSTGRES_PASSWORD` 的注释**（不设会让 compose 直接报错退出，这是刻意的——避免用默认密码上线）。

## 4. 环境变量

| 变量 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `WMIND_ENV` | 否 | `production` | `development` / `production`；影响日志格式与 CORS |
| `WMIND_ADDR` | 否 | `:8080` | 监听地址 |
| `WMIND_DB_DRIVER` | 否 | `sqlite` | `sqlite` / `postgres`；未知值拒绝启动并打印允许值 |
| `WMIND_SQLITE_PATH` | 仅 `sqlite` | `/data/wmind.db` | SQLite 文件路径；首次启动自动创建（含父目录） |
| `WMIND_DATABASE_URL` | 仅 `postgres` | — | PostgreSQL 连接串；`driver=postgres` 时缺失即拒绝启动 |
| `WMIND_DB_MAX_CONNS` | 否 | `20` | 连接池上限；**SQLite 下被忽略**（强制为 1） |
| `WMIND_JWT_SECRET` | **是** | — | ≥ 32 字节，不足则拒绝启动 |
| `WMIND_2FA_ENCRYPTION_KEY` | 否 | 从 JWT 密钥派生 | ≥ 32 字节；用于 2FA、分享密码等独立用途派生；首次使用前配置，保持稳定并备份 |
| `WMIND_ACCESS_TOKEN_TTL` | 否 | `15m` | Access Token 有效期 |
| `WMIND_REFRESH_TOKEN_TTL` | 否 | `168h` | Refresh Token 有效期（7 天） |
| `WMIND_STORAGE_DRIVER` | 否 | `local` | `local` / `s3`（二期） |
| `WMIND_STORAGE_DIR` | 否 | `/data/uploads` | 本地存储目录 |
| `WMIND_AUTO_MIGRATE` | 否 | `true` | 启动时自动执行数据库迁移 |
| `WMIND_ADMIN_EMAIL` | 否 | — | 首次启动创建管理员（仅空库生效） |
| `WMIND_ADMIN_PASSWORD` | 否 | — | 同上 |
| `WMIND_LOG_LEVEL` | 否 | `info` | `debug` / `info` / `warn` / `error` |
| `WMIND_CORS_ORIGINS` | 否 | — | 开发环境允许的跨域来源，逗号分隔 |
| `WMIND_UPLOAD_MAX_MB` | 否 | `10` | 单文件上传上限（可被站点设置覆盖） |
| `WMIND_TRUSTED_PROXIES` | 否 | — | 受信任代理 IP 段，用于正确解析 `X-Forwarded-For` |

**条件必填的两个变量**（这是双数据库带来的唯一配置复杂度）：

```
WMIND_DB_DRIVER=sqlite   → 需要 WMIND_SQLITE_PATH（有默认值，通常不用配）；WMIND_DATABASE_URL 被忽略
WMIND_DB_DRIVER=postgres → 需要 WMIND_DATABASE_URL（无默认值，缺失即启动失败）；WMIND_SQLITE_PATH 被忽略
```

启动时的校验规则是「按当前 driver 只校验它需要的那个」，无关的那个即使填了也不读、不报错。这样切换 driver 时不必删除旧变量。

> **二期新增**：`WMIND_ENCRYPTION_KEY`（**必填**）——base64 编码的 32 字节密钥，用于 AES-256-GCM 加密 SMTP 密码等敏感配置。缺失时允许启动，但后台无法保存 SMTP 密码（返回 503 `ENCRYPTION_KEY_MISSING`）。一期所有可变配置都不含凭据，因此不引入该变量。

## 5. 初始化流程

### 5.1 首次启动

**SQLite（默认）**

```
docker compose up -d
   │
   ├─ api 启动（无 db 依赖）
   │    ├─ 校验必填配置（JWT_SECRET 长度；driver=sqlite 时不需要 DATABASE_URL）
   │    ├─ 打开 /data/wmind.db（不存在则创建）→ 应用 PRAGMA（WAL / busy_timeout / foreign_keys）
   │    ├─ WMIND_AUTO_MIGRATE=true → 执行 migrations/sqlite 迁移集
   │    ├─ users 表为空？
   │    │    ├─ 是 且 配置了 WMIND_ADMIN_EMAIL/PASSWORD → 创建管理员
   │    │    ├─ 是 且 未配置 → 打印一次性随机管理员密码到日志（WARN 级别）
   │    │    └─ 否 → 跳过
   │    ├─ 内嵌内置模板与主题写入数据库（按 uid 幂等 upsert，不覆盖用户改动）
   │    └─ 开始监听 8080
   └─ web 启动 → 可访问
```

**PostgreSQL（可选）**

```
docker compose -f docker-compose.postgres.yml up -d
   │
   ├─ db 启动 → healthcheck 通过
   ├─ api 启动
   │    ├─ 校验必填配置（JWT_SECRET 长度、DATABASE_URL 存在）
   │    ├─ WMIND_AUTO_MIGRATE=true → 执行 migrations/postgres 迁移集
   │    ├─ users 表为空？ → 同上分支
   │    ├─ 内嵌内置模板与主题写入数据库（按 uid 幂等 upsert）
   │    └─ 开始监听 8080
   └─ web 启动 → 可访问
```

**未配置管理员凭据时的行为**（两种方言一致）：生成随机密码并以 `WARN` 级别输出到容器日志，提示用户立即登录修改。

```bash
docker compose logs api | grep "初始管理员"
# [WARN] 初始管理员已创建 email=admin@wmind.local password=Xy7#kP2m... 请登录后立即修改密码
```

**迁移失败时的行为**：两种方言都是**启动中止**（不降级运行），日志中带出失败的文件名与版本号。SQLite 下的迁移失败通常是文件权限问题（见 §3.1 末尾的属主提示）；PostgreSQL 下通常是 DDL 权限或版本冲突。

### 5.2 开发环境

**本地开发用 SQLite，不需要 Docker，也不需要任何数据库服务**。这是选 SQLite 作为默认 driver 的主要收益：

```bash
# 后端（默认 WMIND_DB_DRIVER=sqlite，落到 ./data/wmind.db）
cd backend && go run ./cmd/server

# 前端
cd frontend && pnpm dev          # Vite，端口 5173
```

后端默认读 `./data/wmind.db`，直接 `rm data/wmind.db` 就能重置到干净状态，比清空一个 PostgreSQL 容器快得多。集成测试同样用临时 SQLite 文件（`t.TempDir()` 下一个随机文件名），因此 **CI 里跑集成测试也不需要 Docker 服务**。

**需要验证 PostgreSQL 行为时**（发布前、排查方言差异时）才起容器：

```bash
# 只起数据库，前后端仍在宿主机本地跑
docker compose -f docker-compose.postgres.yml up -d db
WMIND_DB_DRIVER=postgres \
WMIND_DATABASE_URL='postgres://wmind:change-me-please@localhost:5432/wmind?sslmode=disable' \
  go run ./cmd/server
```

| 场景 | 数据库 | 是否需 Docker |
| --- | --- | --- |
| 日常开发、写功能 | SQLite | 否 |
| 单元测试 / 集成测试 | SQLite（临时文件） | 否 |
| 发布前验证 PostgreSQL | PostgreSQL 容器 | 是（仅 `db` 服务） |
| 前端联调 | SQLite | 否 |

> **不要用「开发 SQLite / 生产 PostgreSQL」的方式长期开发**。方言差异（时间函数、并发语义、类型映射）在开发期不会暴露，上线才炸。**每个版本发布前必须在 PostgreSQL 上跑一遍完整回归**——这一条已写进 §12 发布检查清单。

### 5.3 账号找回的运维约定（一期无 SMTP）

一期不接入邮件服务，**不需要配置任何 SMTP 参数**。用户忘记密码时的运维动作是：

1. 用户通过组织内既有渠道（IM、工单、当面）联系管理员。
2. 管理员登录 → `/admin/users` → 找到该用户 → 行操作「重置密码」。
3. 选择「随机生成」或手动指定新密码 → 提交。
4. 界面一次性展示新密码，管理员复制后**线下告知用户**；关闭对话框后无法再次查看。
5. 该用户所有在线设备的会话立即失效，需用新密码重新登录。

**运维须知**：

- 一期**没有**「强制首次登录修改密码」这类设置项（`internal/settings/schema.go` 里不存在对应键）。若组织有此要求，只能用人工约定实现：管理员交付密码时提醒用户登录后立即在「个人设置」中修改。
- 登录页已内置「忘记密码请联系管理员」引导文案，无需额外配置。
- 若组织规模较大、管理员重置成为负担，可评估二期接入 SMTP（见 [09-技术决策记录](./09-技术决策记录.md) ADR-012 的归档设计，届时按 §5.3' 配置 SMTP 即可）。

> **二期配置 SMTP 的步骤（归档，一期不适用）**：后台 `/admin/settings` → 「邮件服务（SMTP）」分组 → 启用并填写主机/端口/加密方式/账号/密码/发件人 → 点「仅测试」（无需先保存）→ 测试通过后保存 → 按需在「注册与登录」分组打开「注册需要邮箱验证」。
>
> 常见服务商参数（二期参考）：腾讯企业邮 `smtp.exmail.qq.com:465 ssl`、阿里云邮件推送 `smtpdm.aliyun.com:465 ssl`、网易 163 `smtp.163.com:465 ssl`、Gmail `smtp.gmail.com:587 starttls`（需应用专用密码）、SendGrid `smtp.sendgrid.net:587 starttls`（用户名固定为 `apikey`）、自建 Postfix 内网 `:25 none`。
>
> 二期注意事项：必须设置 `site.base_url`，否则邮件中的重置链接会用请求头推断的地址；云服务器通常默认封禁出站 25 端口，请用 465/587；部分服务商要求发件人地址与认证账号一致；修改 `WMIND_ENCRYPTION_KEY` 会导致已存 SMTP 密码无法解密。

## 6. 升级与回滚

### 6.1 升级

```bash
cd deploy
git pull                       # 或修改 WMIND_VERSION

# SQLite 部署（默认）
docker compose pull
docker compose build
docker compose up -d

# PostgreSQL 部署（换成 -f 指定文件，其余步骤相同）
docker compose -f docker-compose.postgres.yml pull
docker compose -f docker-compose.postgres.yml build
docker compose -f docker-compose.postgres.yml up -d

docker compose logs -f api     # 观察迁移与启动日志
```

> 建议在 `deploy/.env` 里设 `COMPOSE_FILE=docker-compose.postgres.yml`，这样两种部署都能直接用 `docker compose up -d`，不必每次带 `-f`。SQLite 部署不要设这个变量（默认即 `docker-compose.yml`）。

**迁移兼容性原则**：所有迁移必须**向前兼容一个版本**（新增列可空、不重命名、不删除），保证滚动更新期间新旧容器可共存。破坏性变更拆成两次发布（先加新列并双写，下个版本再删旧列）。

**这条原则在 SQLite 上要更严格**，因为 SQLite 的能力更弱：

| 差异 | 对迁移的约束 |
| --- | --- |
| 无 `ALTER COLUMN` | 改列类型/约束必须走「建新表 → 拷数据 → 改名」三段式，且**必须在迁移文件内显式写全** |
| 无 `ADD CONSTRAINT` | 加外键/唯一约束同样要重建表 |
| 无并发 DDL | 迁移期间整库写锁，迁移应尽量短；大表重建前先评估耗时 |
| 事务内 DDL 支持有限 | 部分 DDL 不能回滚，失败后需人工介入（见下方回滚说明） |

**两套迁移集必须成对修改**。CI 中的 `verify-migration-parity` 检查会校验 `migrations/postgres` 与 `migrations/sqlite` 的**版本号序列完全一致**——版本号对不上直接构建失败。改一边忘改另一边，不会留到运行时才炸。

### 6.2 回滚

```bash
# 1. 切回上一个镜像标签
sed -i 's/WMIND_VERSION=.*/WMIND_VERSION=1.0.0/' .env
docker compose up -d
# PostgreSQL 部署：docker compose -f docker-compose.postgres.yml up -d

# 2. 若新版本执行过不兼容迁移，需恢复数据库（文件名见 §7.1 的产物表）
./scripts/restore.sh backups/wmind-db-20261016-020000.dump   # PostgreSQL
./scripts/restore.sh backups/wmind-db-20261016-020000.db     # SQLite
```

> **回滚前必须先备份数据库**。迁移的 down 脚本仅在开发环境使用，生产环境以「恢复备份」为回滚手段。

**SQLite 回滚的特殊风险**：SQLite 的 DDL 部分不可回滚，一个「建新表 → 拷数据 → 改名」的迁移若在中间失败，会留下一个半成品状态。因此 SQLite 部署的迁移前备份**不是建议而是必须**，且备份要落在 `data` 卷之外（卷内备份会随卷一起被替换）。建议升级脚本里把备份做成 `docker compose up -d` 的前置步骤。

## 7. 备份与恢复

脚本在 `deploy/scripts/`，两个文件，都可从任意目录调用（内部会 `cd` 到 `deploy/` 再跑 compose），`--help` 打印文件头部注释：

```
deploy/scripts/backup.sh    # 数据库 + 上传文件（+ 可选 .env）
deploy/scripts/restore.sh   # 把产物写回正在运行的部署
```

### 7.1 备份

```bash
cd /opt/wmind/deploy
./scripts/backup.sh                # 数据库 + 上传文件
./scripts/backup.sh --with-env     # 额外备份 .env（含密钥，脚本会警告）
```

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `WMIND_DB_DRIVER` | `sqlite` | 必须与 compose 里的设置一致，否则备份的卷对不上 |
| `BACKUP_DIR` | `./backups` | 输出目录（相对 `deploy/`） |
| `KEEP_DAYS` | `30` | 保留天数；**只清理本脚本产出的 `wmind-*`**，不动用户自己放进去的文件 |

产物三件（后两件视情况）：

| 文件 | 内容 |
| --- | --- |
| `wmind-db-<stamp>.db` / `.dump` | 数据库快照 |
| `wmind-uploads-<stamp>.tar.gz` | 上传的头像与导入图片 |
| `wmind-env-<stamp>.txt` | 仅 `--with-env`；权限 `600` |

**两种方言的备份机制完全不同，因此不能共用一条命令**：

| 方言 | 机制 | 是否需停机 | 一致性来源 |
| --- | --- | --- | --- |
| PostgreSQL | `pg_dump --format=custom --no-owner` | 否 | MVCC 快照 |
| SQLite | `VACUUM INTO`（走服务自带的 `wmind db backup`） | 否 | 单事务读快照，且自动合并 WAL、整理碎片 |

> **`/app/wmind db backup` 是后端 CLI 的子命令**，随 M6 实现。之所以不用镜像内的 `sqlite3` 命令行工具：alpine 基础镜像默认没有它，引入 `sqlite3` 等于多一个需要跟随升级的依赖；用自身二进制更省事，也避免版本不一致。它拒绝覆盖已存在的目标文件，所以重跑同名备份不会静默毁掉上一份。

> **绝对不要 `cp /data/wmind.db`**。运行中的数据库在 WAL 模式下，`.db` 文件本身可能不含最近的提交（数据还在 `-wal` 里），拷出来的备份会丢数据；直接拷贝还可能撞上正在写入的页而得到损坏文件。

**脚本里三个容易踩的实现细节**：

- **`docker run -v` 只接受绝对路径**。`BACKUP_DIR` 默认是 `./backups`，若直接传进 `-v`，docker 会把它当成卷名并**静默创建一个空卷**，于是备份"成功"但目录里什么都没有。脚本先 `cd` 进目录再 `pwd` 取绝对路径。
- **上传文件备份前先检查卷是否存在**。同样是上面那个机制：卷不存在时 `docker run` 会新建空卷，tar 出来一个只有 `.` 的包，看起来一切正常。脚本用 `docker volume inspect` 判断，缺了就明确警告跳过。
- **SQLite 先备份到容器内 `/data` 再 `cp` 出来，最后删临时文件**。直接从宿主侧读 `/data` 会绕过容器文件系统视图；而边 `VACUUM INTO` 边 `cp` 可能拿到半成品。

### 7.2 恢复

```bash
cd /opt/wmind/deploy
./scripts/restore.sh ./backups/wmind-db-20261021-020000.db
./scripts/restore.sh ./backups/wmind-db-20261021-020000.db ./backups/wmind-uploads-20261021-020000.tar.gz
FORCE=1 ./scripts/restore.sh ...   # 跳过交互确认（自动化用）
```

恢复是**破坏性**操作：脚本会先打印将要用哪个文件覆盖哪个方言的库，要求输入 `yes` 才继续（`FORCE=1` 跳过）。

| 方言 | 数据库 | 上传文件目标 |
| --- | --- | --- |
| PostgreSQL | `pg_restore --clean --if-exists --no-owner`（先 `stop api`） | `/data`（`wmind_uploads` 卷） |
| SQLite | 一次性 alpine 容器：`mv` 旧库 → 删 `-wal`/`-shm` → `cp` → `chown 10001:10001` | `/data/uploads`（`wmind_data` 卷） |

**SQLite 恢复的四处细节**：

- **先把现有库改名保留**（`wmind.db.before-restore`）而不是直接覆盖。恢复本身也可能恢复出一个坏库，留着旧文件才有第二条退路。
- **`chown 10001`**：`cp` 出来的文件属主是 root，不 chown 的话 `api` 启动时会因无写权限而失败（症状是 `attempt to write a readonly database`）。
- 必须**同时删掉 `-wal` / `-shm`**：它们是旧库的 WAL 日志，留着会和恢复进来的新库不匹配，SQLite 会拒绝打开或静默丢弃已提交数据。
- **恢复上传文件时目标目录是 `/data/uploads` 而不是卷根 `/data`**。SQLite 部署里数据库和上传文件共用 `data` 卷，若沿用 PostgreSQL 的写法对卷根执行 `rm -rf`，会把刚恢复好的数据库一起删掉。

脚本结束会跑一次 `compose ps` 并打印健康检查命令（`/api/v1/health/ready`）。

> **验证状态（2026-10-21）**：`bash -n` 通过；两个脚本的参数/文件/驱动校验分支逐条跑过（未知参数、驱动名写错、缺 docker、备份文件不存在、tar 不存在，退出码与文案均符合预期）；恢复流程里两段真正危险的一次性容器命令（`mv`/`rm`/`cp`/`chown`，以及 `rm -rf /data/uploads/*`）在临时目录里原样执行过，确认旧库被保留、WAL/SHM 被清除、数据库不会被上传文件那步误删。**完整的 docker 编排路径未在本机跑通**（开发机没有 Docker），需在有 Docker 的环境或 CI 里做一次真实的备份→恢复演练。

### 7.3 定时备份

宿主机 crontab：

```cron
0 2 * * * cd /opt/wmind/deploy && ./scripts/backup.sh >> /var/log/wmind-backup.log 2>&1
```

清理不用另写 cron：`backup.sh` 每次跑完会自己删掉 `KEEP_DAYS`（默认 30）天前的 `wmind-*`。要改保留期就改这一行：

```cron
0 2 * * * cd /opt/wmind/deploy && KEEP_DAYS=14 ./scripts/backup.sh >> /var/log/wmind-backup.log 2>&1
```

**备份策略建议**：

| 项 | 建议 |
| --- | --- |
| 频率 | 每日一次全量 |
| 保留 | 本地 30 天；异地/对象存储保留 90 天 |
| 验证 | 每月执行一次恢复演练到临时环境 |
| 加密 | 备份文件含用户数据，传输与存储应加密 |
| 落盘位置（SQLite） | **必须落在 `data` 卷之外**（如宿主机 `./backups`），否则卷损坏会连备份一起丢 |

> **SQLite 额外建议**：SQLite 的备份成本极低（小库通常毫秒级，且 `VACUUM INTO` 顺带整理了碎片），因此可以把频率提高到每 6 小时一次而不影响生产。若导图数量不多，这是性价比很高的一道保险。

**⚠️ 必须一并备份的还有环境变量**：

`deploy/.env` 中的密钥不在数据库备份范围内。`WMIND_JWT_SECRET` 丢失会使旧会话失效。验证器密钥及属主可查看的分享密码使用 `WMIND_2FA_ENCRYPTION_KEY` 按用途独立派生加密，未配置时从 JWT 密钥派生，因此必须备份实际使用的加密密钥。没有独立配置时，修改 JWT 密钥也会使旧密文无法解密。应在首次使用前设置独立密钥；已有数据后不要直接切换有效加密密钥。分享密码密文不可用时，原密码的 bcrypt 验证仍有效，属主可重设；旧哈希无法恢复原文。升级自动应用 `0006_share_password_ciphertext`，ZIP 备份继续要求相同数据库结构版本，升级前备份须先在对应旧版本恢复再升级。

加密密钥丢失后，用户仍可凭密码和预先保存的一次性恢复码登录、停用并重新设置验证器；同时丢失恢复码时没有自动恢复入口。数据库升级至迁移 0003 后提供 2FA；更新程序后需重启后端，账户页可自助启用。

**PostgreSQL 部署还要注意**：`.env` 里的 `POSTGRES_PASSWORD` 丢了就得改库里的密码才能恢复连接。SQLite 部署没有这一项，这是它的一个实际运维优势。

建议把 `.env` 加密后与备份一同保存，或使用密钥管理服务。**不要**把 `.env` 与数据库备份放在同一份未加密的归档里。

> **二期新增备份项**：`WMIND_ENCRYPTION_KEY`。丢失后数据库中的 SMTP 密码无法解密（**不可逆**），需在后台重新填写。一期不引入该变量，故无需备份。

## 8. 监控与日志

### 8.1 健康检查

| 端点 | 用途 | 行为 |
| --- | --- | --- |
| `GET /api/v1/health/live` | 存活探针 | 进程存活即 200，不检查依赖 |
| `GET /api/v1/health/ready` | 就绪探针 | 检查数据库连通（`SELECT 1`），失败返回 503 |

`SELECT 1` 在两种方言上都成立，因此探针实现不需要分叉。但 **SQLite 的「连通」比 PostgreSQL 更容易假阳性**：文件存在且能读，不代表能写。就绪探针在 SQLite 下额外做一次**写检查**（开一个只读事务外的 `PRAGMA quick_check` 或对临时表写一行），否则磁盘满、卷变只读、`-wal` 不可创建这些情况会让探针一直报健康，而实际所有保存操作都在失败。

### 8.2 日志

- 后端输出**结构化 JSON** 到 stdout，由 Docker 收集：

```json
{"level":"info","ts":"2026-10-16T02:30:00Z","msg":"request","method":"PUT","path":"/api/v1/maps/01JFA8","status":200,"dur_ms":42,"user":"01JFA8Z3","request_id":"01JFA8K2"}
```

- 日志级别通过 `WMIND_LOG_LEVEL` 调整。
- 容器日志轮转（`daemon.json` 或 compose `logging` 配置）：

```yaml
logging:
  driver: json-file
  options:
    max-size: "20m"
    max-file: "5"
```

### 8.3 建议的监控指标

| 指标 | 阈值告警 | 适用方言 |
| --- | --- | --- |
| `/health/ready` 连续失败 | 3 次 → 告警 | 两者 |
| 5xx 比例 | > 1% 持续 5 分钟 | 两者 |
| 接口 P95 延迟 | > 1s 持续 10 分钟 | 两者 |
| 数据库连接数 | > 池上限 80% | 仅 PostgreSQL |
| 数据库写事务等待时长 | P95 > 200ms 持续 5 分钟 | 仅 SQLite（单写者，等待直接反映写竞争） |
| SQLite 文件体积 | > 5 GB 或增长异常 | 仅 SQLite（提示该迁 PostgreSQL 了） |
| 磁盘使用率 | > 85% | 两者 |
| 容器重启次数 | 10 分钟内 > 3 次 | 两者 |

> **SQLite 的「写事务等待时长」是最该盯的指标**。SQLite 只有一个写者，一旦某个请求持写锁过久（大导入、批量导出落库），其余写请求全部排队。这条曲线持续抬头是「该换 PostgreSQL 或该优化慢写」的明确信号，比 CPU/内存更能说明问题。

可选接入：Prometheus（后端暴露 `/metrics`，二期）、Uptime Kuma、Sentry（前端错误上报）。

## 9. HTTPS 与反向代理

生产环境必须启用 HTTPS（否则 refresh token Cookie 的 `Secure` 属性会导致登录态无法保持）。

### 9.1 方案 A：外部反向代理（推荐）

由宿主机上的 Nginx / Caddy / Traefik 终止 TLS，转发到 `web` 容器的 80 端口。

```nginx
server {
    listen 443 ssl http2;
    server_name wmind.example.com;

    ssl_certificate     /etc/letsencrypt/live/wmind.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/wmind.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;   # 指向 web 容器映射端口
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

同时把 `web` 端口映射改为 `127.0.0.1:8080:80`，不对外暴露。

### 9.2 方案 B：容器内终止 TLS

在 `web` 容器挂载证书并启用 `nginx.https.conf`，把证书目录与 443 端口映射进容器。适合单机简单部署，但证书续期需自行处理。

### 9.3 代理配置注意

- 必须设置 `WMIND_TRUSTED_PROXIES`，否则限流会以代理 IP 为准导致误封。
- 必须透传 `X-Forwarded-Proto`，后端据此判断是否设置 Cookie 的 `Secure` 属性。

## 10. 安全加固清单

上线前逐项确认：

- [ ] `WMIND_JWT_SECRET` 使用随机生成的长密钥（≥ 48 字节），且未提交到版本库
- [ ] **PostgreSQL 部署**：`POSTGRES_PASSWORD` 使用强随机密码，`db` 与 `api` 不映射宿主机端口
- [ ] **SQLite 部署**：`data` 卷位于本地磁盘（非 NFS/云盘）；`api` 只跑**单实例**，未配 `deploy.replicas`
- [ ] **SQLite 部署**：备份落在 `data` 卷之外，且验证过 `VACUUM INTO` 产物可正常打开
- [ ] 启用 HTTPS，HTTP 自动 301 跳转
- [ ] 关闭注册（若为内部使用），仅管理员创建账号
- [ ] `WMIND_ADMIN_PASSWORD` 首次登录后立即修改，并从 `.env` 中移除
- [ ] 配置定时备份并验证过恢复流程
- [ ] 容器以非 root 用户运行（后端镜像已内置）
- [ ] 宿主机防火墙仅开放 80 / 443；**一期无需放通任何出站端口**（二期接入 SMTP 后再放通邮件端口）
- [ ] 定期更新基础镜像（`postgres:16-alpine`、`nginx:1.27-alpine`、`golang:1.25-alpine`）
- [ ] 检查响应头（`X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`）实际生效
- [ ] 上传目录禁止执行脚本（本地存储不通过 web 服务直接暴露，仅经 API 读取）
- [ ] 明确账号找回渠道：向用户公布管理员联系方式，确认登录页引导文案与组织实际流程一致
- [ ] 确认分享功能策略：是否允许分享、是否强制密码、单图链接上限，与组织的合规要求一致
- [ ] 若涉及敏感数据，评估是否应全局关闭分享（`share.public_link_enabled = false`）

## 11. 常见问题

| 现象 | 排查方向 |
| --- | --- |
| 启动即退出，日志显示配置校验失败 | 检查 `WMIND_JWT_SECRET` 是否 ≥ 32 字节；`WMIND_DB_DRIVER` 是否为 `sqlite` / `postgres`；`driver=postgres` 时 `WMIND_DATABASE_URL` 是否已设 |
| `api` 一直重启，日志报连接数据库失败 | **PostgreSQL**：`db` 的 healthcheck 是否通过；确认 compose 中 `depends_on` 的 `condition: service_healthy` 生效。**SQLite**：`data` 卷是否可写（见下一条） |
| 日志报 `attempt to write a readonly database` | **SQLite 专有**。`data` 卷属主不是 UID 10001（绑定挂载时最常见）→ `chown -R 10001 /opt/wmind/data`；或磁盘已满/被挂载为只读 |
| 日志报 `database is locked` / 保存偶发超时 | **SQLite 专有**。要么起了多个 `api` 副本（SQLite 只允许单实例），要么 `data` 卷落在 NFS/云盘上（文件锁不可靠）。两者都需消除 |
| 写了 `WMIND_SQLITE_PATH` 但没生效 | `WMIND_DB_DRIVER` 仍是 `postgres`；或路径父目录不存在且无权限创建 |
| 页面能打开但接口 502 | `api` 容器是否健康；`nginx.conf` 中 `proxy_pass` 的服务名是否为 `api` |
| 登录后立刻掉登录态 | 未启用 HTTPS 导致 `Secure` Cookie 被浏览器丢弃；或 `X-Forwarded-Proto` 未透传 |
| 上传图片失败，返回 413 | `nginx.conf` 的 `client_max_body_size` 与站点设置 `limit.upload_max_mb` 需同时调大 |
| 导出 PDF 中文显示为方框 | 字体未内嵌；确认「文字转路径」选项已开启 |
| 用户忘记密码找不到入口 | 一期不提供自助重置：告知用户联系管理员，管理员在 `/admin/users` 执行「重置密码」并线下告知新密码 |
| 管理员重置密码后用户仍能操作 | 重置会撤销该用户全部 refresh token；若仍可操作，检查 Access Token 是否在 15 分钟内自然过期（属预期，最长 15 分钟） |
| 分享链接打不开但确认没撤销 | 检查 `share.public_link_enabled` 是否被关闭；或 `site.base_url` 与访问域名不一致 |
| 分享页访问次数不增长 | 去重窗口为 30 分钟，同一 IP 反复刷新不会重复计数 |
| 迁移失败导致启动中止 | 查看 `api` 日志中的迁移版本号。**PostgreSQL**：确认数据库用户有 DDL 权限。**SQLite**：确认 `data` 卷可写、剩余空间充足（重建表需要约 2 倍当前库体积的临时空间） |
| 从 SQLite 换成 PostgreSQL 后数据不见了 | 预期行为——**没有自动搬迁**。改 driver 只是换了连接目标，数据不会过去。一期需逐图导出 `.wmind` 再导入（见 [09](./09-技术决策记录.md) Q-11） |
| 磁盘占满 | **PostgreSQL**：检查 `uploads` + `pgdata` 体积。**SQLite**：检查 `data` 卷（库 + 上传文件同卷），注意 `-wal` 文件在长事务下可能临时膨胀。清理回收站中的彻底删除项 |
