# Agent Note: SMTP 走后台配置，凭据用 AES-256-GCM 加密存储

Status: rejected — 需求方二次修订，一期不接入 SMTP；本文作为二期接入时的完整设计归档保留，届时由 [一期不接入邮件服务，账号找回由管理员重置承担](../../proposed/architecture/2026-10-16-wmind-no-mail-in-phase-1.md) 接管一期范围。

## Problem

需求方确认一期接入邮件服务（2026-10-16），用于「忘记密码」与「注册邮箱验证」。

这带来两个必须同时解决的问题：

1. **配置放哪**——SMTP 主机、端口、加密方式、账号、密码、发件人。放环境变量还是数据库？前者运维重，后者需要处理凭据落库的安全问题。
2. **发送怎么不拖慢接口**——SMTP 在弱网或远端限流时可能耗时数秒，而触发点（注册、找回密码）都是用户等待的同步接口。

此外还有一个容易被忽略的体验问题：SMTP 配置的失败率很高（云厂商封 25 端口、认证方式不匹配、发件人地址限制），如果没有即时验证手段，部署成本会显著上升。

## Proposal

**配置存 `settings` 表，由管理员在后台界面配置。**

| key | 说明 |
| --- | --- |
| `mail.enabled` | 总开关 |
| `mail.host` / `mail.port` / `mail.encryption` | 连接参数（`none` / `starttls` / `ssl`） |
| `mail.username` / `mail.password` | 认证凭据 |
| `mail.from_address` / `mail.from_name` | 发件人 |
| `mail.skip_tls_verify` | 仅内网自签名场景，默认关闭 |

**凭据用 AES-256-GCM 加密后落库**，存储格式 `enc:v1:<nonce>:<ciphertext>`，密钥来自环境变量 `WMIND_ENCRYPTION_KEY`（base64 的 32 字节）。

- 密钥缺失时允许启动，但后台保存 SMTP 密码返回 503 `ENCRYPTION_KEY_MISSING`。
- 解密失败（密钥变更）时把字段视为空并记 `ERROR`，后台提示「SMTP 密码已失效，请重新填写」，不阻断其他功能。
- 不以 `enc:v1:` 开头的值一律拒绝加载，避免历史明文被静默接受。

**发送必须异步**：容量 256 的带缓冲 channel + 2 个 worker goroutine。队列满时降级为同步发送并记 `WARN`。单封超时 10 秒；仅对「连接失败」重试 1 次（间隔 2 秒），认证失败不重试。

**发送失败不回滚主流程**：注册成功但邮件失败时用户仍然创建成功，响应标记 `emailSent: false` 并提示可重发。

**提供「仅测试」接口**：`POST /admin/mail/test` 接受可选的未保存 `config`，返回分阶段的失败原因（`connect` / `tls` / `auth` / `send`）。

**令牌模型**：新增 `user_tokens` 表（`purpose` ∈ `password_reset` | `email_verify`），存 SHA-256 哈希，一次性、短时效（重置 30 分钟 / 验证 24 小时）。签发新令牌时先作废该用户同用途的旧令牌。

## Alternatives considered

### 为什么 SMTP 配置不全部走环境变量？

环境变量方案与数据库解耦、密钥管理简单，是很多自托管项目的默认做法。放弃它的原因是运维摩擦：改一次 SMTP 就要改 `.env` 并重启容器，对非技术背景的部署者尤其不友好；而且与「后台可管站点设置」的产品定位不一致——既然注册开关、上传限制都能在后台改，邮件配置单独走环境变量会显得割裂。

### 为什么加密密钥不也存数据库？

省一个必填环境变量，部署更简单。放弃它的原因是这会让加密形同虚设：密钥与密文同库，任何能读到密文的人（数据库备份泄露、只读账号、误导出）同样能读到密钥。**密钥必须与密文分离存放**是加密存储的基本要求。

### 为什么不引入 KMS / Vault？

企业级密钥管理，支持轮换、审计、权限细分。放弃它的原因是这与「一条命令部署、除 PostgreSQL 外无必需外部依赖」的核心原则直接冲突。为单实例自托管产品引入一个密钥管理服务，是拿主要用户群（个人与小团队）的部署体验去换少数企业场景的能力。`secret` 模块已抽象为接口，二期若有需求可替换实现而不改调用方。

### 为什么凭据不直接明文存数据库？

实现最简单，少一套加解密代码。放弃它的原因是 SMTP 密码往往是企业邮箱主账号或带发信权限的授权码，泄露后攻击者可以以组织名义发信（钓鱼、垃圾邮件），后果远超「数据库里一条配置泄露」的直觉。加解密的实现成本只有几十行代码。

### 为什么不做成同步发送？

同步发送代码更简单，且失败能立刻反馈给用户。放弃它的原因是 SMTP 往返在弱网或远端限流时可能耗时数秒，而触发点是注册与找回密码这类用户正在等待的同步接口——把第三方服务的延迟直接转嫁给用户是不可接受的。异步化的代价是「发送失败无法立刻告知用户」，用响应中的 `emailSent` 字段与重发入口弥补。

### 为什么不提供「仅测试」接口，直接保存后让用户自己试？

少一个接口与一套 UI。放弃它的原因是 SMTP 配置失败率高且失败原因不直观（端口封禁、加密方式不匹配、认证方式、发件人限制），「保存 → 触发一次真实流程 → 看日志 → 回来改」的循环极其低效。分阶段返回失败原因（`connect` / `tls` / `auth` / `send`）能把排查时间从「翻日志猜」降到「看提示改」。

### 为什么邮件发送失败不回滚注册？

回滚能保证「注册成功 = 邮件一定发出」的强一致语义。放弃它的原因是不划算：用户账号本身是有效资源，因第三方邮件服务抖动而丢弃它，会让用户反复重试并可能触发限流。改为「保留账号 + 明确告知 + 提供重发」，把一致性问题降级为可用性问题。

## Acceptance criteria

1. 后台填入错误配置点「仅测试」时，返回可读的分阶段原因；填入正确配置后测试邮件可达。
2. 「仅测试」无需先保存即可使用表单当前值。
3. `WMIND_ENCRYPTION_KEY` 缺失时保存 SMTP 密码返回 503 `ENCRYPTION_KEY_MISSING`，其他功能正常。
4. 密钥变更后读取配置不 panic，降级为空并记录 `ERROR`，后台提示重新填写。
5. mock 邮件服务返回错误时，注册接口仍返回成功且 `emailSent: false`。
6. 忘记密码对存在与不存在的邮箱返回完全一致的响应体与状态码。
7. 重置密码成功后，同一 token 二次使用返回 401；签发新 token 后旧 token 失效。
8. `mail.enabled = false` 时，`forgot-password` 返回 503 `MAIL_NOT_CONFIGURED`，前端隐藏入口。
9. 日志中不出现邮件正文与令牌明文。
10. 连续触发 300 次发信（超出队列容量）时，系统不 panic 且降级为同步发送并记 `WARN`。

## Risks

- **`WMIND_ENCRYPTION_KEY` 丢失不可逆**：已存 SMTP 密码无法解密，需重新填写。已加入必填环境变量并在部署文档的安全加固清单与备份章节中标注「与数据库备份分开保管」。
- **异步队列是进程内实现**：多实例部署时每个实例各有队列，配置变更不会同步。缓解：配置读取走 `atomic.Pointer` 快照 + TTL 60 秒；多实例时换 Redis 队列。
- **`skip_tls_verify` 是危险的逃生口**：可能被误开在生产环境。已在设置项命名与文档中强调「仅限内网可信环境」，并在安全加固清单中加入「确认该开关处于关闭状态」的检查项。
- **邮件模板的变量转义**：站点名称、用户昵称都是用户可控内容，注入到 HTML 邮件需转义，否则可能被用于构造钓鱼内容。使用 `html/template` 自动转义，并在测试中覆盖。
- **开发环境无法验证真实发信**：本地没有 SMTP。需提供开发模式——`mail.enabled = false` 时把邮件内容打印到日志，让本地也能走通「忘记密码」流程。
