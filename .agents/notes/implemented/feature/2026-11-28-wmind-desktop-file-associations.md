# Agent Note: 桌面文件关联打开与本地来源追踪

Status: implemented

## Problem

桌面客户端已经在 `mygo.json` 中声明 `.wmind` 与 `.xmind` 文件关联，但入口没有消费 `mygo.App.OnOpenFile`，所以文件管理器启动参数、第二实例转发参数以及 Dock/任务栏拖放都会只打开首页。`.wmind` 需要直接进入可编辑页面，`.xmind` 需要在「仅查看」与「转换成 Wmind」之间由用户选择；同一个文件重复打开时不能不断创建同名副本。本地导入后的导图还需要支持在系统文件管理器中显示来源文件。

## Decision

桌面壳使用进程内 `openfiles.Queue` 统一接收文件关联事件。队列只保存绝对路径与元信息，不缓存字节；单文件读取上限与前端导入上限同为 50 MiB，路径重复打开时替换旧条目，队列满时只接受已成功入队的前 100 项。前端在 `AppLayout` 全局挂载 `OpenFileHost`，通过「立即拉取 + 可见时轮询 + 壳事件唤醒」消费队列，并严格串行处理。

`.wmind` 直接读取 JSON 并通过 `parseDocument` 归一化，创建本地导图后进入现有 `/maps/:uid` 编辑器。`.xmind` 复用既有 XMind 导入适配器与图片收尾流程，弹出使用只读 `MindMapViewer` 的完整画布；关闭查看不落库，转换操作才创建导图并记录来源。打开前按来源路径反查导图，只有确认 `MAP_NOT_FOUND` 才认为旧绑定失效，暂时性 API 错误不会静默制造副本。

桌面数据库新增独立 `map_source` 表，路径唯一映射到一个本地导图，记录文件名、大小和纳秒级修改时间。它与 `map_sync` 分离：同步状态描述本机与云端关系，来源状态描述用户文件与本机导图关系。来源记录通过桌面接口随导图列表返回，列表卡片仅在来源文件仍存在时显示「在文件夹中显示」。永久删除单张导图或清空回收站后，前端调用桌面清理接口移除来源记录。

macOS 打包配置同时声明稳定的 `app.wmind.document` 与 `org.xmind.openformat.xmind` UTI，并覆盖 `CFBundleDocumentTypes.LSItemContentTypes`，让 Finder/Dock 将拖入文件识别为应用接受的文档，而不是动态 UTI。

文件完成接口用大小受限 JSON，并通过队列原子 `Take` 防止并发重复确认。创建导图成功但确认请求失败时，当前会话不重复创建；界面提示确认未保存，服务端队列保留到下一次启动重试。

## Alternatives considered

### 直接把文件路径拼到前端启动 URL

这样实现很短，但第二实例、Dock 拖放和冷启动时序仍需各写一套；文件路径也会暴露在路由和页面历史中。统一队列让系统入口只有一条路径，且能在页面尚未就绪时保留任务。

### 把 `.xmind` 仅作为普通导入

复用导入对话框能减少组件，但它会直接创建导图，无法满足用户先查看再决定是否转换的要求。单独的只读画布保留现有查看器能力，同时避免为临时预览写数据库。

### 让来源路径进入 `map_sync`

字段改动更少，但会把本地文件身份与云端同步状态耦合，清理同步记录时可能误删来源；独立表也让路径唯一性和生命周期更容易验证。

### 每次双击都新建导图

实现简单，但重复打开同一文件会堆积副本，且「打开所在目录」无法稳定关联。来源路径唯一索引是为去重和右键操作付出的必要持久化成本。

## Consequences

桌面端的文件关联现在具备冷启动、第二实例、文件管理器打开和 Dock/任务栏拖放的统一入口；Wmind 文件直接可编辑，XMind 文件既可临时只读查看也可转换。代价是桌面专有数据库增加一张表、前端增加轮询和只读查看器，以及确认失败时需要用户重新打开文件重试。来源路径是本机绝对路径，文件移动后不会自动追踪；系统文件管理器的显示调用由壳提供，极简 Linux 环境可能只能报不支持。Web 端不启用这些接口，现有导入和分享流程保持不变。

验证包括：`cd desktop && go test ./...`、`cd web && pnpm typecheck`、前端全量 Vitest、openfiles/mapsource 单测、双击/第二实例/Dock 拖放手工验收，以及 macOS 生成包的 `Info.plist` UTI 断言。
