# Agent Note: 用户手册按源码写，不按印象写

Status: implemented

## Problem

M6 的文档交付项里，「用户使用手册」一直挂着 ⬜。缺它的代价很具体：新用户第一次
进来要问的是「怎么换结构」「导出的 PDF 为什么选不中文字」「为什么列表里的缩略图
还是旧的」，而这些问题目前只散落在代码注释和提交信息里，使用者看不到。

更麻烦的是写手册的诱惑：很多东西看起来「应该是那样」。导出的留白大概是「小/中/大」
吧？管理后台总该有个审计页吧？这些猜测一旦写进手册，用户就会去界面上找一个不
存在的下拉框，然后认定是自己不会用。

## Decision

写 `docs/10-用户使用手册.md`，并且**每一句都要能在源码里指出来**。凡是拿不准的，
去读实现，不读文档——`docs/` 里的设计文档描述的是意图，手册描述的是当前行为，
两者已经有过不一致（`docs/README` 的「50 个接口」对不上 `docs/04` §5.10 的 49）。

### 结构

15 节：登录与账号、导图列表、模板、编辑器、样式与配色、多画布/大纲/ZEN、导入、
导出、分享、回收站、个人设置、管理后台、快捷键速查、常见问题、**一期做不到的事**。

最后一节是刻意留的。把实时协作、指定用户共享、Zone/录音、概要/边界覆盖范围、演说模式、服务端导出、版本历史逐条列成表——用户不必再花时间
找入口，部署方也能据此判断要不要接住这类需求。

[Insert 内容](../../implemented/feature/2026-10-23-wmind-insert-content.md)落地后，图片、备注、标签、待办、任务、链接、附件、素材与公式进入编辑器章节，移除旧的未实现说明。

手册同步[双因素认证](../feature/2026-10-23-wmind-two-factor.md)的设置、两步登录、恢复码下载与单次消费，以及联系/边界的画布选择、统一删除和撤销；明确管理员改密不能绕过第二因子。

### 核对过程纠正了两处

1. **导出的「留白」不是无/小/中/大**，是 `PADDINGS = [0, 24, 40, 80]`，下拉里直接
   显示像素值。同时补上了漏掉的「长宽比」（跟随内容 / 16:9 / 4:3 / 1:1 / 9:16）与
   倍率的真实范围（预设 1–4，自定义 0.5–8，保留一位小数）。
2. **审计日志没有独立页面**，也不支持按时间或操作者筛选。它只在管理概览页露出
   **最近 8 条**（`adminApi.auditLogs({ page: 1, pageSize: 8 })`），完整记录只能走
   接口。原稿写的是「可以按时间与操作者筛选」。

### 顺带确认的四个实际行为

- **缩略图有 3 分钟限频**（`THUMBNAIL_MIN_INTERVAL_MS`）。没有缩略图的会立刻补；
  改过内容的要等下次打开，同一会话内最多每 3 分钟生成一次。手册必须说清这一点，
  否则「我刚改完列表还是旧图」会被当成 bug。
- **导图在回收站期间分享链接失效**，恢复后重新可用。`shares.sql` 把
  `m.deleted_at` 折进「找不到」的分支，所以表现出来和「链接被撤销」完全一样。
- **改密码会踢掉其它设备**：`ChangePassword` 从 Cookie 取当前 refresh token 并保留，
  其余全部撤销。
- **「显示备注」开关是真的在服务端剥字段**（`stripShareDocument` 递归删 `notes`），
  不是前端隐藏。但备注本来也不画在画布上——它只在导入时带进来、导出 Markdown/OPML
  时带出去，所以这个开关的可见效果接近零，隐私效果是实的。手册按这个说法写。

### 术语对齐

一律用界面上的原文：`Tab` 新建子主题、`Ctrl/⌘ + .` 折叠、ZEN 模式、画布（sheet）、
「最近」「我的分享」「个人设置」。快捷键表直接对照 `keymap.ts` 文件头那张表抄，
包括「`Shift + Tab` 不拦」和「`Alt` 组合一律不拦」这两条容易被漏掉的边界。

## Consequences

- `docs/README.md` 的索引与阅读路径加上第 10 篇；`docs/08` 的 M6「文档」行从 🟡 转 ✅。
- **写手册时发现 `feature.export_enabled` 是个死开关**：它进了设置表、进了公开配置、
  进了后台表单，但前端从来没读过它，服务端也没有导出接口可以拦（导出全在浏览器里
  做）。同一批还把编辑器里的「分享」按钮接上了 `share.public_link_enabled`——列表页
  早就按它隐藏了，编辑器漏了。两处都是三行改动，一起补上，并给 `export.mjs` 加了
  两条断言（关闭后按钮消失、重开后回来）。不加的话，手册里「管理员可以整体关闭导出」
  这句就是假的。
- 手册是**使用者视角**的，不含架构与取舍。改行为时要同步改它——这是继
  `router.go` / `docs/04` §5 / `openapi.yaml` 之后的第四处。没有测试能兜住它，
  只能靠改功能时想起它。
- 手册里「一期做不到的事」那张表是硬承诺：二期补上某一项时，这张表和对应章节
  要一起改，否则会变成「文档说没有、实际有」的另一种误导。
- 快捷键表与 `keymap.ts` 的文件头表格是两份，改动键位时要一起改。没有测试比对
  两者——`keymap.test.ts` 测的是行为，不是文案。

## Alternatives considered

- **不写手册，只留 `docs/` 01–09**：那些是需求与设计基线，读者是开发者。用户手册
  要回答的是「我现在该点哪里」，混进设计文档里两边都不好用。
- **放进根 `README.md`**：README 是「怎么把它跑起来」，用户手册是「跑起来之后怎么
  用」，受众与更新节奏都不同。README 里放一段指路即可。
- **写成 FAQ 而不是手册**：FAQ 只覆盖「已经出问题的人」，第一次使用的人仍然需要
  一条从头到尾的路径。手册里保留了一节 FAQ 承接具体疑问。
- **照着 `docs/01` 的功能清单写**：那是需求条目（FR-XXX），不是操作路径。按功能
  清单写出来的手册会变成「系统具备以下能力」的列表，用户还是不知道先点哪个。
- **用截图代替文字**：截图会随界面改版立刻过期，而且无法被搜索。这一版全文字，
  需要时再补图。
