# Agent Note: M3 验收：6 条标准的证据、两处判定口径与一条推迟到 M4 的标准

Status: implemented

## Problem

M3 的 6 条验收标准（[08 §5](../../../../docs/08-开发路线图.md)）要求的证据形式各不相同，而且有两条的**字面意思和实现语义对不上**，必须先定口径再验收：

- 第 1 条「逐项比对截图 3 与截图 4 的 UI 控件」——没有可比对的基线图，只能按控件清单逐项验证「存在 + 生效」。
- 第 4 条「无节点重叠、无连线穿越节点」——时间轴与鱼骨的连线**本来就从父节点拉到子节点中心、节点盖在线上**（`makeBone` 的注释与 `mind-map-viewer` 的分层顺序都写明了）。字面意义的「不穿越」在这两种结构里做不到，也不该做。
- 第 6 条「导出 SVG 与 XMind 视觉对比 ≤ 2%」——SVG 导出是 M4 的交付项，现在还没有。
- 另外「8 种结构」与代码里的 **9 个结构项**不是一回事（`logic-right` / `logic-left` 是同一类的镜像）。

## Decision

### 逐条证据

| # | 标准 | 证据 |
| --- | --- | --- |
| 1 | 截图 3/4 的控件全部存在且生效 | 浏览器脚本 39 项控件断言（样式面板 20 + 配色面板 19）+ 3 项生效抽查：形状 `rect → ellipse → rounded-rect` 渲染跟着变；加粗让字重 `700 → 400`；彩虹序列随开关出现/消失 |
| 2 | 10 套配色切换后分支/线条/中心主题同步改变，内容零丢失 | 每套配色断言：节点数恒为 17、标题串逐字节相等、连线有颜色；10 套的「配色指纹」（所有节点填充 + 所有连线描边）互不相同；中心主题填充 `#7B2CBF → #4F812C` |
| 3 | 手动颜色在换配色后保持 | 自定义取色写入 `#8B5CF6` → 节点变该色；切到「玫瑰」后仍是 `#8B5CF6`，且全图只有这 1 个节点是该色 |
| 4 | 8 种结构无节点重叠、无连线穿越 | 9 个结构项 × 3 项：节点数不变、两两无重叠、全部落在画布内；外加一条**图层闸门**：父子连线必须画在主题之下 |
| 5 | 全部配色对比度 ≥ 4.5:1 | `npm run check:palette`：10 套（缤纷 5 / 经典 5），最低 **4.56:1** |
| 6 | 与 XMind 导出 SVG 视觉对比 ≤ 2% | **推迟到 M4**：SVG 导出尚未实现，见下文 |

### 第 4 条的口径：「不穿越」= 不可见

`mind-map-viewer.tsx` 的分层顺序是 **边界 → 父子连线 → 关系线 → 主题 → 插件 overlay**，`makeBone` 的注释也写着「从父节点中心拉到子节点中心，节点画在连线之上，视觉上就是一根骨」。也就是说时间轴/鱼骨里连线穿过兄弟节点的包围盒是**设计**，被节点遮住，用户看到的是一条骨或一条轨道。

所以第 4 条验两件事，而不是「包围盒不相交」：

1. 9 个结构项都没有节点重叠、都落在画布内（几何正确性）。
2. **连线图层在节点图层之下**（`compareDocumentPosition`）。只要这条成立，包围盒相交就不可见；一旦有人把连线提到节点之上，这条闸门立刻红。

穿越计数仍然记下来，作为「哪天要重做这两种结构」的输入：timeline 15 处、fishbone 5 处，全部落在节点之下。

### 第 1 条：按可访问名字枚举，不按截图

控件清单从 `aria-label` / `role` 取，而不是从像素位置取。这一步顺带纠正了三处想当然：

- **结构下拉有两个**：工具栏一个、样式面板一个，指向同一个字段。断言「存在 1 个」会误判。
- **「对齐」不是下拉**，是分段按钮（`role="group"` + `aria-pressed`）。
- **彩虹序列只在开关打开时才渲染**，关着的时候断言「色板存在」必然失败——这本身是正确行为（不渲染比渲染再禁用干净）。

### 第 2 条：用「配色指纹」代替逐色断言

逐个断言「某个节点是某个颜色」会把测试绑死在调色板的第几号色上，改一次配色校准就要改一遍测试。改成每套配色取一个指纹（所有节点的 `fill` + 所有连线的 `stroke` 拼串），断言两件事：**同一套配色下节点数与标题串不变**（内容零丢失）、**10 套指纹互不相同**（配色真的生效了）。

### 第 6 条：明确推迟，而不是含糊地「基本达成」

SVG 导出排在 M4。硬要在 M3 补一个最小导出，会把 M4 的字体内嵌策略（内嵌 WOFF2 还是转路径）提前锁死——那是 M4 的核心设计点。所以这条记成**未完成**，M4 验收时补齐，届时它同时也是 M4 导出实现的第一个验收用例。

### 「8 种结构」= 8 类，9 个可选项

`logic-right` / `logic-left` 是同一套逻辑图布局的镜像（`dirX` 不同），所以文档说 8 种、选择器里 9 项。验收脚本按 9 项逐个跑，比按 8 类跑更严。

## Consequences

- 浏览器验收 **105/105**：39 项控件清单 + 3 项生效抽查 + 30 项配色逐套（10 套 × 节点数 / 文字 / 连线）+ 2 项配色汇总（指纹互不相同、中心主题跟随）+ 3 项手动颜色 + 27 项结构（9 项 × 节点数 / 重叠 / 出界）+ 1 项图层闸门。
- 对比度脚本 `npm run check:palette`：最低 4.56:1。
- 验收过程中逼出一个真 bug 并已修：**骨架屏缺 `flex-1`**——等字体时它是 `flex` 行的子元素，不拉伸就只有内容那么宽，加载指示器贴在画布左边缘（截图里一眼看出）。已并入 M3.6 的提交。
- 验收脚本仍在 `/tmp`（沿用 M2 的结论：`playwright-core` 不在 `package.json` 里，提交一个别人跑不起来的文件比不提交更糟）。断言与口径写进本笔记，M6 做正式 E2E 套件时以此为清单。
- 同步的文档：[05 §5.3.2 / §5.3.3](../../../../docs/05-前端设计.md)（分片来源、按族注入、「假就绪」、缓存作废）、[08 §5](../../../../docs/08-开发路线图.md)（M3.6 交付项与字体风险段的实测数字）、[09 ADR-016 修订横幅与 ADR-018](../../../../docs/09-技术决策记录.md)。
- 遗留：第 6 条待 M4；`Ctrl/Cmd + F` 查找仍排 M6（M2 起就挂着）。

## Alternatives considered

**按截图逐像素比对控件**：最贴近标准字面。放弃原因：没有可比对的基线图，且像素比对对「控件是否存在且生效」这件事给不出可读的失败信息——失败了也说不清是位置偏了还是功能没了。

**给时间轴/鱼骨改连线走线，绕开兄弟节点**：能让包围盒也不相交，标准字面上更漂亮。放弃原因：这两种结构的语义就是「骨」与「轨道」，绕开会把一条连续的主干拆成断开的折线，可读性反而下降；而且节点盖在线上本就是渲染层的既定分层。

**把「不穿越」放宽成「不重叠」直接不提连线**：省事。放弃原因：那就等于放弃了这条标准里真正有风险的一半——连线被误提到节点之上是很容易犯的错（加个 `z-index` 或调一下 DOM 顺序就会发生），必须有闸门。

**在 M3 顺手做一版 SVG 导出以满足第 6 条**：验收表上能全部打勾。放弃原因：导出链路（内嵌 WOFF2 / 转路径 / jsPDF 子集）与字体策略互相牵制，草率实现会把 M4 的设计提前锁死，代价远大于「一条标准延后一期」。

**把验收脚本提交进仓库并接进 CI**：可复现。放弃原因同 M2：浏览器与 `playwright-core` 不在依赖里，M6 的 E2E 任务才是它该落地的位置。
