# Agent Note: 其余结构布局：单向树、纵向树与「结构」切换

Status: implemented

## Problem

M2.7 要补 `logic-right` / `logic-left` / `tree-right` / `org-chart`。落地前要定：

- 四套算法，还是一套算法换个方向？
- org-chart 里父节点「居中于子节点」到底居中于什么？
- 连线的走向（贝塞尔控制点、折线的折法、箭头方向）由谁决定？
- 切换结构之后视野怎么办？

## Decision

### 一套带式算法，两个方向

横向树（`mindmap` / `logic-right` / `logic-left` / `tree-right`）共用 `layoutHorizontal`，
差别只在 `splitSides`：`logic-left` 全左、`logic-right` / `tree-right` 全右、
`mindmap` 按**下标奇偶**交替。

纵向树（`org-chart`）是它的转置：带从「垂直高度」换成「水平宽度」，`subtreeHeightOf`
换成 `subtreeWidthOf`，`placeSubtreeH` 换成 `placeSubtreeV`。

不复制四份的理由很实际：间距常量、折叠处理、自由主题、收尾平移这些逻辑一旦分开，
下次调间距就要改四处，而漏掉的那一处不会报错，只会「看起来有点不一样」。

### `tree-right` 只改连线样式，且改在布局层

几何与 `logic-right` 完全相同，`lineStyle` 覆盖成 `elbow` 由 `edgeLineStyle()` 统一做。

不让渲染层读 `sheet.structure`：渲染层只认识 `EdgePath`，让它去判断结构等于把「结构」
这个概念漏进渲染层——而 M2.3 定下的边界是「布局算坐标，渲染画坐标」。

### 连线走向由布局层给出，不靠几何猜

`EdgePath.orientation: 'h' | 'v'`。贝塞尔控制点、折线的折法、箭头方向全都依赖它。

用 `from.y === to.y` 之类的几何条件去猜，在斜边上会猜错：org-chart 里根到子节点
常常既横向又纵向移动，横向树里父子也可能不等高。走向是布局的产物，就该由布局说清楚。

思维导图增加独立根间距、分散端点及可选曲线控制点，仍由布局计算，见[分散端点与圆角分叉](2026-10-23-wmind-mindmap-branch-routing.md)。其余结构不采用思维导图专用几何。

### org-chart 的父节点跟着子节点走，不跟着带居中

父节点中心 = **首尾子节点中心的中点**（d3.tree 的规则）。

按带居中（父节点在自己那条水平带里居中）看起来更「对称」，但有两个问题：

1. 只有一个子节点时，父与子的中心对不齐，连线是一条斜线，看起来像连错了；
2. 兄弟子树的宽度常常相差很多（一个分支深、一个浅），按带居中会让父节点明显
   偏离自己的子节点群，视觉上像挂到了隔壁分支。

代价是这个函数必须**先排子节点、再定父节点**，所以它返回 box（连线要等父节点位置
确定后才能算）。

### 自由主题永远横向向右

即使主结构是纵向的。它们是脱离结构的东西，混进纵向树里只会更乱；而且横向排布
直接复用 `placeSubtreeH`，不需要为它们再写一套。副作用是单元测试里必须把自由主题
的连线排除在「所有连线都是纵向」的断言之外——第一次写测试时正是这么红的。

### `Side` 增加 `bottom`

折叠徽标的位置依赖 `side`：左侧分支在左边缘、右侧在右边缘、org-chart 在下沿。
徽标的 `cy` 与展开按钮的横线都跟着 `badgeY` 走，否则 org-chart 里那个减号会画在
节点的右边缘，而用户的眼睛在下方找它。

### 切换结构后重新适配视野

结构的几何差别很大：`mindmap` 横向铺开、`org-chart` 竖向铺开，同一张图换个结构
包围盒可能宽高互换。不重新适配的话，用户切完看到的是半棵跑到画布外的树。

只在 `sheet.structure` 变化时触发，**不跟着布局走**：每敲一个字都重新适配会把用户
手动缩放和平移的位置抢走。

### 工具栏只列已实现的五种

`timeline` / `fishbone` / `brace` / `tree-table` 不在下拉框里：选了会看到退回 `mindmap`
的样子，等于骗人。布局层对未实现结构的退回是显式的、只有一处（`if (structure === 'org-chart')`）。

- 已知限制：`Topic.structure`（单节点覆盖结构）没有实现，只有 sheet 级。数据结构里
  留了字段，M3 的「结构面板」再补。

  `curve` 主题下是贝塞尔，不随主题改走线策略。

## Alternatives considered

**四套独立算法**：更直白，改一个结构不会影响别的。放弃原因是横向三种只差一个分侧函数，
复制三份之后调间距要改四处，而漏掉的那一处不会报错。

**引入 d3-hierarchy**：省下轮廓合并的活，也是 docs/05 原本的写法。放弃原因是文档在
ADR 里明确不引 d3（体积换一个函数），而带式布局已经够用、可预测，出错时是「空得多
一点」而不是「重叠」。

**用 CSS transform 翻转实现 `logic-left`**：省一个分支。放弃原因是连线端点、徽标位置、
箭头方向全都要跟着翻，实际比多传一个方向参数麻烦得多。

**让渲染层根据 `sheet.structure` 决定折线还是曲线**：少一个字段。放弃原因是渲染层会
依赖 sheet，而它现在只依赖 `LayoutResult`——这条边界是 M2.3 为了「只读查看器与导出复用
同一套渲染」定下来的。

**org-chart 用「父节点在自己带里居中」**：几何上更对称。放弃原因见上（斜线、偏离子节点群）。
