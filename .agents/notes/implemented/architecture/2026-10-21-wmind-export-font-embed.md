# Agent Note: 导出的 SVG 内嵌字体分片：栅格化与独立打开都用思源

Status: implemented

## Problem

`docs/06` §3.4 记着一条「已知保真缺口（M4.11 前必须解决）」：导出的 SVG 通过
`<img>` 载入做栅格化时**拿不到父页面的 `@font-face`**，于是 PNG 与独立打开的
SVG 都用系统字体画。

验收 IE-29 把它量出来了。同一张图、同一个节点：

| 场景 | 「Keyboard Shortcuts」实测字宽 |
| --- | --- |
| 画布（思源宋体） | 134.2 |
| 独立打开的导出 SVG | 113.0 |

差 16%。这不只是「字形长得不一样」：节点框是按思源量的，导出时换成更窄的系统
字体，文字在框里显得空；反过来换成更宽的系统字体就会**溢出节点框**。IE-11 要求
「内容与画布一致」，这一条在缺口填上之前根本过不了。

## Decision

导出前把用到的字体分片读成 base64，以 `@font-face` 写进 SVG 的 `<defs><style>`。

`<img>` 载入的 SVG 不许引用**外部**资源，但 `data:` 是文档自身的一部分，不算外部
引用——这是这条路能走通的原因。

### 按「族 + 字重 + 码位」筛片，不整包嵌

思源黑体 5 个字重 × 102 片、宋体 2 × 102，全嵌 4.5 MB。三层筛选后，一张 200 节点
的中文导图只需要 **5 片、约 250 KB（base64 后 340 KB）**：

- **族**：从[实际可见文字收集器](2026-10-21-wmind-font-fallback-detection.md) `paintedRuns` 读取字体族，覆盖主题、标签、附加文字、注解和页脚；`system` 族没有 face，跳过。
- **字重**：一张图通常只用 2 个字重（正文 400 + 中心主题 800），筛掉 5 个字重里
  的另外 3 个就减少内嵌声明。字重从实际渲染的文字段取；当请求字重不在分发的静态声明中时，按 [CSS 字重匹配规则](https://www.w3.org/TR/css-fonts-4/#font-style-matching)选择已有字重，保留原始 face 声明与文字渲染字重。
- **码位**：只保留 `unicode-range` 与实际文字相交的片。

### 字重匹配先于码位筛选

精确字重存在时优先使用；缺失时按 CSS 三段顺序匹配：请求小于 400 先向下再向上；请求在 400–500 内先向上查到 500，再向下，最后查 500 以上；大于 500 先向上再向下。例如默认概要的 500 在本包中匹配 400，350 匹配 300，650 匹配 700。匹配在整族 face 上完成，之后才检查码位；匹配到的字重没有某个字时继续沿字体族回退，不能偷偷借用同族另一个字重的字形。

回归用其他主题均为 system、无品牌与日期、仅概要使用 sans 500 的场景，验证读取 400 分片且概要文字仍以 500 渲染；同时覆盖已有原生字重、上下方向、400–500 特例与匹配字重缺字的情况。

### 字体声明与文件读取分别去重

本包的可变 woff2 文件跨字重共用 URL。`pickFaces` 按 family、style、weight、URL 和原始 unicode-range 的完整声明身份去重，不能只按 URL 合并，否则正文 400 与中心主题 800 的声明会丢一条。`loadFontCss` 则按 URL 只读取一次字节，`faces` 继续返回成功读取的唯一 URL 数；多个声明仍各自写入 CSS。回归验证共享 URL 的多字重和多范围声明、完全重复声明合并、字节只读一次。

### 通配写法必须展开

`unicode-range` 里除了 `U+3002` 与 `U+4E00-9FFF`，还有 `U+4E??` 这种通配。漏解析
它的症状是「嵌了字体却还是回退」——最难查的一类，因为体积、规则数、加载状态
全都正常。

### 写回时**原样**保留 `unicode-range`

不重新格式化。浏览器按这个区间挑 face，重排一遍就可能把 `U+4E??` 展开成 256 个
单码位，把 CSS 撑大几十倍。

### 与图片内嵌同构

纯函数负责「选哪些」（`planFamilies` / `pickFaces` / `buildFontCss`），异步负责
「读字节」（`loadFontCss` + 注入的 `FontEmbedDeps`），中间用映射表接起来。这样
改一次倍率或留白不会重新下载一遍字体——依赖是「族/字重/码位」拼出来的签名。

拆分导出复用**整份文档**算出来的那份 CSS：每个分支的文字都是它的子集，覆盖面
只多不少。逐分支重算要多读几次分片，收益只是每个文件小一点，而分支图本来就要
发给别人。

## Consequences

- IE-29 从 113 变成 134.3（画布 134.2），差 0.1px；PNG 的栅格化也一并吃到同一份
  字体，IE-11 的「内容与画布一致」不再靠运气。
- 体积代价：一张 11 节点的中文图导出 SVG **418 KB**（6 条 `@font-face`）；三个
  分支拆分的 zip 972 KB。超过 512 KB 时对话框会报一句「内嵌字体 408 KB（6 个
  分片）」，半兆以下不提——内嵌是默认行为，每次都报只会变成噪音。
- `export-dialog` 分块 263.18 → 267.33 kB（gzip 90.02 → 91.48）。
- 缺字提示（IE-26）在 SVG / PNG 下**仍然显示**：内嵌的是分片，分片里本来就没有的
  字形（emoji、扩展区汉字）照样回退。只有 Markdown / OPML 才收起这句。
- 字体抓取失败时降级为「不嵌这一片」，导出继续——宁可拿到一张字不对的图，也不
  让导出整个失败。
- 同一 URL 的多个字重各自带一条 data URL 声明，导出文本可能比错误地丢掉字重声明时更大；下载、读取和分片计数仍只算一次。这样保留与应用样式表一致的离散字重，不把未分发字重误声明成可直接使用的可变轴范围。

## Alternatives considered

**按绝对数值距离选最近字重**：实现短，能覆盖多数常见字重。未采用，因为 CSS 的 400–500 区间有特殊优先级，例如缺少 400 时先找 500，再找 300，数值距离不能决定平局与方向。

**将概要硬改为 400**：可以直接消除默认概要的缺档情况。未采用，因为这会改变渲染样式，导入或其他样式仍可包含任意字重，不能修复通用导出匹配问题。

**按 URL 合并字体声明**：同一可变文件只写一份 data URL，产物更小。未采用，因为不同字重、字体族或 unicode-range 仍需要各自的 CSS 声明；只在读取字节时按 URL 去重。

**按用到的字形做子集化（docs/06 原本的方案）**：体积能小一个数量级（418 KB →
30 KB 量级）。放弃原因：子集化要解析并重写 woff2（Brotli 解压 + `glyf`/`loca`
重排 + 重新压缩），是一个独立工程；`opentype.js` 也不吃 woff2 输入。而这条路
需要新增依赖，当前环境的依赖安装被卡住（见 M4.8 PDF 的阻塞）。整片内嵌是
「体积换工期」的取舍，等依赖能进 `package.json` 时再换成子集化。

**只在 PNG 路径嵌字体，SVG 保持原样**：PNG 是「贴进文档」的主场景，SVG 用户
多半自己装字体。放弃原因：同一份 SVG 会被两条路共用（预览、栅格化、下载），
分叉意味着「预览里有字体、下载的没有」，而预览即成品是导出的底线。

**把文字转成路径**：一劳永逸，连字体都不用带。放弃原因：同样需要解析字体轮廓，
且转路径后文字不可搜索、不可复制，对「把导图贴进 PPT 再改字」的用法是倒退。

**在服务端用无头浏览器渲染**：保真度最高。放弃原因：一期没有服务端导出
（`docs/08` M4 把它列为可延后），且镜像要装 Chromium（+400 MB）。
