# Agent Note: 桌面客户端与 Web 并行交付，本地优先 + 可选云端同步

Status: implemented

## Problem

Web 版已经是一套完整的自托管服务：Go 模块化单体 + SQLite/PostgreSQL 双方言 + React SPA，编辑器内核自研（SVG 渲染、自研布局、命令栈），文档持久化是「服务端为唯一真相源 + 乐观锁版本号」，见 [autosave](2026-10-18-wmind-autosave.md) 与 [map persistence](2026-10-18-wmind-map-persistence.md)。

现在要并行交付一个桌面客户端（macOS / Windows / Linux），核心约束是：

1. **功能体验与 Web 一致**：编辑器、导入导出、主题、模板、AI、i18n 全部要对得上，不能出现「桌面版功能残缺」。
2. **任何情况下离线优先**：没有服务器也必须能用完整功能；能连服务器是增强项，不是前提。
3. **本地文件与云端文件并存**：像腾讯文档那样，导图带「本地 / 云端」身份，本地可转云端；离线改动与在线改动冲突时要能处理。
4. **AI 与备份要能离线配置**：不能依赖某个服务器管理员账号。

失败条件是：桌面版变成「需要先部署服务器才能用的浏览器壳」，或者离线改动只能整体覆盖/丢弃，或者为了桌面版把 Web 版的编辑器与 API 链路改坏。

一期已经预留了扩展点（`/api/v1` 版本化、Bearer 认证、`updated_since` + `deleted` 标记的接口设计、`user_devices` 空表、`.wmind` 与语言无关、`map_revisions` 表已建未启用），但**预留不等于实现**：`updated_since` 目前在 handler 里没有任何实现，`POST /maps` 也不接受客户端指定 uid，图片在文档里存的是 URL 而不是稳定资产标识。

## Decision

### 1. 一个 Go 二进制：mygo 窗口 + 复用现有后端 + 内嵌前端

用 [egoist/mygo](https://github.com/egoist/mygo) 做壳：窗口里是系统 WebView（WKWebView / WebView2 / WebKitGTK），加载内嵌的现有 React SPA；同一进程里跑现有 gin router，数据落在本机 SQLite。

```
mygo 窗口 ──fetch /api/v1/*──▶ 本机回环后端（现有 router/service/repository）
                                     ├─ 本地 SQLite（复用 migrations/sqlite）
                                     ├─ 本地 uploads（复用 storage.NewLocalStore）
                                     ├─ 同步引擎（新）──▶ 远端 /api/v1（JWT）
                                     ├─ 本地 AI 配置（复用 internal/ai + 本地 settings）
                                     └─ 本地备份（复用 internal/backup + folder 目标）
```

**三种形态，同一份前端与后端代码**：Web（服务器 DB，现状不变）／桌面·本地模式（本机 SQLite，免登录）／桌面·云端模式（登录自填的自托管地址，本地缓存）。

**模块布局**：桌面是嵌套模块 `backend/desktop`（`module github.com/woliubang256/wmind/backend/desktop`，Go 1.27.3）。mygo 要求 Go 1.27.3，而后端基线与发布镜像是 Go 1.26.10（[安全工具链基线](../process/2026-10-26-wmind-security-toolchain-baseline.md)）。模块路径仍落在 `backend` 之下，因此桌面可以直接复用 `backend/internal/*`——Go 的 internal 规则按导入路径前缀判定，不按 go.mod 边界，已实测可行。后端装配抽到 `backend/internal/bootstrap`，`cmd/server` 与桌面共用。

**发布**：M-D1~M-D4 一起发，不单独发纯离线版本；版本号与 `VERSION` 同号；macOS 与 Windows 首发，Linux 适配（`libwebkit2gtk-4.1` 与渲染性能）随发布后补齐。

### 2. 前端只跟本机回环后端说话（本地 BFF）

云端的 HTTP 请求由**本地 Go 后端**代发，前端永远只访问 `http://127.0.0.1:<随机端口>/api/v1/*`。因此：单源同源（无 CORS）、cookie 会话照旧、`/uploads/:key` 的私有鉴权照旧、离线与在线是同一段前端代码。

本地后端启动时生成一次性访问令牌注入页面（`window.__WMIND__`），并要求 `Origin` 匹配，避免本机其它进程读走接口。

### 3. 本地模式：单机单用户，免登录

本地库固定一个 owner 身份，由中间件注入，保留 JWT 结构以复用 `service`/`handler`，不写登录页。server 端装配抽成 `internal/bootstrap`，`cmd/server` 与 `cmd/desktop` 共用，只有配置源、DB 路径、storage 路径、身份来源不同。

### 4. 同步：三层状态 + 整文档三选项（一期）

本地新增 `map_sync` 表（`map_uid` / `remote_uid` / `base_version` / `base_hash` / `base_document` / `last_synced_at` / `state`），配合三层数据：本地工作副本 / 上次同步基线 / 远端文档。

- 拉取：`GET /maps?updated_since=&include_deleted=1`（**需实现**，一期只设计了参数）。
- 推送：`PUT /maps/{uid}` 现有 `version` 乐观锁；409 时重新拉取远端文档。
- **一期冲突处理沿用现有三选项**（保留我的 / 放弃我的 / 另存副本，见前端设计 §7.3），补「查看差异」的节点数之外的最小信息。**节点/字段级三路合并与可视化合并面板放二期**。
- 同步范围：导图文档（含多画布）、图片附件、缩略图、回收站删除状态。自定义主题与用户模板不同步。
- 图片：文档里存 URL，跨端 URL 不同，靠 `asset_map` 做 URL 重写（先上传拿远端地址再替换）。文档格式加稳定 `assetId` 要升 `formatVersion`，一期不做。

### 5. 本地/云端标识

列表页状态徽标（`本地` / `云端` / `已同步` / `有本地修改` / `同步中` / `冲突`）+ 来源筛选；本地文件可「上传到云端」（幂等，重复点击只产生一份），云端文件可「下载为本地副本」；编辑器保存状态扩展为「已保存到本机 · 未上传 / 已同步 / 有冲突」。

### 6. AI 与备份的离线配置

- AI：复用 `internal/ai`，把「管理员配置」变成「本机设置 → AI」，配置写本地 `settings` 表（同一 `ai.config` 键），API Key 由本地主密钥派生 AES-GCM 加密，出站请求由本地 Go 直接发。云端模式下默认用服务器配置，允许本机覆盖。
- 备份：复用 `internal/backup`（cron、保留 30 份、去重开关、归档含 DB 行 + uploads、恢复暂存），新增 `target = "folder"`（默认 `userData/backups`），保留 `s3` / `webdav`。

### 7. 里程碑

1. **M-D1** 壳 + 本地模式（离线全功能，无同步）：bootstrap 抽取、`cmd/desktop`、本地 SQLite/uploads/身份、三端打包。
2. **M-D2** 双模式 + 同步：登录云端、`map_sync`、增量拉取/推送、来源徽标、本地转云端、图片映射、删除状态同步。
3. **M-D3** AI/备份本地配置。
4. **M-D4** 发布：签名/公证、NSIS、.deb、自动更新 feed、CI 三端产物。
5. 二期：三路合并 + 可视化合并面板；文档资产标识；主题/模板同步。

## Alternatives considered

### 为什么不用 Electron / Tauri 做壳？

Electron 是这套方案最稳的等价物：生态成熟、WebView 就是 Chromium、行为与浏览器完全一致，几乎零适配风险。放弃它是因为要额外分发一个 Chromium（安装包与内存开销都翻倍），而且壳是 Node/Rust 生态，和本项目「前后端都是 Go」的结构多一层语言与工具链。Tauri 同理（Rust 工具链 + 系统 WebView），能力上更接近 mygo，但没有复用 Go 后端进程这条路。

### 为什么不让前端直连远端服务器？

改动最小：云端模式只要把 API base 换成远端地址即可，不需要代理层。放弃它是因为断网即整站失效、图片与缩略图的私有鉴权要跨源处理、CORS 与 cookie 策略要重配，而且**冲突合并没有落点**——三路合并必须在能同时看到本地副本与远端文档的一侧做，前端直连时这一侧只能是自己，等于把同步状态机塞进浏览器存储。

### 为什么桌面不并入后端模块（顺带把后端升到 Go 1.27.3）？

一个模块最省事：不需要为跨模块复用设计公开包边界，`cmd/server` 与 `cmd/desktop` 共享一切，构建脚本也只有一个 `go.mod`。放弃它是因为那会把 Web 侧的生产工具链从 1.26.10 抬到 1.27.3——这不是加个桌面功能该顺带改变的约束：发布镜像、CI、安全扫描基线都要跟着动，而 mygo 仍在 0.x 快速演进，未来还可能继续抬高 Go 版本要求。用嵌套模块把这份工具链需求关在桌面侧，代价只是桌面构建需要 Go 1.27.3。

### 为什么不在桌面版重写成原生 Go UI（例如 viva 路线）？

原生 UI 能给出更小的内存占用与更原生的观感，且能彻底摆脱 WebView 运行时依赖（Linux 上不用装 WebKitGTK）。放弃它是因为编辑器内核（SVG 渲染、自研布局、文本编辑与输入法、导出字体嵌入、xmind/pdf 导入）是数万行的既有资产，重写等于把「和 Web 一样的功能体验」这条硬约束变成一次全量重做，且原生框架的 Windows/Linux 后端目前都还在实验阶段。

### 为什么本地存储不用「每个导图一个 `.wmind` 文件」？

文件形态最贴近用户直觉，可被网盘/外部工具直接同步，也便于用户自己备份与版本管理。放弃它是因为同一份数据要有两种持久化（文件 + 索引库）：列表、搜索、回收站、缩略图、历史版本都需要索引，事务与迁移也要另起一套，而且会和 Web 版的「服务端 SQLite 表」形成两套真相源，同步状态机要在两者之间搬数据。用本地 SQLite 换取与 Web 版完全同构的数据层，文件导出仍是既有能力。

### 为什么一期就上三路合并 / CRDT？

三路合并是「离线改动 + 在线改动」的最优解，用户不用整体取舍，体验对标腾讯文档；CRDT（Yjs）则是它的极致形态，能顺带把实时协作一次性解决。放弃一期做的原因是成本：三路合并要在多画布、关系线、边界、概要、兄弟顺序上逐类定义规则，还要配套可视化合并面板与冲突回归测试（估 10–15 人日），而一期先把「离线可用 + 本地/云端标识 + 不丢数据」这三件事做扎实更划算。CRDT 的成本更高，且会把文档模型绑到 CRDT 的内部表示上——这与 [collaboration deferred](../../proposed/feature/2026-10-16-wmind-collaboration-deferred.md) 中「一期不让 CRDT 渗透模型层」的结论一致。

### 为什么同步引擎放在 Go 侧而不是前端？

放在前端能省掉一层代理，且合并算法天然靠近文档类型定义（TS）。放弃它是因为同步需要长期后台运行（定时拉取、断点续传、退避重试、应用关闭前的落盘），浏览器环境做不到；而且本地 SQLite 与 uploads 的读写都在 Go 侧，跨语言搬数据只会增加失败面。合并算法二期仍会写在 TS 侧，同步状态机留在 Go 侧。

## Consequences

一期落地后，桌面端与 Web 共用同一份前端与后端：断网时窗口里的一切照旧可用，
数据落在本机 SQLite；连上自托管服务器后导图带「本地 / 云端」身份，本地可上传
云端，删除状态双向同步，冲突走三选项流程且不丢数据。AI 与备份都能在本机配置，
不需要先有服务器。代价是三条：桌面壳依赖 mygo（0.x，需要单独一条 Go 1.27.3
工具链）、Linux 仍依赖系统 `libwebkit2gtk-4.1` 且渲染性能待实测、图片在文档里
仍以 URL 存储因此跨端同步要靠映射表。

验收表面（均已可观察）：

1. 断开网络（或从未配置服务器）时，新建 / 编辑 / 删除 / 回收站 / 导入导出 / 主题 / 模板 / AI 生成全部可用，重启不丢数据。
2. 本地模式首次启动不需要任何账号，不出现登录页，不产生指向远端的请求。
3. 列表页每张导图都有来源标识，可按本地/云端筛选；本地导图「上传到云端」重复点击只产生一份远端导图。
4. 云端模式下断网编辑，恢复网络后改动被推送；若远端同时被修改，走三选项冲突流程，任何一个选项都不丢数据。
5. 删除状态双向同步：本地删除后云端列表不再显示，云端恢复后本地能看到；回收站期限按真实 `deleted_at` 计算。
6. AI 配置在本机填写后断网可用（provider 不可达时有明确错误），API Key 不明文落盘、不出现在日志与导出文件里。
7. 备份可配置到本地目录，定时与手动备份都落盘，保留份数正确，恢复后数据一致。
8. 三端二进制可由一条命令交叉编译，macOS 上能出已签名的 `.app`（`.dmg` 与公证、Windows 安装包、自动更新需凭据就绪后开启，见 docs/11 §8）。
9. Web 形态不受影响：现有 e2e 套件与后端契约测试全部通过，未登录用户不因新增接口改变任何行为。

已知风险与缓解：

- **Linux 运行时与渲染性能**：桌面版依赖系统 `libwebkit2gtk-4.1`；mygo 默认关闭 WebKitGTK 的 DMA-BUF 渲染器（NVIDIA/虚拟机/容器下会白屏），退回 CPU 光栅化，SVG 重绘在 2000 节点量级可能掉帧。需要在 Debian/NVIDIA 真机压测，并按环境用 `App.SetDMABUFRenderer` 取舍。
- **图片是 URL 而不是资产标识**：跨端同步靠 URL 映射表，合并时同一图片可能在两端各上传一份，产生冗余文件与潜在失效链接。彻底解法是文档格式加 `assetId`（要升 `formatVersion`），一期先接受这个不完美。
- **双份文档模型漂移**：合并与校验分别落在 TS 与 Go 两侧，新增文档字段时容易只改一边。需要一条文档模型一致性门禁（类似现有迁移 parity 检查）。
- **壳框架处于 0.x**：mygo API 仍在快速演进（8 天内 0.7.3 → 0.8.3）。缓解方式是 `go.mod` 用 `tool` 指令锁版本，并保持桌面壳足够薄——前端始终可独立部署，必要时换壳。
- **本地保存频率与 SQLite 单写者**：离线后保存不再受网络影响，防抖可缩短，但大文档保存耗时与锁竞争需实测，否则会出现「输入卡顿」这类离线独有的问题。
- **版本与迁移同源**：本地库复用服务端迁移集，桌面版升级必须保证迁移可前滚且不破坏既有本地数据；回滚窗口需要明确（本地方案：升级前自动备份一次）。

## 远程管理界面走回环反向代理

「网站设置」在客户端窗口内加载服务器自己的管理后台（iframe），由 `desktop/internal/remoteproxy` 在回环端口提供：

- 注入 `Authorization: Bearer`，401 时刷新令牌重试一次；
- 远端 `Set-Cookie` 改写成回环 cookie（去掉 Domain），让远程页面自己的刷新流程在 iframe 里可用；
- 剥掉 `X-Frame-Options` / CSP `frame-ancestors`，禁用缓存。

**放弃的方案**：系统浏览器打开远程后台。它最省事，但用户要的是「和系统设置一样在客户端里」，跳浏览器既断开上下文，又要在浏览器里再登录一次；把远程设置表单复制进客户端则会在字段与校验上长期分叉。
