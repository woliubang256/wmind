# Agent Note: 键盘交互：键位表纯函数化、焦点作用域、几何邻接

Status: implemented

## Problem

M2.4 要把「按了键之后发生什么」接通。docs/05 §4.6.2 给了一张 20 多行的键位表，真正要定的是**结构**：

- 键位映射写在哪、以什么形式存在？
- 快捷键挂在哪个元素上？`window` 还是画布？
- 编辑态（输入框打开）怎么处理——表内判断还是整体关闭？
- 方向键到底是「几何邻接」还是「父子兄弟跳转」？两者混着用会怎样？
- 编辑中按 Tab 应该干什么？
- 输入框卸载后焦点去哪？
- 剪贴板做应用内还是系统级？
- 新建的节点在画布外怎么办？

## Decision

### 键位表是纯函数，动作是字符串

```ts
export function resolveKey(event: KeyLike): EditorAction | null
```

`EditorAction` 是字符串联合类型（`'topic.add-child'` / `'nav.parent'` / …），调用方查表派发。

这么拆的理由很实际：**键盘是交互层里最难在浏览器里验证的部分**。真要在 Playwright 里覆盖 20 个键位 × 3 种修饰键组合，脚本会长到没人愿意维护，而且每个断言都要等 DOM 更新。做成纯函数之后，`resolveKey` 的 8 个用例覆盖了全部组合（含 macOS 的 ⌘、`Ctrl+Shift+Z` 与 `Ctrl+Y` 两个重做入口、Alt 一律放行），跑完 6ms；浏览器脚本只验「表接对了没有」这一件事。

顺带的好处是键位表与命令实现解耦：将来做「自定义快捷键」只换这张表。

### 快捷键的作用域是「画布有焦点」，不是「页面存在」

监听挂在画布容器上（`tabIndex={0}`，`pointerdown` 时聚焦），不是 `window`。

挂在 `window` 上的话，用户在标题输入框里按 Tab、在搜索框里按 Backspace，都会被导图截走——用户只会描述成「输入框坏了」。用 `isTextEntryTarget` 再挡一次是第二道防线，第一道防线是「监听器根本收不到事件」。

代价是画布必须先被点一下才能用键盘。这符合直觉（和 Figma / XMind 一致），但意味着**任何让焦点离开画布的操作都必须把焦点还回来**——见下面两条。

### 编辑态整张表关掉，而不是表内加 `if`

`useHotkeys(canvasRef, actions, { enabled: !preview && editingId === null })`。

编辑态下 Esc / Enter / Shift+Enter / Tab 全部由 `<textarea>` 自己处理（它有 IME 上下文、有选区、有撤销栈）。如果键位表还活着，`Tab` 会被导图截成「新建子主题」，用户的换行与焦点移动就没了。

这跟 M2.8 的「只读 = 插件没挂载」是同一个思路：**用结构消除分支，而不是用条件消除行为**。

### 方向键是几何邻接，Ctrl+方向键才是结构跳转

两套语义并存：

- `←↑→↓`：几何邻接。往哪个方向按，选那个方向上最近的节点，跨分支是自然的。
- `Ctrl/⌘ + ←↑→↓`：父 / 第一个子 / 上一个兄弟 / 下一个兄弟。

只有结构跳转的话，用户点了一个远处的节点、想「往右边那个看看」就做不到；只有几何跳转的话，「沿一条分支逐层往下」会不断串到隔壁分支。两者都要，靠修饰键区分。

几何邻接的打分：`score = 主轴距离 + 0.5 × 侧向偏移`，但**优先在锥形内挑**（侧向偏移 ≤ 主轴距离，即偏离方向不超过 45°），锥内为空才退化到锥外（侧向权重提到 2）。

锥形不是为了好看，是为了修一个很具体的错：从根节点按 `→`，右侧所有一级分支都是候选。纯按 `主轴 + 0.5 × 侧向` 打分时，远处同高的叶子（侧向 0）会赢过近处的子节点（侧向 200），于是按一下右键直接飞到另一个分支的末端。锥形先把「明显不在那个方向」的候选排除，剩下的按距离取最近。

结构跳转里 `child` 在折叠状态下返回 `null` 而不是「第一个子节点」：折叠后子节点不在布局里，选中一个看不见的节点等于选区凭空消失。

### 编辑中按 Tab = 落字 + 建子节点

XMind 的语义是「先提交当前文字，再在这个节点下新建子节点并继续编辑」。实现上没有新加回调，而是把意图塞进提交参数：

```ts
commitTitle(id, title, { addChild?: boolean; restoreFocus?: boolean })
```

`addChild` 由 `<textarea>` 在 Tab 时置位，查看器原样转给宿主，宿主先 `rename` 再 `addChild`。查看器不需要认识命令层。

`restoreFocus` 则只在该按键**来自键盘**时为真：

- Enter / Tab 提交 → 输入框卸载 → 焦点掉到 `body` → 画布快捷键全失效。必须还回去，否则「改名之后按方向键没反应」会被当成导航坏了。
- 失焦提交（用户点了别处，比如标题输入框）→ **不能**抢焦点，否则那次点击等于没生效。

这两个分支是同一个「提交」的不同后果，用一个布尔参数区分比让宿主去猜事件来源干净。

### 新建 / 编辑时只平移不缩放，把节点挪进视野

新建的节点总挂在子树末尾，子树往右长。在已经「缩放到适应」的画布上按 Tab，输入框会正好压在右边缘外，用户看到一个半截的框。

`editingId` 变化时算一次盒子与视口的差，超出内边距就平移。**只平移不缩放**：缩放会改变用户的视野基准，连按 Tab 时画面会一直跳。

没有位移时返回原 `viewport` 对象，让 React 跳过重渲染——否则每次布局变化都会写一次视口，用户手动缩放的位置会被反复重置。

### 剪贴板只做应用内

`copyToClipboard` 存 `structuredClone(topic)`，`pasteTopicsCommand` 再按新 id 克隆一遍。

不碰系统剪贴板的理由：导图的复制单位是「子树 + 样式 + 备注」，纯文本装不下；序列化成 JSON 塞进去又会在粘贴到其他应用时露出一坨乱码。M3 做导入导出时再补 `text/html`（嵌套 `<ul>`）与 `application/x-wmind` 两个 MIME 类型。

存深拷贝而不是引用：「复制 → 改原节点 → 粘贴」应该粘出复制那一刻的内容。

## Consequences

- 单测 22 个（键位表 8 + 导航 14），全量 163 个通过。
- 浏览器验收 38 项全过：Tab/Enter/F2/Esc/Delete、几何与结构导航、Ctrl+A、Ctrl+C/X/V、Ctrl+0/1、编辑态 Tab、焦点不抢输入框、只读预览下整张表失效。
- 键位表覆盖 docs/05 §4.6.2 的全部条目，只有 `Ctrl+F`（查找主题）没接——它需要查找面板，属于 M3 的「大纲与查找」。
- `Ctrl+S` 目前只把保存状态置为「已保存」：M2.6 接上后端后，替换 `save` 这一个函数的实现即可，键位表不用动。
- 已知限制：`Ctrl+A` 选的是「同级」，不是「全部节点」——与 XMind 一致，但和多数表格应用的习惯不同，第一次用会意外。这条写进 M3 的交互说明里。
- 已知限制：没有框选与拖拽（M2.5），没有撤销提示条（M2.6 的保存状态里做）。

## Alternatives considered

**监听挂在 `window` 上**：实现最短，不用管焦点。放弃原因是输入框抢键位的 bug 会源源不断——每加一个输入框就要加一次守卫，而守卫漏一处就是「输入框里打不了字」。

**只做结构跳转（方向键 = 父子兄弟）**：心智模型简单，实现也简单。放弃原因是导图的视觉结构是二维的，用户对「右边那个」的直觉强于「第 3 个子节点」；纯结构跳转在宽扁的分支上会显得很笨。

**纯距离打分（不设锥形）**：代码更短。放弃原因是根节点按右键会飞到另一个分支的末端——这是实测出来的，不是推测。

**编辑态在键位表内加 `if (editing) return`**：少一个参数。放弃原因是每个新增键位都要记得加这个判断，而漏掉的那一个会静默吞掉用户输入。

**把 `tabIndex` 放在 `<svg>` 上**：少一层容器。放弃原因是编辑用的 `<textarea>` 是 svg 的兄弟节点（不能用 `foreignObject`），焦点在两者之间转移时 `relatedTarget` 判断会变得很绕；容器持有焦点更简单。

**用 `navigator.clipboard` 做系统剪贴板**：能跨应用粘贴。放弃原因见上（序列化格式未定、权限与降级分支多），留给 M3 与导入导出一起做。
