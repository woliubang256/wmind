# Agent Note: 按主分支拆分导出（zip）

Status: implemented

## Problem

一张大导图直接贴出去，字号会被缩到看不清。更常见的用法是「一个主分支一张图」：
每张只讲一个主题，贴进文档或 PPT 时还能自己排版。docs/06 §3.7 把这项列为待实现。

## Decision

### 每张图都带中心主题

只把分支单独画出来会丢掉「这是哪张导图的哪一支」，而中心主题往往就是上下文本身。
所以每个文件是「中心主题 + 一个主分支」，文件名取分支标题。

实现上不复制模型，而是构造一张**只挂一个分支的画布**（`isolate`）：根主题浅拷贝，
`children.attached` 只放这一支。布局是纯函数，这样每张图都能独立 `layoutMindmap`。

### 装饰要提前过滤，不能指望渲染层兜底

关系线、边界、汇总只保留**两端都还在**的那些。渲染层确实会对找不到节点的装饰
返回 `null`（`RelationshipsLayer` 里 `boxes.get()` 为 undefined 就跳过），但那是
兜底不是设计：留着它们等于把「这张图里有一条看不见的关系线」当成正常状态。

游离主题不进分支图——它们本来就不在树上。

### 重名分支加序号

两个分支都叫「一期」时，zip 里同名条目在多数解压工具里会**静默丢掉一个**（不是
报错，是少一个文件）。序号从 2 开始，读起来像「副本」而不是「编号」。

标题里的 `\ / : * ? " < > |` 会被去掉（与 `exportFileName` 同一套规则），空标题给
「未命名」。

### 出图串行，不并发

每张图都要过一次 `canvas.toBlob`。`Promise.all` 十张会让峰值内存翻十倍——而这一步
用户看得见进度条慢一点，崩掉却没法解释。

### 依赖注入，让「拆了几张、叫什么」可以在 node 里测

`exportBranches(doc, sheetId, options, ext, deps)`，`deps` 提供 `prepare`（出图前最后
加工上下文，对话框用它内联图片）与 `encode`（SVG 直接转字节，位图走栅格化）。
测试里注入 `svgEncoder` 就能断言 zip 的条目名与内容，不需要浏览器。

### zip 的中文文件名

`fflate` 的 `zipSync` 会写 UTF-8 文件名并置 `flag_bits` 的 `0x0800`。**macOS 自带的
命令行 `unzip` 不认这个标志**，`unzip -l` 显示乱码——一度以为文件坏了，用 Python
`zipfile` 读才发现名字完全正确。Finder、Windows 资源管理器都正常。

这条写进了 docs/06，免得下一个人重复怀疑。

## Consequences

- 「拆分」是对话框的界面状态（`split`），不进 `ExportOptions`：它不改变导出上下文，
  只改变**产出几个文件**。
- 拆分时 `scope` 被强制回到 `current`，否则每张图会把整份文档的所有画布拼进来。
- 只有图形格式、且主分支 ≥ 2 时才显示这个开关：只有一个分支时拆出来就是整张图。
- 尺寸闸门仍按**整张图**判，比逐张判保守。代价是极端大的导图即使拆分后每张都不大，
  也会被「太大」拦住——这类导图（单边 16384px 以上）本来就该降倍率。
- 底部尺寸在拆分时换成文件数：逐张尺寸不同，报一个数只会误导。

## Alternatives considered

- **每个分支单独成图（不含中心主题）**：图更紧凑，但丢掉上下文；文件名虽然有分支名，
  打开图的人看不出它属于哪张导图。
- **所有分支拼一张长图**：那不是「拆分」，是把问题换个形状。
- **自己写 zip 容器**：为了控制 UTF-8 标志位——查过之后发现 fflate 已经置位了，
  多写一百行只会多一处能出错的地方。
- **并发出图**：快，但内存峰值不可控，见上。
