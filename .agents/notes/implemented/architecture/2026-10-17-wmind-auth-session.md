# Agent Note: 认证会话：无状态 Access + 有状态 Refresh，轮换即撤销

Status: implemented

## Problem

M1 要实现注册 / 登录 / 刷新 / 登出 / 改密 / 当前用户。表面上照 docs/04 §5.2 的接口写就行，但下面几件事一旦选错，后面很难改：

- Access Token 用 JWT（无状态、撤销不了）还是查库（可撤销、每请求一次 IO）？
- Refresh Token 轮换后，旧令牌被再次使用时该怎么办？
- 账号被禁用，已经签发的 Access Token 怎么「立刻」失效？
- 登录失败时，怎么避免「响应时间」和「错误码」泄露账号是否存在？
- 用户名唯一性按大小写敏感还是不敏感？

## Decision

### 混合：无状态 Access + 有状态 Refresh

Access Token 是 HS256 JWT，15 分钟，基础 claims 包含 `sub`（用户 uid）、`role`、`jti`、`iat`/`nbf`/`exp`、`iss=wmind`，并允许 2FA 安全版本 `sv`。**刻意不放 status**：JWT 一旦签发就收不回来，把状态写进去等于「禁用要等 15 分钟才生效」。

Refresh Token 是 32 字节随机串（base64url），**只存 SHA-256**，7 天，落在 `refresh_tokens` 表里，所以可以撤销。刷新时轮换：旧令牌撤销、新令牌签发，两者在同一事务里完成。

### 复用检测：旧令牌再次出现 → 撤销该用户全部会话

轮换后的旧令牌若被再次使用，说明它可能被复制过（攻击者与真实用户各持一份）。此时不能只拒绝这一次请求——真实用户的令牌也可能已经在攻击者手里。策略是撤销该用户**全部** refresh token，强制重新登录。

代价是：客户端并发刷新（多个请求同时 401）会互相踩踏，后到的那个请求拿到「已撤销」→ 触发全量撤销 → 用户被踢下线。所以前端必须把并发刷新合并成一次单例 Promise（docs/08 验收标准 5）。这是有意的严格策略：宁可让前端多做一步，也不放过一次可能的令牌泄露。

### 登录：等时比较 + 先验密码再查状态

- 账号不存在时，仍然对一个固定的假哈希跑一次 bcrypt（`sync.OnceValue` 延迟计算，避免启动时多 250ms）。否则「不存在」比「密码错」快一个数量级，用响应时间就能枚举账号。
- 先校验密码，再判断 `status`。反过来的话，拿别人的邮箱随便试一个密码，就能从「403 账号已禁用」得知该账号存在且被禁用。
- 密码错误与账号不存在返回同一个 `AUTH_INVALID_CREDENTIALS`。

### 密码：bcrypt cost 12 + 长度 + 黑名单，不强制字符集

72 字节是 bcrypt 的硬上限，超过部分会被静默截断——必须在入口拒绝，否则用户以为设了更长的密码。长度按**字符**判断（中文密码 8 个字合规），上限按**字节**判断。

不要求大小写+符号组合：那类规则会把人逼成 `Password1!`。改为内置常见弱密码表（当前约 120 条，Top-1000 的其余部分作为纯数据补丁后续补齐）。

### 用户状态缓存 60 秒 + 主动失效

`Authenticate` 每次都要知道用户是否被禁用，但每请求一次查库在 SQLite 上会排队。折中是 60 秒缓存，且禁用/删除/改角色时由管理端调用 `InvalidateUser(uid)`——缓存只是削峰，不是「允许 60 秒的越权窗口」。

缓存返回副本而不是指针：调用方会把用户挂到请求上下文，共享指针会让一次意外的字段赋值污染所有并发请求。缓存条目上限 4096，超过时清理过期项，避免长期运行的实例把每个登录过的用户都留在内存里。

### Cookie：HttpOnly + SameSite=Lax + Path=/api/v1/auth

Web 端的刷新令牌走 Cookie，`Secure` 在生产为 true，`Path` 收窄到 `/api/v1/auth`——浏览器不会把它带到别的请求上。请求体里的 `refreshToken` 只在没有 Cookie 时采用（客户端 App 用），Cookie 优先：CSRF 场景下不该让攻击者用 body 覆盖浏览器里的会话。

刷新失败时顺手清 Cookie，避免前端拿着死 Cookie 反复重试。

### 迁移 0002：`lower(username)` 唯一索引

0001 只有 `uq_users_email_lower`，用户名是大小写敏感的 `UNIQUE`。但查询走 `lower(username)`，于是「Alice」与「alice」可以并存，而按 `alice` 查询会返回其中任意一个。补一个与邮箱对称的部分唯一索引（`WHERE deleted_at IS NULL`，与软删除改名逻辑一致）。

[双因素认证](../feature/2026-10-23-wmind-two-factor.md)增加密码后的短期挑战及安全版本，启停 2FA 时旧访问令牌也立即失效；部分替代原先访问令牌不可撤销的前提。密码、Cookie、刷新轮换和状态缓存策略保持本篇的决定。

[登录密码信封](2026-10-24-wmind-login-encryption.md)增加密码验证前的公钥加密与共享一次性挑战；HTTP 登录只接受密文信封，解密后继续使用本篇的 bcrypt、账号状态、会话及 2FA 规则。传输挑战与密码验证后的第二因子挑战相互独立，不能代替 HTTPS。

## Alternatives considered

- **Access Token 也存库、每请求查一次** — 撤销立即生效，无需缓存。被否是因为它把认证变成每请求一次数据库往返；SQLite 单写者模型下，这会让并发登录/刷新直接排队。
- **Access Token 里带 status** — 省掉状态查询。被否是因为「禁用」需要等令牌过期才生效，而禁用恰恰是管理员最需要立即生效的操作。
- **刷新令牌不轮换（长期有效，只在登出时撤销）** — 实现最简单，也不会出现并发刷新踩踏。被否是因为令牌一旦泄露就长期可用，且没有任何检测手段。
- **复用检测只拒绝当前请求，不撤销全部** — 对用户更友好（并发刷新不会掉线）。被否是因为它默认「泄露没发生」，而检测到复用的前提恰恰是「泄露可能已经发生」。
- **密码用 argon2id** — 更现代，抗 GPU 更好。被否是因为 bcrypt 是 Go 标准扩展库直接支持、部署方无需额外依赖，而 docs/04 已定 bcrypt cost 12；换算法属于安全策略变更，应单独决策而不是夹在 M1 里。
- **用户名保持大小写敏感** — 不改迁移。被否是因为查询已经是 `lower()`，索引与查询不一致会产生「能注册但登录到别人账号」这类极难复现的 bug。

## Consequences

- **收益**：禁用账号、删除用户、改密后踢其它设备都能立即生效；令牌泄露有检测手段。
- **收益**：登录接口不泄露账号存在性，也不泄露禁用状态。
- **代价**：并发刷新必须由前端合并，否则用户会被踢下线。这条在前端实现里是硬要求，不是优化项。
- **代价**：`refresh_tokens` 会持续增长；`DeleteExpired` 方法已就位，但调度（后台任务）留到 M6 的运维任务。
- **已知上限**：弱密码表只有约 120 条，不是文档里写的 Top-1000。补齐是纯数据改动，不影响接口。
- **已知上限**：种子管理员只在 `users` 表为空时创建，且密码不合规时只记 WARN 不阻止启动——运维需要看启动日志确认。
