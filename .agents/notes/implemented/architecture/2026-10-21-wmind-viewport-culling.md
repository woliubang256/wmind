# Agent Note: 视口裁剪与面板降优先级

Status: implemented

## Problem

M6 的性能那一格在草图上写着「视口裁剪、Web Worker 布局、降级渲染、虚拟滚动」。
先量了一遍才发现该做的只有第一项：

`/maps/stress` 是 2001 个节点的压测文档。在生产构建下按一次方向键，中位
**22.6ms**、p90 26.1ms——比一帧（16.6ms）多出一截，按住方向键连走时会明显
发涩。滚轮缩放反而满帧，因为缩放只改 `<g transform>` 一个属性。

原因是选中变化会让 `TopicsLayer` 重新创建**全部 2001 个**节点的 React 元素。
`React.memo` 能拦住 DOM 更新，拦不住「2001 个元素逐个 diff」这件事本身。

所以这一格真正要做的是：**少创建元素**，而不是把布局挪进 Worker。

## Decision

### 裁剪放在渲染层，按需开启

`editor/viewer/cull.ts` 提供三个纯函数（`expandRect` / `cullBoxes` /
`cullEdges`）和一个阈值 `CULL_THRESHOLD = 400`。`TopicsLayer` 与 `EdgesLayer`
接一个 `cullRect`，`null` 表示不裁剪。

- **阈值 400 而不是 2000**：几百个节点的一次全量 diff 还在 10ms 以内，感觉不
  出来；而裁剪本身要多一次全量遍历，小图上反而亏。草图里的 2000 是拍脑袋的。
- **余量「半屏 + 240 世界单位」**：贴着视口边缘裁，快速拖动会在边上看到节点
  「长出来」。固定值兜住缩放到很大时比例余量不够的情况。
- **选中的与被编辑的节点无条件保留**。`aria-activedescendant` 指向一个不存在
  的 id 时读屏会静默失声；而且键盘把选区移出视口之后，元素一旦被裁掉就再没有
  任何痕迹。这不是性能问题，是可用性问题。
- **连线用包围盒近似求交**，不做精确贝塞尔求交：线都很短，近似足够；代价是
  边缘可能多画几条其实不相交的线——只多不省，不会缺。

容器尺寸用 `ResizeObserver` 量一次存进 state，而不是渲染时读
`getBoundingClientRect()`：后者在渲染期读布局会触发 React 告警，而且量到的是
上一帧的尺寸。只在尺寸变化时更新，平移缩放不触发。

### 面板的显示降一档优先级

量到「收起右侧面板后按键从 25ms 回到单帧 16.9ms」之后才知道，剩余开销几乎全
在面板上——那是一棵几十个控件的树，每次选中变化都整棵重画，而用户按方向键想看
的是画布上的选中框。

所以 `panelStyle` 改用 `useDeferredValue(selection)` 算。**只降级显示，
`panelTargets` 仍是即时选区**：否则「选中 A 后立刻点色块」会作用到上一帧的 B
上，那是个静默的数据错误。

### 刻意不做 Web Worker 布局与降级渲染

2000 节点的 `layoutMindmap` 实测 27–30ms。而 `LayoutResult` 是
`Map<string, NodeBox>` + `Map<string, TopicSize>` + `Map<string, ComputedStyle>`
+ 边数组——2000 个节点来回结构化克隆的开销与这 30ms 同量级，很可能得不偿失。
首屏 1.5s 里布局只占 2%，大头是网络、JS 解析与字体分片。

降级渲染（关阴影/渐变）也没有可关的东西：当前主题系统里节点本来就不画阴影与
渐变。这条是从草图继承下来的，留着当备忘。

### 数字必须来自生产构建

dev 构建是双渲染 + 未压缩，同一个操作慢 1.5~2 倍。第一版在 dev 上量到
「53ms → 26ms」，看起来提升一倍；换成生产构建之后真相是「22.6ms → 16.5ms，
即额外开销归零」。结论一样（该做），但幅度差得很远，拿 dev 的数字写进文档会
误导下一个人。

为了量生产包，写了一个 40 行的静态服务器（`/tmp/wmind-accept/serve-prod.mjs`）：
发文件 + 把 `/api` `/uploads` 转给 8080 + SPA 回退。`vite preview` 不套用
`server.proxy`，所以不能直接用。

## Consequences

- **裁剪只在超过 400 节点时生效**，所以普通导图的渲染路径与之前完全一样——
  这也是回归测试（分享 24、模板 27、多画布 25、无障碍 23）能全部通过的原因。
- **`TopicsLayer` 多接两个可选 prop**（`cullRect` / `keep`），导出路径不传，
  仍然渲染全部。
- **`aria-activedescendant` 依赖 `keep`**：如果将来有人给裁剪加「更激进的
  阈值」而忘了保留选中节点，读屏会在选中离开视口时静默失声。这条在 `cull.ts`
  的注释和 `cull.test.ts` 里各写了一遍。
- **`useDeferredValue` 让面板晚一帧**，理论上存在「面板还显示上一个节点样式」
  的一帧。可接受：它只是显示，动作走的是即时选区。
- 首屏 1542ms 仍然高于 1.5s 的预算，但那是 `/maps/stress`（2000 节点 + 本地
  生成文档）；普通导图远低于这个数。这条预算的真实口径（首屏到可交互）还没在
  真机上量过，属于 M6「部署」那一格的事。

## Alternatives considered

- **Web Worker 布局**：27–30ms 的收益，换来跨线程克隆四张 Map 的成本。否决，
  理由记在 docs/05 §8，等有 1 万节点的真实需求再做。
- **虚拟滚动**：SVG 里没有「滚动容器」，坐标是绝对的，虚拟滚动等于自己实现
  裁剪——就是现在这个方案。
- **只对连线做裁剪**：连线是 2000 条 `<path>`，比节点便宜得多，裁它收益小。
- **把 `TopicNode` 的 memo 比较做得更细**：`React.memo` 已经拦住了 DOM 更新，
  瓶颈在「创建 2001 个元素」而不是「更新」，细化比较器不解决问题。
- **给面板整个加 `React.memo`**：props 里有每次新建的数组与回调，加了也拦不住；
  要拦就得把回调全部稳定化，改动面比 `useDeferredValue` 大得多。
- **阈值取 2000（照抄草图）**：500 节点的图每次按键也要多花几毫秒，没理由不给
  它裁。
