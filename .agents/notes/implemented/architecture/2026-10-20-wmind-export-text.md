# Agent Note: Markdown / OPML 导出（M4.9）

Status: implemented

## Problem

M4.6 / M4.7 解决了「导出一张图」。但导图的内容本身常常要进别的工具：写周报要贴
进 Markdown 文档、导入 OmniOutliner 或幕布要 OPML、丢进代码仓库要能被 diff 的
纯文本。这些场景里 SVG / PNG 都不合适——前者没人愿意看源码，后者根本不可编辑。

难点不在「把树写成文本」，而在**写出来的文本能被读回来**。IE-16 / IE-17 的验收
标准是：导出后重新导入，层级与文字不变。这里有三处会踩：

1. **根主题会丢**。本项目 Markdown 导入器的模式判定是 `headingCount >= 2 &&
   headingCount >= listCount / 2`。如果导出全用列表，文件只有一个 `#`（或者
   一个都没有），导入器判成 list 模式，根主题被文件名取代——导出的树凭空少一层。
2. **层级有上限**。全用标题的话，Markdown 只有 6 级，第 7 层开始没法表示。
3. **行首字符是语法**。标题 `# 不是标题` 写进列表会变成嵌套标题，`- 不是列表`
   会变成下一层列表项。

## Decision

### 两级标题 + 无限层列表

根用 `#`、一级分支用 `##`、第 2 层往下用 2 空格缩进的 `- `。这正好卡在两种极端
之间：标题数 ≥ 2 让导入器走 heading 模式（根保住），列表层级没有 6 级上限。
输出形状与 docs/06 §3.6 的示例逐字一致，`text.test.ts` 里有一条用例直接钉住它。

依赖标题数量保住结构的假设由[混合标题保留修复](../bug-fix/2026-10-25-wmind-markdown-heading-preservation.md)纠正：少量标题与大量列表仍会触发旧公式，原往返样本未覆盖这个分布。当前导入只看真实标题令牌，输出格式保留为两级标题加列表，理由是 Markdown 可读性和无限列表深度。

### 转义只在行首，且导入器负责还原

导出给行首的 `#` `-` `*` `+` `>` 加一个反斜杠；`import/markdown.ts` 的
`unescapeLineStart` 在 `parseInline` 里还原行首那一个。只处理行首：Markdown 里
也只有行首这几个字符会被误读，标题中间的 `\`（`路径 C:\temp`）是用户自己写的，
动了就是新的 bug。

顺序上先剥强调再还原转义。反过来的话 `\*a\*b` 会先变成 `*a*b`，然后被当成强调
吃掉。

改导入器不是为了迁就自己导出的特殊处理：`\#` 读成 `#` 本来就是 CommonMark 的
行为，我们只是之前没实现。

### 顺带修掉的两个导入器缺陷

做往返验证时，浏览器里导入一份 `# 根 / ## 分支 / - 甲 / - 乙` 的 Markdown，
`乙` 变成了 `甲` 的子节点——整棵树凭空多一层。原因在 `buildHeadingMode` 的
item 分支：`listStack` 弹空之后拿 `current` 兜底，而 `current` 是「备注/代码块
该挂哪」的游标，此刻正好是上一个列表项。改成回落到 `headingStack` 顶（它始终
至少有根主题）。这条以前没有用例覆盖，现在补了「同级列表项是兄弟」与「缩进
更深的仍是子节点」两条回归。

另一个是 OPML 的 `_labels`：导出写标签、导入不读，往返静默丢掉标签，而 Markdown
那边是保住的。两个格式对同一个字段一个丢一个留，比丢字段本身更难解释。既然
`opml.ts` 已经在读 `_note` / `_link` / `_status` / `_icon`，`_labels` 与
`_collapse` 就按同一套下划线扩展补上（逗号分隔，空白项丢弃）。

### 换行压成空格，而不是保留

XMind 的富文本标题可能带 `\n`。Markdown 里一个 `\n` 就是新的一行，读回来会多出
一个节点——结构性的破坏，比丢一个换行严重得多。所以 `escapeLineStart` 顺手把
`\s*\n\s*` 压成一个空格，代价是这一条用例没法断言「文字完全不变」，只能断言
「还是一个节点」（用例里直接钉住读回来的轮廓）。

### 备注用 `>` 引用块，缩进跟随层级

导入器只把 `quote` 令牌挂回当前节点（`appendNotes`），表格和代码块都会被降级成
子主题。所以备注必须写成引用块，且缩进要跟节点层级对齐，否则会挂到隔壁节点上。

### OPML 用 `_note` / `_labels` / `_collapse`

OPML 2.0 没有备注、标签、折叠的标准字段。下划线前缀是 OmniOutliner 等工具的
事实惯例，不认识它的工具会直接忽略——比自定义一个 `<wmind:note>` 命名空间
兼容性好得多。

游离主题挂在 `body` 顶层、根主题之后。塞进根主题下面等于凭空改结构，而 OPML
本来就允许 `body` 有多个 `outline`。

### 对话框：收起无效选项，预览换成文本

文本格式下倍率、留白、透明背景、边框、日期、品牌全部不适用。禁用一屏控件不如
整体收起，配一句话说清丢的是什么。预览也从 `<img>` 换成等宽 `<pre>`——这两种
格式没有「画出来」的样子，画一张图是骗人。

顺带两条必要的短路：

- `collectImageSources` 直接返回空数组。文本里没有内嵌图片，抓一遍纯属浪费带宽。
- 不构建 SVG。一张巨型导图每次改选项都重算 `buildExportSvg` + `svgDataUrl`
  要几百毫秒，而这些字节最后会被丢掉。
- 尺寸闸门只对 PNG / JPEG 生效。否则一张巨型导图会被判成 `too-large` 并把「下载」
  按钮禁掉——用户只是想导个 Markdown。

## Consequences

- 文本格式**只导当前画布**。两个序列化器都是单画布语义，多画布拼进一个文件会让
  根主题变成两个。对话框在有多张画布时明说这一点，而不是让「全部画布」静默失效。
- OPML 的 `_labels` 用逗号分隔，所以**标签里含逗号会被拆成两个**。写转义规则
  （`\,`）的收益不抵复杂度，这个边界先记在这里。
- 样式必然丢失，这是格式本身的性质，不是实现缺陷。对话框有常驻提示条。
- 图片在 Markdown 里写成 `![](src)`，但相对路径的图片**不会被上传**：用户只拖
  进来一个 `.md`，旁边的 `img/` 目录没跟过来。这条与导入侧的既有行为一致。
- `ExportOptions['format']` 从三个值扩到五个，`isTextFormat` 是唯一的判定入口。
  以后加 PDF 时它仍是图形路径，不需要动这里。

## Alternatives considered

- **全用标题**：实现最简单，但 6 级就截断。真实导图 7 层以上很常见。
- **全用列表**：导入器会判成 list 模式，根主题退化成文件名。为了让根留住而给
  导入器加一个「首行是 `#` 就用它当根」的特例——这会让所有用户手写的 Markdown
  笔记的行为跟着变，为一个导出场景改所有人的导入，不划算。
- **把多画布拼成一个 Markdown 文件**：每张画布一个 `#`，导入时会被读成兄弟根，
  结构已经不是原来的了。宁可明确只导一张。
- **导出的同时写一份 YAML front matter 存样式**：导入器不认，别的工具也不认，
  等于把「不承载样式」这个事实藏起来。不如在对话框里说清楚。
- **OPML 用自定义命名空间存折叠与备注**：别的工具会整段丢掉，而我们自己的导入器
  也要多写一条解析分支，收益只有一个「语义更正确」。
