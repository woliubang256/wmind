# Agent Note: 后台备份 ZIP 格式与维护闸门

Status: implemented

## Problem

后台需要一个数据库与上传文件统一的归档格式。恢复入口接收管理员上传的文件，必须在碰到业务数据前拒绝路径穿越、损坏、类型或版本不匹配的归档。原有 CLI 和部署脚本仍保留独立运维价值。

## Decision

`internal/backup` 提供版本 1 ZIP 归档，manifest 记录时间、数据库类型、迁移版本、用途隔离的密钥指纹和每个成员的大小/SHA-256。只接受固定应用表的 JSONL 文件与 uploads 下的普通文件。解压仅写入新的私有暂存目录，拒绝目录穿越、Windows 路径、特殊文件、重复成员、未知数据库表、缺失表、校验和错误；压缩文件上限 2 GiB、解压总量 8 GiB、成员数 100000。

`domain.BackupRepository` 定义一致导出、格式校验与事务恢复契约。`internal/backupformat` 保存固定表顺序和有界逐行格式，SQL 标识符不从归档接受。文件安装回调在数据库提交之前执行，提交失败调用文件撤回函数。

`backup.Gate` 在独占维护前拒绝新业务请求并排空已进入的请求；恢复或捕获完成释放闸门。此原语只约束单进程，不能宣称具备跨实例维护互斥。

SQLite 与 PostgreSQL 适配器采用固定表 JSONL 导出，分别使用读事务和 repeatable-read 事务。恢复逐行校验列集合、按外键逆序清空和正序插入；事务内轮换所有用户的 SessionVersion，清除刷新令牌、一次性令牌与待验证挑战，保留已启用 2FA 的密文。PostgreSQL 自增序列只前移，不在可回滚事务里降低非事务性序列。恢复要求至少一个有效管理员。

这套核心是后台工作流的基础，调度与页面在独立单元接入。[原有 CLI/脚本](2026-10-21-wmind-backup-restore.md) 的物理快照和分离归档决定仍成立；后台 ZIP 不取代其格式。

## Alternatives considered

- 原生数据库文件与 SQL：复用现有运维工具最直接，但热恢复需要重新装配连接或额外客户端，且上传 SQL 不适合作为受限后台格式；后台使用固定表 JSONL。
- 仅依赖 ZIP CRC：零额外格式开销，但不能校验完整成员集合和数据库兼容性；增加 manifest。
- 边解压边覆盖 uploads：省暂存空间，但校验失败已毁掉当前文件；只向私有暂存目录解包。

## Consequences

归档与环境密钥分开保管；跨服务器需原有效密钥。逻辑格式限制恢复到相同数据库类型和迁移版本。闸门需要路由和作业装配后才覆盖真实请求。数据库与文件系统没有跨介质崩溃原子性，后续恢复工作流必须保留恢复前归档。

验证使用隔离目录，覆盖 Unicode 文件名往返、兼容性拒绝、重复成员、路径穿越、损坏校验和、符号链接、临时上传过滤及在途请求排空。

数据库契约测试覆盖大于 2^53 的 ID、Unicode 内容、文件安装失败回滚、非法外键回滚和取消；SQLite 实库通过。PostgreSQL 使用独立 WMIND_TEST_BACKUP_DATABASE_URL，未配置时明确跳过，不能把编译通过当作实库验证。
