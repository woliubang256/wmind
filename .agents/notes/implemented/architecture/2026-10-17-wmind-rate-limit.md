# Agent Note: 限流与登录锁定：内存令牌桶 + IP×账号维度

Status: implemented

## Problem

docs/04 §3.1 要求认证接口限流（注册 3 次/小时、刷新 30 次/分钟、登录 5 次/分钟且连续失败 5 次锁 15 分钟），但没规定两件会影响实现形态的事：

- 限流状态放哪：进程内存、Redis，还是数据库表？
- 登录的「IP + 用户名」维度怎么拿：中间件读不到请求体里的账号。

## Decision

### 限流：每键一个令牌桶，进程内存，LRU 淘汰

`middleware.RateLimiter` 内部是 `map[key]*rate.Limiter`，用 `golang.org/x/time/rate` 的桶做实际计算，自己负责建桶、淘汰与并发。

- 参数形式是「每 interval 多少次 + burst」，而不是「每秒多少」：文档写的是「3 次/小时」，直接按小时表达，避免调用点自己换算成 0.00083/s 这种不可读的数字。
- 桶的空闲淘汰：超过 `idleTTL`（10 分钟）没访问的键会被清掉；键数达到上限（10 万）时，先清空闲项，仍超限则清掉一半——这是防内存无限增长，不是精确 LRU。
- 键由调用方决定：注册/刷新按 IP（`ClientIPKey`），登录按「IP|账号」。

### 登录限流放在 handler，锁定放在 service

登录的限流维度包含账号，而账号在请求体里。中间件要拿到它就得先读一遍 body 再塞回去（`io.NopCloser` 重建），任何一处忘了恢复，后面的 handler 就读到空 body——这类 bug 只在特定路由上出现，很难查。所以：

- **限流**（每次尝试都计数）在 handler 里做，body 已经解析完，键是 `c.ClientIP() + "|" + lower(identifier)`。
- **锁定**（连续失败计数）在 service 里做，因为它是认证策略而不是 HTTP 策略，且需要与「登录成功」共享状态。

### 锁定：5 次失败锁 15 分钟，锁定期内连正确密码也拒绝

- 键同样是 `IP|账号`：只按 IP 会让同一间办公室的人互相连坐，只按账号则换 IP 就能绕过。
- 登录成功清零计数：否则「一天里断断续续错 5 次」也会被锁。
- 锁定期内**不验密码直接拒绝**：如果还验，攻击者就能从「密码错误」与「账号禁用」的差异继续探测，锁定只剩延迟作用。
- 第 5 次失败直接返回 `AUTH_TOO_MANY_ATTEMPTS`（429）+ `details.retryAfter`，而不是先给 401 再在下一次才 429——用户需要知道「现在该等」而不是「密码又错了」。

### 多实例的已知局限

两套状态都在进程内存里。多实例部署时每个实例各算各的，实际配额变成 N 倍，锁定也可以靠「换实例」绕过。这与 docs/04 「多实例时替换为 Redis 实现」的约定一致；替换点只有 `RateLimiter.Allow` 与 `LoginThrottle.Locked/Fail/Reset`，调用方无感。

## Alternatives considered

- **限流状态入库（新表）** — 跨实例一致、重启不丢。被否是因为限流是每请求一次写，SQLite 单写者模型下会直接把认证接口变成串行队列；为了一个可以接受的近似值付出写放大不值得。
- **用 `redis` 客户端 + 固定窗口** — 更接近生产级方案。被否是因为一期部署是「一条命令、零外部依赖」，引入 Redis 与产品前提冲突；接口已留好替换点。
- **中间件解析 body 拿账号** — 让登录限流与其它接口统一走中间件。被否是因为 body 读一次就要重建，漏掉一处就静默失效；handler 里做只多三行。
- **只按 IP 锁定** — 实现最简单。被否是因为 NAT 后面的用户会互相锁死，而这是最常见的部署形态。
- **锁定用 `users` 表加 `failed_attempts` / `locked_until` 列** — 持久化且跨实例。被否是因为它把「安全策略」写进了用户数据模型，每次失败都变成一次用户行更新（写冲突、审计噪声），而失败次数本身没有长期价值。

## Consequences

- **收益**：注册/刷新/登录都有可配置配额，超限返回 429 + `Retry-After`，前端可以直接倒计时。
- **收益**：锁定不会误伤同 IP 的其它账号，也不会因为换用户名绕过。
- **代价**：重启会清空锁定与配额；多实例下配额是 N 倍。
- **工具链约束**：`x/time v0.16.0` 要求 Go 1.26；[安全工具链基线](../process/2026-10-26-wmind-security-toolchain-baseline.md)已将 go.mod 与构建镜像同步提升到 Go 1.26.10，取消 M0 为维持 Go 1.25 而钉住 v0.15.0 的限制。后续升级仍须核对模块声明与镜像工具链一致。
- **已知上限**：`maxKeys` 的淘汰策略是「清掉一半」，极端情况下会误伤活跃键，表现为偶发的配额重置。这个取舍是为了让内存有硬上限。

## Verification

- `go test ./internal/httpapi/middleware/...`：burst 用尽后拒绝、`retryAfter` 约等于 1/rate、不同键互不影响、时间推进后配额恢复、非法构造参数不 panic、Bearer 头解析大小写与空值。
- `go test ./internal/service/...`：5 次失败锁定、锁定期内正确密码被拒、换 IP 不受影响、到期恢复、成功登录清零计数。
- `go test ./internal/httpapi/...`：HTTP 层注册第 4 次 429 `RATE_LIMITED` 且带 `retryAfter`；登录第 5 次 429 `AUTH_TOO_MANY_ATTEMPTS`。
