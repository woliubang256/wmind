# Agent Note: 字体回退检测（M4 验收第 9 条）

Status: implemented

## Problem

导出是发给别人的最后一步。如果某个字在本机用了系统字体渲染，在别人的机器上可能
长成另一副样子、或者干脆是豆腐块——而用户完全不知道为什么。

M4 的验收标准第 9 条要求「含生僻字 / emoji 的导图导出时，给出『N 个字符使用了
系统字体』提示，不静默出图」。难点不在提示，在**怎么知道缺字**：

- `document.fonts.check(font, text)` 只回答「这个字体加载了没」。对没有字形的码位
  它照样返回 true——用它判覆盖率永远得出「全都覆盖」，而这正是要发现的问题。
- 字体是**按 unicode-range 切片**分发的（M3.6，101 片）。某个字有没有字形，
  信息其实已经在切片自己的 `unicode-range` 里了，只是没人读。

## Decision

### 覆盖率来自分片清单，不是浏览器 API

`scripts/gen-font-coverage.mjs` 读 `public/fonts/manifest.json`，把 505 条 face
记录里的 `unicode-range` 解析、排序、合并，产出
`frontend/src/editor/theme/font-coverage.json`（36 KB）。

三处细节：

- **按内容去重**。思源黑体与思源宋体用的是同一套 Google CJK 切分，覆盖完全相同，
  存两份纯属浪费。生成器按编码后的字符串分组，族名指向表名（现在只有 `cjk` 与
  `latin` 两张表）。
- **必须合并区间**。不合并的话是 4734 段，二分查找的前提（有序且不重叠）也不成立。
- **`U+4E??` 这种通配写法要展开**。Google 的切片里三种写法都有，漏一种就静默
  丢一片覆盖——表现出来是「明明有字形却报缺字」。

不直接读 manifest（841 KB）：导出对话框只需要「哪些码位被覆盖」，不需要分片
文件名与字节数。36 KB 进懒加载分块，连请求都不用发。

### 只扫「会被画出来」的文字

- 主题标题取 `layout.sizes.lines`（折行后的实际行），不是 `topic.title`——标题里的
  `\n` 渲染时被拆成多行，取原文会多算换行符。
- 边界标题、关系线标题：这两处没有单独的 `font-family`，继承 SVG 根上的 `sans`。
- **备注不算**：备注不画在画布上，为它报缺字是误报。
- **标签目前不算**：`viewer/` 里没有任何地方读 `topic.labels`，标签根本不上画布。
  等标签上画布了要同步加进来，否则又会漏报。
- 节点用 `system` 族时跳过：那本来就是系统字体，报「回退到系统字体」自相矛盾。

### 计数按去重的字符，不按出现次数

提示语是「N 个字符使用了系统字体」，用户关心的是「哪些字」。同一个 emoji 出现
十次报 10 个，除了让数字变大没有任何用。所以按码位去重、保持首次出现顺序，并把
前 5 个字符当样本写进提示——只说个数，用户没法判断要不要处理。

按 `for...of` 遍历（按码位）而不是 `for (let i...)`（按 UTF-16 单元）：后者会把
一个 emoji 拆成两个代理码位各报一次。

空白与控制字符不算缺字：它们不画字形。

### 闸门

`check-fonts.mjs` 加第 7 项：用**生成它的同一个函数**（`renderCoverage`）重算一遍，
与磁盘上的文件逐字节比对。表过期不会报错，只会让提示说谎——说没缺字而实际缺，
或者反过来。用同一个函数比对，就不存在「两套实现跑偏」这种可能。

## Consequences

- 新增一个生成产物（`font-coverage.json`）与一个脚本（`npm run fonts:coverage`）。
  改字体后必须重跑，否则 CI 红——这是刻意的：宁可红，也不要一张过期的表。
- 体积代价实测：导出对话框分块 220.19 kB / 68.97 kB gzip → 258.32 kB / 88.48 kB
  gzip。多出来的约 38 kB 就是码位表，只在打开对话框时下载。
- 覆盖率是**声明值**，不是实际字形数。理论上某个码位在 `unicode-range` 里而字体
  没画字形时会被漏报。实测这类不一致在这套分片里不存在（`check-fonts.mjs` 的常用字
  抽检也覆盖了这一点），而且这是唯一不依赖浏览器、可离线测试的信息源。
- 提示只说「哪些字」，不给出「换成什么字体」的建议：能做的只有改用其他字体或
  换掉这几个字，替用户做决定不合适。

## Alternatives considered

- **`document.fonts.check()` 逐字判断**（docs/06 §4.2 原文的写法）：实测对缺字返回
  true，等于永远不报警。这条路走不通，文档已按实现改写。
- **运行时 fetch 841 KB 的 manifest**：多一次大请求，且要在浏览器里解析 505 条记录。
  派生一份 36 KB 的表更好。
- **把码位表内联成 TS 常量**：36 KB 的字符串常量会让 `tsc` 与打包都慢一点，JSON
  导入更干净。
- **逐字渲染到 canvas 比较宽度来探测缺字**：不可靠（不同字体的回退字可能等宽），
  且需要 DOM，无法在 node 里测。
- **在编辑器里实时提示**：那是每次按键都要跑一遍的检查，收益（导出前才知道也来得及）
  不抵成本。放在导出对话框，正好在用户要发出去的那一刻。
