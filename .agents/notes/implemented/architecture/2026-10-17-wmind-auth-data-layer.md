# Agent Note: M1 数据层三张表：软撤销令牌、快照式设置、只增审计

Status: implemented

## Problem

M1 要在不新增迁移的前提下把三张已建但未使用的表接上仓储：`refresh_tokens`、`settings`、`audit_logs`。表结构是 M0 定的，但「怎么用」有几个必须先想清楚的点，否则后面每个调用点都会各自发挥：

- 刷新令牌轮换后，旧行是删还是留？
- 站点设置是逐键查，还是一次全量加载？
- 审计日志要不要给应用留删除能力？
- 同一段仓储代码在 SQLite 与 PostgreSQL 上，写入内容会不会不一样？

## Decision

### `refresh_tokens`：软撤销，永不物理删除（除过期清理）

`RevokedAt` 而不是 `DELETE`。轮换后的旧令牌若再次出现，是「令牌被复制」的唯一信号；删掉行就等于销毁证据，攻击者拿着旧令牌来换新令牌时系统只会答「不存在」，与「从未签发」无法区分。

撤销方法返回受影响行数而不是 error：`(bool, error)` / `(int64, error)`。调用方需要区分「刚刚撤销」与「本来就无效」，后者不是错误。

`Expired(at)` / `Usable(at)` 的时间由调用方传入，不在模型里调 `time.Now()`。测试因此可以把「过期」从真实时间上解耦，不必 sleep。

### `settings`：一次全量加载 + 内存快照

仓储只有 `List` 与 `Upsert`，**没有 `Get(key)`**。站点配置每个请求都要读，逐键查询会把「一次快照」退化成 N 次往返；写路径只有管理员的整体保存，也不需要按键更新。`Value` 是原始 JSON 文本，键的语义属于 service 层——这样加一个设置项不用改仓储、不用改迁移。

Upsert 用 `ON CONFLICT (key) DO UPDATE`（两种方言都支持）。不用 SQLite 的 `INSERT OR REPLACE`：它会先删后插，把 `updated_by` 这类没出现在 INSERT 列表里的列重置成默认值。

### `audit_logs`：接口层面就没有 UPDATE / DELETE

审计表由 `domain.AuditRepo` 暴露，接口只有 `Create` / `List` / `Count`。应用改不动自己的审计轨迹，这不是靠代码评审守的，是类型系统守的。

`Detail` 是 JSON 文本，敏感字段（密码、令牌明文）由 service 层剔除——列约束管不了这件事，只能靠写入点自律。

### 跨方言一致：IP 在 domain 里归一化

审计的 `ip` 列在 PostgreSQL 是 `INET`、在 SQLite 是 `TEXT`。同一个非法值 `"not-an-ip"`，SQLite 老实存下，PostgreSQL 直接报错——契约测试第一次跑就撞上了这个分叉（SQLite 侧断言「空 IP」失败）。

修法是把校验提到 `domain.NormalizeIP`：空串与非法地址一律归一为 `""`，两侧仓储都调它，PostgreSQL 侧再从归一化结果解析成 `netip.Addr`。**方言差异必须在 domain 里抹平，而不是在各自的仓储里各写一套「差不多」的逻辑。**

### 契约测试改用 `Repos` 结构体

`Run(t, users, maps, tx)` 换成 `Run(t, Repos{...})`。仓储数量会随里程碑增长，位置参数每加一个都要改所有调用点，且漏传时报错只说「参数不够」。结构体字段名让调用点自解释。

## Alternatives considered

- **轮换即删旧令牌行** — 表更小、查询更简单。被否是因为它抹掉了令牌复用检测的唯一证据；而「检测到复用就撤销该用户全部会话」是这套机制的核心价值。
- **`Revoke` 返回 error，撤销不到就当失败** — 语义更「严格」。被否是因为登出接口对「令牌本来就无效」必须幂等成功：用户连点两次登出不该收到 500。
- **设置逐键 `Get` + `Update`** — 与常见的 key-value 仓储一致。被否是因为读路径是热路径且总是读全量，逐键查询纯属浪费；写路径也总是整组保存。
- **审计表提供 `Delete` 供「清理旧日志」** — 运维上确实会需要。被否是因为它把「不可篡改」降级成「靠自觉不调用」；真要做保留期清理，应该走独立的运维脚本或数据库侧策略，而不是给应用一把删除钥匙。
- **让 SQLite 仓储也接受非法 IP，由上层保证输入合法** — 少一处校验。被否是因为「上层保证」在跨模块调用时必然失守，而且两侧行为不一致正是契约测试存在的理由。

## Consequences

- **收益**：三张表的语义在接口层就定死了（软撤销、只增、快照读），后续 service 层不需要再讨论「这里能不能删」。
- **收益**：契约测试现在覆盖令牌全生命周期（创建 / 查询 / 幂等撤销 / 保留当前设备 / 全撤销 / 过期清理）、设置的插入与更新、审计的写入与读取，且两侧跑同一份断言。
- **代价**：`settings` 没有按键查询，若将来出现「只读一个键」的冷路径，需要再加方法——这是有意的延迟决策。
- **代价**：`NormalizeIP` 会静默丢弃非法 IP。审计记录保留、地址缺失，比整条记录写失败要好；但如果某天发现审计 IP 大量为空，说明上游传了非 IP 的东西（例如带端口的 `host:port`），这是排查信号。
- **已知上限**：`DeleteExpired` 目前没有后台任务调用，过期行会持续累积。M1 只提供方法，调度留到 M6 的运维任务里。
