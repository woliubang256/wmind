# Agent Note: 文本测量与 mindmap 布局：手写带式布局、测量后端抽象

Status: implemented

## Problem

M2.2 要给出「文档 → 几何」这一步：文本折行与测量、`mindmap` 结构的左右平衡布局。docs/05 §4.3/§4.4 给了接口与常量，但有几处必须自己定：

- 布局用 `d3.tree` 还是自己写？
- 文本宽度只能靠 Canvas 的 `measureText` 拿到，但单元测试跑在 node 环境，没有 DOM，怎么办？
- 折行规则是什么？中文可以在任意字之间断，英文不能拆词。
- 测量结果要不要取整？
- 父节点和它的子节点组在垂直方向上怎么对齐？
- 左右两侧怎么分？

## Decision

### 不用 d3，自己写「带式」布局

d3-hierarchy 的 `tree()` 是 Reingold–Tilford 轮廓合并：相邻子树能互相嵌进对方的空隙，比朴素布局紧凑 10%~20%。不用它，理由是：

1. **依赖成本**：`d3-hierarchy` 会带进 `d3-*` 一串包，而我们只需要一个函数；这个项目的依赖清单已经在 M1 里刻意收窄过（不引 zod / shadcn / lucide）。
2. **可控性**：轮廓合并的失败模式是「节点重叠」，而带式布局的失败模式是「空得多了点」。前者在导图里是致命的，后者只是不够好看。调参时能一眼看出对不对。
3. **结构一致性**：M2.7 还要做 `logic-right` / `org-chart` / `tree-right` 三种结构，它们共用同一套「测量 → 高度 → 摆放」的骨架，自己写反而更容易复用。

带式布局的定义：子树高度 = `max(自身高度, 子节点高度之和 + 间距)`。每个子树占满一条垂直带，节点在自己的带里居中。**这个定义保证任意两个盒子不重叠**——测试里用两两矩形求交来守这条不变量。

左右分配**按下标奇偶交替**（0、2、4… 在右，1、3、5… 在左）。

这里偏离了 docs/05 §4.4 的「按子树高度贪心分配以平衡两侧」，原因是实测发现贪心在编辑过程中**不稳定**：贪心的输入是子树高度，而高度会随节点文字变长而变。改一个二级节点的标题，四个一级分支就全部换了边——用户会以为文档被改坏了。交替分配的代价是极端情况下不平衡（第 0 个分支有 50 个子节点、其余各 1 个时右侧会很长），但导图的一级分支通常规模相近，「位置稳定」比「高度均衡」更影响可用性。

### 测量后端抽象成接口

```ts
export interface MeasureBackend { widthOf(text: string, font: FontSpec): number }
```

默认实现按环境选：有 `document` 用 Canvas（缓存的 canvas 与 2d context 各只建一次），没有就用启发式估算（CJK 按 1em、数字 0.55em、小写 0.54em……）。

不这么做的话，内核测试必须跑在 jsdom 里，而 jsdom 的 canvas 要么需要 `node-canvas` 原生依赖，要么直接返回 0 宽度——两者都会让测试变成「测了个寂寞」。

代价是测试里的绝对宽度与浏览器不一致。所以测试只断言**相对关系**（CJK 比拉丁宽、缓存命中、折行位置），不断言像素值；需要精确断言时注入固定宽度的假后端（每字符 `size * 0.5`）。

### 缓存键含字体标识符，LRU 5000

`${family}|${size}|${weight}|${italic}\u0000${text}`。docs/05 §4.3 特别强调「缓存键必须含字体标识符」——只按文本缓存的话，切换字体后节点宽度与实际渲染对不上，而这种错位在视觉上表现为「文字溢出了气泡」，很难联想到缓存。

Map 的插入顺序天然是 LRU 顺序：命中后 `delete` 再 `set` 挪到队尾，超限时删队首。不用额外维护链表。

### 折行：中文按字、英文按词、超宽词硬断

- CJK 逐字成 token（中文可以在任意字之间断行）；
- 西文按空格切词，词内不断；
- 单个词比整行还宽时按字符硬断，否则会溢出节点；
- 行首空格跳过、行尾空格裁掉；
- `\n` 强制换行，且保留空行（用户按 Shift+Enter 换行后不该被吃掉）。

### 测量结果四舍五入到 0.5px

亚像素宽度会让相邻节点看起来「差一点对齐」，而这种瑕疵在缩放后会放大成明显的锯齿。0.5px 是能对齐设备像素又不过度损失精度的折中（docs/05 §4.3 的同一结论）。

### 父节点在自己子节点组的垂直中间

`cursor = top + (subtreeHeight - childrenTotal) / 2`。

漏掉这个偏移时，子节点从带的顶端开始排，父节点却在带中间——连线会全挤在父节点的上半部分，看起来像「父节点浮在子节点上方」。这个 bug 在节点少时几乎看不出来，节点一多非常明显。

## Consequences

- 1001 个节点的布局在开发机上是个位数毫秒（测试里连同构造文档一起 41ms），远低于验收标准 3 的 1.5s 预算。
- 布局结果完全可预测：同一份文档 + 同一套常量 = 同一份坐标，方便截图对比与回归。
- 比 d3 的轮廓合并松 10%~20%，长分支多时右侧会偏长。等 M3 有真实导图对比再评估是否值得换。
- 测量缓存与样式缓存（`resolveStyle`）都是模块级、有上限的；长时间编辑不会无限增长。
- 已知限制：`subtreeHeight` 按「节点高度」累加，没有考虑节点下方的标记/备注图标——M3 引入图标后高度要重新计算，`measureTopic` 是唯一的改动点。

## Alternatives considered

**d3-hierarchy 的 `tree()`**：紧凑度最好，且久经考验。放弃原因是依赖成本与失败模式（重叠 vs 松散），以及 M2.7 的另外三种结构复用不上它的输出。

**完整 Reingold–Tilford 轮廓合并（自己实现）**：不引依赖又能拿到紧凑度。放弃原因是实现复杂度陡增（左轮廓 / 右轮廓 / 线程指针 / 冲突位移），而收益只有 10%~20% 的紧凑度——在 M2 这个阶段，把时间花在交互和渲染上更值。

**用 `getBBox()` 测量**：结果最准（就是实际渲染宽度）。放弃原因是它要求元素已挂载到文档并触发同步 reflow，1000 节点会退化成 O(n) 次强制布局，直接违背性能目标。

**测量放到 Web Worker**：能避免主线程卡顿。放弃原因是 Canvas 测量本身很快（缓存命中后是纯 Map 查找），真正的瓶颈是首次测量 1000 个不同字符串——实测也在 10ms 量级，不值得为它引入 worker 通信与序列化开销。
