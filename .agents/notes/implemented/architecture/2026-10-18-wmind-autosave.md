# Agent Note: 自动保存：状态机、冲突三选一、草稿与离开保护

Status: implemented

## Problem

M2.6 的前端要回答「怎样才算可靠地保存了」。要定的问题：

- 保存状态机放哪、怎么测？它牵扯防抖、重试、单飞、串行补存，塞进组件里就测不动。
- 「保存成功」和「文档干净」是一回事吗？
- 409 之后怎么办？继续重试只会一直 409。
- 断网 30 秒后恢复，谁来补存？
- 本地草稿和自动保存会不会互相覆盖？
- 离开保护拦到哪一步才算够？

## Decision

### 状态机是纯对象，不碰 React

`createAutosave({ read, save, onSaved, onConflict, onError, debounceMs, maxWaitMs, retryDelays })`
返回 `{ notifyChange, flush, resume, markClean, dispose, paused, hasPendingWork }`。

React 侧（`use-autosave.ts`）只做三件事：把 store 的 `revision` 变化喂进去、把回调写回 store、挂离开保护。
12 个单测用假计时器覆盖全部分支，不需要渲染。

### 防抖与最长等待是两个计时器

800ms / 5s（docs/01 FR-MAP-11）。只有防抖的话用户一直打字就永远不保存；只有最长等待的话停下来要等满 5 秒才落盘。
**最长等待只在「第一笔改动」时起算**，不随每次按键重置——重置等于它永远不会触发。

### 「保存成功」不等于「文档干净」

`markSaved(version, revisionAtStart)`：请求往返期间用户可能又敲了几个字。无条件置 `saved` 会显示「已保存」而实际有没落盘的改动，那是最坏的一种谎。
但**版本号必须采纳**：这次保存已经让服务端自增了版本，继续用旧版本号发下一次请求必然 409。

### 空转闸门按文档引用，不按 revision

`lastSavedDoc === snapshot.document` 才跳过。immer 保证「没改动 = 同一个对象」，所以引用相等就是内容相等。

用 `revision` 会漏：`loadDocument` 之后 revision 归零，恢复草稿时明明换了文档，revision 却可能和上次保存时一样。
没有这道闸门，最长等待计时器可能在保存成功后才到期，白发一次请求——而每次空请求都让服务端版本号 +1，两个标签页的冲突会来得毫无道理。

`markClean()` 用在「放弃我的修改」之后：刚拉下来的就是服务端版本，不重置闸门的话订阅者会把它当成一次编辑，立刻又存回去。

### 409 是暂停态，不是错误态

`paused = true` 之后 `notifyChange` 直接返回。继续重试只会拿到同一个 409，把对话框刷成屏保。
用户选「保留我的版本」时才 `setVersion(服务器版本)` + `resume()` + `flush()`——**拿服务器的版本号重发**才是「我确认覆盖」的表达方式，而不是把乐观锁关掉。

store 的 `dirtySave()` 同步保证：冲突期间用户继续编辑不会把状态打回 `dirty`，否则自动保存会立刻再撞一次 409。

### 重试耗尽的坑（测试抓到的）

网络错误按 1s / 2s / 4s 退避三次后放弃。但最长等待计时器是在第一笔改动时起的，此刻还没到期；不清掉它，几秒后又会调一次 `run()`——于是「重试三次放弃」变成每 5 秒重来一轮，页脚在「保存失败」与「保存中」之间反复跳，而用户根本没再动过。

写测试时断言「一共 4 次调用」，实际拿到 8 次，才发现的。修法是失败分支里也 `clearTimers()`。

### 网络恢复靠 `online` 事件

退避三次大约 7 秒就放弃了，而验收标准写的是「断网编辑 30 秒后恢复网络，内容自动补存」。指望退避撑到网络回来不现实。
`window.addEventListener('online')` 是唯一可靠的信号：状态是 `error` 或 `dirty` 就 `resume()` + `flush()`。

### 草稿是第二道保险，不是第一道

自动保存救不了「标签页直接没了」——请求还没发出去，内存里的文档随进程消失。

- 每 3 秒检查一次，只在「有未落盘内容」时写；保存成功立刻删（留着只会在下次打开时弹一个内容完全一样的「发现本地修改」）。
- 写失败（配额满 / Safari 隐私模式 / 被禁用）静默降级 + `console.warn`：丢草稿只是少一层保险，不该让编辑器崩掉。
- 读的时候验形状：localStorage 用户能手改，也可能是旧版本前端写的。直接 `JSON.parse` 之后当文档用，会炸在布局阶段某个想不到的地方。
- 7 天过期，打开任意导图时顺带清理（单独做清理任务需要定时器，而打开导图本来就要遍历 localStorage）。
- 打开时只有「草稿比服务端新」**且**「内容不同」才提示恢复。内容一样还弹窗纯属打扰。

### 离开保护：三条路都要堵

- 关标签页 / 刷新 → `beforeunload`（现代浏览器忽略自定义文案，但仍需 `preventDefault` + `returnValue`）；
- 路由切换 → react-router 的 `useBlocker`（它不接管浏览器级关闭，所以两条都要）；
- 两条路离开前都同步写一次草稿，`pagehide` 里也写——那是页面生命周期里最后一个还能写 localStorage 的时机。

### StrictMode 把控制器弄哑了

`dispose()` 原本会设一个永久的 `disposed = true`。StrictMode 的「挂载 → 清理 → 挂载」把第一次清理时的 dispose 留在了控制器上，第二次挂载之后**一个请求都不发**。

症状极具误导性：编辑了，页脚一直「未保存」，网络面板里一次 PUT 都没有，而且只在开发模式出现（生产构建不跑 StrictMode 的双调用）。

改成 `dispose()` 只清计时器，不留任何永久状态。卸载后残留的唯一影响是「在途请求回来时写一次 store」，那是无害的——store 是外部 store，不涉及 React 的 setState。

### 状态指示器放页脚，不放标题栏

docs/01 说「保存状态在标题栏可视化」。实际标题栏已经被返回、标题、撤销重做、新建删除折叠、缩放、预览挤满；再塞一个宽度随文案变化的块，窄屏下标题输入框会被压到几十像素。
页脚本来就有一行统计信息，而且离「刚编辑完」的视线更近。五种状态都有明确文案：只显示一个小圆点的话，「保存中」和「保存失败」在用户眼里是一样的。

### 根主题标题就是导图标题

`changeTitleCommand` 现在同时改 `doc.title` 与当前画布的 `rootTopic.title`，一条命令一条历史。

两个字段在模型里是分开的（`doc.title` 是文件名/列表项，`rootTopic.title` 是画布上的中心主题），但对用户是同一件事。页头写着「未命名导图」而中心主题写着「断网期间改名」，看起来就像保存串了——截图里一眼就能看到。

### 本地入口保留

`/maps/demo` 与 `/maps/stress` 仍走本地文档（`enabled=false`，不挂自动保存），与真实导图共用同一套页面代码。M2.3/M2.4/M2.5 的验收脚本靠它们跑渲染、键盘、拖拽回归——没有它们，每次回归都要先注册账号、建图、造数据。

## Consequences

- 单测 218 → 244（autosave 12、草稿 11、store 保存态 5、文档标题 3，另有既有 218 中的改动）。
- 浏览器验收 21 项全过：新建→自动保存→刷新保持、Ctrl+S 立刻落盘、断网 30 秒后恢复补存、两标签页 409、三个选项各自的行为、原导图版本号推进。
- 回归：M2.3 渲染（17 节点 / 折叠徽标 / 文字对比色）、M2.4 键盘 38/38、M2.5 拖拽 20/20 全过。
- 编辑器 chunk 54.67 kB → 63.12 kB（gzip 20.55 kB），远低于 350 kB 预算。
- 已知限制：标题留空时 `doc.title` 会变空，保存后服务端归一为「未命名导图」，客户端要刷新才看到。留到 M3 在失焦时归一。
- 已知限制：两个标签页共用一个草稿键，后写的覆盖先写的。同一张图本来就不该在两处同时编辑，M5 做多标签提示时再看。
- 已知限制：`另存为副本` 的标题后缀与后端 `duplicate` 一致，但不做重名去重（列表页允许重名）。

## Alternatives considered

**用 react-query 的 mutation 管保存**：重试、去重、状态它都有。放弃原因是保存的时序要求（防抖 + 最长等待 + 单飞 + 串行补存 + 暂停态）比 mutation 的语义复杂，塞进去等于在它上面再写一层状态机，还多一层缓存语义要对齐。

**冲突时自动「后写覆盖」**：省掉对话框。放弃原因是用户会静默丢掉另一个标签页的修改，而且完全没有察觉。

**用 IndexedDB 存草稿**：容量大得多，不会撞配额。放弃原因是 `pagehide` 里只能用同步 API——IndexedDB 是异步的，最需要它的那一刻正好用不了。

**用 `useBlocker` 拦 beforeunload**：少一个监听器。放弃原因是 react-router 的 blocker 只管它自己的导航，不接管浏览器级关闭。

**把「未保存」做成阻断式弹窗**：更醒目。放弃原因是它会在用户还在打字时打断，而自动保存的存在意义就是不需要用户操心。

**把状态机做成 class**：看起来更「正规」。放弃原因是它没有任何继承或复用的需求，而闭包版本不用处理 `this`。
