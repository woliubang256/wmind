# Agent Note: 加密的 XMind 报「已加密」而不是「解析失败」

Status: implemented

## Problem

验收 IE-06 要求「导入加密的 XMind 文件 → 给出明确提示，不崩溃」。改之前
`ENCRYPTED` 这个错误码只在 `errors.ts` 里声明过、在 i18n 里有文案，**没有任何代码
会抛它**——它是个空壳。

加密文件在导入器眼里最糟糕的形态是「看起来正常」：条目名一个不少（`content.xml`
还在，只是内容换成了密文），格式探测照样给 0.95 分，直到 XML / JSON 解析才炸。
于是用户看到的是 `PARSE_FAILED`，界面文案是「解析失败」——那句话在暗示「你的文件
坏了」，而事实是「文件是好的，你得先去 XMind 里去掉密码」。两句话对应的下一步
动作完全不同。

## Decision

`frontend/src/editor/import/encryption.ts` 提供 `assertNotEncrypted(zip)`，由
XMind 适配器在**任何内容解析之前**调用。三条互不依赖的证据，任一条成立即判加密：

1. **`META-INF/manifest.xml` 的根元素带 `password-hint` 属性**。XMind 8 设密码时
   写进去的密码提醒（可以为空串）。最权威的一条：文件自己声明了。只认
   `password-hint=` 这种属性赋值，不认正文里提到这几个字。
2. **`manifest.json` / `metadata.json` 里出现 `password` / `encrypt` 字样的键**。
   现代格式（2020+）的清单文件，键名大小写与嵌套层级都不固定，所以深度遍历所有
   键名，而不是按固定路径取。
3. **`content.json` / `content.xml` 的前 512 字节里有 C0 控制字符**（除 `\t`
   `\n` `\r`）。文本文件不会有控制字节，密文一定有。这一条不看格式，只问「这堆
   字节到底是不是文本」，兜住前两条都不认的版本。

### 不用「解不开就当加密」

第 3 条刻意判「像不像二进制」而不是「能不能解析」。损坏的文本文件仍然是文本，
应该报 `PARSE_FAILED`；用「能否解析」当判据，会把损坏文件误标成加密，用户照着
提示去 XMind 里找密码，然后发现根本没有密码——比不提示更糟。

## Consequences

- 加密文件仍然被判为 XMind（探测给 0.95），但报 `ENCRYPTED`，界面文案是
  「该文件已加密，请先在 XMind 里移除密码再导入」。
- `encryption.test.ts` 25 条：三种证据各自单独验一遍，再验四条「不该误报」
  （清单正文提到这几个字但没有属性赋值、清单自己坏掉、损坏但仍属文本的
  `content.xml`、空包）。
- 现代格式的密码标记只能靠第 2、3 条：XMind 2020+ 的清单文件里 `password-hint`
  放在哪一层没有公开文档，所以按「键名里出现 password/encrypt」宽匹配。将来拿到
  真实样本时应收紧到具体路径，宽匹配有误报风险（虽然目前没遇到）。

## Alternatives considered

**只做 XML / JSON 解析失败后猜原因**（比如报「可能已加密或已损坏」）：零成本。
放弃原因：「可能」二字让这条提示失去价值——用户没法据此决定下一步，而两种原因
的下一步完全不同。

**在探测阶段就拦掉加密文件**（`detect` 返回 0）：界面会报 `UNKNOWN_FORMAT`
（「不支持的文件格式」），比「已加密」更差，而且会让「换个版本另存再试」成为
用户的第一反应。

**自己实现解密**：不现实。密码是用户设的，XMind 的密钥派生也没有公开规范；
IE-06 要的只是「说清楚」，不是「打开它」。
