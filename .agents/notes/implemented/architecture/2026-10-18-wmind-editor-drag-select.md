# Agent Note: 拖拽与多选：落点语义、批量命令、监听器被重渲染拆掉的坑

Status: implemented

## Problem

M2.5 要做「拖着节点改结构」。docs/05 §4.6.3 给了语义，但落地时要定：

- 落点判定放哪、怎么测？
- 多选拖拽怎么保证「一次拖拽 = 一条撤销」？
- 框选与拖拽怎么分工，会不会互相抢事件？
- 拖到自己的后代上被拒绝——「拒绝」的视觉反馈到什么程度才算够？
- 2000 节点拖拽能不能保持 60fps？

## Decision

### 落点判定是纯函数，语义按「上 25% / 中 50% / 下 25%」

```ts
resolveDrop(boxes, sheet, dragIds, point, { anchorId?, zoom? }?): DropCandidate | null
```

`DropCandidate` 带 `mode`（child / before / after / detach / restore）、`parentId`、`index`、`valid`、`reason`、`noop`。

抽成纯函数的理由和键位表一样：拖拽是「肉眼判断」最容易飘的地方。同一个落点，今天觉得「应该成为子节点」，明天觉得「应该插到后面」——写成测试之后这个标准就固定了。而且下标修正这种 off-by-one 在多选场景下几乎无法靠手测发现。

**下标必须按「被拖节点已经被摘掉之后」的数组算**：

```
index = (before ? target.index : target.index + 1) - 同父且在被插位置之前的被拖节点数
```

不扣这一位的话，把下标 2 的节点拖到下标 3 的节点前面，会插到下标 3——正好越过目标一位，用户看到的是「拖到前面结果跑到后面去了」。

`noop` 单独标出来：拖回原位是合法的，但派发命令会产生一条「什么都没变」的撤销记录。同级插入的判定条件是单节点拖拽且修正后的下标等于它自己当前的下标。原主题附近回归使用 restore 候选，整组保留原关系，不提交历史；屏幕距离、抓取锚点和目标优先级见[拖拽回归修复](../../implemented/bug-fix/2026-10-23-wmind-drag-return.md)。

**根节点的上/下沿退化成「成为子节点」**：根没有兄弟，不退化的结果是「拖到根的上方什么都不会发生」，用户会以为拖拽坏了。

### 批量命令：一次拖拽一条历史

新增 `moveTopicsCommand(ids, parentId, index?)` 与 `detachTopicsCommand(ids)`。

不循环调用单节点版本，因为 N 条撤销记录会让 Ctrl+Z「只退一个节点」，看起来像撤销坏了。

实现是「先全部摘下来，再按顺序插进去」：边摘边插会让后续节点的目标下标随数组变短而错位。

两个容易漏的点：

1. **去掉「祖先也在被拖集合里」的节点**（`topLevelOnly`）。框选很容易同时选中父节点和它的子节点，两个都搬的话，子节点会被父节点带进新位置再单独插一遍——同一棵子树在文档里出现两份。
2. **非法时整批拒绝**，不做「能动的先动」。半成功比失败更难解释，而且用户的意图是「把这几个搬到那」，搬一半等于没搬。

### 拒绝要有「为什么」，不只是变色

非法落点画两样东西：目标节点描红虚线框 + 指针旁写明原因（「不能放到自己的子节点里」/「中心主题不能移动」/「自由主题不能作为父节点」）。

只变颜色不够：红绿色盲用户看不出区别，而「为什么不行」本身就是用户需要的信息。同理，拖到空白处会显示「松开转为自由主题」——静默把节点变成自由主题，用户会以为节点丢了。

### 框选与拖拽靠 `pointerdown` 的目标分工

- 按在节点上 → 拖拽插件；
- 按在空白处 → 框选插件；
- 两者不需要互相通信，也不需要状态机。

框选用**相交**而不是包含：用户随手划一道横线，期望选中被扫到的节点；要求完全框住会逼他把框画得比内容大一圈，缩小状态下很别扭。

### 选中插件不再在 `pointerdown` 收敛选区

原来点任何节点都会 `setSelection([id])`。多选之后要整组拖走，而 pointerdown 就把选区收敛成一个的话，拖拽插件永远只拿到一个节点。

改成：点在**已选中**的节点上且无修饰键时保持选区不动，收敛交给拖拽插件在「没越过 4px 阈值 = 一次点击」时做。带修饰键的点击（加选/减选）不收敛——否则刚加上的那个又被踢掉。

### 监听器必须活在「只依赖 svgRef」的 effect 里

这是这一批里最值得记的一条，因为它的症状极具迷惑性。

现象：拖拽在「节点已经被选中」时正常，在「节点未被选中」时完全没反应。框选则是完全没反应。

原因：插件把 `selection` / `setSelection` / `layout` 放进了 effect 的依赖数组。`pointerdown` 时选中插件先跑（插件顺序在前），它调 `setSelection`——而 zustand 是**外部 store**，React 18 对 `useSyncExternalStore` 的通知会**同步**重渲染。重渲染让其它插件的 effect 跑清理，把刚注册的 `pointerdown` 监听器摘掉了，而事件还在分发途中。于是同一个事件，排在前面的插件收到了，排在后面的没收到。

「已选中时正常」正好对上：那时选中插件不改变选区，没有重渲染，监听器活着。

修法是 `useLatest`（`plugins/use-latest.ts`）：挂监听的 effect **只依赖 `svgRef`**（引用恒定），监听器里通过 `latest.current` 读最新值。六个插件全部改成这个写法。

副作用是好的：监听器不再随每次渲染反复解绑重绑，2000 节点的图上这也是一笔可观的开销。

### 指针捕获 + Esc 中断

越过阈值后 `setPointerCapture`：拖出 svg 边界（甚至拖到工具栏上）也要继续收到事件，否则松手时收不到 `pointerup`，拖拽状态会卡住（表现为「鼠标已经松开了，但幽灵还跟着走」）。

Esc 中断：拖到一半发现拖错了，第一反应是取消。

## Consequences

- 单测 27 个（落点判定 16 + 批量命令 11），全量 190 个通过。
- 浏览器验收 20 项全过：中心落点成子节点、上沿成同级、非法落点有文字与描红且不改变结构、空白处脱离、框选、Ctrl 加选、多选拖拽、一次拖拽一步撤销。
- 2001 节点拖拽：平均 17.8ms / p95 18.7ms，约 60fps；落定后的一次全量重排约 900ms（与 M2.3 测得的单次布局成本一致，是提交一次编辑的固有成本）。
- 拖拽起始时会有一帧约 120ms 的卡顿：选中态变化让 2001 个 `TopicNode` 重新比对。只发生一次（按下时），不影响拖动过程；要彻底消除需要把选中态从节点 props 里挪到独立的 overlay 层，留到 M3 视口裁剪时一起做。
- 已知限制：多选拖拽的落点是「相对某个目标节点」的单一语义，不支持「把 N 个节点依次插到不同位置」。这是刻意的——多选拖拽的意图就是「这一组搬到那里」。
- 已知限制：自由主题之间不能互相拖拽排序（`floatingTopics` 的顺序没有 UI 入口），M3 做「自由主题排版」时补。

## Alternatives considered

**在 `pointermove` 里直接算落点、不用 rAF 合并**：代码更短。放弃原因是高刷屏上 pointermove 能到 240Hz，每帧做多次全量扫描纯属浪费，而人眼分辨不出 4ms 的差别。rAF 合并之后每帧最多一次。

**框选用「完全包含」判定**：更符合「框住」的字面语义。放弃原因是实际操作中用户随手划的框很少完整包住节点，导致「明明框到了却没选中」。

**拖拽与框选合并成一个插件 + 状态机**：少一个文件。放弃原因是两者的生命周期、阈值、取消语义都不同，合在一起会变成一堆 `if (mode === 'marquee')`；而它们靠 `pointerdown` 的目标就能干净分工。

**批量命令循环 dispatch 单节点命令**：实现最少。放弃原因是撤销粒度。真要这么做，就得给 store 加「事务」概念把多次 dispatch 合并成一条历史——那比直接写一个批量命令复杂得多。

**监听器照旧依赖 `selection` 等值，改成在 `pointerdown` 里用 `setTimeout(0)` 推迟 `setSelection`**：能绕过同步重渲染。放弃原因是它把「事件时序」变成了隐式契约，下一个人加插件时完全不知道有这个约束。`useLatest` 是显式的、局部的、不依赖时序的。
