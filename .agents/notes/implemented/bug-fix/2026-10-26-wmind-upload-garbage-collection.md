# Agent Note: 上传资源延迟回收与跨实例维护门

Status: implemented

## Problem

封面上传每次生成新地址，替换、导入失败、永久删除和删除账号没有统一资源回收，旧文件会继续占用磁盘并进入备份。头像即时删除又可能破坏被模板、正文或站点 Logo 复用的资源。仅在删除前查一次引用会与其他实例新建引用竞争，现有备份维护门只有进程内锁。

## Decision

`internal/uploadgc` 提供独立回收组件，`UploadReferencesRepo` 分页读取两种数据库中的现有引用，不增加资源表或改变备份格式。

普通请求与回收站任务在现有 Gate 的共享区运行；备份捕获、恢复和资源清理在独占区运行。生产 Gate 使用 uploads 父目录稳定锁文件，所有共享本地上传卷的实例遵守同一 flock 协议；锁文件不在可被恢复交换的 uploads 目录中。获取锁失败关闭操作，不回退到无锁模式。零值 Gate 保留单元测试和独立内存使用方式，生产必须显式配置共享锁。

清理任务在独占区现读数据库引用，包含活跃与回收站导图所有画布图片及封面、模板、未删除账号头像、设置中的本站上传引用。只回收应用已知命名的普通文件和严格命名的 .upload 临时文件，未知条目、目录与符号链接不处理。完整扫描及解析成功才能删除，每批最多 100 个。首次发现未引用后至少等待 24 小时，同时要求文件本身超过 24 小时；出现引用或文件变动重置候选，重启从头计时。

成功替换头像交给延迟统一回收，写库失败的新头像仍可即时回滚。引用扫描保守保留 JSON 字符串中嵌入的上传地址，覆盖备注图片、绝对 URL 和未来水印字段，未知结构宁可多保留不误删。

## Alternatives considered

- 每次替换立即删旧文件实现最少，但模板、正文、设置可能复用地址，也无法覆盖中断上传与崩溃，采用统一延迟回收。
- 资产登记表与引用表适合大量资源和跨对象存储事务，但会扩大两个数据库迁移、旧备份格式及所有写路径。当前只有共享本地文件存储，以共享卷文件锁和现有数据库事实保证一致性，不引入第二套引用真相。
- 只用文件修改时间不需要候选状态，但老文件刚失去引用就会立即删除，采用内存首次未引用计时；重启延后回收比持久候选与恢复的耦合更简单安全。

## Testing

共享锁失败复现见[跨实例维护门](2026-10-26-wmind-shared-maintenance-gate.md)。回收测试覆盖引用来源、24 小时边界、重新引用与文件变化、另一个实例绑定与维护暂停、临时文件、未知/符号链接、扫描与解析失败保留、删除失败重试、100 文件批次、重启重计和取消。SQLite 契约覆盖超过 100 条的分页、回收站、禁用账号头像保留、删除账号头像释放、模板与设置；PostgreSQL 同一契约由 CI 环境运行，本地仅编译不得声称实库通过。

## Consequences

所有实例必须同步采用共享锁协议，上传卷及其父目录必须是支持 flock 的同一共享文件系统。当前部署是本地卷，不宣称支持无 flock 的对象存储。完整引用扫描会短暂阻断请求，规模扩大时再引入索引化资产表；重启会延迟未引用清理。离线超过宽限的未保存附件可能需要重新上传，绑定失败必须明确报错。
