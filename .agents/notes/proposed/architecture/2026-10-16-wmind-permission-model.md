# Agent Note: 权限模型为「资源属主 + 全局角色」，越权一律返回 404

Status: proposed

## Problem

系统需要一个权限模型：管理员要能管理用户与站点设置，普通用户只能操作自己的导图。同时需求明确提到「预留扩展：后期可能开发客户端 App」以及未来可能的团队/协作能力。

需要决定的是：一期的权限模型做到什么粒度，以及管理员对他人内容的可见范围。后者不只是功能问题，还涉及隐私与合规——管理员能读所有导图内容意味着任何一次管理员账号泄露都会导致全量数据泄露。

## Proposal

**两层模型：全局角色 + 资源属主。**

- `users.role ∈ {user, admin}`，控制能否访问 `/admin/*` 接口。
- 导图通过 `maps.owner_id` 隔离，仓储层提供 `FindByIDAndOwner` 而非 `FindByID`，从类型层面强制隔离。
- **管理员默认不能直接读写他人导图内容**，只能管理账号与执行删除。
- **唯一例外是公开分享接口**：它按 `share_links.token` 查询而非按 `owner_id`，被收敛在 `share` 模块内，且只能读取渲染所需字段。见 [分享链接独立建表](2026-10-16-wmind-share-link.md)。

**越权访问统一返回 404 而非 403。** 用户 A 请求用户 B 的导图 ID 时返回 `MAP_NOT_FOUND`，不泄露「该资源存在但你没权限」这一信息，避免被用于枚举探测有效 ID。

**数据隔离靠仓储层签名强制，而非靠开发者记得加 `WHERE owner_id`。** 所有导图相关查询方法都必须接收 `ownerID` 参数，没有不带 owner 条件的公开方法（管理场景与公开分享场景走独立的、带审计的方法）。

## Alternatives considered

### 为什么不做完整 RBAC？

角色-权限-资源三层模型（如 Casbin）能表达任意权限矩阵，是通用系统的正解。未选是因为一期只有两个角色、没有团队/空间概念，引入权限引擎属于为不存在的复杂度付费——多出来的配置与调试成本远大于收益。若未来引入团队空间，再评估引入。

### 为什么不做导图级 ACL？

支持把导图共享给指定用户，是协作场景的自然需求。未选是因为一期要的是「公开只读链接」而非「指定用户共享」——两者是不同的问题，前者已由 [分享链接独立建表](2026-10-16-wmind-share-link.md) 覆盖。`owner_id` 字段已存在，二期可平滑扩展为 `map_acl` 表而不改现有查询——这是一个可以推迟的决定，不是被否决的方案。

### 为什么越权不返回 403？

403 语义更准确（「已认证但无权限」），调试时也更容易定位。未选是出于安全考虑：403 会让攻击者区分「ID 不存在」与「ID 存在但无权限」，从而可以枚举出系统中有多少导图、哪些 ID 是有效的。404 让两种情况不可区分。代价是排查权限问题时需要看日志而不是看状态码。

### 为什么不允许管理员读他人导图内容？

从「运维方便」角度，管理员能看所有内容确实更省事（用户求助时可以帮忙排查）。但代价是任何一次管理员账号泄露都导致全量数据泄露，且需要额外的审计与合规评估。自托管场景下用户往往对隐私更敏感。若二期确实需要「管理员协助找回导图」，应新增**显式的、带审计记录的、需二次确认的**越权操作入口，而不是放宽默认权限。

## Acceptance criteria

1. 用户 A 构造请求访问用户 B 的导图 ID → 404 `MAP_NOT_FOUND`。
2. 普通用户访问 `/admin/*` 任意接口 → 403 `AUTH_FORBIDDEN`。
3. 禁用用户后其已签发 Access Token 立即失效。
4. 管理员不能删除自己，也不能降级或删除最后一个管理员（409）。
5. 删除用户时其导图默认一并删除，但确认框提供「保留（转为无主）」选项。
6. 仓储层不存在不带 `ownerID` 条件的导图查询公开方法（code review / 静态检查）。

## Risks

- **「转为无主」的导图无人可访问**：选择保留策略后，导图存在但没有任何用户能打开，成为数据垃圾。需在管理后台提供「无主导图」视图供管理员处置。一期若不做该视图，应把默认策略改为「一并删除」并只在明确需要时提供保留选项。
- **仓储层签名约束可能被绕过**：开发者仍可能新写一个不带 owner 条件的方法。缓解：把该约束写入 `AGENTS.md` 与 review checklist；必要时用静态检查工具扫描。
- **404 掩盖权限问题**：排查时需要看日志而非状态码，运维体验略差。缓解：日志中记录「越权访问尝试」并带上真实原因。
- **二期扩展 ACL 时需重写查询**：`FindByIDAndOwner` 要演化为「属主或 ACL 允许」的查询。缓解：把权限判断收敛在 service 层的一个函数中，届时只改一处。
