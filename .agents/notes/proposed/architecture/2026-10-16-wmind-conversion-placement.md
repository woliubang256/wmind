# Agent Note: 导入在前端解析，导出以前端为主、服务端兜底

Status: proposed

## Problem

需求要求支持 XMind / Markdown / OPML 导入与 PNG / JPEG / SVG / PDF / Markdown / OPML 导出。这些转换放在前端还是服务端，会同时影响：安全边界（处理不可信文件的位置）、部署复杂度（是否需要在容器里装 Chromium）、前后端代码复用度、以及超大文件的可用性。

另外，如果前后端各实现一套转换逻辑，视觉与行为必然漂移——这是必须在设计阶段就消除的风险。

## Proposal

**导入全部在前端（浏览器）完成。**

`.xmind` 由 JSZip 解压后读 `content.json`（XMind 2020+）或 `content.xml` + `styles.xml`（XMind 8），由适配器解析为 `.wmind` 模型。Markdown 与 OPML 同理。解析结果先展示摘要与降级清单，用户确认后再调 `POST /maps` 创建。

**导出以前端为主，服务端作为超大导图的兜底。**

导出直接复用屏幕上的 SVG：序列化为 SVG 文件、经 Canvas 栅格化为 PNG/JPEG、经 jsPDF + svg2pdf 生成 PDF。Markdown 与 OPML 是纯文本序列化，从文档模型直接生成，不依赖渲染。

**一致性保证机制**：服务端导出复用前端构建的同一份 SVG 模板——把导出模块编译为独立 ESM 产物，服务端页面加载它。避免两套渲染逻辑漂移。

**适配器模式**：导入导出都通过 `ImportAdapter` / `ExportAdapter` 接口 + 注册表管理，内核不感知任何第三方格式。新增格式（如 FreeMind `.mm`）只需新增一个适配器文件并注册。

**前端包体积控制**：JSZip、fast-xml-parser、jsPDF 等通过动态 `import()` 做代码分割，不进首屏 bundle。

## Alternatives considered

### 为什么不在服务端处理全部导入导出？

服务端处理能让前端更薄、多端行为完全一致，也是很多同类产品的做法。放弃它有三个理由：需要把大文件上传到服务端；服务端要处理不可信的 zip / XML（zip 炸弹、XML 实体注入、超大 JSON），攻击面与资源消耗都更大；导出需要在服务端重新实现一套渲染，等于把前端渲染逻辑抄一遍并长期维护两份。

### 为什么不让前端处理全部导出？

前端处理全部导出看起来更彻底、服务端零负载。但浏览器 Canvas 有硬性尺寸上限（Chrome 单边 16384px，Safari 视设备 4096~8192px，总面积上限各不相同），8000 节点的导图在高倍率导出时必然撑爆内存。必须保留服务端兜底路径。

### 为什么不用服务端 Headless Chrome 作为主导出路径？

chromedp 渲染 + `Page.printToPDF` 保真度最高，字体处理最省心（不用纠结中文嵌入）。未选为主路径的原因是容器镜像要装 Chromium（+400MB），直接冲击「轻量、一条命令部署」的产品定位；且每次导出都有渲染进程启动开销，交互延迟远高于前端导出。作为兜底保留，若中文 PDF 质量不达标再在 M6 切换。

### 为什么导出 SVG 时不把文本转成路径？

转路径能彻底规避字体丢失，是 PDF 导出的默认策略。但 SVG 导出转路径后文本不可搜索、不可复制、不可编辑，破坏了 SVG 作为「可继续编辑的矢量源文件」的价值。所以 SVG 导出默认内嵌字体（base64 WOFF2），把「文字转路径」作为可选开关；PDF 因字体嵌入更复杂，默认开启转路径。

## Acceptance criteria

1. 导入 50MB 以内的真实 XMind 文件不崩溃，内存峰值 < 500MB。
2. 伪造的 zip 炸弹（解压后 1GB）在 200MB 处被中止并报错。
3. 导出的 PNG 与画布所见像素级一致（容差 1%）。
4. 导出的 SVG 用浏览器打开，中文正常显示。
5. 超出 Canvas 尺寸上限时给出明确提示并引导服务端导出，而不是静默失败或崩溃。
6. 编辑器首屏 JS（gzip）≤ 350KB，解析类依赖未进首屏 bundle。
7. 新增一种导入格式时，不改动 `model` / `layout` / `theme` / `render` 任何文件。

## Risks

- **XMind 格式无公开文档**：解析逻辑必须样本驱动。准备 5+ 真实样本（含自定义主题、图片、联系、外框、概要各一）作为测试夹具，不凭推测编码。
- **XMind 8 的 `styles.xml` 版本差异**：解析失败时降级为「只导入内容 + 默认主题」并在摘要中提示，不阻断导入。
- **前后端导出漂移**：一致性靠「服务端加载前端构建产物」保证，但这条链路本身需要测试覆盖，否则会随时间腐化。
- **字体分发（已解决）**：XMind 默认字体 `NeverMind` 不可分发，已由 [ADR-016](../../../../docs/09-技术决策记录.md) 定为**思源黑体（Noto Sans SC，SIL OFL 1.1）**，随应用分发 TTF 静态实例并做 `unicode-range` 分片；导入时按映射表把字体名归一为标识符。**该风险的剩余部分转为**：服务端兜底导出的容器必须预装同一套字体，否则两条导出路径结果不一致（见下方「服务端导出」一条）。
- **服务端导出是可选优化项**：若一期不做，超大批量导出能力缺失。需在路线图中明确标注为 M6 可选。
