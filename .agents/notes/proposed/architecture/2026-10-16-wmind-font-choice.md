# Agent Note: 默认字体改用思源黑体（Noto Sans SC），字体族以标识符存储

Status: proposed

## Problem

XMind 的默认字体 `NeverMind` 是 XMind 自有字体，**不可再分发**。这本来只是一个「换个字体」的问题，但 wmind 有两条硬性需求把它放大成了一个必须认真设计的决策：

1. **私有化部署必须离线可用**——不能用 Google Fonts 之类的 CDN，字体必须随应用分发。
2. **导出要可预期**——导出的 SVG/PDF 要在**别人没装这个字体的设备上**也正常显示，因此必须内嵌或转路径。

这两条都建立在「我们有权分发并修改这个字体」之上。而 WOFF2 分片和 PDF 子集内嵌在技术上都属于**修改**，所以字体许可必须是允许修改与再分发的标准开源许可，厂商自定义的「免费商用」EULA 不够用。

同时还有三个连带问题必须一起回答，否则决策是不完整的：

**问题一：字体怎么存？** 文档里的 `fontFamily` 原本存字体名（`"NeverMind"`）。如果换成 `"Noto Sans SC"`，就等于把每一份存量文档与一个具体字体绑死——将来因许可、体积或观感任何一条换字体，都要迁移全部文档。

**问题二：子集还是分片？** 中文全量字体很大（每字重 5~8 MB）。直觉是「只打包常用字」，但「常用」的边界在哪里？截断到 3755 字（GB2312 一级）能让单文件降到 1.5 MB，代价是表外的常用字显示成方框。

**问题三：字体什么时候加载？** 这个问题最容易被忽略，但后果最明显：布局引擎用 Canvas 测量文本宽度来算节点尺寸。**如果先用回退字体测量、等 webfont 到达后再重排，整张导图的节点尺寸都会变，画面会跳一下。** 这不是细节，是首屏体验的硬伤。

## Proposal

### 默认字体：思源黑体（Source Han Sans SC / Noto Sans SC）

两者是**同一字形的两个发行名**（Adobe 与 Google 联合开发）。本项目分发 **Noto Sans SC 的 TTF 静态实例**，理由是导出链路：jsPDF 子集化与 `opentype.js` 转路径对 TTF 的支持最稳，而 Adobe 的 Source Han Sans 以 OTF/CFF 发行为主。

许可 **SIL OFL 1.1**：允许商用、修改、子集化、再分发，无版税，不要求在渲染输出中署名。这是本项目唯一能接受的许可类型。

### 字重：4 个静态实例

取 **300 / 400 / 700 / 800**，覆盖 FR-EDIT-26 要求的 Light / Regular / Bold / ExtraBold。不用可变字体（见备选方案）。

### 字体族标识符（closed enum）

`fontFamily` 存**标识符**，不存字体名：

| 标识符 | 显示名 | 实际字体 | 优先级 |
| --- | --- | --- | --- |
| `sans` | 思源黑体（默认） | Noto Sans SC | P0 |
| `system` | 跟随系统 | 系统字体栈（零字节） | P0 |
| `serif` | 思源宋体 | Noto Serif SC | P1 |
| `mono` | 等宽 | JetBrains Mono + 系统等宽 | P1 |

前端用一张注册表把标识符解析成 CSS 字体栈，**任何地方都不得把标识符直接当 `font-family` 用**。未知取值回退 `sans` 并计入 warnings，不抛错。

### 分发方式：`unicode-range` 分片，不做硬子集截断

- 全量 CJK 覆盖，按 `unicode-range` 切片，浏览器只下载当前文档实际用到的分片。
- 产物约 20~30 MB（4 字重 × 全量 CJK 分片），**单页实际传输约 100~400 KB**。
- 分片由本站源提供，**不依赖任何外部 CDN**。
- **CI 必须校验分片产物完整**：缺分片不会报错，只会静默显示方框。

放弃「只打包 GB2312 一级字库 3755 字」：导图内容完全任意（人名、术语、生僻字），截断会让常用但不在表内的汉字显示为方框。这是用户直接可见的质量缺陷，比多传输几百 KB 严重得多。

### 加载顺序：字体 → 测量 → 布局

1. 首屏**显式阻塞等待**所需分片加载完成（`document.fonts.load()` + `await document.fonts.ready`），等待期间显示骨架屏。
2. **不使用 `font-display: swap`** 的可见回退。宁可等一下，也不要跳一下。
3. 测量缓存的**键必须包含字体标识符**——只按文本缓存会在切换字体后命中过期结果，导致节点宽度与实际渲染不符。
4. 用户切换字体族时清空测量缓存并整体重排，切换期间显示 loading 态。

### 导入归一

XMind 的 `fo:font-family` 按映射表归一为标识符（精确匹配 → 关键字子串匹配 → 回退 `sans`），**不保留原始字体名**。

不保留的理由：XMind 文件里的字体名是「源机器上装了什么」，在服务端和别人的浏览器上大概率不存在。直传等于把一份必然失效的引用写进文档，会让同一份文档在不同机器上渲染结果不同，直接摧毁「主题可移植」。

### 导出

- SVG：内嵌该导图实际用到的 WOFF2 分片，或按需转路径。
- PNG/JPEG：导出前 `await document.fonts.ready`。
- PDF：默认转路径（`opentype.js`），关闭时用 jsPDF 子集内嵌 TTF。
- **导出前逐码点检查覆盖情况**，命中回退字体时给出「N 个字符使用了系统字体」提示，不静默出图。
- 服务端兜底（chromedp）的容器预装同一套字体到 `/usr/share/fonts`；默认镜像不含 Chromium，需要时用构建参数开启变体。

## Alternatives considered

### 继续使用 `NeverMind`

与 XMind 视觉完全一致，零改造成本。**未选**：XMind 自有字体，随应用打包是侵权。这一条没有讨论空间——它直接违反了「可自由分发」这个前提。

### HarmonyOS Sans SC / MiSans / 阿里巴巴普惠体

观感更现代、更接近 XMind 的圆润风格，厂商也都声明「免费商用」，是国内商业产品里很常见的选择。**未选**：许可为厂商自定义 EULA 而非标准开源许可。条款可随版本变更，且对**修改与子集化**的限制表述不清——而 WOFF2 分片与 PDF 子集内嵌在技术上都属于「修改」。对要长期自托管、可能部署在客户内网的产品，字体许可的确定性比观感值钱得多。如果将来这几家改用标准开源许可，可以重新评估。

### 思源宋体作默认

衬线体更适合长文阅读，中文排版传统上也更「正式」。**未选**：思维导图是短标签，无衬线在小字号下的辨识度更好；XMind 默认也是无衬线，改宋体会让「像不像 XMind」这个主观验收标准更难达成。保留为 `serif` 选项。

### 霞鹜文楷（LXGW WenKai）

楷体观感在中文导图里很讨喜，OFL 许可，社区口碑好。**未选为默认**：楷体笔画粗细对比大，小字号下可读性不如黑体，且体积比 Noto Sans SC 更大。保留为二期的第 5 个字体族 `kai`（届时把楷体的导入映射从 `serif` 改到 `kai`）。

### 不随应用分发字体，只用系统字体栈

零体积、零许可风险、无加载延迟，实现最简单。**未选**：跨平台观感不一致（macOS 苹方 / Windows 雅黑 / Linux 各家不同），导致导出的 SVG/PDF 在不同机器上结果不同——而「导出结果可预期」是本项目的明确要求（FR-UI-03）。系统字体栈降级为 `system` 选项保留，作为「我不在乎一致性、只要快」的用户出口。

### `fontFamily` 存字体名（如 `"Noto Sans SC"`）

与 XMind 的 `fo:font-family` 语义一致，实现最直接，不需要映射表。**未选**，三个理由：

1. **换字体要迁移存量数据**。字体名把文档与具体字体绑死；存标识符只需改一处映射。这是一个自托管产品会在现场升级多年的场景，绑定越松越好。
2. **字体名是注入面**。任意字符串会被拼进 CSS/SVG，需要额外转义；标识符是封闭枚举，可以直接当白名单校验。
3. **标识符建模更准**。用户真实意图是「我要黑体 / 宋体」这类**样式类别**，而不是「我要 Noto Sans SC 这个具体字体」。前者才是产品语义。

### 可变字体（Variable Font）单文件覆盖全部字重

只分发一个文件，理论上体积更小、字重连续可调。**未选**：导出链路对可变字体支持不稳——jsPDF 子集化与 opentype.js 转路径都需要「先实例化到具体字重」这一步，工具链尚不成熟。改用 4 个静态实例，用一点体积换导出链路的确定性。

### 只打包 GB2312 一级字库（3755 字）以控制体积

单字体可压到 1.5 MB 以内，加载极快，是国内不少项目的做法。**未选**：导图内容完全任意（人名、术语、生僻字、专业词汇），截断会让常用但不在该表内的汉字显示为方框。而且这类缺陷**只在特定用户的特定内容上出现**，测试很难覆盖，属于典型的「上线后才发现」问题。改为全量覆盖 + 分片按需加载，把「体积问题」换成「分片策略问题」——后者可控，前者不可控。

## Acceptance criteria

1. **默认字体正确**：新建导图的 `theme.global.fontFamily` 为 `sans`，渲染使用 Noto Sans SC；文档中不出现任何字体名。
2. **许可合规**：随应用分发的字体全部为 SIL OFL 1.1，仓库内附 `LICENSES/` 与字体来源说明；不含 `NeverMind` 或任何厂商 EULA 字体。
3. **离线可用**：断网状态下首次打开导图，中文正常显示，无任何对外部域名的请求。
4. **无硬子集截断**：含 GB2312 表外汉字（如「龘」「㸚」）的导图正常显示，不出现方框。
5. **分片按需加载**：单页实际传输的字体资源 < 500 KB；未用到的分片不下载。
6. **分片完整性有闸门**：人为删除一个分片后 CI 校验失败。
7. **加载顺序正确**：冷缓存打开 200 节点导图，先骨架屏、字体就绪后首次布局，**全程无可见跳动**。
8. **测量缓存键含字体**：切换字体族后全量重排，节点宽度与新字体实测一致（不命中旧缓存）。
9. **字体族切换生效**：`sans` / `serif` / `mono` / `system` 四档切换后画布立即更新，切换期间有 loading 态。
10. **标识符不外泄为 CSS**：静态检查确认没有把 `fontFamily` 值直接写进 `font-family` 的地方，全部经注册表解析。
11. **导入归一正确**：含 `NeverMind` / 微软雅黑 / 楷体 / Consolas 的 XMind 文件分别得到 `sans` / `sans` / `serif` / `mono`，原始字体名不残留。
12. **导出保真**：导出的 SVG / PDF 在未安装思源黑体的设备上打开，中文正常显示。
13. **回退可见**：含 emoji 或字体未覆盖字符的导图导出时，给出「N 个字符使用了系统字体」提示。
14. **两条导出路径一致**：同一导图用浏览器导出与服务端兜底导出，结果像素级一致。

## Risks

- **分片缺失是静默失败**。少一个分片不会报错，只会让某些字显示成方框，且往往只在特定内容上复现。对策：CI 校验分片产物完整性（按 unicode-range 覆盖全集自检），并把它当作构建阻断项。
- **字体加载阻塞首屏**。为了不跳动，我们选择阻塞等待字体就绪，这会让首屏 FCP 变慢。对策：只等待当前文档实际用到的分片（而非全部），配合骨架屏；在 M2 实测首屏到可交互时间，若不达标则评估「先渲染骨架 + 局部布局」的降级方案。这是「不跳动」与「快」之间的取舍，已明确选前者。
- **产物体积 20~30 MB 是估算值**。实际取决于 `cn-font-split` 的分片策略与字重数量。若偏差过大，退路是减少字重（4 → 2，用浏览器合成粗体，但观感会下降）或对 `serif` / `mono` 延后到二期。需在 M2 实测后复核。
- **测量缓存键容易写错**。只按文本缓存是一个很自然的实现，但在多字体族下就是 bug。对策：缓存键类型上强制包含字体标识符（把缓存键做成一个结构体而非字符串拼接），并写一个「切换字体后宽度变化」的测试。
- **服务端与前端导出漂移**。两条路径的字体来源不同（前端分片 vs 容器系统字体），一旦不一致就会产出不同字形。对策：容器预装同一套字体；把「两条路径像素级一致」作为硬验收项而非「可接受差异」。
- **未来新增字体族会扩大产物**。每加一个 CJK 字体族就多一份 5~8 MB/字重的分片。对策：把字体族数量当作一个需要论证的决策，而不是顺手就加；`kai` 排在二期也是出于这个考虑。
- **OFL 的署名要求容易被漏**。OFL 1.1 不要求在渲染输出中署名，但要求在**分发字体文件本身**时附带许可与版权声明。对策：在仓库内放 `LICENSES/OFL-1.1-NotoSansSC.txt` 与来源说明，并在构建产物中包含它。
- **字体与「导出结果可预期」的耦合**。这条决策的隐含前提是「所有 wmind 实例分发同一套字体」。若将来允许运维方自定义字体，导出可预期性会失效。对策：把「自定义字体」明确划到范围外，若要支持需先解决分发与一致性问题。
