# Agent Note: 一期不接入邮件服务，账号找回由管理员重置承担

Status: proposed

## Problem

需求方最初选择「一期接入 SMTP」，随后同日二次修订，改回原推荐方案：**一期不接入邮件服务**。这留下两个必须一起回答的问题：

1. **边界画在哪**——不接邮件，一期到底不做什么？哪些东西要一并回滚（模块、接口、设置项、环境变量、页面），哪些必须**保留**为二期启用点，以免二期改表结构或重编号错误码？
2. **「忘记密码」怎么办**——这是 SMTP 存在的主要理由。不接邮件后，用户忘记密码必须有一条能走通的路径，且这条路径要在一期就落地，不能留到打磨阶段。

问题不在于「邮件好不好」，而在于**在自托管场景下，邮件带来的持续运维成本是否匹配它省下的那一步人工**。

## Proposal

**一期完全不引入邮件能力**：

- 不建 `mail` / `secret` 两个模块目录。
- 不注册 `forgot-password` / `reset-password` / `verify-email` / `resend-verification` / `admin/mail/test` 五个路由。
- 不读写任何 `mail.*` 设置项；不引入 `WMIND_ENCRYPTION_KEY` 环境变量。
- 注册即生效（`status = active`），不做邮箱验证。

**账号找回改由管理员重置承担**：`POST /admin/users/{uid}/reset-password`，服务端生成强随机密码或接受管理员指定，响应中**一次性**返回新密码（不落库明文、不写日志），并撤销该用户全部 refresh token。管理员不能重置自己（`ADMIN_CANNOT_RESET_SELF`，改自己密码走常规流程）。操作写审计日志但不记密码。

**登录页给出唯一入口**：密码框下方静态文案「忘记密码？请联系站点管理员为你重置。」——一期不建任何找回相关路由。

**保留为二期启用点**（建好但不启用，避免二期改结构）：

- `user_tokens` 表建好，保持空表；`purpose` 取值 `password_reset` / `email_verify` 一经确定即视为契约。
- 错误码 `AUTH_ACCOUNT_PENDING` / `MAIL_SEND_FAILED` / `MAIL_NOT_CONFIGURED` / `ENCRYPTION_KEY_MISSING` 编码预留但不返回。
- 用户表 `status` 枚举预留 `pending` 值；二期启用邮箱验证只需 `ALTER TABLE ... ADD COLUMN email_verified_at`（纯增量、不锁表）。

二期按 [SMTP 走后台配置，凭据用 AES-256-GCM 加密存储](../../rejected/architecture/2026-10-16-wmind-mail-service.md) 的归档设计实施，预计约 3 人日。二期落地后，管理员重置与邮件自助重置是**并存**的两条路径，不互相替换。

## Alternatives considered

### 为什么不接 SMTP（即原方案）？

能力更完整，用户可自助找回，不需要联系管理员。放弃它的原因是收益与成本不匹配：收益是省去用户发一条 IM 消息，成本是**持续**的运维负担——发信域信誉（新 IP 常被判垃圾）、云厂商默认封禁出站 25 端口、退信与投诉处理、发件人地址与认证账号的约束。这些成本不会因为「代码写完了」而消失。本产品定位是「一个实例服务一个组织」，管理员与用户通常在同一组织内，人工找回的闭环其实更短。

### 为什么不做「只做忘记密码、不做邮箱验证」的折中？

工作量减半，仍能覆盖主要诉求。放弃它的原因是折中只减了代码量，没减运维成本：发信域、端口封禁、退信处理这些负担与发几封邮件无关，只要接了 SMTP 就全部存在。用一个更小的方案保留同一个根本矛盾，不划算。

### 为什么不用「安全问题」自助找回？

不依赖邮件，用户可自助。放弃它的原因是安全性反而更低：安全问题答案普遍弱且易被社工（母亲姓名、出生城市这类信息在社交网络上大量存在），比「管理员人工核验身份」更不可靠；同时还要新增问题配置界面、答案哈希存储与重置流程，实现成本并不比管理员重置低。

### 为什么不用「一次性恢复码」？

注册时下发恢复码，用户自行保管，无需管理员介入。放弃它的原因是把责任转移给用户，而绝大多数用户会丢失恢复码——最终仍然要联系管理员。等于多写一套代码（生成、展示、存储哈希、校验、轮换）却解决不了问题。

### 为什么不做成「一期完全不做账号找回」？

成本最低，少一个接口与一个对话框。放弃它的原因是管理员重置的实现成本本来就极低（一个接口 + 一个对话框），而完全不做会让忘记密码的用户彻底无路可走，是明显的负收益。

### 为什么 `user_tokens` 表要提前建好而不是二期再加？

避免二期改表。建一张空表没有运行时代价，换来的是二期接入邮件时不需要走一次 schema 变更（也就没有迁移失败风险与停机窗口）。同理，错误码编码与 `status` 枚举值提前预留，避免二期出现「新增错误码要重排编号」这种无谓的破坏性变更。

## Acceptance criteria

1. 路由表中不存在 `forgot-password` / `reset-password` / `verify-email` / `resend-verification` / `admin/mail/test`，调用返回 404。
2. `settings` 表中不存在任何 `mail.*` 键；`GET /admin/settings` 的响应里也不出现。
3. 一期注册成功后 `status` 直接为 `active`，可立即登录，响应不含 `requiresEmailVerification` 字段。
4. 管理员重置密码后：新密码可登录、旧密码不可登录、该用户其他设备 refresh token 全部失效、响应中的密码不可再次查询。
5. 管理员对自己执行重置返回 409 `ADMIN_CANNOT_RESET_SELF`，界面按钮禁用。
6. 登录页在密码框下方渲染「忘记密码请联系管理员」文案，且不存在找回相关路由。
7. `.env.example` 与 compose 文件中不出现 `WMIND_ENCRYPTION_KEY`；启动日志无任何邮件服务相关行。
8. `user_tokens` 表存在且为空；`status` 枚举注释包含 `pending` 预留说明。

## Risks

- **账号找回依赖人工渠道**：若管理员长期不可达，用户会被阻塞在登录页。缓解：部署检查清单新增「向用户公布管理员联系方式」，并要求登录页引导文案与组织实际流程一致；规模变大后评估二期接入 SMTP。
- **管理员重置的误操作风险**：重置会踢掉目标用户全部会话，且新密码只在响应中出现一次。缓解：对话框二次确认 + 明确提示影响范围 + 对自己禁用 + 审计留痕。
- **`user_tokens` 空表可能被误当作「已实现」**：后续 Agent 看到表存在可能以为邮件能力已就绪。缓解：表结构注释与文档中显式标注「二期预留，本期无写入路径」。
- **二期回归成本被低估**：归档设计虽然完整，但 `mail` / `secret` 模块、前端页面、设置分组都要新建，不能只算「一个接口」。已在开发路线图中按约 3 人日估算并列入一期之后的候选方向首位。
- **回滚不彻底的风险**：`mail.*` 设置项与 `WMIND_ENCRYPTION_KEY` 若残留，会形成「看起来支持邮件但实际不工作」的中间态。缓解：验收标准第 1、2、7 条以「断言不存在」的方式机械检查，而非依赖人工确认。
