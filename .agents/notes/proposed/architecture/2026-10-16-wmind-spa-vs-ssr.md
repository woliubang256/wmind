# Agent Note: 前端采用纯 SPA，不做服务端渲染

Status: proposed

## Problem

需求方确认前端为「纯 SPA」（2026-10-16）。这个决定需要被明确记录下来，因为它看似只是「用不用 Next.js」的实现细节，实际约束了部署形态（要不要 Node 运行时容器）、首屏性能策略（SSR 能省下的首屏时间要自己想办法补回来）、以及分享页的社交预览能力。

不记录的话，后续很容易出现「给分享页加个 SSR 改善预览」这类局部优化，把整体架构拖向混合渲染，破坏部署与构建的简单性。

## Proposal

**纯客户端渲染的单页应用。** Vite 构建为静态资源，由 Nginx 托管，后端只提供 API。不做 SSR，不做 SSG。

**首屏性能靠这四件事解决**（替代 SSR 带来的首屏优势）：

1. 路由级代码分割（编辑器内核、导入导出、管理后台分别 `React.lazy`）。
2. 字体子集（仅 GB2312 一级字库 + 拉丁 + 常用标点，控制在 1.5MB 内）+ `font-display: swap`。
3. 关键 CSS 内联；暗色模式的首帧脚本内联在 `<head>` 同步执行，防止主题闪烁。
4. 首屏 JS（gzip）预算 ≤ 350KB，编辑器可交互 ≤ 1.5s。

**部署产物是纯静态文件**，Nginx 只需 `try_files $uri $uri/ /index.html` 做 SPA 路由回退。**不引入 Node 运行时容器。**

**明确接受的局限**：分享页 `/s/:token` 的 `og:title` / `og:description` 由前端 JS 注入，不执行 JS 的社交平台爬虫拿不到。若二期确需良好预览，**单独为 `/s/*` 做预渲染**，而不是把整个应用改成 SSR。

## Alternatives considered

### 为什么不用 Next.js SSR / SSG？

SSR 能做落地页 SEO、首屏更快、更好的社交预览。放弃它的原因是收益与成本严重失衡：本产品的核心界面（导图列表、编辑器、管理后台）全部在登录后，这些页面**无法也不应被搜索引擎索引**，SSR 的核心价值在此不成立。为了「营销落地页」这一个页面的 SEO 而引入整套 SSR 运行时与 Node 容器，是拿主要用户群（自托管部署者）的部署复杂度去换一个边缘收益。若将来确需落地页 SEO，用一个独立静态页或 SSG 子站解决即可。

### 为什么不用 Next.js 的静态导出（`output: 'export'`）？

能享受 Next 的开发体验（文件路由、图片优化、构建优化）而不跑服务端，看起来是「两全」。放弃它的原因是既然不跑服务端，Next 的多数能力（Server Actions、Route Handlers、ISR、中间件）都用不上，剩下的能力（路由、构建）Vite + React Router 也能提供，还少一层框架抽象与构建复杂度。为不使用的能力付出框架心智负担不划算。

### 为什么不自建同构渲染？

完全掌控，不依赖框架。放弃它的原因是同构渲染的核心成本在于维护服务端与客户端渲染的一致性（样式注入、副作用隔离、数据预取时机），而本产品是以编辑器为核心的**交互型应用**，首屏 HTML 里放一个空的画布容器对用户毫无帮助——渲染一致性的维护成本换不来实际体验提升。

### 为什么不用 MPA（多页面应用）？

每页独立 HTML，天然有 SEO 与首屏优势，部署也简单。放弃它的原因是编辑器与应用外壳之间需要保持状态（未保存草稿、视图变换、主题偏好、多标签页），MPA 的页面跳转会反复丢失上下文，要么靠 sessionStorage 手工传递（脆弱），要么放弃这些体验。

### 为什么不用「编辑器 SSR + 其余 SPA」的混合方案？

只对少数页面做 SSR，兼顾两端。放弃它的原因是混合渲染会同时引入两套构建产物、两套数据获取路径与两套缓存策略，是复杂度增长最快的架构方向；而且它解决的问题（首屏与预览）都有成本更低的局部替代方案。

## Acceptance criteria

1. 构建产物是纯静态文件，部署不需要 Node 运行时。
2. 首屏 JS（gzip）≤ 350KB；编辑器首屏到可交互 ≤ 1.5s（本地网络）。
3. Lighthouse 性能分 ≥ 85（列表页）。
4. 管理后台与导入导出相关依赖不出现在首屏 bundle 中（构建产物分析验证）。
5. Nginx 配置只需 `try_files` 回退，无额外代理规则（`/api` 除外）。
6. 分享页在禁用 JavaScript 时至少能看到明确的「需要启用 JavaScript」提示，而不是空白页。

## Risks

- **首屏性能完全靠自己兜**：没有 SSR 的「首屏 HTML 即内容」优势，所有优化都得手工做。已把四项措施与预算写进前端设计文档，并在 M6 用 Lighthouse 与产物分析做验收。
- **分享页社交预览受限**：`og:*` 由 JS 注入，部分爬虫（微信、部分 IM 的链接预览）不执行 JS。已明确接受该局限并给出二期的局部解决方案（仅为 `/s/*` 预渲染），但**要警惕它被当作「顺便把应用改成 SSR」的理由**。
- **无 JS 环境下白屏**：纯 SPA 在禁用 JS 时没有任何内容。已加入「至少给出明确提示」的验收项，但这是 SPA 的固有代价。
- **未来若出现真正的 SEO 需求**（例如公开的模板市场、分享广场），当前架构无法直接支撑。届时应新增一个独立的 SSG 站点而不是改造主应用——这条边界需要在新需求出现时主动守住。
