# Agent Note: 后端选型 Gin + PostgreSQL + pgx/sqlc，认证用 JWT 双令牌

Status: proposed

## Problem

需求指定后端用 Go 并「选用主流优秀的 web 框架」，同时要求预留客户端 App 的扩展接口。需要一次性定下四件事：Web 框架、数据库与数据访问方式、认证方案、并发保存的冲突策略。

这四项彼此关联：认证方案决定了能否水平扩展，数据访问方式决定了保存事务怎么写，冲突策略决定了 API 契约与前端交互。

## Proposal

### Web 框架：Gin v1.10

在生态成熟度、中间件完备度、问题可检索性、团队上手速度上综合最优。其「不够 idiomatic」的缺点（业务代码依赖 `gin.Context`）通过分层约束弥补：service 层禁止 import gin，保证业务逻辑可脱离 HTTP 单测。

### 数据库：PostgreSQL 16 + pgx v5 + sqlc，迁移用 golang-migrate

- JSONB 适配导图文档存储，支持局部路径更新与 GIN 索引。
- `pg_trgm` 扩展直接满足标题模糊搜索，无需引入全文检索引擎。
- sqlc 提供编译期类型安全、SQL 显式可控、无运行时反射开销。
- 本项目 schema 简单（约 10 张表），手写 SQL 成本可控。

### 认证：JWT 双令牌

- Access Token：HS256，15 分钟，前端存**内存**（不落 localStorage）。
- Refresh Token：不透明随机串（32 字节 base64url），7 天，服务端只存 SHA-256 哈希。
- Web 端 Refresh Token 走 `HttpOnly; Secure; SameSite=Lax` Cookie（path 限 `/api/v1/auth`）；客户端 App 用请求体传，**同一接口两种来源都接受**。
- 用户 `status` **不写入 JWT**，`RequireAuth` 每次从 60 秒 TTL 的缓存读取，禁用操作主动失效缓存，保证「禁用即生效」。

### 并发保存：`maps.version` 乐观锁

保存时校验 `WHERE id = ? AND version = ?`，不匹配返回 409 `MAP_VERSION_CONFLICT` 并在 `details.currentVersion` 给出服务端版本。事务内部仍用 `SELECT ... FOR UPDATE` 防同事务竞态，两层叠加。

## Alternatives considered

### 为什么不用 Echo / Chi / Fiber？

Echo 的 API 设计更统一、内置能力更多，是 Gin 之外最合理的选择；未选是因为生态规模与中文资料量明显少于 Gin，与需求里「主流」的措辞匹配度略低。Chi 100% 兼容 `net/http`、最 idiomatic、长期维护性最好，但要自行拼装日志/校验/绑定/响应封装，前期成本高。Fiber 基于 fasthttp，吞吐最高，但不兼容 `net/http` 生态，部分中间件需重写，与 `httptest`、`testcontainers` 等标准测试工具有摩擦——为吞吐付出生态割裂的代价，在本项目不划算。

### 为什么不用 GORM / Ent？

GORM 开发速度快、自动迁移、生态庞大，是「最快出活」的选项。未选是因为 SQL 不透明、复杂查询难调优、隐式行为多（软删除、钩子、零值忽略）容易埋坑。Ent 的图式 schema 与类型安全很强，但对 10 张表的项目属于过度设计。sqlc 用「写 SQL + 生成类型安全的 Go」换来了透明与可控，代价是维护 `.sql` 文件与生成步骤。

### 为什么不用 SQLite 作为主库？

SQLite 单文件、零运维，对「个人部署」体验更好，是很有吸引力的方案。未选为主库是因为并发写弱、JSON 查询能力弱于 PG、无 `pg_trgm` 等价能力。但 repository 层已通过接口隔离，二期可加 SQLite 驱动支持单机极简部署——保留为选项而非现在做。

### 为什么不用纯 Session + Cookie？

Session 实现简单、天然可撤销、无需处理令牌过期与刷新。未选是因为它需要共享会话存储（Redis）才能水平扩展，且客户端 App 使用不便——而需求明确要求为 App 预留接口。JWT 的无状态特性直接消除了这两点障碍。

### 为什么不用单一长期 JWT 或 RS256？

单一长期 JWT 最简单，但无法撤销，泄露后风险不可控。RS256 允许服务只持有公钥验签，适合多服务架构；单实例场景下 HS256 已足够且密钥管理更简单。若未来拆分服务，可平滑切换——这是一个可以推迟的决定。

### 为什么不用 Last-Write-Wins 或悲观锁？

LWW（直接覆盖）实现最简单，但多标签页场景会静默丢数据——这是最难排查的一类 bug。悲观锁（整个编辑会话持锁）无冲突丢失，但自动保存是高频写操作，长时间持锁不可接受。乐观锁在无冲突时零开销，冲突时给出明确提示并让用户选择处理方式，是这一场景的正解。

## Acceptance criteria

1. 用户 A 构造请求访问用户 B 的导图 → 404。
2. 禁用用户后其已签发 Access Token 立即失效（下一次请求返回 403）。
3. 两个标签页同时编辑同一导图，后保存者收到 409，前端三个处理选项（覆盖/放弃/另存副本）行为正确。
4. 多个并发请求同时遇到 401 时，前端只触发**一次**刷新（需专门的测试覆盖）。
5. 连续 5 次密码错误后账号锁定 15 分钟。
6. 集成测试使用 `testcontainers-go` 起真实 PostgreSQL，不 mock 数据库。

## Risks

- **刷新令牌并发风暴**：多个请求同时 401 会各自触发刷新。必须在前端用单例 Promise 合并。这是最常见也最容易被忽略的坑，需专门写测试。
- **HS256 密钥泄露即全盘沦陷**：启动时校验 `WMIND_JWT_SECRET` 长度 ≥ 32 字节，不足则拒绝启动。
- **`status` 缓存导致禁用延迟**：TTL 60 秒是延迟上限，管理动作主动失效缓存把实际延迟降到接近 0，但缓存失效逻辑本身是单点，需测试覆盖。
- **sqlc 生成步骤增加构建复杂度**：需在 CI 中校验生成产物与 `.sql` 源一致，避免忘记重新生成。
