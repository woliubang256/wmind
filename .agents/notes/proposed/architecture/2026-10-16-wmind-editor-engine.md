# Agent Note: 编辑器自研 SVG 渲染与布局引擎，不用现成导图库

Status: proposed

## Problem

需求把「xmind 一样的编辑体验」与「要和 xmind 一样的主题、颜色、形状那些」列为硬指标。编辑器是整个项目的技术核心，占一期工作量约 30%，且是关键路径——样式系统与导出都建立在它的文档模型与渲染层之上。

选型错误在这里的代价极高：不是性能问题，而是**能不能做到**的问题。若底层库的主题/形状表达能力不足，后期每加一个样式都要与库对抗。

## Proposal

**自研 SVG 渲染层 + 自研布局引擎，不依赖任何现成导图库或通用图库。**

分层约束（ESLint `no-restricted-imports` 强制）：

```
UI 层（React 组件）      → 只读 store，通过 dispatch(command) 修改
Store 层（Zustand+immer）→ doc · selection · viewport · history · saveState
内核层（纯 TS）          → model / layout / theme / export
```

内核层 **must** 是纯函数：不 import React、不访问 DOM。唯一例外是 `measure` 模块（文本测量必须用 Canvas 2D 的 `measureText`），它单独成模块并做 LRU 缓存，其余内核模块保持纯净。这样布局与主题计算可单测，也能被导出模块直接复用。

**渲染载体选 SVG 而非 Canvas**，理由按重要性排序：

1. 导出 SVG = DOM 序列化，零成本；Canvas 需重新实现一套绘制。
2. DOM 文本可选中、可编辑、字体渲染交给浏览器；Canvas 需自己实现文本编辑与测量。
3. 便于无障碍（`role="tree"` / `aria-*`）与调试。
4. 代价（大节点量性能弱于 Canvas）用视口裁剪 + 降级渲染（> 2000 节点关闭阴影/渐变、线条简化）处理。

**样式一律内联到 SVG 元素属性，不用 CSS class。** 这样序列化导出时样式自动携带，无需额外注入 `<style>`。这条约束反过来约束了 UI 层的实现方式：面板改样式必须走文档模型，不能直接改 DOM。

**布局输出与渲染解耦**：`layout` 是纯函数，输入 `sheet + theme + measure`，输出 `LayoutResult`（`boxes: Map<id, NodeBox>` + `edges` + `bounds`）。节点数 > 1000 时布局搬进 Web Worker。

## Alternatives considered

### 为什么不用 MindElixir / jsMind？

MindElixir（MIT、轻量、自带主题与导入导出）是这一类里最接近需求的。放弃它的核心原因是**主题系统深度不足**：它的主题是「一套配色 + 少量开关」，而需求要求形状、填充、边框、线条样式、端点、彩虹分支、8 种结构布局都可独立配置——这需要一套完整的「样式解析链 + 形状枚举 + 布局算法族」，不是给库加几个 prop 能覆盖的。另外它的文档模型固定，与 `.wmind` 格式冲突，会形成两套真相源。jsMind 样式能力更弱，社区活跃度也在下降。

### 为什么不用 KityMinder？

KityMinder 功能完整、曾广泛使用，布局类型与主题能力都不错。**已停止维护**是决定性因素：代码年代久远、依赖链陈旧，且它基于自研的 Kity 图形库而非 SVG，导出与定制成本高于自研。基于一个不再更新的渲染内核构建产品核心，长期风险不可接受。

### 为什么不用 React Flow / @xyflow/react？

React Flow 的交互层（缩放、平移、拖拽、连线、小地图）非常成熟，直接用能省下大量交互代码。但它的模型是**有向图**而非**树**：层级布局、折叠展开、同级排序、拖拽改父级这些树语义的操作，都要在它之上再包一层；主题/形状定制同样要自研。等于付出了抽象成本却没省下核心工作量，还多了一个大依赖与包体积负担。

### 为什么不用 Canvas 作为主渲染载体？

Canvas 在 5000+ 节点场景下性能确实显著优于 SVG。但它会同时破坏三件事：SVG 导出的零成本（需重写绘制到离屏 canvas 再栅格化）、文本编辑（需自己实现光标与选区）、无障碍（DOM 语义不存在）。折中方案是 SVG 为主 + 超大规模时降级，把 Canvas 留作未来的性能后备选项而非主路径。

## Acceptance criteria

1. 内核层（`model` / `layout` / `theme` / `export`）文件中不出现 React 与 DOM API 的 import（lint 规则保证）。
2. 每个布局算法的单测：给定固定文档，断言根节点坐标、分支数、包围盒尺寸。
3. 命令的 `apply` 后 `undo` 应回到完全相同的文档快照（`JSON.stringify` 比对）。
4. 1000 节点导图打开 < 1.5s；拖拽稳定 60fps。
5. 导出 SVG 后浏览器打开，视觉与画布一致（像素对比容差 1%）。
6. 2000 节点时开启视口裁剪，交互仍保持可用（> 30fps）。

## Risks

- **工作量最大**：M2 占一期约 30% 人日，是关键路径，延期会整体延期。缓解：拆成 7 个子阶段，每 2~3 天向需求方演示一次，用截图逐项打勾校准「像不像 XMind」这个主观标准。
- **「像 XMind」难以量化**：容易反复返工。缓解：把参考截图 3 的每一项交互列成 checklist 逐项验收，而不是靠口头感觉。
- **撤销栈内存**：依赖 immer 结构共享控制增量，栈深上限 200，需在 1000 节点场景下实测内存。
- **Safari 的 `foreignObject` 兼容问题**：编辑态改用绝对定位 `div` 叠加，不用 `foreignObject`。
- **未来若引入实时协作**：`commands/` 中的操作必须幂等且可序列化，以便映射为 CRDT 的 op——这条约束已写入前端设计文档，但需要在实际编码时守住。
