# Agent Note: 一期不做实时协作，但把文档模型与命令层按可迁移设计

Status: proposed

## Problem

思维导图产品的天然演进方向是多人协作（XMind 有协作空间、同类 Web 产品普遍支持多人同编辑）。需求没有把协作列入一期，但也明确要求「预留扩展」。

问题是「预留」怎么做才有效：如果只是口头说「以后再说」，等真要上协作时会发现文档模型、状态管理、保存链路全都需要推倒重来——那才是真正的成本。需要在写第一行编辑器代码前就确定哪些约束必须现在就守。

## Proposal

**一期不实现多人同时编辑。** 不做 WebSocket、不做 CRDT/OT、不做在线状态与光标共享。

**但保留四条可迁移约束**（编码时必须守住）：

1. **文档模型可完整序列化**：`.wmind` 是纯 JSON，无循环引用、无函数、无类实例。任何时刻的文档状态都能无损转成字符串。
2. **命令必须幂等且可序列化**：`commands/` 中的每个操作定义为一个可 JSON 化的对象（`{ type, payload }`），`apply(draft)` 对同一输入产生同一结果。这是将来把命令映射为 CRDT op 的前提。
3. **保存接口带版本号**：`PUT /maps/{uid}` 接受 `version` 字段并做乐观锁校验。协作引入后，这个字段会演化为服务端合并的基准点。
4. **服务端不持有编辑会话状态**：后端无状态，不记录「谁正在编辑哪张导图」。协作引入时由新增的 WebSocket 网关与 Redis Pub/Sub 承载，不改现有 HTTP 链路。

**二期协作的迁移路径**（供评估，非承诺）：引入 Yjs 作为 CRDT 层 → 把 `.wmind` 模型映射为 Y.Doc 结构 → 把现有 `commands` 的 op 定义复用为 Yjs 的事务内容 → 新增 WebSocket 网关 + Redis Pub/Sub 做多实例广播 → 保存链路改为「定期快照 + 增量持久化」。

## Alternatives considered

### 为什么一期就上 Yjs？

一步到位，避免二次改造，是很有吸引力的方案——Yjs 成熟、生态好、与 React 集成方案现成。放弃它是因为它会**迫使文档模型迁就 CRDT 的内部表示**（Y.Map / Y.Array 的嵌套方式会渗透到 model 层），而这会显著增加 M2（编辑器内核，已占一期 30% 工作量）的复杂度与不确定性。用「现在就要付出确定成本」换「未来可能省下的成本」，在当前阶段不划算。

### 为什么不做「锁定编辑」防冲突？

实现简单（打开导图时加锁，关闭时释放），能避免内容互相覆盖。未选是因为体验明显更差（第二个打开的人直接被挡住），而现有的**乐观锁 + 冲突对话框**已经覆盖了主要风险场景（多标签页、多设备），成本更低且不阻断使用。锁定编辑也没有为将来的真正协作留下任何技术积累。

### 为什么不做只读分享链接作为「轻协作」？

只读分享能让别人看到导图，是低成本的协作替代品，实现只需一张 `share_tokens` 表与一个只读路由。这是一个合理的一期候选功能，但**与实时协作是两条不同的技术路径**——它不能降低未来上 CRDT 的难度。把它作为独立的功能项评估（见技术决策记录待确认问题 1），不混在协作决策里。

### 为什么不把协作能力直接写进一期路线图？

协作会同时冲击前端状态管理（单一 store → 多副本同步）、后端（新增有状态服务）、部署（新增 Redis 与 WebSocket 网关）、测试策略（需要多客户端并发测试）。它不是一个功能点，而是一次架构升级。混进一期会让所有里程碑的估时失真。

## Acceptance criteria

1. `JSON.parse(JSON.stringify(doc))` 与 `doc` 深度相等（无循环引用、无不可序列化值）。
2. `commands/` 中每个操作的类型定义为纯数据对象，payload 中不含函数、不含 DOM 节点、不含类实例。
3. 相同文档 + 相同命令序列，在任何机器上 `apply` 后产生完全相同的文档（可断言）。
4. `PUT /maps/{uid}` 的 `version` 字段为必填且参与校验。
5. 后端代码中不存在记录编辑会话的内存结构（无「正在编辑的用户」映射）。

## Risks

- **约束容易被侵蚀**：这些约束是「为未来留门」，短期内看不到收益，容易在赶工时被破坏（例如为了省事把 DOM 节点塞进命令 payload，或引入不可序列化的编辑器状态）。缓解：写进前端设计文档的硬性约束章节；命令层的序列化测试作为门禁。
- **迁移成本仍可能很高**：即使守住了这四条约束，从单机模型迁到 CRDT 仍需要重写布局缓存、选区模型与保存链路。这四条约束降低的是「模型层」的成本，不是全部成本——不要高估它的作用。
- **`version` 乐观锁在协作下的语义变化**：引入 CRDT 后 `version` 会从「乐观锁基准」变成「快照序号」，语义不同但字段复用，容易引起误解。届时应考虑改名或新增字段而非复用。
